## 3. Архитектура и спецификация протокола Actions AOTA

Данный документ описывает результаты реверс-инжиниринга сетевого уровня проприетарного протокола **Actions Semiconductor OTA (AOTA)**, применяемого в смарт-часах на базе чипсетов ATS3085 / ATS3085S (включая DT NO.1).

---

### 3.1. Топология Bluetooth GATT

Взаимодействие осуществляется через фиксированный сервис и две основные характеристики:

| Параметр | UUID / Значение | Назначение |
| :--- | :--- | :--- |
| **GATT Service / Data Characteristic** | `e49a25e0-f69a-11e8-8eb2-f2801f1b9fd1` | Основной канал управления и передачи полезной нагрузки (AOTA Stream) |
| **Control / Keep-Alive Characteristic** | `26078ae1-dfe6-4657-9427-178458b911a1` | Канал инкрементального пинга сессии (Heartbeat) |

---

### 3.2. Структура управляющих команд (Handshake)

Все управляющие команды передаются в характеристику `e49a25e0-...` с включенным подтверждением ответа (`Write With Response`).

Заголовок кадра управления имеет структуру:
`[CMD_ID: 1B] [SUB_CMD: 1B] [FLAGS: 1B] [LENGTH: 2B Little-Endian] [PAYLOAD]`

#### Последовательность сессии:

1. **`CMD_OTA_REQUEST` (`0x09 0x01`)**
   * **Бинарный кадр:** `09 01 80 43 00 01 20 00 31 2e 30 30 5f 26 02 28 31 37 30 33 ...`
   * **Описание:** Запрос на инициализацию OTA. Передает аппаратный ID платформы (`A5S10GLY`), версию текущей прошивки и структуры идентификаторов разделов. Загрузчик микроконтроллера валидирует применимость контейнера к данному устройству.

2. **`CMD_OTA_START` (`0x09 0x02`)**
   * **Бинарный кадр:** `09 02 80 00 00`
   * **Описание:** Сигнал на перевод часов в режим приема прошивки. Загрузчик подготавливает буферы ПЗУ и подготавливает внутреннюю Flash-память к поблочному стиранию/записи.

3. **`CMD_OTA_SET_PARAMS` (`0x09 0x09`)**
   * **Бинарный кадр:** `09 09 80 04 00 01 01 00 01`
   * **Описание:** Настройка параметров передачи (размер окна, режим подтверждений, MTU).

4. **`CMD_OTA_END` (`0x09 0x06`)**
   * **Бинарный кадр:** `09 06 80 00 00`
   * **Описание:** Завершение передачи. Получив эту команду, загрузчик выполняет итоговую проверку целостности записанных секторов, обновляет векторы прерываний и инициирует программный сброс MCU (System Reset).

---

### 3.3. Блочная пагинация и структура пакета данных (Data Stream)

Передача физического бинарника прошивки идет через суб-команду **`0x0B`** с использованием режима без подтверждения на уровне GATT (`Write Without Response`).

#### Архитектура страниц SPI Flash (1 KB Align)
Загрузчик ATS3085S производит физическую запись во внешнюю SPI Flash блоками строго по **1024 байта (1 КБ)**. Протокол AOTA привязан к этой аппаратной особенности:

1. Исходный бинарный файл делится на логические страницы по 1024 байта.
2. Каждая 1 КБ страница нарезается на BLE-чанки максимальным объемом до **230 байт полезной нагрузки**.
3. Счетчик Sequence ID обнуляется в начале каждой 1 КБ страницы.

Типичная 1 КБ страница передается за **5 BLE-пакетов**:
* **Chunk 0:** 230 байт данных (`Sequence ID = 0x00`)
* **Chunk 1:** 230 байт данных (`Sequence ID = 0x01`)
* **Chunk 2:** 230 байт данных (`Sequence ID = 0x02`)
* **Chunk 3:** 230 байт данных (`Sequence ID = 0x03`)
* **Chunk 4:** 104 байта данных (`Sequence ID = 0x04`) — *остаток до 1024 байт*.

#### Структура кадра данных (Sub-command 0x0B)

Длина кадра: 10 байт заголовка/СУ + Payload.

```text
+----------+----------+-------+---------------+--------+------------------+-------------------+
| CMD ID   | SUB CMD  | FLAGS | PAYLOAD LEN   | SEQ ID | CHUNK CRC32      | BINARY DATA       |
| (1 byte) | (1 byte) | (1 B) | (2 bytes LE)  | (1 B)  | (4 bytes LE)     | (Up to 230 bytes) |
+----------+----------+-------+---------------+--------+------------------+-------------------+
|  0x09    |  0x0B    | 0x80  | Payload+5 len | 0x00.. | Standard CRC32   | Raw bytes         |
+----------+----------+-------+---------------+--------+------------------+-------------------+
```

---

### 3.4. Расчет контрольных сумм (Checksum)

Каждый чанк полезной нагрузки защищен собственной контрольной суммой:
* **Алгоритм:** Стандартный 32-битный CRC (IEEE 802.3 / zlib).
* **Полином:** `0xEDB88320` (Reverse) / `0x04C11DB7`.
* **Порядок байт в пакете:** Little-Endian.
* **Область расчета:** Вычисляется строго от массива полезных данных текущего чанка (`BINARY DATA`, от 1 до 230 байт). Заголовок в расчет CRC32 не входит.

---

### 3.5. Физический уровень и управление потоком (Flow Control)

При передаче бинарного файла размером ~4.2 МБ (около 18 500 BLE-пакетов) со скоростью `Write Without Response`:

1. **DLE (Data Length Extension):** Необходим для отправки пакетов L2CAP размером до 247 байт за один интервал событий (Connection Event). Без DLE стек ОС нарезает 240-байтовый пакет AOTA на 12 фрагментов по 20 байт, что вызывает переполнение TX-очереди адаптера ПК.
2. **Pacing (Задержка пакетов):** Микрозадержка в `0.005 с` (5 мс) между вызовами `write_gatt_char` предотвращает дроп пакетов в драйвере контроллера ПК, обеспечивая стабильную скорость прошивки порядка **40–50 КБ/сек** (полный цикл прошивки занимает ~90 секунд).
