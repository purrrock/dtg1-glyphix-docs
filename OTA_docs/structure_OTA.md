# Спецификация формата OTA-прошивки (Actions Semiconductor AOTA)

**Платформа:** Actions Semiconductor ATS3085S
**ОС:** Glyphix / Zephyr RTOS
**Целевое устройство:** Смарт-часы DT NO.1 и аналоги

На основе проведенного статического и динамического анализа hex-дампов, а также успешного брутфорса алгоритма хэширования, ниже представлено описание структуры OTA-контейнера. В данную ревизию внесены точные адреса захвата контрольных сумм и аппаратные константы.

---

## 1. Общая архитектура контейнера

Формат `AOTA` (Actions OTA) представляет собой нешифрованный многоуровневый архив без криптографической подписи (RSA/ECC). Безопасность и целостность базируются исключительно на алгоритме **CRC32 (IEEE 802.3 / zlib)**, применяемом каскадно.

Файл состоит из четырех логических зон:
1. **Root Header (Главный заголовок)** — 512 байт (0x0200).
2. **FAT (Таблица размещения файлов)** — 512 байт (0x0200), начинается сразу после заголовка (вмещает до 16 файлов).
3. **Data Payload (Полезная нагрузка)** — сами файлы, строго выровненные по границам секторов.
4. **Tail Padding (Хвостовое выравнивание)** — нулевые байты до границы сектора.

## 2. Бинарные структуры данных

Все многобайтовые значения записаны в формате **Little-Endian** (если явно не указано иное).

### 2.1. Главный заголовок (AOTA Header)

Заголовок всегда занимает ровно один сектор (512 байт, `0x0200`).

```c
struct aota_header_t {
    char     magic[4];          // 0x000: Магическое число "AOTA" (0x41 0x4F 0x54 0x41)
    uint32_t header_checksum;   // 0x004: CRC32 заголовка и FAT (диапазон расчета: 0x0008 - 0x03FF)
    uint32_t flags;             // 0x008: Флаги контейнера (В дампе: 00 01 00 04)
    uint32_t file_count;        // 0x00C: Количество файлов в таблице FAT (например, 4)
    uint16_t fat_offset;        // 0x010: Абсолютное смещение FAT-таблицы (всегда 0x0200)
    uint16_t data_offset;       // 0x012: Абсолютное смещение полезной нагрузки (всегда 0x0400)
    uint32_t total_file_size;   // 0x014: Итоговый размер AOTA-файла с учетом всех секторных паддингов
    uint32_t payload_checksum;  // 0x018: CRC32 полезной нагрузки (диапазон расчета: 0x0400 - EOF)
    uint32_t reserved1;         // 0x01C: Зарезервировано (0x00000000)
    uint8_t  padding1[32];      // 0x020: Нулевой паддинг до 0x040
    char     build_ver[32];     // 0x040: Версия и таймстемп сборки (null-terminated, макс 32 байта)
    char     platform_id[30];   // 0x060: Идентификатор платформы (null-terminated, макс 30 байт)
    uint16_t hardware_rev;      // 0x07E: Аппаратная ревизия платы (в дампе: 01 00)
    uint8_t  slot_protection[4];// 0x080: Системные флаги слота A/B или защиты (в дампе: 00 00 00 01)
    uint8_t  padding2[380];     // 0x084 - 0x01FF: Нулевой паддинг до конца сектора заголовка
};
```

### 2.2. Таблица распределения файлов (File Allocation Table)

Находится по смещению, указанному в `fat_offset` (базово `0x0200`). Представляет собой массив структур. Количество элементов массива равно `file_count`. Размер одной записи — 32 байта (`0x20`).

```c
struct aota_fat_entry_t {
    char     filename[16]; // 0x00: Имя файла (null-terminated ASCII). Макс 15 символов.
    uint32_t offset;       // 0x10: Абсолютное смещение начала файла от начала контейнера (0x00000000)
    uint32_t size;         // 0x14: Истинный физический размер файла (без учета секторного паддинга)
    uint32_t reserved;     // 0x18: Зарезервировано (0x00000000)
    uint32_t file_crc32;   // 0x1C: CRC32 (zlib) от бинарных данных текущего файла
};
```

## 3. Математика выравнивания (Sector Alignment)

Аппаратный загрузчик Actions Semiconductor работает с флэш-памятью блоками (секторами) по 512 байт. Это накладывает жесткие требования на компоновку файла:

1. **Смещение данных (Data Offset):** Первый файл (обычно `ota.xml`) всегда начинается со смещения `0x0400` (1024 байта), так как секторы `0x0000` и `0x0200` заняты заголовком и FAT-таблицей.
2. **Паддинг между файлами:** Каждый последующий файл внутри архива обязан начинаться с новой границы 512-байтового сектора.
3. **Хвостовой паддинг:** Конец последнего файла добивается нулями до границы 512 байт, формируя итоговый размер контейнера (`total_file_size`).

**Формула расчета следующего смещения на Python / C:**

```python
# SECTOR_SIZE = 512
next_offset = (current_offset + file_size + 511) & ~511
```

Пустое пространство между концом `file_size` и вычисленным `next_offset` **обязательно** заполняется нулями (`0x00`).

## 4. Алгоритмы контрольных сумм (CRC)

Используется стандартный алгоритм хэширования со следующими параметрами:
* **Алгоритм:** `CRC-32 (IEEE 802.3 / zlib)`
* **Полином:** `0x04C11DB7`
* **Init (Начальное значение):** `0xFFFFFFFF`
* **XorOut (Финальный XOR):** `0xFFFFFFFF`
* **Reflect In / Out:** `True / True`

### Цепочка доверия (Trust Chain) и зоны захвата памяти:

1. **`file_crc32` (FAT):** Считается напрямую от `file_size` байт полезной нагрузки файла (строго без учета 512-байтового секторного паддинга).
2. **`payload_checksum` (смещение 0x018):** Считается от смещения `0x0400` до конца файла (включая все файлы и все паддинги). Это хэш всей полезной нагрузки.
3. **`header_checksum` (смещение 0x004):** Считается от смещения `0x0008` до `0x03FF`. Этот хэш покрывает:
   * Флаги и метаданные заголовка (включая записанный внутрь него `payload_checksum`).
   * Всю таблицу FAT (`0x0200` - `0x03FF`).
   * Первые 8 байт файла (сигнатура и само поле хэша) в этот расчет не включаются.

## 5. Внутренняя иерархия файлов (Матрешка)

Для платформы ATS3085S (DT NO.1) контейнер `AOTA` имеет вложенную архитектуру.
Внешний уровень (`ota_...bin`) содержит:

* `ota.xml` — метаданные для парсера (ID дисплея, версии сборки).
* `TEMP.bin` — является **вложенным архивом**. Описан в отдельном документе`).
* `sdfs_a.bin` и `sdfs_k.bin` — образы System Data File System (ресурсы, шрифты, базовые UI-компоненты).

### Инструкция по перепаковке (Workflow):

1. Разобрать внешний `AOTA` по FAT-смещениям. Экспортировать `version.txt`.
2. Извлечь `TEMP.bin`, найти сигнатуру LZMA (`FD 37 7A 58 5A 00`).
3. Распаковать LZMA -> получить внутренний `AOTA`.
4. Разобрать внутренний `AOTA`, извлечь `app.bin`.
5. Внести изменения в ассемблер (патчинг / модификация ресурсов).
6. Собрать внутренний `AOTA` (пересчитать секторные выравнивания, `Payload CRC` и `Header CRC`).
7. Сжать внутренний `AOTA` обратно в алгоритм LZMA/XZ.
8. Собрать внешний `AOTA` (вложить новый `TEMP.bin`, выровнять сектора, пересчитать FAT, `Payload CRC` и `Header CRC`, сохранив аппаратные константы и версию).
