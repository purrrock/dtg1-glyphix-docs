# Установка приложений

Glyphix — это фреймворк приложений для встраиваемых устройств. После выпуска устройства с завода конечные пользователи или производители всё равно могут добавлять на него приложения — прямо как установку приложений на смартфоне. Однако на ресурсоограниченных микроконтроллерах (MCU) то, что именно означает «установка приложения», и то, как фреймворк находит и запускает его, не так широко известно, как на мобильных телефонах.

В этом документе описывается полный жизненный цикл пакета приложения на устройстве: установка → запуск → удаление, а также объясняется, как конфигурация каталогов влияет на поиск, обновление и удаление приложений.

## «Установка приложения» на устройство

Приложение Glyphix поставляется в виде файла `.pkg` — это контейнер ресурсов только для чтения, который содержит манифест приложения (`manifest.json`), код JavaScript, изображения и другие ресурсы. Приложение не распаковывается во время выполнения, фреймворк считывает файлы из `.pkg` напрямую по мере необходимости.

**Установка** приложения сводится к двум основным действиям: поместить файл `.pkg` в определенный каталог на устройстве, который сканирует фреймворк, и зарегистрировать его имя в базе данных пакетов. После регистрации фреймворк может найти соответствующий `.pkg` по имени пакета и запустить его. **Удаление** — это обратный процесс: удаление файла `.pkg`, очистка данных, созданных приложением, и аннулирование регистрации в базе данных.

::: tip Формат ресурсного бандла
Во время выполнения используется полноценный файл ресурсов `.pkg`, а не распакованная директория. Такой режим бандлов также часто используется в игровых движках, поскольку пакеты ресурсов приложений только читаются, но не записываются. Режим бандлов позволяет уменьшить фрагментацию файловой системы и предотвратить чрезмерное занятие инодов (inode) файловой системы кучей мелких файлов.
:::

Здесь задействованы две роли, и данное руководство предназначено для второй из них:
- **Разработчик приложений**: пишет приложения на JavaScript, создает файл `.pkg` с помощью команды `gx build` и поставляет его.
- **Разработчик платформы**: интегрирует среду выполнения Glyphix на устройство, настраивает каталоги для хранения приложений и вызывает интерфейсы установки и запуска в C++. Вы получаете файл `.pkg`, и ваша цель — запустить его.

::: tip
В этом руководстве предполагается, что у вас уже есть рабочий каркас платформы Glyphix (`Application` + `JsVM` + `AppletKit`). Если у вас его нет, обратитесь к примеру `examples/emulator`, входящему в состав SDK.
:::

## Подготовка

Перед началом убедитесь, что выполнены следующие условия:

- Имеется работающая платформа Glyphix. Минимальный каркас выглядит следующим образом, и все дальнейшие операции выполняются в этом контексте.
- Имеется файл `.pkg`, готовый к установке. Его можно получить у разработчика приложения или собрать пример приложения самостоятельно с помощью `gx build`. В этом руководстве предполагается, что имя файла — `com.example.demo.pkg`, а имя пакета — `com.example.demo` (имя пакета указано в [`manifest.json`](/framework/application/manifest.md#package) приложения).
- На устройстве имеется доступный для записи раздел для хранения файла `.pkg` и данных приложения во время выполнения. Далее в тексте этот раздел обозначается как `/data`.

Простой каркас платформы Glyphix выглядит следующим образом (это не псевдокод, всё действительно так просто):

```cpp
#include "gx_application.h"
#include "gx_appletkit.h"
#include "gx_jsvm.h"
#include "gx_widget.h"

using namespace gx;

int main() {
    Application app{new MyPlatform}; // Адаптация платформы, подключается в зависимости от устройства
    JsVM vm;                         // Среда выполнения JavaScript
    Widget window;                   // Родительское окно для всех приложений
    AppletKit kit(&window, "/pkgs.db"); // Второй аргумент — путь к базе данных пакетов
    // ...Код конфигурации и установки из этого руководства пишется здесь
    return app.exec();
}
```

::: tip Второй аргумент `AppletKit`
Он указывает на файл «базы данных пакетов» (например, `/pkgs.db`). `AppletKit` использует его для записи информации об установленных приложениях. Вы можете получить объект `PackageDatabase` с помощью `kit.database(ADBT_Applet)` для запроса списка установленных приложений, что будет использоваться позже.
:::

## Указание фреймворку, где хранятся приложения

Перед установкой любых приложений необходимо указать Glyphix расположение двух типов каталогов: **каталога пакетов приложений** (где хранятся файлы `.pkg`) и **каталога данных приложений** (где хранятся данные, создаваемые приложением во время выполнения). У них разные обязанности, не путайте их.

### Каталог пакетов приложений

Каталог пакетов приложений управляется с помощью `EnvPath::packages()`. Это список, каждый элемент которого указывает на каталог, содержащий `.pkg` файлы. Этот список выполняет несколько семантических функций одновременно, и их понимание лежит в основе всей последующей конфигурации:

- **Поиск**: Когда фреймворку необходимо загрузить ресурс вроде `pkg://com.example.demo/...`, он обходит список **спереди назад**, ищет `com.example.demo.pkg` в каждом каталоге и загружает первый попавшийся.
- **Установка**: При вызове интерфейса установки новый пакет **всегда записывается в последний каталог списка**.
- **Удаление**: При удалении выполняется сканирование **спереди назад**, и пакет удаляется из первого каталога, который его содержит.

Поскольку установка всегда происходит в конец списка, а поиск и удаление начинаются с головы списка, порядок каталогов в списке определяет их роль: каталоги в начале подходят для «предустановленных на заводе и не подлежащих перезаписи» приложений; каталоги в конце подходят для «устанавливаемых пользователем в дальнейшем» приложений.

::: important Предварительное условие
Перед вызовом интерфейса установки список `packages()` должен содержать хотя бы один каталог, причем последний каталог в списке (т. е. целевой каталог для установки) должен существовать и быть доступным для записи. В противном случае установка завершится неудачей.
:::

Метод конфигурации заключается в добавлении каталогов в список на этапе инициализации платформы:

```cpp
#include "gx_environment.h"
using namespace gx;

// Вызывается после конструирования Application и до установки/запуска
EnvPath::packages().emplace_back("/data/apps");
```

### Каталог данных приложений

Во время работы приложениям требуется пространство для записи кэша, файлов, временных данных и т. д. Эти каталоги настраиваются с помощью `EnvPath::setEntry(role, path)`, где каждая роль соответствует определенному назначению. Их семантические контракты следующие:

| Роль | Значение | Типичный путь |
|:---|:---|:---|
| `AppletCache` | Кэш, доступный для записи приложением; фреймворк может очистить и пересоздать его при нехватке места | `/data/cache` |
| `AppletFiles` | Личные файлы приложения, сохраняются персистентно, не очищаются автоматически | `/data/files` |
| `AppletMass` | Хранилище больших файлов (например, медиаресурсов), большая емкость | `/data/mass` |
| `AppletTemp` | Временные файлы, могут быть очищены после выхода из приложения | `/data/temp` |
| `AppletStorage` | Персистентное хранилище приложения | `/data/storage` |
| `LoggingDirectory` | Каталог логов фреймворка | `/logs` |

**Изоляция данных**: Фреймворк создает независимые подкаталоги для каждого приложения под вышеуказанными каталогами на основе имени пакета. Например, личные файлы приложения `com.example.demo` попадают в `/data/files/com.example.demo/`. Вам не нужно вручную управлять этими подкаталогами, фреймворк автоматически создает и очищает их при установке и удалении.

Кроме того, существует специальная роль `GlobalPackage`, которая указывает на глобальный общий `.pkg` (например, `/global.pkg`). Все приложения могут читать общие ресурсы, такие как шрифты и значки, из него через протокол `pkg:///...`. Он не принадлежит какому-то конкретному ứng dụng (приложению) и обычно прошивается вместе с прошивкой.

Пример конфигурации:

```cpp
EnvPath::setEntry(EnvPath::AppletCache,   "/data/cache");
EnvPath::setEntry(EnvPath::AppletFiles,   "/data/files");
EnvPath::setEntry(EnvPath::AppletMass,    "/data/mass");
EnvPath::setEntry(EnvPath::AppletTemp,    "/data/temp");
EnvPath::setEntry(EnvPath::AppletStorage, "/data/storage");
EnvPath::setEntry(EnvPath::GlobalPackage, "/global.pkg");
```

::: tip Момент вызова
При конструировании `Application` сбрасывает `EnvPath` в конфигурацию по умолчанию, поэтому пользовательская конфигурация должна выполняться сразу после конструирования `Application` и до любых вызовов `installPackage`/`launch`. Поздняя конфигурация приведет к непредвиденным ситуациям.
:::

### Пример конфигурации

Объединяя оба типа каталогов, минимальный рабочий фрагмент инициализации выглядит следующим образом:

```cpp
Application app;
// Каталог пакетов приложений: по крайней мере один доступный для записи каталог
EnvPath::packages().emplace_back("/data/apps");
// Каталоги данных приложений: настраиваются в соответствии с фактическими разделами устройства
EnvPath::setEntry(EnvPath::AppletFiles,   "/data/files");
EnvPath::setEntry(EnvPath::AppletCache,   "/data/cache");
EnvPath::setEntry(EnvPath::AppletTemp,    "/data/temp");
EnvPath::setEntry(EnvPath::AppletStorage, "/data/storage");
EnvPath::setEntry(EnvPath::AppletMass,    "/data/mass");

JsVM vm;
Widget window;
AppletKit kit(&window, "/pkgs.db");
```

## Установка приложения

Перед вызовом `installPackage` необходимо убедиться в следующем:

1. Список `EnvPath::packages()` не пуст, а его последний каталог существует и доступен для записи.
2. `AppletKit` сконструирован (для установки требуется запись в управляемую им базу данных пакетов).
3. Устанавливаемый файл `.pkg` уже существует в файловой системе устройства (например, находится по пути `/tmp/com.example.demo.pkg`).
4. Если используется стратегия проверки версий по умолчанию (`NormalVerify`), на устройстве должны быть настроены vendor ID и product ID; в противном случае установка завершится ошибкой `InvalidDevice` из-за сбоя проверки ID устройства.

### Вызов установки

Интерфейс установки — `AppletKit::installPackage(fileUri, policy)`. Первый аргумент — путь к файлу `.pkg`, второй — стратегия проверки, которую можно опустить (по умолчанию используется `NormalVerify`):

```cpp
auto status = kit.installPackage("/tmp/com.example.demo.pkg");
if (status != AppletKit::ValidPackage) {
    LogError() << "install failed:" << AppletKit::packageStatusMessage(status);
    return;
}
LogInfo() << "install ok";
```

Возвращаемое значение имеет тип `PackageStatus`, основные варианты следующие:

| Статус | Значение |
|:---|:---|
| `ValidPackage` | Успешная установка |
| `FileNotExists` | Путь к файлу `.pkg` не существует |
| `InvalidPackage` | Пакет поврежден или манифест нечитаем |
| `InvalidVersion` | Версия не соответствует стратегии проверки |
| `InvalidDevice` | Несоответствие vendor/product ID устройства |
| `FileIOError` | Ошибка копирования, обычно каталог установки недоступен для записи или не хватает места |

Стратегия проверки `PackageVerify` определяет строгость фреймворка к установочному пакету:

| Стратегия | Проверка версий | Проверка ID устройства |
|:---|:---|:---|
| `NormalVerify` (по умолчанию) | Новая версия не должна быть ниже установленной | Обязательно |
| `UpgradeOnly` | Должна быть строго выше установленной | Обязательно |
| `IgnoreVersion` | Пропустить | Обязательно |
| `NoVerify` | Пропустить всё, лишь бы пакет был легитимным | Пропустить |

::: tip
Если при первой установке и отладке вы столкнулись с `InvalidDevice` или `InvalidVersion`, вы можете временно использовать `AppletKit::NoVerify`, чтобы исключить помехи проверки, убедиться, что сам процесс установки работает нормально, а затем восстановить официальную стратегию.
:::

### Что происходит при установке

`installPackage` гарантирует следующие результаты на выходе:

- Проверяется легитимность файла `.pkg`, а также проверяются версия и ID устройства в соответствии с выбранной стратегией.
- Если приложение с тем же именем в данный момент запущенно, оно сначала завершается (terminate), чтобы избежать блокировки файлов или конфликтов данных.
- Файл `.pkg` копируется в последний каталог из списка `packages()` под именем `<package-name>.pkg`. Если файл с тем же именем уже существует, он перезаписывается.
- Приложение регистрируется в базе данных пакетов с указанием пути его установки и URI доступа `pkg://<package-name>`.
- Если в манифесте приложения объявлена схема URI (например, оно зарегистрировало себя как обработчик метода ввода `ime`), это также регистрируется.
- Отправляется уведомление об «изменении пакета», позволяющее другим частям фреймворка узнать о новом приложении.

::: important Возможности проверки пакетов
`AppletKit::installPackage()` сам по себе не имеет возможностей проверки целостности файла или подписи. Производители устройств должны самостоятельно разработать соответствующие функции, проверять файл `.pkg` перед вызовом `installPackage()`, а также обеспечивать согласованность процесса установки с помощью защиты от отключения питания файловой системы, отката (rollback) и т. д. Фреймворк гарантирует выполнение установки только при условии, что файл `.pkg` является легитимным, читаемым и записываемым.
:::

### Наблюдение за состоянием

После того как установка возвращает `ValidPackage`, вы можете проверить результат следующим образом:

- В каталоге установки должен быть виден файл: `/data/apps/com.example.demo.pkg`.
- `kit.database(ADBT_Applet)->contains("com.example.demo")` должен возвращать `true`.
- Список, возвращаемый `kit.installedApplets()`, должен содержать `"com.example.demo"`.

```cpp
EXPECT_TRUE(File::exists("/data/apps/com.example.demo.pkg"));
EXPECT_TRUE(kit.database(ADBT_Applet)->contains("com.example.demo"));
EXPECT_NE(std::find(kit.installedApplets().begin(),
                    kit.installedApplets().end(),
                    "com.example.demo"),
          kit.installedApplets().end());
```

## Запуск и наблюдение

Установка лишь помещает пакет на место. Чтобы приложение действительно отобразилось, нужно вызвать `AppletKit::launch(name)`, где `name` — это имя пакета из манифеста:

```cpp
Applet *applet = kit.launch("com.example.demo");
if (!applet)
    LogError() << "launch failed";
```

`launch` возвращает указатель на объект приложения или `nullptr` в случае неудачи. После успешного запуска приложение переходит на передний план и отображается.

::: tip Описание зависимостей
То, сможет ли `launch()` реально отобразить приложение, также зависит от движка JavaScript, оконной системы, графической адаптации платформы и готовности кода самого приложения. Если `launch()` возвращает непустой указатель, но экран ничего не показывает, проблема обычно кроется в других упомянутых системах, а не в процессе установки.
:::

После успешного запуска можно проверить:

- Интерфейс приложения появляется в окне (зависит от готовности вышеуказанных систем).
- После запуска приложения и записи им данных появляется его личный каталог: `/data/files/com.example.demo/`.
- Ресурсы внутри пакета приложения доступны через `pkg://com.example.demo/<asset-path>` (можно манипулировать через класс `File`).

## Удаление приложения

Интерфейс удаления — `AppletKit::removePackage(package)`. Передается имя пакета, возвращается `bool`, указывающий, был ли найден и удален файл пакета:

```cpp
if (!kit.removePackage("com.example.demo"))
    LogError() << "uninstall failed: package not found";
```

Гарантии, предоставляемые при удалении:

- Если приложение в данный момент запущено, оно сначала завершается.
- Файл `.pkg` удаляется из первого каталога в списке `packages()`, который содержит этот пакет.
- Удаляются подкаталоги приложения в различных каталогах данных (`<package-name>/` в `AppletCache`/`AppletFiles`/`AppletTemp`/`AppletStorage`).
- Приложение снимается с регистрации в базе данных пакетов.

Проверка после удаления:

- Файл `/data/apps/com.example.demo.pkg` в каталоге установки исчез.
- Подкаталоги данных, такие как `/data/files/com.example.demo/`, были очищены.
- `kit.installedApplets()` больше не содержит `"com.example.demo"`.

## Продвинутый уровень: Каталог предустановленных системных приложений

Многим устройствам необходимо разделять два типа приложений: **системные приложения, предустановленные на заводе и неизменяемые**, и **пользовательские приложения, устанавливаемые пользователем позже и удаляемые**. Используя семантику порядка списка `packages()`, можно реализовать такое разделение с помощью двух каталогов.

### Сценарий использования

Предустановленные на заводе приложения (например, системный циферблат, приложение настроек) обычно прошиваются во флэш-память только для чтения и не должны удаляться или перезаписываться пользователем. Приложения, устанавливаемые пользователем, должны попадать в записываемый раздел, где их можно в любой момент добавлять или удалять. Если использовать только один каталог для смешивания обоих типов, последующее управление обновлениями или удалением приложений станет сложным.

### Рекомендуемая структура

Добавьте два каталога в `packages()`. Порядок имеет значение: каталог предустановленных данных только для чтения идет в начале, а пользовательский записываемый каталог — в конце:

```cpp
EnvPath::packages().emplace_back("/system/apps");  // Предустановленные (только чтение), в начале
EnvPath::packages().emplace_back("/data/apps");    // Пользовательские (запись), в конце
```

Возвращаясь к первому шагу [Каталог пакетов приложений](#каталог-пакетов-приложений), при такой структуре семантика трех операций следующая:

- **Поиск** идет спереди назад. Предустановленный каталог находится в начале, поэтому заводские приложения имеют приоритет при поиске, обеспечивая стабильную загрузку.
- **Установка** записывает в последний каталог списка, то есть в пользовательскую область. Новые установленные приложения не загрязняют предустановленный каталог.
- **Удаление** идет спереди назад и удаляет из первого каталога, содержащего этот пакет.

### Механизм защиты: Белый список на стороне вызова

Семантика порядка определяет только путь хранения приложений и процесс поиска при запуске, но она не может помешать пользователю удалить предустановленное приложение. Встроенный метод <code>AppletKit&#8203;::&#8203;removePackage</code> не имеет понятия «предустановленный» или «защищенный». Следовательно, точка входа для удаления на устройстве должна быть реализована на стороне native-кода, где поддерживается белый список имен предустановленных пакетов, выполняющий перехват перед вызовом `removePackage`: если имя найдено в белом списке, удаление отклоняется.

Сторона установки не нуждается в белом списке. Каналы установки производителя устройства (магазин приложений, предустановленная рассылка и т. д.) контролируются сами по себе, легитимность имен пакетов гарантируется механизмом подписи, и это не входит в обязанности данного уровня; кроме того, из-за маскировки при прямом разрешении (см. «Известные ограничения» ниже), обновление предустановленных приложений во время выполнения изначально не может вступить в силу, поэтому нет необходимости дополнительно предотвращать перезапись. Таким образом, установка может напрямую вызывать `kit.installPackage`.

Пример обертки для native-удаления:

```cpp
#include "gx_hashset.h"

class PackageManager {
public:
    PackageManager(AppletKit &kit, HashSet<String> preinstalled)
        : m_kit(kit), m_preinstalled(std::move(preinstalled)) {}

    auto install(const String &packageUri) {
        return m_kit.installPackage(packageUri);
    }

    bool uninstall(const String &packageName) {
        if (m_preinstalled.count(packageName)) {
            LogWarning() << "refuse to uninstall protected package:" << packageName;
            return false;
        }
        return m_kit.removePackage(packageName);
    }

private:
    AppletKit &m_kit;
    HashSet<String> m_preinstalled;
};
```

::: tip Монтирование только для чтения и белый список
Монтирование предустановленного раздела в режиме только для чтения по-прежнему остается рекомендуемым подходом (для предотвращения случайной записи), но оно не является зависимостью для защиты от удаления. Даже если предустановленный каталог доступен для записи, белый список будет перехватывать вызовы перед `removePackage`.

Поле permission структуры `EnvPath::Entry` не участвует в принятии решений для каталога пакетов приложений, оно ограничивает доступ кода JavaScript только для каталога данных приложений.
:::

### Сброс к заводским настройкам (Factory Reset)

Используя разделение на предустановленный каталог и пользовательский каталог, сброс к заводским настройкам может быть реализован следующим образом: удаление всех файлов `.pkg` в пользовательском каталоге и сброс `pkgs.db`; предустановленные пакеты в системном каталоге остаются нетронутыми. Установка во время выполнения всегда записывает в `packages().back()` (пользовательский каталог) и никогда не перезаписывает предустановленную копию в системном каталоге. Поэтому после очистки пользовательского каталога и сброса базы данных предустановленные приложения все еще могут нормально анализироваться и загружаться через `pkg://`.

По желанию можно реализовать «удаление обновлений предустановленных приложений» — то есть удаление копии обновления определенного предустановленного приложения в пользовательском каталоге для отката к заводской версии в системном каталоге. Эта возможность в настоящее время находится лишь на стадии потенциальной реализации и официально пока не поддерживается.

### Известные ограничения

Следующее поведение фреймворка требует активного обхода или учета на стороне native-логики:

1. **Обновление предустановленных приложений через магазин приложений реализовать невозможно**. Текущий анализ ресурсов `pkg://<name>` выполняет прямой обход списка `packages()`, в то время как установка во время выполнения всегда записывает в `packages().back()` (пользовательский каталог). При попытке обновить предустановленное приложение через установку во время выполнения новая версия попадет в пользовательский каталог, но из-за прямого перехвата старой версией из системного каталога она никогда не вступит в силу. Данная функция обновления еще ожидает реализации.
2. **В удалении отсутствует понятие «защищенности»**. `removePackage` определяет местоположение только по принципу «первое успешное удаление» и без разницы удаляет пакеты из любого каталога, не имея пометки «является ли пакет предустановленным». Перехват с помощью белого списка должен быть реализован вызывающим native-кодом, фреймворк не предоставляет такую проверку.
3. **Удаление пакета циферблата не очищает базу данных**. `removePackage` выполняет снятие с регистрации только из таблицы приложений (`ADBT_Applet`), но не очищает записи в базе данных для пакетов циферблатов (`ADBT_Dial`), оставляя устаревшие записи. Это задача из б็эклога фреймворка; если логике native-удаления требуется поддержка циферблатов, она должна обрабатывать это самостоятельно.
4. **Поле permission в элементах каталога пакетов приложений недействительно**. Поле permission структуры `EnvPath::Entry` не участвует в поиске/установке/удалении списка `packages()`, а лишь ограничивает доступ кода JavaScript к каталогу данных приложения. С его помощью невозможно выразить правило «запретить установку в этот каталог».

## Шаблоны инициализации платформы

Ниже приведены полные конфигурации `EnvPath` для трех типичных сценариев, которые можно напрямую скопировать и настроить в соответствии с путями на вашем устройстве. Все конфигурации должны быть выполнены после конструирования `Application` и до <code>AppletKit&#8203;::&#8203;launch</code> / `installPackage`.

### Хост-эмулятор

Минимальная конфигурация, приложения хранятся в одном каталоге:

```cpp
os::chroot(".");
EnvPath::setEntry(EnvPath::GlobalPackage, "/global.pkg");
EnvPath::packages().emplace_back("/apps");
```

### Встраиваемая цель (один раздел)

Устройство с единственным разделом, доступным для записи, приложения и данные совмещены:

```cpp
EnvPath::setEntry(EnvPath::GlobalPackage, "/global.pkg");
EnvPath::setEntry(EnvPath::AppletCache,   "/data/cache");
EnvPath::setEntry(EnvPath::AppletFiles,   "/data/files");
EnvPath::setEntry(EnvPath::AppletMass,    "/data/mass");
EnvPath::setEntry(EnvPath::AppletTemp,    "/data/temp");
EnvPath::setEntry(EnvPath::AppletStorage, "/data/storage");
EnvPath::packages().emplace_back("/data/apps");
```

### Устройство с предустановленным разделом

Предустановленный раздел только для чтения отделен от пользовательского записываемого раздела:

```cpp
EnvPath::setEntry(EnvPath::GlobalPackage, "/system/global.pkg");
EnvPath::setEntry(EnvPath::AppletCache,   "/data/cache");
EnvPath::setEntry(EnvPath::AppletFiles,   "/data/files");
EnvPath::setEntry(EnvPath::AppletMass,    "/data/mass");
EnvPath::setEntry(EnvPath::AppletTemp,    "/data/temp");
EnvPath::setEntry(EnvPath::AppletStorage, "/data/storage");

// Порядок имеет значение: предустановленный каталог только для чтения в начале, пользовательский записываемый каталог в конце
EnvPath::packages().emplace_back("/system/apps");
EnvPath::packages().emplace_back("/data/apps");
```

После завершения конфигурации вы можете устанавливать и запускать приложения в соответствии со вторым и третьим шагами. Рекомендуется при первом успешном запуске использовать `AppletKit::NoVerify` для установки простого примера пакета, убедиться, что в `/data/apps` появился `.pkg`, а `launch` возвращает непустой указатель, и только после этого постепенно возвращать официальную стратегию проверки и предустановленную структуру.
