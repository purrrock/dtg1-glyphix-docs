# Установка приложений

Glyphix — это фреймворк приложений для встраиваемых устройств. После выпуска устройства с завода конечный пользователь или производитель все еще могут добавлять на него приложения — прямо как установку приложений на смартфон. Однако на ресурсоограниченных MCU то, что именно означает «установка приложения» и как фреймворк находит и запускает его, не так широко известно, как на мобильных устройствах.

В этом документе описывается полный жизненный цикл пакета приложения на устройстве: установка → запуск → удаление, а также объясняется, как конфигурация каталогов влияет на поиск, обновление и удаление приложений.

## «Установка приложения» на устройство

Приложение Glyphix поставляется в виде файла `.pkg` — это контейнер ресурсов только для чтения, внутри которого содержатся манифест приложения (`manifest.json`), код на JavaScript, изображения и другие ресурсы. Приложение не распаковывается во время работы: фреймворк считывает файлы напрямую из `.pkg` по мере необходимости.

**Установка** приложения по сути сводится к двум действиям: поместить файл `.pkg` в определенный каталог на устройстве, который сканирует фреймворк, и зарегистрировать его имя пакета в базе данных пакетов. После регистрации фреймворк может найти соответствующий `.pkg` по имени пакета и запустить его. **Удаление** — это обратная операция: удаление файла `.pkg`, очистка данных, созданных приложением, и аннулирование регистрации в базе данных.

::: tip Формат ресурса bundle
Во время выполнения используется полноценный файл ресурсов `.pkg`, а не распакованная директория. Такой режим bundle также часто используется в игровых движках, так как пакеты ресурсов приложения только читаются и никогда не записываются. Режим bundle позволяет уменьшить фрагментацию файловой системы и избежать чрезмерного использования inode файловой системы множеством мелких файлов.
:::

Здесь задействованы две роли, и это руководство предназначено для второй из них:
- **Разработчик приложений**: пишется код на JavaScript, с помощью команды `gx build` создается файл `.pkg`, который затем передается дальше.
- **Разработчик платформы**: интегрирует среду выполнения Glyphix на устройство, настраивает директорию для хранения приложений и вызывает интерфейсы установки и запуска в C++. Вы получаете на входе файл `.pkg`, а ваша задача — заставить его работать.

::: tip
В этом руководстве предполагается, что у вас уже есть рабочий каркас платформы Glyphix (`Application` + `JsVM` + `AppletKit`). Если его нет, обратитесь к примеру `examples/emulator` из комплекта SDK.
:::

## Подготовка

Перед началом убедитесь, что выполнены следующие условия:

- Имеется работающая платформа Glyphix. Ниже приведен минимальный каркас, и все дальнейшие операции будут выполняться в этом контексте.
- Имеется файл `.pkg`, готовый к установке. Его можно получить у разработчика приложения или собрать собственный пример приложения с помощью `gx build`. В этом руководстве предполагается, что имя файла — `com.example.demo.pkg`, а имя пакета — `com.example.demo` (имя пакета указано в [`manifest.json`](/framework/application/manifest.md#package) приложения).
- На устройстве имеется доступный для записи раздел для хранения файлов `.pkg` и данных приложений во время выполнения. В дальнейшем этот раздел обозначается как `/data`.

Простой каркас платформы Glyphix выглядит следующим образом (это не псевдокод, всё действительно так просто):

```cpp
#include "gx_application.h"
#include "gx_appletkit.h"
#include "gx_jsvm.h"
#include "gx_widget.h"

using namespace gx;

int main() {
    Application app{new MyPlatform}; // Адаптация платформы, подключается в зависимости от устройства
    JsVM vm;                         // Среда выполнения JavaScript
    Widget window;                   // Родительское окно для всех приложений
    AppletKit kit(&window, "/pkgs.db"); // Второй аргумент — путь к базе данных пакетов
    // ...Код конфигурации и установки из этого руководства пишется здесь
    return app.exec();
}
```

::: tip Второй аргумент `AppletKit`
Он указывает на файл «базы данных пакетов» (например, `/pkgs.db`). `AppletKit` использует его для записи информации об установленных приложениях. Вы можете получить объект `PackageDatabase` для запроса списка установленных приложений с помощью `kit.database(ADBT_Applet)`, это будет использоваться позже.
:::

## Указание фреймворку, где хранятся приложения

Перед установкой любых приложений необходимо указать Glyphix расположение двух типов каталогов: **каталог пакетов приложений** (где хранятся файлы `.pkg`) и **каталог данных приложений** (где хранятся данные, создаваемые приложением во время выполнения). У них разные обязанности, не путайте их.

### Каталог пакетов приложений

Каталог пакетов приложений управляется с помощью `EnvPath::packages()`. Это список, каждый элемент которого указывает на каталог, содержащий файлы `.pkg`. Этот список одновременно выполняет несколько семантических функций, понимание которых является основой для всей последующей настройки:

- **Поиск**: когда фреймворку необходимо загрузить ресурс вроде `pkg://com.example.demo/...`, он обходит список **спереди назад** (от начала к концу) в поисках `com.example.demo.pkg` в каждом каталоге, и загружает ресурс при первом же совпадении.
- **Установка**: при вызове интерфейса установки новый пакет **всегда записывается в последний каталог списка**.
- **Удаление**: при удалении поиск сканирует список **спереди назад** и удаляет пакет из первого каталога, в котором он встретился.

Поскольку установка всегда происходит в конец списка, а поиск и удаление начинаются с головы списка, порядок каталогов в списке определяет их роль: каталоги в начале списка подходят для приложений, «поставляемых с заводом и не подлежащих перезаписи»; каталоги в конце списка подходят для приложений, «устанавливаемых пользователем позже».

::: important Предварительное условие
Перед вызовом интерфейса установки список `packages()` должен содержать как минимум один каталог, а последний каталог в списке (т. е. целевой каталог для установки) должен существовать и быть доступным для записи. В противном случае установка сразу завершится ошибкой.
:::

Метод настройки заключается в добавлении каталогов в список на этапе инициализации платформы:

```cpp
#include "gx_environment.h"
using namespace gx;

// Вызывается после конструирования Application, но до установки/запуска
EnvPath::packages().emplace_back("/data/apps");
```

### Каталог данных приложений

Во время работы приложениям требуется пространство с возможностью записи для хранения кэша, файлов, временных данных и т. д. Эти каталоги настраиваются с помощью `EnvPath::setEntry(role, path)`, где каждая роль соответствует определенному назначению. Их семантические контракты следующие:

| Роль | Значение | Типичный путь |
|:---|:---|:---|
| `AppletCache` | Кэш, доступный для записи приложением; фреймворк может очистить и пересоздать его при нехватке места | `/data/cache` |
| `AppletFiles` | Личные файлы приложения, сохраняются персистентно, не удаляются автоматически | `/data/files` |
| `AppletMass` | Хранилище больших файлов (например, медиаресурсов) большой емкости | `/data/mass` |
| `AppletTemp` | Временные файлы, могут быть очищены после выхода из приложения | `/data/temp` |
| `AppletStorage` | Персистентное хранилище приложения | `/data/storage` |
| `LoggingDirectory` | Каталог логов фреймворка | `/logs` |

**Изоляция данных**: фреймворк создает независимые подкаталоги для каждого приложения под вышеуказанными путями на основе имени пакета. Например, личные файлы приложения `com.example.demo` попадают в `/data/files/com.example.demo/`. Вам не нужно вручную управлять этими подкаталогами — фреймворк автоматически создает и очищает их при установке и удалении.

Кроме того, существует специальная роль `GlobalPackage`, которая указывает на глобально разделяемый `.pkg` (например, `/global.pkg`). Все приложения могут читать общие ресурсы, такие как шрифты и иконки, из него через протокол `pkg:///...`. Он не принадлежит какому-то конкретному приложению и обычно прошивается вместе с прошивкой.

Пример конфигурации:

```cpp
EnvPath::setEntry(EnvPath::AppletCache,   "/data/cache");
EnvPath::setEntry(EnvPath::AppletFiles,   "/data/files");
EnvPath::setEntry(EnvPath::AppletMass,    "/data/mass");
EnvPath::setEntry(EnvPath::AppletTemp,    "/data/temp");
EnvPath::setEntry(EnvPath::AppletStorage, "/data/storage");
EnvPath::setEntry(EnvPath::GlobalPackage, "/global.pkg");
```

::: tip Момент вызова
При конструировании `Application` сбрасывает `EnvPath` к конфигурации по умолчанию, поэтому пользовательскую конфигурацию следует выполнять сразу после конструирования `Application` и до любых вызовов `installPackage`/`launch`. Слишком поздно выполненная настройка приведет к непредсказуемому поведению.
:::

### Пример конфигурации

Объединяя оба типа каталогов, минимально рабочий фрагмент инициализации выглядит так:

```cpp
Application app;
// Каталог пакетов приложений: как минимум один каталог с возможностью записи
EnvPath::packages().emplace_back("/data/apps");
// Каталог данных приложений: настраивается в соответствии с фактическими разделами устройства
EnvPath::setEntry(EnvPath::AppletFiles,   "/data/files");
EnvPath::setEntry(EnvPath::AppletCache,   "/data/cache");
EnvPath::setEntry(EnvPath::AppletTemp,    "/data/temp");
EnvPath::setEntry(EnvPath::AppletStorage, "/data/storage");
EnvPath::setEntry(EnvPath::AppletMass,    "/data/mass");

JsVM vm;
Widget window;
AppletKit kit(&window, "/pkgs.db");
```

## Установка приложения

Перед вызовом `installPackage` необходимо убедиться, что:

1. Список `EnvPath::packages()` не пуст, а его последний каталог существует и доступен для записи.
2. `AppletKit` сконструирован (для установки требуется запись в управляемую им базу данных пакетов).
3. Устанавливаемый файл `.pkg` уже существует в файловой системе устройства (например, находится по пути `/tmp/com.example.demo.pkg`).
4. Если используется стратегия проверки версий по умолчанию (`NormalVerify`), на устройстве должны быть настроены ID производителя/продукта (vendor/product ID); в противном случае установка завершится ошибкой `InvalidDevice` из-за сбоя проверки ID устройства.

### Вызов установки

Интерфейс установки — это `AppletKit::installPackage(fileUri, policy)`, где первый аргумент — путь к файлу `.pkg`, а второй — стратегия проверки (может быть опущена, по умолчанию используется `NormalVerify`):

```cpp
auto status = kit.installPackage("/tmp/com.example.demo.pkg");
if (status != AppletKit::ValidPackage) {
    LogError() << "install failed:" << AppletKit::packageStatusMessage(status);
    return;
}
LogInfo() << "install ok";
```

Возвращаемое значение — `PackageStatus`, наиболее распространенные варианты:

| Статус | Значение |
|:---|:---|
| `ValidPackage` | Установка успешна |
| `FileNotExists` | Путь к файлу `.pkg` не существует |
| `InvalidPackage` | Пакет поврежден или манифест нечитаем |
| `InvalidVersion` | Версия не соответствует стратегии проверки |
| `InvalidDevice` | ID вендора/продукта устройства не совпадает |
| `FileIOError` | Ошибка копирования, обычно каталог установки недоступен для записи или не хватает места |

Стратегия проверки `PackageVerify` определяет степень строгости фреймворка к устанавливаемому пакету:

| Стратегия | Проверка версий | Проверка ID устройства |
|:---|:---|:---|
| `NormalVerify` (по умолчанию) | Новая версия не должна быть ниже уже установленной | Обязательно |
| `UpgradeOnly` | Должна быть строго выше уже установленной | Обязательно |
| `IgnoreVersion` | Пропустить | Обязательно |
| `NoVerify` | Пропустить всё, лишь бы пакет был легитимным | Пропустить |

::: tip
Если при первой отладке установки вы столкнулись с `InvalidDevice` или `InvalidVersion`, вы можете временно использовать `AppletKit::NoVerify`, чтобы исключить влияние проверки, убедиться, что сам процесс установки работает нормально, а затем вернуть стандартную стратегию.
:::

### Что происходит при установке

`installPackage` гарантирует следующие результаты:

- Проверяется легитимность файла `.pkg`, а также проверяются версия и ID устройства в соответствии с выбранной стратегией.
- Если приложение с тем же именем уже запущенно, оно сначала завершается (terminate), чтобы избежать блокировки файлов или конфликтов данных.
- Файл `.pkg` копируется в последний каталог из списка `packages()` под именем `<package-name>.pkg`. Если файл с таким именем уже существует, он перезаписывается.
- Приложение регистрируется в базе данных пакетов, где фиксируются путь его установки и URI доступа `pkg://<package-name>`.
- Если в манифесте приложения объявлена схема URI (например, если оно зарегистрировало себя как обработчик ввода `ime`), это также регистрируется.
- Отправляется уведомление об «изменении пакетов», позволяющее остальным частям фреймворка узнать о новом приложении.

::: important Возможности проверки пакетов
Сам по себе метод `AppletKit::installPackage()` не имеет функций проверки целостности файла или подписи. Производители устройств должны самостоятельно разработать соответствующие функции и перед вызовом `installPackage()` проверить файл `.pkg`, а также обеспечить защиту файловой системы от потери питания и откат (rollback) для поддержания согласованности. Фреймворк гарантирует выполнение установки только при условии, что файл `.pkg` легитимен, читаем и доступен для записи.
:::

### Проверка манифеста

После того как установка вернула `ValidPackage`, вы можете проверить результат следующим образом:

- В каталоге установки должен появиться файл: `/data/apps/com.example.demo.pkg`.
- `kit.database(ADBT_Applet)->contains("com.example.demo")` должен вернуть `true`.
- Список, возвращаемый `kit.installedApplets()`, должен содержать `"com.example.demo"`.

```cpp
EXPECT_TRUE(File::exists("/data/apps/com.example.demo.pkg"));
EXPECT_TRUE(kit.database(ADBT_Applet)->contains("com.example.demo"));
EXPECT_NE(std::find(kit.installedApplets().begin(),
                    kit.installedApplets().end(),
                    "com.example.demo"),
          kit.installedApplets().end());
```

## Запуск и наблюдение

Установка лишь помещает пакет на место. Чтобы приложение действительно отобразилось, нужно вызвать `AppletKit::launch(name)`, где `name` — это имя пакета из манифеста:

```cpp
Applet *applet = kit.launch("com.example.demo");
if (!applet)
    LogError() << "launch failed";
```

Метод `launch` возвращает указатель на объект приложения или `nullptr` в случае неудачи. После успешного запуска приложение переходит на передний план и отображается.

::: tip Примечание о зависимостях
То, сможет ли `launch()` заставить приложение реально отобразиться, также зависит от того, готовы ли движок JavaScript, оконная система, графическая адаптация платформы и код самого приложения. Если `launch()` вернул не-null, но экран пуст, проблема обычно кроется в других перечисленных системах, а не в процессе установки.
:::

После успешного запуска можно проверить:

- Интерфейс приложения появился в окне (при условии готовности вышеуказанных систем).
- После запуска приложения и записи им данных появился его личный каталог: `/data/files/com.example.demo/`.
- Ресурсы внутри пакета приложения доступны через `pkg://com.example.demo/<asset-path>` (можно работать через класс `File`).

## Удаление приложения

Интерфейс удаления — это `AppletKit::removePackage(package)`, куда передается имя пакета, а возвращается `bool`, указывающий, был ли найден и удален файл пакета:

```cpp
if (!kit.removePackage("com.example.demo"))
    LogError() << "uninstall failed: package not found";
```

Гарантии, предоставляемые при удалении:

- Если приложение запущено, оно сначала завершается.
- Файл `.pkg` удаляется из первого каталога в списке `packages()`, в котором он содержится.
- Удаляются подкаталоги этого приложения во всех каталогах данных (`<package-name>/` внутри `AppletCache`/`AppletFiles`/`AppletTemp`/`AppletStorage`).
- Приложение аннулируется в базе данных пакетов.

Проверка после удаления:

- Файл `/data/apps/com.example.demo.pkg` исчез из каталога установки.
- Подкаталоги данных вроде `/data/files/com.example.demo/` были очищены.
- `kit.installedApplets()` больше не содержит `"com.example.demo"`.

## Продвинутый уровень: каталоги предварительно установленных системных приложений

Многим устройствам необходимо разделять приложения на две категории: **предустановленные на заводе неудаляемые** системные приложения и **устанавливаемые пользователем позже удаляемые** пользовательские приложения. Используя семантику порядка списка `packages()`, можно реализовать такое разделение с помощью двух каталогов.

### Сценарии использования

Предустановленные на заводе приложения (например, системный циферблат, приложение настроек) обычно прошиваются в флеш-память только для чтения и не должны удаляться или перезаписываться пользователем. Приложения, устанавливаемые пользователем, должны попадать в раздел с возможностью записи и могут свободно добавляться или удаляться. Если использовать для всего один смешанный каталог, управление последующими обновлениями или удалениями приложений станет сложным.

### Рекомендуемая компоновка

Добавьте в `packages()` два каталога с учетом порядка: каталог предустановленных приложений только для чтения идет первым, а каталог для пользовательской установки с возможностью записи — вторым:

```cpp
EnvPath::packages().emplace_back("/system/apps");  // Предустановленные (только чтение), ставятся первыми
EnvPath::packages().emplace_back("/data/apps");    // Пользовательские (запись), ставятся вторыми
```

Возвращаясь к [каталогу пакетов приложений](#каталог-пакетов-приложений) из первого шага, семантика трех операций при такой компоновке выглядит следующим образом:

- **Поиск** идет спереди назад. Поскольку предустановленный каталог находится в начале, заводские приложения находят совпадение в первую очередь, что гарантирует стабильную загрузку.
- **Установка** записывает пакет в последний каталог списка, т. е. в пользовательскую область, поэтому вновь установленные приложения не загрязняют предустановленный каталог.
- **Удаление** идет спереди назад, удаляя пакет из первого каталога, в котором он обнаружен.

### Механизм защиты: белый список на стороне вызова

Семантика порядка определяет лишь путь хранения и порядок поиска для запуска приложений, но она не может запретить пользователю удалить предустановленное приложение: встроенный метод <code>AppletKit&#8203;::&#8203;removePackage</code> не имеет концепции «предустановленный» или «защищенный». Поэтому точка входа удаления на устройстве должна быть реализована на стороне native-кода, где поддерживается белый список имен предустановленных пакетов, перехватывающий вызовы перед `removePackage`: если имя пакета входит в белый список, удаление отклоняется.

Для установки белый список не требуется. Каналы установки производителя устройства (магазин приложений, предустановленная доставка и т. д.) контролируются самостоятельно, легитимность имен пакетов гарантируется механизмом подписи и не относится к ответственности данного уровня; кроме того, из-за перекрытия при разрешении спереди назад (см. «Известные ограничения» ниже) обновление предустановленных приложений во время выполнения изначально не может вступить в силу, поэтому нет необходимости дополнительно препятствовать перезаписи. Таким образом, установка может напрямую вызывать `kit.installPackage`.

Пример наброска native-обертки для удаления:

```cpp
#include "gx_hashset.h"

class PackageManager {
public:
    PackageManager(AppletKit &kit, HashSet<String> preinstalled)
        : m_kit(kit), m_preinstalled(std::move(preinstalled)) {}

    auto install(const String &packageUri) {
        return m_kit.installPackage(packageUri);
    }

    bool uninstall(const String &packageName) {
        if (m_preinstalled.count(packageName)) {
            LogWarning() << "refuse to uninstall protected package:" << packageName;
            return false;
        }
        return m_kit.removePackage(packageName);
    }

private:
    AppletKit &m_kit;
    HashSet<String> m_preinstalled;
};
```

::: tip Монтирование только для чтения и белый список
Монтирование предустановленного раздела в режиме только для чтения по-прежнему рекомендуется (для предотвращения случайной записи), но оно не является зависимостью для защиты от удаления. Даже если предустановленный каталог доступен для записи, белый список все равно перехватит вызов до `removePackage`.

Поле permission у `EnvPath::Entry` не участвует в принятии решений для каталога пакетов приложений, оно ограничивает доступ кода JavaScript только для каталогов данных приложений.
:::

### Сброс к заводским настройкам

Благодаря разделению предустановленного и пользовательского каталогов сброс к заводским настройкам можно реализовать следующим образом: удалить все файлы `.pkg` в пользовательском каталоге и сбросить `pkgs.db`; при этом предустановленные пакеты в системном каталоге не затрагиваются. Установка во время выполнения всегда записывает пакеты в `packages().back()` (пользовательский каталог) и никогда не перезаписывает предустановленную копию в системном каталоге. Поэтому после очистки пользовательского каталога и сброса базы данных предустановленные приложения по-прежнему могут нормально распознаваться и загружаться по протоколу `pkg://`.

Опционально можно реализовать «удаление обновлений предустановленных приложений» — то есть удаление копии обновления конкретного предустановленного приложения из пользовательского каталога, чтобы оно откатилось до заводской версии из системного каталога. На данный момент эта возможность существует лишь как потенциальная реализация и официально пока не поддерживается.

### Известные ограничения

Следующее поведение фреймворка требует активного обхода или учета со стороны native бизнес-слоя:

1. **Обновление предустановленных приложений через магазин приложений реализовать невозможно**. Текущее разрешение ресурсов `pkg://<name>` выполняет обход списка `packages()` спереди назад, в то время как установка во время выполнения всегда записывает пакет в `packages().back()` (пользовательский каталог). Если попытаться обновить предустановленное приложение через установку во время выполнения, новая версия попадет в пользовательский каталог, но из-за перекрытия старой версией из системного каталога при поиске спереди назад она никогда не вступит в силу. Данная функция обновления еще ожидает реализации.
2. **Удаление не имеет концепции «защищенности»**. Метод `removePackage` находит пакет только по принципу «первое успешное удаление» и без раздумий удаляет пакет из любого каталога, не имея пометки «является ли пакет предустановленным». Перехват через белый список должен быть реализован вызывающим native-кодом, сам фреймворк такую проверку не предоставляет.
3. **Удаление пакета циферблата не очищает базу данных**. Метод `removePackage` выполняет аннулирование только в таблице приложений (`ADBT_Applet`), но не очищает записи в базе данных для пакетов циферблатов (`ADBT_Dial`), оставляя устаревшие записи. Это задача из б็лога фреймворка, и если логика удаления на стороне native должна поддерживать циферблаты, ей нужно обрабатывать это самостоятельно.
4. **Поле permission элементов каталога пакетов приложений не работает**. Поле permission структуры `EnvPath::Entry` не участвует в логике поиска/установки/удаления списка `packages()`, оно ограничивает доступ кода JavaScript только для каталогов данных приложений. Выразить с его помощью правило «запретить установку в этот каталог» нельзя.

## Шаблоны инициализации платформы

Ниже приведены полные конфигурации `EnvPath` для трех типичных сценариев, которые можно скопировать и настроить под пути вашего устройства. Все настройки должны быть выполнены после конструирования `Application` и до вызовов <code>AppletKit&#8203;::&#8203;launch</code> / `installPackage`.

### Хост-симулятор

Минимальная конфигурация, один каталог для хранения приложений:

```cpp
os::chroot(".");
EnvPath::setEntry(EnvPath::GlobalPackage, "/global.pkg");
EnvPath::packages().emplace_back("/apps");
```

### Встраиваемое целевое устройство (один раздел)

Устройство с единственным разделом, доступным для записи; приложения и данные находятся вместе:

```cpp
EnvPath::setEntry(EnvPath::GlobalPackage, "/global.pkg");
EnvPath::setEntry(EnvPath::AppletCache,   "/data/cache");
EnvPath::setEntry(EnvPath::AppletFiles,   "/data/files");
EnvPath::setEntry(EnvPath::AppletMass,    "/data/mass");
EnvPath::setEntry(EnvPath::AppletTemp,    "/data/temp");
EnvPath::setEntry(EnvPath::AppletStorage, "/data/storage");
EnvPath::packages().emplace_back("/data/apps");
```

### Устройство с предустановленным разделом

Предустановленный раздел только для чтения отделен от пользовательского раздела с возможностью записи:

```cpp
EnvPath::setEntry(EnvPath::GlobalPackage, "/system/global.pkg");
EnvPath::setEntry(EnvPath::AppletCache,   "/data/cache");
EnvPath::setEntry(EnvPath::AppletFiles,   "/data/files");
EnvPath::setEntry(EnvPath::AppletMass,    "/data/mass");
EnvPath::setEntry(EnvPath::AppletTemp,    "/data/temp");
EnvPath::setEntry(EnvPath::AppletStorage, "/data/storage");

// Порядок важен: предустановленный каталог только для чтения идет первым, пользовательский каталог записи — вторым
EnvPath::packages().emplace_back("/system/apps");
EnvPath::packages().emplace_back("/data/apps");
```

После завершения конфигурации вы можете устанавливать и запускать приложения в соответствии со вторым и третьим шагами. Рекомендуется при первом успешном запуске использовать `AppletKit::NoVerify` для установки простого тестового пакета, убедиться, что в `/data/apps` появился файл `.pkg`, а `launch` возвращает не-null, и только после этого постепенно возвращать официальную стратегию проверки и предустановленную компоновку.
