# Конфигурация SDK-проекта

Glyphix поставляется производителям устройств в виде предварительно скомпилированных библиотек. В этой статье описывается, как настроить среду сборки в проекте SDK для разработки на его основе нативных модулей (Native Module), нативных виджетов (Native Widget) или кода адаптации под конкретную платформу.

### Предварительные требования

Перед началом убедитесь, что у вас установлены:
- CMake 3.14 или выше
- C++ компилятор с поддержкой C++14 (GCC, Clang или MSVC)
- Компилятор метаобъектов Glyphix `meta` (должен соответствовать версии SDK, подробности получения см. ниже)
- Инструментарий кросс-компиляции (если требуется сборка под встраиваемые цели)

::: tip Системные требования
- Для инструментария MSVC требуется установить Visual Studio 2022 или новее.
- Для Linux рекомендуется использовать дистрибутивы с графической средой, такие как Ubuntu 22.04 или новее.
- Не рекомендуется использовать Ubuntu 20.04, так как версии пакетов в ней обычно устарели, что часто требует ручной установки нового ПО.
- Использование WSL, Docker и других окружений без графического интерфейса не позволит запускать симулятор и графические примеры (GUI).
- В настоящее время хост-окружение предоставляет только предварительно скомпилированные библиотеки для Linux; библиотеки для Windows и macOS пока не подготовлены.
:::

## Структура пакета SDK

Распакованный SDK содержит следующие директории:

```
glyphix-sdk/
├── libs/
│   └── <target-triple>/       # Предварительно скомпилированные библиотеки по целевым триплет-платформам
│       ├── include/           # Заголовочные файлы Glyphix (gx_*.h)
│       └── lib/               # Статические библиотеки (libglyphix-core.a и др.)
├── cmake/
│   ├── GlyphixSDK.cmake       # Основной конфигурационный скрипт SDK
│   ├── meta.cmake             # Интеграция компилятора метаобъектов (glyphix_add_meta_objects)
│   ├── cross-compile.cmake    # Загрузка тулчейна кросс-компиляции
│   ├── arch/                  # Параметры сборки для различных архитектур (mips-linux-gnu, cortex-m33 и др.)
│   └── toolchain/             # Файлы тулчейнов CMake для различных сред
├── wrapper/                   # Уровень адаптации платформы (реализации для хоста: сеть, файловая система и т.д.)
├── app/                       # Точки входа примеров приложений (emulator, async и т.д.)
└── vendor/                    # Сторонние библиотеки зависимостей
```

### `libs/<target-triple>/`

Предварительно скомпилированные библиотеки SDK разделены по платформам с использованием имен **целевых триплетов** (target triple) в качестве названий директорий, например:

- `x86_64-linux-gnu/`: разработка / симуляция на 64-битном хосте Linux
- `mips-linux-gnu/`: встраиваемая цель MIPS Linux
- `cortex_m55-none-gnu/`: цель без ОС (bare-metal) для Cortex-M55

Директория `include/` содержит все публичные заголовочные файлы Glyphix, каждый из которых имеет префикс `gx_`. В директории `lib/` находятся статические библиотеки, к основным из которых относятся:

| Библиотечный файл | Описание |
|:---|:---|
| `libglyphix-core.a` | Ядро фреймворка (система объектов, дерево виджетов, события и т.д.) |
| `libglyphix-widgets.a` | Библиотека встроенных виджетов |
| `libglyphix-reactive.a` | Реактивный фреймворк (мост JavaScript) |
| `libglyphix-platform.a` | Интерфейсы уровня абстракции платформы (PAL) |
| `libglyphix-service.a` | Уровень системных служб |

::: tip Предварительно скомпилированные vendor-библиотеки
Дистрибутив SDK также содержит некоторые сторонние предварительно скомпилированные библиотеки, например `libfreetype.a` и др. Для удобства мы не распространяем исходный код этих библиотек напрямую, однако при желании вы можете не использовать готовые прекомпилированные бинарники, а собрать их самостоятельно из исходников.
:::

## Подготовка

### Настройка компилятора метаобъектов

Компилятор метаобъектов `meta` поставляется отдельно от SDK в виде независимого архива. После распаковки вы получите две директории: `bin/` и `lib/`. **Обе они должны оставаться в одной директории**, так как исполняемый файл `meta` зависит от библиотек времени выполнения из папки `lib/`.

В Linux и macOS рекомендуется распаковывать его в `/usr/local`, чтобы `meta` автоматически оказался доступен в переменной `PATH`:

::: code-tabs#bash

@tab Linux

```bash
sudo tar -xJf glyphix-meta-vX.X-linux-x86_64.tar.xz -C /usr/local
```

@tab macOS

```bash
sudo tar -xJf glyphix-meta-vX.X-darwin-arm64.tar.xz -C /usr/local
```

:::

Его также можно распаковать в произвольную директорию, а затем добавить папку `bin/` из нее в переменную `PATH`. После завершения проверьте доступность с помощью следующей команды:

```bash
meta --version
```

Если вы не хотите изменять `PATH`, вы можете явно указать полный путь к исполняемому файлу во время конфигурации CMake с помощью параметра `-DGX_META=/path/to/bin/meta`.

## Настройка CMakeLists.txt

### Минимальная конфигурация

::: tip
Конфигурация CMake, описанная в этом разделе, аналогична стандартному шаблону примера проекта Glyphix SDK. Вы можете напрямую ссылаться на исходные файлы SDK.
:::

Ниже представлен минимально рабочий `CMakeLists.txt`, демонстрирующий стандартный каркас конфигурации проекта:

```cmake
cmake_minimum_required(VERSION 3.14)

# Должен загружаться до project(), чтобы тулчейн был готов к моменту определения компилятора в project()
include(cmake/cross-compile.cmake)

project(my_glyphix_app)
set(CMAKE_CXX_STANDARD 14)

# Загрузка Glyphix SDK (настройка путей заголовочных файлов, путей компоновки, цели glyphix::sdk)
include(cmake/GlyphixSDK.cmake)

add_subdirectory(vendor)  # Сторонние зависимости (при наличии)
add_subdirectory(src)     # Ваш исходный код
```

Создайте цель в `src/CMakeLists.txt` и скомпонуйте ее с SDK:

```cmake
add_executable(my_app
  main.cpp
  my_module.cpp
  my_widget.cpp
)

# Компоновка с Glyphix SDK
target_link_libraries(my_app PRIVATE glyphix::sdk)

# Генерация метаданных для заголовочных файлов, содержащих GX_OBJECT
glyphix_add_meta_objects(my_app
  my_module.h
  my_widget.h
)
```

### Регистрация метаобъектов (`glyphix_add_meta_objects`)

Как упоминалось в документации по [системе объектов](./object-system), любой класс, объявивший `GX_OBJECT`, должен быть зарегистрирован в системе сборки, чтобы компилятор метаобъектов сгенерировал для него файл `*_meta.cpp`. Функция CMake `glyphix_add_meta_objects()` служит именно для этой цели:

```cmake
glyphix_add_meta_objects(<target> [header1.h header2.h ...])
```

В качестве аргументов она принимает имя цели и набор путей к **заголовочным файлам**. Для каждого заголовочного файла утилита `meta` генерирует соответствующий файл `*_meta.cpp` в поддиректории `meta/` внутри директории сборки и автоматически добавляет его в список исходных файлов цели для компиляции.

**Пример:** Предположим, проект имеет следующую структуру:

```
src/
├── CMakeLists.txt
├── main.cpp
├── sensors/
│   ├── step_counter.h       # Содержит GX_OBJECT
│   └── step_counter.cpp
└── widgets/
    ├── activity_ring.h      # Содержит GX_OBJECT
    └── activity_ring.cpp
```

Соответствующий `CMakeLists.txt`:

```cmake
include(${CMAKE_CURRENT_SOURCE_DIR}/../cmake/meta.cmake)

add_executable(my_app
  main.cpp
  sensors/step_counter.cpp
  widgets/activity_ring.cpp
)
target_link_libraries(my_app PRIVATE glyphix::sdk)

glyphix_add_meta_objects(my_app
  sensors/step_counter.h
  widgets/activity_ring.h
)
```

::: tip Передавайте только заголовочные файлы, а не .cpp
`glyphix_add_meta_objects()` требует передачи только **заголовочных файлов** (`.h`), содержащих объявление `GX_OBJECT`. Компилятор метаобъектов считывает макроопределения из заголовочных файлов для генерации кода, и ему не нужно разбирать файлы реализации. Напротив, файлы `.cpp` не должны содержать определение классов с `GX_OBJECT`.
:::

::: warning Не пропускайте регистрацию
Если класс объявляет `GX_OBJECT`, но не зарегистрирован через `glyphix_add_meta_objects()`, это приведет к **ошибке компоновки** (не найдены символы, такие как `staticMetaObject`). Не забывайте обновлять `CMakeLists.txt` всякий раз при добавлении новых заголовочных файлов, содержащих `GX_OBJECT`.
:::

### Цель интерфейса `glyphix::sdk`

Файл `GlyphixSDK.cmake` определяет цель библиотеки интерфейсов CMake `glyphix::sdk`, которая инкапсулирует все зависимости компоновки SDK. В вашем `CMakeLists.txt` вам нужно связать только эту единственную цель:

```cmake
target_link_libraries(my_target PRIVATE glyphix::sdk)
```

Внутри это эквивалентно следующему:

```cmake
# Псевдокод — фактически управляется автоматически через GlyphixSDK.cmake
target_include_directories(... ${GLYPHIX_INCLUDE_DIRS} wrapper/include)
target_link_libraries(... -Wl,--start-group ${glyphix-*.a} glyphix-wrapper -Wl,--end-group)
target_link_libraries(... m pthread dl)  # Системные библиотеки UNIX
```

Обертывание статических библиотек с помощью `-Wl,--start-group ... -Wl,--end-group` используется для решения проблем компоновки циклических зависимостей между статическими библиотеками на встраиваемых платформах.

::: tip Проблемы порядка компоновки
Если в вашем проекте есть собственные статические библиотеки (например, `add_library(my_module STATIC ...)`), их следует скомпоновать **внутри** `glyphix::sdk`, иначе область действия `--start-group` не распространится на них, что может вызвать ошибки компоновки. Способ решения заключается в добавлении пути к вашей статической библиотеке после определения переменной `GLYPHIX_LIBS` в `GlyphixSDK.cmake` и до создания цели `glyphix-sdk`, либо в принудительной одновременной компоновке финального исполняемого файла с `my_module` и `glyphix::sdk` с ручным указанием `--start-group`.
:::

## Сборка на хосте

Сборка на хосте используется для запуска примеров программ Glyphix на машине разработчика, что позволяет быстро проверить логику виджетов и модулей без необходимости подключения аппаратного обеспечения.

```bash
mkdir build && cd build
cmake -G Ninja ..
cmake --build .
```

Директория `app/` в SDK содержит несколько примеров, причем каждая поддиректория соответствует отдельной исполняемой цели. Например:

| Поддиректория | Результат сборки | Описание |
|:---|:---|:---|
| `app/emulator/` | `demo` | Симулятор с графическим интерфейсом, зависит от бэкенда окна MiniFB |
| `app/async/` | `async-demo` | Пример асинхронной службы без графического интерфейса, демонстрирующий Native Module и асинхронные обратные вызовы |

`GlyphixSDK.cmake` автоматически определяет триплет компилятора хоста (через `gcc -dumpmachine` или `clang -dumpmachine`) и использует его в качестве ключа для поиска соответствующей предварительно скомпилированной библиотеки в каталоге `libs/`. Например, на машине разработчика x86_64 Linux путь автоматически разрешится в `libs/x86_64-linux-gnu/`.

Если автоматически определенный триплет не совпадает с фактическим каталогом библиотек, вы можете указать его вручную:

```bash
cmake -G Ninja -DTARGET_TRIPLE=x86_64-linux-gnu ..
```

Если вам нужно собрать только определенный пример, вы можете указать имя цели:

```bash
cmake --build . --target demo
cmake --build . --target async-demo
```

## Кросс-компиляция CMake

Для встраиваемых целевых платформ необходимо указать целевую архитектуру с помощью параметра `-DARCH`. В SDK предустановлены следующие конфигурации архитектур:

| Значение `-DARCH` | Целевая платформа | Префикс тулчейна |
|:---:|:---:|:---:|
| `mips-linux-gnu` | MIPS Linux | `mips-linux-gnu-` |
| `cortex_m33-gnu` | ARM Cortex-M33 (GNU) | `arm-none-eabi-` |
| `cortex_m7-gnu` | ARM Cortex-M7 (GNU) | `arm-none-eabi-` |

### Пример для MIPS Linux

```bash
export MIPS_TOOLCHAIN_DIR="/opt/mips-gcc720-glibc229"

mkdir build-mips && cd build-mips
cmake -G Ninja .. \
  -DARCH=mips-linux-gnu \
  -DMIPS_TOOLCHAIN_DIR="$MIPS_TOOLCHAIN_DIR" \
  -DCMAKE_BUILD_TYPE=Release
cmake --build .
```

Если тулчейн уже находится в переменной `PATH` (то есть можно напрямую вызывать `mips-linux-gnu-gcc`), параметр `-DMIPS_TOOLCHAIN_DIR` можно опустить — CMake выполнит поиск автоматически.

### Пример для ARM Cortex-M

```bash
mkdir build-cm33 && cd build-cm33
cmake -G Ninja .. \
  -DARCH=cortex_m33-gnu \
  -DARM_TOOLCHAIN_DIR="/opt/arm-none-eabi-gcc" \
  -DCMAKE_BUILD_TYPE=Release
cmake --build .
```

При кросс-компиляции `GlyphixSDK.cmake` не пытается автоматически определить триплет — файлы архитектур (такие как `cmake/arch/cortex_m33-gnu.cmake`) напрямую задают `TARGET_TRIPLE`, указывая на правильный каталог библиотек.

### Поддерживаемые целевые архитектуры

SDK предоставляет предварительно скомпилированные библиотеки только для архитектур, перечисленных в таблице выше. Если вашей целевой платформы нет среди них, вам потребуется запросить у Glyphix пакет SDK для соответствующей архитектуры; добавить поддержку самостоятельно поверх существующего SDK нельзя.

## Другие системы сборки

Хотя в качестве основной системы сборки SDK использует CMake, Glyphix также предоставляет поддержку других систем сборки для компаний-партнеров. Обычно это сводится к подключению предсобранных библиотек и заголовочных файлов SDK, а также добавлению исходных файлов уровня портирования (porting).

### Ограничения проекта

Этот подход применим для проектов, которым требуются только стандартные функции SDK. Как только возникает необходимость в создании кастомных виджетов, нативных модулей и т.д., становится обязательным подключение компилятора метаобъектов `meta` для генерации необходимого кода привязок (bindings), и на текущий момент CMake является единственной поддерживаемой для этого системой сборки.

Доступно несколько альтернативных вариантов:
1. Использовать проект SDK на CMake для сборки кастомного кода, а затем скомпоновать сгенерированные библиотеки с вашим основным проектом.
2. Использовать проект SDK на CMake для сборки кастомного кода, а затем включить сгенерированные исходные файлы (`*_meta.cpp`) в ваш основной проект.
3. Напрямую вызывать утилиту `meta` в вашей системе сборки для генерации кода привязок.

Сам SDK Glyphix собирается посредством Способа 1. Однако этот способ не подходит для внутреннего процесса разработки сторонних производителей, так как требует поддержки отдельного проекта вне основного проекта прошивки и привязки сгенерированных бинарных библиотек обратно к основному проекту. Это влечет за собой серьезные проблемы управления версиями.

Способ 3 также обычно несовершенен, поскольку производители, как правило, не хотят внедрять внешний инструмент в систему сборки основного проекта.

### Рекомендуемый подход

Поэтому рекомендуется использовать **Способ 2**. Этот метод копирования исходного кода, несмотря на необходимость ручных операций, прост в аудите и интеграции в существующий процесс сборки. Вы можете собрать кастомный код в проекте SDK на CMake, сгенерировать файлы `*_meta.cpp`, а затем скопировать эти файлы в ваш основной проект и скомпилировать их в системе сборки последнего.

Еще одно ограничение этого метода заключается в том, что кастомные исходные файлы должны успешно собираться в среде проекта SDK. В частности, это означает, что они должны собираться независимо от основного проекта, а именно:
- Необходимо правильно настроить пути включения (include paths) и препроцессорные макросы; заголовочные файлы кастомных компонентов не должны содержать специфичных для основного проекта заголовочных файлов.
- Желательно, чтобы файлы `.cpp` кастомных компонентов также успешно компилировались; хотя это не влияет на генерацию файлов `*_meta.cpp`, это упрощает быструю итерацию и отладку в хост-окружении.

::: tip
Для большинства [кастомных виджетов](widget.md) это не является проблемой. Для [нативных модулей (Native Module)](native-module.md) это может быть несколько сложнее, поэтому следует следить за тем, чтобы заголовочные файлы, объявляющие `GX_OBJECT`, не включали специфичные для основного проекта заголовочные файлы.
:::
