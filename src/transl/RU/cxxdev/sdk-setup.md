# Конфигурация SDK-проекта

Glyphix поставляется производителям устройств в виде предварительно скомпилированных библиотек. В этой статье описывается, как настроить среду сборки в проекте SDK для разработки на ее основе Native Module, Native Widget или кода адаптации под конкретную платформу.

### Предварительные требования

Перед началом работы убедитесь, что установлены следующие компоненты:
- CMake 3.14 или выше
- C++ компилятор с поддержкой C++14 (GCC, Clang или MSVC)
- Компилятор метаобъектов Glyphix `meta` (соответствующий версии SDK, подробности получения см. ниже)
- Инструментарий кросс-компиляции (если требуется сборка под встраиваемую цель)

::: tip Системные требования
- Для инструментария MSVC требуется установить Visual Studio 2022 или новее.
- Для Linux рекомендуется использовать дистрибутив с графической средой, например Ubuntu 22.04 или выше.
- Не рекомендуется использовать Ubuntu 20.04, так как версии пакетов в нем обычно устарели, что часто требует ручной установки нового ПО.
- Использование окружений без графического интерфейса, таких как WSL или Docker, не позволит запускать симулятор и графические примеры (GUI).
- В настоящее время хост-окружение предоставляет только предварительно скомпилированные библиотеки для Linux; библиотеки для Windows и macOS пока не готовы.
:::

## Структура пакета SDK

Распакованный SDK содержит следующие директории:

```
glyphix-sdk/
├── libs/
│   └── <target-triple>/       # Предварительно скомпилированные библиотеки по целевому триплету
│       ├── include/           # Заголовочные файлы Glyphix (gx_*.h)
│       └── lib/               # Статические библиотеки (libglyphix-core.a и др.)
├── cmake/
│   ├── GlyphixSDK.cmake       # Основной скрипт конфигурации SDK
│   ├── meta.cmake             # Интеграция компилятора метаобъектов (glyphix_add_meta_objects)
│   ├── cross-compile.cmake    # Загрузка инструментария кросс-компиляции
│   ├── arch/                  # Параметры сборки для различных архитектур (mips-linux-gnu, cortex-m33 и др.)
│   └── toolchain/             # Файлы инструментария CMake для различных toolchain
├── wrapper/                   # Уровень адаптации платформы (реализации для хоста: сеть, файловая система и т.д.)
├── app/                       # Точки входа примеров приложений (emulator, async и др.)
└── vendor/                    # Сторонние библиотеки зависимостей
```

### `libs/<target-triple>/`

Предварительно скомпилированные библиотеки SDK разделены по платформам с использованием имен **целевых триплетов** (target triple), например:

- `x86_64-linux-gnu/`: разработка / симуляция на 64-битном хосте Linux
- `mips-linux-gnu/`: встроенная цель MIPS Linux
- `cortex_m55-none-gnu/`: цель без ОС (bare-metal) Cortex-M55

Директория `include/` содержит все публичные заголовочные файлы Glyphix, все они имеют префикс `gx_`. В директории `lib/` находятся статические библиотеки, основные из которых включают:

| Файл библиотеки | Описание |
|:---|:---|
| `libglyphix-core.a` | Основной фреймворк (система объектов, дерево виджетов, события и т.д.) |
| `libglyphix-widgets.a` | Библиотека встроенных виджетов |
| `libglyphix-reactive.a` | Реактивный фреймворк (мост JavaScript) |
| `libglyphix-platform.a` | Интерфейс уровня абстракции платформы (PAL) |
| `libglyphix-service.a` | Уровень системных служб |

::: tip Предварительно скомпилированные библиотеки vendor
Дистрибутив SDK также содержит некоторые предварительно скомпилированные сторонние библиотеки, такие как `libfreetype.a` и др. Для удобства мы не распространяем исходный код этих библиотек напрямую, однако вы можете не использовать готовые бинарники, а выполнить сборку непосредственно из исходного кода.
:::

## Подготовка

### Настройка компилятора метаобъектов

Компилятор метаобъектов `meta` распространяется отдельно от SDK в виде независимого архива. После распаковки вы получите две директории: `bin/` и `lib/`. **Обе они должны находиться в одной директории**, так как исполняемый файл `meta` зависит от библиотек времени выполнения из папки `lib/`.

В Linux и macOS рекомендуется распаковывать архив в `/usr/local`, чтобы `meta` автоматически оказался в переменной окружения `PATH`:

::: code-tabs#bash

@tab Linux

```bash
sudo tar -xJf glyphix-meta-vX.X-linux-x86_64.tar.xz -C /usr/local
```

@tab macOS

```bash
sudo tar -xJf glyphix-meta-vX.X-darwin-arm64.tar.xz -C /usr/local
```

:::

Также можно распаковать архив в произвольную директорию и добавить ее папку `bin/` в переменную `PATH`. После завершения проверьте доступность команды:

```bash
meta --version
```

Если вы не хотите изменять `PATH`, вы можете явно указать полный путь к исполняемому файлу во время конфигурации CMake с помощью параметра `-DGX_META=/path/to/bin/meta`.

## Настройка CMakeLists.txt

### Минимальная конфигурация

::: tip
Описанная в этом разделе конфигурация CMake аналогична стандартному шаблону примера проекта Glyphix SDK, на который вы можете напрямую ссылаться в исходных файлах SDK.
:::

Ниже приведен минимальный рабочий файл `CMakeLists.txt`, демонстрирующий стандартный каркас конфигурации проекта:

```cmake
cmake_minimum_required(VERSION 3.14)

# Должен быть загружен до project(), чтобы инструментарий был готов во время определения компилятора в project()
include(cmake/cross-compile.cmake)

project(my_glyphix_app)
set(CMAKE_CXX_STANDARD 14)

# Загрузка Glyphix SDK (настройка путей к заголовкам, путей компоновки, цели glyphix::sdk)
include(cmake/GlyphixSDK.cmake)

add_subdirectory(vendor)  # Сторонние зависимости (при наличии)
add_subdirectory(src)     # Ваш исходный код
```

Создание цели и компоновка с SDK в `src/CMakeLists.txt`:

```cmake
add_executable(my_app
  main.cpp
  my_module.cpp
  my_widget.cpp
)

# Компоновка с Glyphix SDK
target_link_libraries(my_app PRIVATE glyphix::sdk)

# Генерация метаданных для заголовочных файлов, содержащих GX_OBJECT
glyphix_add_meta_objects(my_app
  my_module.h
  my_widget.h
)
```

### Регистрация метаобъектов (`glyphix_add_meta_objects`)

Как упоминалось в документации по [системе объектов](./object-system), любой класс, объявивший макрос `GX_OBJECT`, должен быть зарегистрирован в системе сборки, чтобы компилятор метаобъектов мог сгенерировать для него файл `*_meta.cpp`. Функция `glyphix_add_meta_objects()` в CMake выполняет именно эту задачу:

```cmake
glyphix_add_meta_objects(<target> [header1.h header2.h ...])
```

Она принимает имя цели и набор путей к **заголовочным файлам** в качестве аргументов. Для каждого заголовочного файла утилита `meta` генерирует соответствующий файл `*_meta.cpp` в поддиректории `meta/` директории сборки и автоматически добавляет его в список исходных файлов цели для компиляции.

**Пример:** Предположим, проект имеет следующую структуру:

```
src/
├── CMakeLists.txt
├── main.cpp
├── sensors/
│   ├── step_counter.h       # Содержит GX_OBJECT
│   └── step_counter.cpp
└── widgets/
    ├── activity_ring.h      # Содержит GX_OBJECT
    └── activity_ring.cpp
```

Соответствующий `CMakeLists.txt`:

```cmake
include(${CMAKE_CURRENT_SOURCE_DIR}/../cmake/meta.cmake)

add_executable(my_app
  main.cpp
  sensors/step_counter.cpp
  widgets/activity_ring.cpp
)
target_link_libraries(my_app PRIVATE glyphix::sdk)

glyphix_add_meta_objects(my_app
  sensors/step_counter.h
  widgets/activity_ring.h
)
```

::: tip Передавайте только заголовки, а не файлы .cpp
Функции `glyphix_add_meta_objects()` требуется передавать только **заголовочные файлы** (`.h`), содержащие объявления `GX_OBJECT`. Компилятор метаобъектов считывает макросы из заголовочных файлов для генерации кода и не нуждается в парсинге файлов реализации. И наоборот, файлы `.cpp` не должны содержать объявления классов с макросом `GX_OBJECT`.
:::

::: warning Не пропускайте регистрацию
Если класс объявил `GX_OBJECT`, но не был зарегистрирован через `glyphix_add_meta_objects()`, это приведет к **ошибке компоновки** (не найдены символы, такие как `staticMetaObject`). Не забывайте обновлять `CMakeLists.txt` каждый раз при добавлении новых заголовочных файлов с макросом `GX_OBJECT`.
:::

### Цель интерфейса `glyphix::sdk`

Файл `GlyphixSDK.cmake` определяет цель интерфейсной библиотеки CMake `glyphix::sdk`, которая инкапсулирует все зависимости компоновки SDK. В вашем файле `CMakeLists.txt` достаточно связать только эту цель:

```cmake
target_link_libraries(my_target PRIVATE glyphix::sdk)
```

Внутри это эквивалентно следующему:

```cmake
# Псевдокод — фактически автоматически управляется через GlyphixSDK.cmake
target_include_directories(... ${GLYPHIX_INCLUDE_DIRS} wrapper/include)
target_link_libraries(... -Wl,--start-group ${glyphix-*.a} glyphix-wrapper -Wl,--end-group)
target_link_libraries(... m pthread dl)  # Системные библиотеки UNIX
```

Использование конструкций `-Wl,--start-group ... -Wl,--end-group` для оборачивания статических библиотек необходимо для решения проблем с циклическими зависимостями при компоновке статических библиотек на встраиваемых платформах.

::: tip Проблемы с порядком компоновки
Если в вашем проекте есть собственные статические библиотеки (например, `add_library(my_module STATIC ...)`), их следует компоновать **внутри** `glyphix::sdk`, иначе область действия `--start-group` на них не распространится, что может вызвать ошибки компоновки. Способ решения заключается в том, чтобы добавить путь к вашей статической библиотеке после определения переменной `GLYPHIX_LIBS` в `GlyphixSDK.cmake` и до создания цели `glyphix-sdk`, либо заставить итоговый исполняемый файл одновременно ссылаться как на `my_module`, так и на `glyphix::sdk`, вручную указав нужные группы.
:::

## Сборка на хосте

Сборка на хосте используется для запуска примеров Glyphix на машине разработчика, что позволяет быстро проверять логику виджетов и модулей без подключения реального аппаратного обеспечения.

```bash
mkdir build && cd build
cmake -G Ninja ..
cmake --build .
```

Директория `app/` в SDK содержит несколько примеров, каждый из которых представляет собой отдельную исполняемую цель. Например:

| Поддиректория | Результат сборки | Описание |
|:---|:---|:---|
| `app/emulator/` | `demo` | Симулятор с графическим интерфейсом, зависящий от бэкенда окна MiniFB |
| `app/async/` | `async-demo` | Пример асинхронной службы без графического интерфейса, демонстрирующий Native Module и асинхронные вызовы обратного вызова (callback) |

Файл `GlyphixSDK.cmake` автоматически определяет триплет компилятора хоста (через `gcc -dumpmachine` или `clang -dumpmachine`) и использует его в качестве ключа для поиска соответствующих предварительно скомпилированных библиотек в директории `libs/`. Например, на машине разработчика x86_64 Linux автоматически выбирается путь `libs/x86_64-linux-gnu/`.

Если автоматически определенный триплет не совпадает с реальной директорией библиотек, его можно задать вручную:

```bash
cmake -G Ninja -DTARGET_TRIPLE=x86_64-linux-gnu ..
```

Если требуется собрать только конкретный пример, можно указать имя цели:

```bash
cmake --build . --target demo
cmake --build . --target async-demo
```

## Кросс-компиляция CMake

Для встраиваемых целей необходимо указать целевую архитектуру с помощью параметра `-DARCH`. В SDK предустановлены следующие конфигурации архитектур:

| Значение `-DARCH` | Целевая платформа | Префикс инструментария |
|:---:|:---:|:---:|
| `mips-linux-gnu` | MIPS Linux | `mips-linux-gnu-` |
| `cortex_m33-gnu` | ARM Cortex-M33 (GNU) | `arm-none-eabi-` |
| `cortex_m7-gnu` | ARM Cortex-M7 (GNU) | `arm-none-eabi-` |

### Пример для MIPS Linux

```bash
export MIPS_TOOLCHAIN_DIR="/opt/mips-gcc720-glibc229"

mkdir build-mips && cd build-mips
cmake -G Ninja .. \
  -DARCH=mips-linux-gnu \
  -DMIPS_TOOLCHAIN_DIR="$MIPS_TOOLCHAIN_DIR" \
  -DCMAKE_BUILD_TYPE=Release
cmake --build .
```

Если инструментарий уже прописан в переменной `PATH` (то есть команды вроде `mips-linux-gnu-gcc` вызываются напрямую), параметр `-DMIPS_TOOLCHAIN_DIR` можно опустить, и CMake найдет его автоматически.

### Пример для ARM Cortex-M

```bash
mkdir build-cm33 && cd build-cm33
cmake -G Ninja .. \
  -DARCH=cortex_m33-gnu \
  -DARM_TOOLCHAIN_DIR="/opt/arm-none-eabi-gcc" \
  -DCMAKE_BUILD_TYPE=Release
cmake --build .
```

При кросс-компиляции `GlyphixSDK.cmake` не пытается автоматически определить триплет — файлы архитектур (например, `cmake/arch/cortex_m33-gnu.cmake`) напрямую задают `TARGET_TRIPLE`, указывая на корректную директорию с библиотеками.

### Поддерживаемые целевые архитектуры

SDK предоставляет предварительно скомпилированные библиотеки только для архитектур, перечисленных в таблице выше. Если ваша целевая платформа отсутствует в списке, вам потребуется запросить у Glyphix пакет SDK для соответствующей архитектуры; добавить поддержку самостоятельно на базе существующего SDK нельзя.

## Другие системы сборки

В качестве основной системы сборки SDK использует CMake, однако Glyphix также предоставляет поддержку других систем сборки для компаний-партнеров. Обычно это сводится к подключению предварительно собранных библиотек и заголовков SDK с добавлением исходных файлов уровня портирования (porting).

### Ограничения проекта

Такой подход применим для проектов, которым требуются только стандартные функции SDK. Как только возникает необходимость кастомизации виджетов, создания Native Module и т.д., становится обязательным использование компилятора метаобъектов `meta` для генерации необходимого кода связывания (bindings). На данный момент CMake является единственной поддерживаемой для этого системой сборки.

Доступно несколько альтернативных вариантов:
1. Использовать CMake-проект SDK для сборки пользовательского кода, а затем скомпоновать полученные библиотеки с вашим основным проектом.
2. Использовать CMake-проект SDK для сборки пользовательского кода, а затем добавить сгенерированные исходные файлы (`*_meta.cpp`) в ваш основной проект.
3. Напрямую вызывать утилиту `meta` из вашей системы сборки для генерации кода связывания.

Стоит отметить, что сам SDK Glyphix собирается по методу 1. Однако это не подходит для внутренних процессов разработки сторонних производителей, поскольку требует поддержки отдельного проекта вне основного проекта прошивки и обратной компоновки полученных бинарников, что создает серьезные проблемы с управлением версиями.

Метод 3 также обычно не идеален, так как производители, как правило, не хотят внедрять сторонние инструменты в систему сборки основного проекта.

### Рекомендуемый подход

Поэтому рекомендуется использовать **метод 2**. Хотя копирование исходного кода этим способом требует ручных операций, он прост в проверке и интеграции в существующие процессы сборки. Вы можете собрать пользовательский код в CMake-проекте SDK, сгенерировать файлы `*_meta.cpp`, а затем скопировать эти файлы в ваш основной проект и скомпилировать их средствами его системы сборки.

Еще одно ограничение этого подхода заключается в том, что пользовательские исходные файлы должны успешно собираться в окружении проекта SDK. В частности, это означает, что они должны собираться независимо от основного проекта, а именно:
- Необходимо правильно настроить пути поиска заголовочных файлов (include paths) и определения препроцессора; заголовочные файлы кастомизируемых компонентов не должны ссылаться на специфичные для основного проекта заголовки.
- Желательно, чтобы файлы `.cpp` кастомизируемых компонентов также успешно компилировались; хотя это не влияет на генерацию файлов `*_meta.cpp`, это упрощает быстрый цикл итераций и отладку в окружении хоста.

::: tip
Для большинства [кастомизируемых виджетов](widget.md) это не представляет проблемы. Для [Native Module](native-module.md) это может оказаться несколько сложнее: следует следить за тем, чтобы заголовочные файлы, объявляющие `GX_OBJECT`, не содержали специфичных для основного проекта зависимостей.
:::
