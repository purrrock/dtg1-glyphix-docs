# Объектная система

Объектная модель фреймворка Glyphix на C++ базируется на классе `PrimitiveObject`. Понимание этой модели является фундаментом для дальнейшей разработки.

Объектная система состоит из трех взаимодействующих частей: **иерархия базовых классов объектов** определяет общие возможности и правила жизненного цикла всех управляемых объектов; **метаобъектная система** генерирует метаданные для классов C++ на этапе сборки с помощью метакомпилятора, наделяя их возможностями рефлексии, привязки свойств и экспорта в JavaScript; а **механизм обеспечения безопасности памяти** решает универсальную для GUI-фреймворков проблему висячих указателей (dangling pointers) с помощью защищенных указателей и подсчета ссылок.

## Рефлексия и метаобъектный компилятор

Классы в стандартном C++ «молчат»: получив указатель на объект, вы не можете узнать в рантайме, какие у него есть члены, как они называются и как их читать или записывать. Для статической разработки на C++, не требующей скриптинга, это не является препятствием.

Но Glyphix работает иначе. Когда в шаблоне страницы приложения написано `:value="progress"`, реактивному фреймворку необходимо во время выполнения найти по строке `"value"` свойство элемента управления, соответствующее этому значению, и автоматически обновить его при изменении данных. Способность программы «знать свою структуру во время выполнения» называется **рефлексией (Reflection)**, и стандартный C++ ее не поддерживает.

Решением в Glyphix является добавление в процесс сборки **метаобъектного компилятора (Meta Compiler)**. Перед официальной компиляцией C++ он сканирует исходный код и генерирует метаданные для тех классов, которые должны участвовать в объектной системе. Разработчику достаточно поместить макрос **`GX_OBJECT`** в начале определения класса, и метаобъектный компилятор обработает его — после этого фреймворк сможет читать и записывать его свойства по имени, вызывать методы, а также обращаться к нему из JavaScript.

Вам пока не нужно вдаваться во внутреннее устройство метаобъектной системы. Достаточно запомнить одно правило: все классы, которым требуется рефлексия, должны содержать макрос `GX_OBJECT` при определении и наследоваться от `PrimitiveObject` или `Object`.

## `PrimitiveObject` и `Object`

Объектная система фреймворка делится на два уровня:

**`PrimitiveObject`** — это базовый класс для всех **управляемых объектов**. Классы, наследующие его, получают возможности фреймворка по рефлексии свойств, динамическому приведению типов и безопасному отложенному удалению. Однако сам по себе `PrimitiveObject` **не имеет** иерархии родитель-потомок — это просто «объект C++, о котором осведомлен фреймворк». Такие типы, как `AsyncSession` и `BindableObject`, наследуются от него, поскольку им не нужно выстраиваться в древовидную структуру.

**`Object`** наследует `PrimitiveObject` и добавляет к нему **иерархическую структуру родитель-потомок**: при создании передается указатель `parent`, и при уничтожении родительского объекта все дочерние объекты также рекурсивно уничтожаются. Дерево элементов управления (Widget Tree) организуется именно с помощью этого механизма.

::: tip Аналогии с другими фреймворками
Если у вас есть опыт разработки на Qt, метаобъектную систему Glyphix можно сравнить с системой MOC в Qt: `GX_OBJECT` соответствует `Q_OBJECT`. Однако есть и множество различий, например, в Glyphix возможности `QObject` из Qt разделены на два слоя; кроме того, `Signal` здесь — это просто обычный шаблонный класс, не зависящий от метаобъектного компилятора.

Другие фреймворки, такие как UCLASS в Unreal Engine, также имеют похожие системы рефлексии.
:::

Выбор базового класса зависит от того, должен ли ваш класс являться частью дерева:

```cpp
// Требуется участие в объектном дереве → наследуем Object
class MySensor : public Object {
    GX_OBJECT
public:
    explicit MySensor(Object *parent = nullptr) : Object(parent) {}
};

// Требуется только осведомленность фреймворка, без дерева → наследуем PrimitiveObject
class MyNetworkSession : public PrimitiveObject {
    GX_OBJECT_KINDS(ExplicitDeleteKind)
public:
    MyNetworkSession() = default;
};
```

Вызов `GX_OBJECT_KINDS(ExplicitDeleteKind)` в коде — это дополнительное объявление. Подобно макросу `GX_OBJECT`, оно объявляет метаобъектный класс, но сообщает фреймворку, что за жизненный цикл этого объекта отвечает разработчик и он не будет автоматически уда сборщиком мусора JavaScript. Типы, чувствительные к жизненному циклу, такие как `AsyncSession`, используют именно его.

## Свойства и сигналы

Макрос **`GX_PROPERTY`** используется для объявления свойства, распознаваемого фреймворком, с привязкой соответствующих геттера и сеттера. После объявления свойство может управляться реактивной системой фреймворка: при изменении значения пользовательский интерфейс, зависящий от него, автоматически обновляется, а анимационная система может применять к нему интерполяцию:

```cpp
class MyWidget : public Widget {
    GX_OBJECT
public:
    int value() const { return m_value; }
    void setValue(int v) { m_value = v; update(); }

    GX_PROPERTY(int value, get value, set setValue)

private:
    int m_value = 0;
};
```

### Сигналы (Signal)

**`Signal<>`** представляет собой механизм уведомления о событиях и объявляется непосредственно как член класса. При наступлении события сигнал «испускается» (emitted), а другие объекты получают уведомления путем «подключения» (connection) ([лямбда-выражения](https://en.cppreference.com/w/cpp/language/lambda) являются синтаксисом анонимных функций в C++):

```cpp
class MyWidget : public Widget {
    GX_OBJECT
public:
    Signal<int> valueChanged;

    void setValue(int v) {
        m_value = v;
        valueChanged(v);  // Испускание сигнала
    }
private:
    int m_value = 0;
};

// Подключение к методу класса
myWidget->valueChanged.connect(this, &MyClass::onValueChanged);

// Или подключение к лямбда-функции
auto slot = make_slot([](int v) { /* Реакция на изменение */ });
myWidget->valueChanged.connect(slot);
```

::: tip Сравнение с сигналами и слотами Qt
Классический механизм сигналов и слотов в Qt требует поддержки генерации кода с помощью MOC, в то время как `Signal<>` — это чистый шаблонный класс C++, не зависящий от метаобъектного компилятора. Поэтому использовать объект `Signal<...>` необязательно в каком-то конкретном классе, его можно применять где угодно.

Поскольку `Signal` является классом, он занимает память (даже при отсутствии подключений), поэтому ради экономии памяти рекомендуется по возможности использовать перечисления типов событий и единые переменные-члены для сигналов, вместо объявления отдельного члена `Signal` под каждое событие.
:::

### Полная форма макроса `GX_PROPERTY`

Помимо `get` и `set`, макрос `GX_PROPERTY` поддерживает объявление связанного сигнала изменения (`signal`), который выступает стандартным интерфейсом реактивного фреймворка для подписки на изменения свойств:

```cpp
class ProgressRing : public Widget {
    GX_OBJECT
public:
    int value() const { return m_value; }
    void setValue(int v) {
        if (m_value == v) return;
        m_value = v;
        update();
        valueChanged(v);
    }

    Signal<int> valueChanged;

    GX_PROPERTY(int value, get value, set setValue, signal valueChanged)

private:
    int m_value = 0;
};
```

Изменения свойств, для которых объявлен `signal`, автоматически передаются через реактивный фреймворк выражениям JavaScript, привязанным к этим свойствам. Это лежит в основе двусторонней синхронизации между свойствами элементов управления и данными приложения.

Поле `signal` внутри макроса `GX_PROPERTY` не зависит от типов параметров `Signal<T>` — фреймворку важно лишь то, существует ли он и когда испускается. Напротив, в этом случае обязательно предоставление поля `get`, чтобы фреймворк мог считывать значение свойства на стороне JavaScript.

## Защищенные указатели и безопасность памяти

В GUI-фреймворках асинхронные сценарии легко могут стать причиной аварийных завершений из-за висячих указателей (Segmentation Fault). Типичный пример:
```cpp
void onNetworkResponse(const String &data) {
    // Сетевой запрос занимает 2 секунды
    // Однако за эти 2 секунды пользователь мог покинуть текущую страницу, и label был уничтожен
    this->label->setText(data); // Segmentation Fault!
}
```
Коллбэки таймеров, коллбэки ввода-вывода и любые другие асинхронные сценарии несут в себе аналогичный риск. В фреймворках со скриптинг-поддержкой подобные случаи структурно неизбежны, поэтому необходимо предоставлять безопасный механизм отслеживания жизненного цикла.

### Защищенный указатель `Pointer<T>`

Для всех производных классов `PrimitiveObject` во фреймворк встроена поддержка подсчета слабых ссылок. Используйте `Pointer<T>` для хранения не владеющих межобъектных ссылок; когда целевой объект уничтожается, `Pointer<T>` автоматически зануляется, и для безопасного использования достаточно выполнить проверку перед разыменованием:

```cpp
Pointer<Label> m_label; // Объявление в качестве члена класса

// ...присваивание после создания...
m_label = label;

// В любом асинхронном коллбэке, который может привести к уничтожению label:
void onNetworkResponse(const String &data) {
    /if (!m_label)
        return; // label уже уничтожен, безопасный выход
    m_label->setText(data); // Теперь доступ безопасен
}
```

::: tip Когда применять
Используйте `Pointer<T>` вместо «голого» указателя `T *` для отслеживания жизненного цикла, когда удерживаете указатель на другой объект, но не владеете им. Механизм `connect` у класса `Signal` также опирается на защищенные указатели: при уничтожении получателя (объекта, содержащего слот) соединение автоматически разрывается, предотвращая вызов висячего коллбэка.
:::

::: warning Ограничения потокобезопасности
Защищенные указатели не поддерживают межпоточный доступ — они предназначены практически исключительно для использования в UI-потоке. Кроме того, они не являются абстракцией с нулевой стоимостью: каждое создание влечет за собой операции с подсчетом ссылок.
:::

### Интрузивный подсчет ссылок `SharedRef<T>`

Для обычных объектов-значений, не наследующих `PrimitiveObject` (таких как пользовательские структуры данных), фреймворк предоставляет интрузивный разделяемый подсчет ссылок. Унаследуйте тип-значение от `SharedValue` и удерживайте его с помощью `SharedRef<T>`, чтобы получить семантику разделения, аналогичную [`std::shared_ptr`](https://en.cppreference.com/w/cpp/memory/shared_ptr), избегая при этом выделения дополнительного управляющего блока:

```cpp
class MyData : public SharedValue {
public:
    int x = 0;
    String name;
};

auto ref1 = make_shared<MyData>();
ref1->x = 42;

SharedRef<MyData> ref2 = ref1; // Количество ссылок увеличивается, объект разделяется
```

`SharedRef` также поддерживает семантику Copy-on-Write (копирование при записи): перед модификацией скопированной версии создается независимая копия, гарантирующая отсутствие влияния между несколькими владельцами. Этот механизм реализован с использованием атомарного подсчета ссылок для обеспечения потокобезопасности.

## Динамическое приведение типов

[`dynamic_cast`](https://en.cppreference.com/w/cpp/language/dynamic_cast) в стандартном C++ зависит от RTTI (Run-Time Type Information), в то время как в средах встроенных систем сборка обычно выполняется с флагом `-fno-rtti`. Функция `dyn_cast` предоставляет эквивалентную безопасную возможность понижающего приведения типов в рантайме, используя метаобъектную систему.

Целевой тип `T` для `dyn_cast<T *>()` должен удовлетворять двум условиям:
1. Наследоваться от `PrimitiveObject`.
2. Содержать макрос `GX_OBJECT`/`GX_OBJECT_KINDS`.

```cpp
PrimitiveObject *obj = getSomeObject();

// Безопасное понижающее приведение, при неудаче возвращает nullptr
auto *btn = dyn_cast<Button *>(obj);
if (btn)
    btn->setText("OK");

// Версии для const также поддерживаются
const auto *constBtn = dyn_cast<const Button *>(obj);
```

::: warning Необходимость `GX_OBJECT`
Проверка типов в `dyn_cast` опирается на статическую информацию о метаобъекте целевого класса (`staticMetaObject`). Если в целевом классе не объявлен макрос `GX_OBJECT`, ему будет не хватать необходимой информации о типе в рантайме, что приведет к ошибке компиляции.
:::

В разработке Native Module функция `dyn_cast` используется особенно часто: фреймворк нередко передает объекты по указателям на базовый класс (`PrimitiveObject *` или `Object *`), и `dyn_cast` требуется для безопасного восстановления конкретного типа перед выполнением операций.

Учитывая, что политика безопасности песочницы не доверяет объектам, поступающим из скриптов, мы не можем предполагать, что переданный в рантайме указатель на объект имеет корректный тип, поэтому обязаны использовать `dyn_cast` для проверки типа и безопасного доступа к его членам.

### Ловушка утечки памяти

Типичный паттерн использования `dyn_cast` таит в себе риск утечки памяти, например:
```cpp
auto *session = dyn_cast<Session *>(takeObjectOwnership());
if (session) {
    // Успешное приведение, обращение к членам session и перенос владения
}
```
Проблема заключается в том, что если объект, возвращаемый функцией `takeObjectOwnership()`, не имеет типа `Session`, `dyn_cast` вернет `nullptr`, однако владение исходным объектом уже было перенесено — если нет иного механизма для утилизации этого объекта, произойдет утечка памяти.

При разработке Native Module API с подобными проблемами можно столкнуться на практике, поэтому соответствующие модули предоставляют лучшие API для их предотвращения. Тем не менее, разработчики должны осознавать этот потенциальный риск и не вводиться в заблуждение «безопасностью» `dyn_cast`.

### Необходимость макроса `GX_OBJECT`

Не все классы, наследующие `PrimitiveObject`, обязаны содержать `GX_OBJECT`. Назначение макроса `GX_OBJECT` заключается в регистрации класса в метаобъектной системе, что включает поддержку рефлексии, привязки свойств, `dyn_cast` и других возможностей. Если ваш класс:

- не нужно экспортировать в JavaScript;
- не нуждается в механизмах рефлексии вроде `GX_PROPERTY` или `GX_METHOD`;
- не должен подвергаться безопасному приведению через `dyn_cast`.

Тогда вы можете опустить `GX_OBJECT`, просто унаследовав базовый класс и используя возможности C++ в обычном режиме:

```cpp
// Внутренний вспомогательный класс, не требующий возможностей метаобъекта; GX_OBJECT опущен
class InternalBufferManager : public PrimitiveObject {
public:
    explicit InternalBufferManager() = default;
    void flush();
private:
    // ...
};
```

Классы без `GX_OBJECT` по-прежнему обладают базовыми возможностями `PrimitiveObject`, включая `deleteLater()` и поддержку защищенных указателей, но теряют рефлексию и распознавание типов в рантайме.

Другой сценарий: ваш конечный тип нуждается в метаобъектных возможностях, но некоторые из промежуточных базовых классов — нет. В этом случае промежуточные базовые классы могут не объявлять `GX_OBJECT`. Это приведет к потере некоторой информации о типах в рантайме, но сократит объем кода.

::: tip
Если вы сомневаетесь, нужен ли вам `GX_OBJECT`, в большинстве случаев рекомендуется перестраховаться и добавить его.
:::

Последнее важное отличие заключается в следующем: после того как класс помечен макросом `GX_OBJECT`, он должен находиться в заголовочном файле (`*.h`) и регистрироваться в системе сборки с помощью макроса CMake `glyphix_add_meta_objects()`. Для классов без `GX_OBJECT` такого требования нет, их можно определять непосредственно в файлах `.cpp`.

## Система типов времени выполнения

Во всех предыдущих обсуждениях `GX_PROPERTY` оставался один безмолвный вопрос:

```cpp
GX_PROPERTY(int value, get value, set setValue)
```

Откуда JavaScript знает, что такое `int`? Когда на стороне JavaScript пишется `widget.value = 42`, это `42` имеет тип `number` в JavaScript. А метод сеттера `setValue(int v)` принимает `int` из C++. Что происходит между ними? И наоборот, как `int`, возвращаемый функцией `getValue()`, превращается в `number` в JavaScript?

Очевидно, что при отсутствии какого-либо связующего кода фреймворк должен выполнять за кулисами определенную работу по сопряжению статических типов C++ и динамических типов скрипта. Этот процесс устроен достаточно прозрачно, и в данном разделе будет объяснено, что именно происходит «под капотом».

### Универсальный контейнер типов `Variant`

Ответ кроется в типе `Variant`. Он представляет собой стирающий типы контейнер, способный хранить значения произвольных типов, и служит ключевым мостом, связывающим статическую систему типов C++ и динамические типы JavaScript.

Всякий раз, когда фреймворку требуется пересечь эту границу, он использует путь через `Variant`:

1. **Промежуточный слой чтения и записи свойств**: при чтении и записи свойств, объявленных через `GX_PROPERTY`, через API рефлексии значения передаются в виде `Variant`. Фреймворк преобразует `JsValue` из JavaScript в `Variant`, а затем из `Variant` в фактический тип параметра сеттера C++ (и наоборот при чтении).
2. **Маршалинг параметров вызовов методов**: аргументы и возвращаемые значения методов `GX_METHOD` перед передачей в C++ предварительно представляются в виде `Variant`.

```cpp
Variant v1;                  // Пустое значение (null)
Variant v2{42};              // Хранит int
Variant v3{3.14};            // Хранит double
Variant v4{String("Hello")}; // Хранит String
// Variant должен конструироваться явно, неявное преобразование не поддерживается
// Variant v5 = 42; // Ошибка, необходимо писать Variant v5{42};

// Проверка типов
if (v2.is<int>()) { /* ... */ }
// Проверять приводимость не рекомендуется; лучше сразу вызвать to<T>() и проверить результат на невалидное значение
if (v3.convertible<double>()) { /* ... */ }

// Чтение по ссылке (самое быстрое, требует точного совпадения типов)
int n = v2.as<int>();
// Чтение по ссылке, при несовпадении типов возвращает значение по умолчанию
double d = v2.as<double>(0.0); // int != double, возвращает 0.0
// Чтение с преобразованием типов (по значению)
int fromDouble = v3.to<int>();   // 3.14 -> 3
String fromInt = v2.to<String>(); // 42 -> "42"
```

::: tip
Это не [`std::variant`](https://en.cppreference.com/w/cpp/utility/variant) из C++17, а скорее аналог [`std::any`](https://en.cppreference.com/w/cpp/utility/any), поддерживающий идентификацию типов в рантайме и автоматическое преобразование типов.

Обычно вам не требуется напрямую взаимодействовать с `Variant` в бизнес-коде — фреймворк автоматически выполняет все преобразования. Вы будете сталкиваться с ним напрямую только при реализации низкоуровневых расширений фреймворка, написании универсальных служебных функций или при необходимости непосредственной работы с API рефлексии времени выполнения.
:::

### Встроенные маппинги типов

Фреймворк имеет встроенные двусторонние маппинги распространенных базовых типов C++ в JavaScript:

| Тип C++ | Тип JavaScript | Примечания |
|:---:|:---:|:---:|
| `int`, `float`, `double` и т.д. | `number` | Числовые типы проецируются напрямую |
| `bool` | `boolean` | |
| `String` | `string` | |
| Производные от `PrimitiveObject *` | Ссылка на объект JavaScript | Жизненным циклом объекта управляет фреймворк |
| Типы-значения `Color`, `Length` и т.д. | `string` | Представляются строками в определенном формате |

Именно поэтому после написания `GX_PROPERTY(int value, ...)` на стороне JS можно сразу сделать `widget.value = 42`: тип `int` присутствует во встроенной таблице маппингов, и фреймворк знает, как его конвертировать.

::: note Не используйте строки C
Класс `Variant` требует, чтобы хранимый тип `T` владел данными, поэтому невладеющие типы, такие как C-строки (`const char *`) и срезы строк (`String::View`), не могут храниться в `Variant`. Всегда используйте `String` для представления текстовых данных, а при необходимости явно преобразуйте их в `String` перед сохранением в `Variant`.

Использование неподдерживаемого типа строк приведет к ошибке компиляции.
:::

::: important
В таблице встроенных маппингов типов отсутствует регистрация для типов, связанных с `std::string`, поэтому хранить `std::string` в `Variant` также не рекомендуется. Неподдерживаемые типы могут быть сохранены, но будут обрабатываться как непрозрачные объекты C++, которые невозможно использовать в JavaScript.
:::

### Рефлексия сложных типов

Для классов, объявленных с макросом `GX_OBJECT`, можно также использовать макросы `GX_ENUM` и `GX_STRUCT` для экспорта перечислений и типов членов структур, чтобы они могли естественным образом использоваться в JavaScript. Такой экспорт типов происходит автоматически и не требует написания какого-либо дополнительного связующего кода вручную.

#### Рефлексия перечислений `GX_ENUM`

Когда тип свойства или параметра метода является перечислением (enum) C++, прямое его предоставление JavaScript в виде целого числа неу интуитивно, ни безопасно. Макрос `GX_ENUM` экспортирует перечисление в виде константных строк, позволяя JavaScript оперировать удобочитаемыми строками, а не «магическими числами»:

```cpp
class ScrollArea : public Widget {
    GX_OBJECT
public:
    enum GX_ENUM ScrollBarStyle {
        RemoveScrollBar GX_ALIAS("hidden"),
        LinearScrollBar GX_ALIAS("line"),
        DotsScrollBar   GX_ALIAS("dots")
    };

    GX_PROPERTY(ScrollBarStyle indicator, set setScrollBar)
};
```

Макрос `GX_ENUM` размещается сразу после ключевого слова `enum`, сообщая метакомпилятору, что данное перечисление подлежит экспорту. Конструкция `GX_ALIAS("...")` задает видимое в JavaScript строковое имя для каждого члена перечисления — если она опущена, по умолчанию используется исходное имя члена в C++. Разработчики приложений используют это на JavaScript следующим образом:

```js
scroll.indicator = "hidden"; // Соответствует RemoveScrollBar
scroll.indicator = "dots";   // Соответствует DotsScrollBar
```

При чтении свойства `indicator` фреймворк преобразует строку `"dots"` в значение перечисления `DotsScrollBar` перед передачей в сеттер; при чтении значение перечисления конвертируется обратно в строку. Весь этот процесс полностью прозрачен для стороны C++, которая всегда оперирует конкретным типом перечисления.

#### Рефлексия параметров структур `GX_STRUCT`

Для параметров методов иногда требуется передавать несколько связанных конфигурационных параметров в рамках одной операции. В таких случаях параметры можно инкапсулировать в структуру и экспортировать с помощью `GX_STRUCT`, позволяя передавать со стороны JavaScript литерал объекта:

```cpp
class Scroll : public ScrollArea {
    GX_OBJECT
public:
    struct GX_STRUCT ScrollOptions {
        Length left;
        Length top;
        ScrollBehavior behavior;
    };
    struct GX_STRUCT IndexOptions {
        int index;
        ScrollBehavior behavior;
    };

    GX_METHOD void scrollTo(const ScrollOptions &options);
    GX_METHOD void scrollBy(const ScrollOptions &options);
    GX_METHOD void setIndex(const IndexOptions &options);
};
```

Макрос `GX_STRUCT` располагается после ключевого слова `struct`, и каждое поле структуры автоматически экспортируется в соответствии со своим типом (также через встроенный маппинг типов или вложенный `GX_ENUM`). На стороне JS можно напрямую передавать объекты:

```js
scroll.scrollTo({ left: 0, top: 200, behavior: "smooth" });
scroll.setIndex({ index: 3, behavior: "instant" });
```

Функция `scrollTo` на стороне C++ всегда получает строго типизированный объект `ScrollOptions`, избавляя от необходимости выполнять какой-либо парсинг в C++.

::: warning Не забывайте про аннотации
При объявлении `GX_PROPERTY` или `GX_METHOD`, если соответствующий тип представляет собой пользовательское перечисление или структуру, обязательно корректно отмечайте его макросом `GX_ENUM` или `GX_STRUCT`. В противном случае эти свойства или методы будут недоступны на стороне JavaScript, причем без каких-либо предупреждений об ошибках компиляции.
:::

### Существует ли «промежуточное представление»?

При использовании `Variant` для связи C++ и JavaScript транслирует ли фреймворк объекты JavaScript в какое-то универсальное промежуточное представление, например, в структуру сериализации, похожую на JSON?

Ответ — нет. `Variant` напрямую хранит объекты C++ (включая `JsValue`), что также включает всю информацию о типах и семантику операций этого объекта. Система корректно выполняет преобразования типов и вызовы методов на основе меток типа в рантайме для значений `Variant`, не прибегая к какому-либо специфическому промежуточному представлению или процессу сериализации.
