# Объектная система

Объектная модель фреймворка Glyphix на C++ базируется на классе `PrimitiveObject`. Понимание этой модели является фундаментом для дальнейшей разработки.

Объектная система состоит из трех взаимодействующих частей: **иерархия базовых классов объектов** определяет общие возможности и правила жизненного цикла всех управляемых объектов; **метаобъектная система** генерирует метаданные для классов C++ на этапе сборки с помощью метакомпилятора, наделяя их возможностями рефлексии, привязки свойств и экспорта в JavaScript; а **механизм обеспечения безопасности памяти** решает универсальную для GUI-фреймворков проблему висячих указателей (dangling pointers) с помощью защищенных указателей (guards) и подсчета ссылок.

## Рефлексия и метаобъектный компилятор

Классы в стандартном C++ «молчат»: получая указатель на объект, вы не можете во время выполнения узнать, какие у него есть члены, как они называются и как их читать или записывать. Для статической разработки на C++, не требующей скриптов, это не является препятствием.

Но Glyphix работает иначе. Когда в шаблоне страницы приложения написано `:value="progress"`, реактивному фреймворку необходимо во время выполнения найти по строке `"value"` свойство элемента управления, соответствующее этим данным, и автоматически обновить его при изменении. Способность «программы понимать собственную структуру во время выполнения» называется **рефлексией (Reflection)**, и стандартный C++ ее не поддерживает.

Решением в Glyphix является интеграция в процесс сборки **метаобъектного компилятора (Meta Compiler)**. Он сканирует исходный код до официальной компиляции C++, генерируя метаданные для классов, участвующих в объектной системе. Разработчику достаточно разместить макрос **`GX_OBJECT`** в начале определения класса, и метакомпилятор обработает его — после этого фреймворк сможет читать и записывать его свойства или вызывать методы по имени, а также обращаться к нему из JavaScript.

Вам пока не нужно вдаваться во внутренние принципы работы метаобъектной системы. Достаточно запомнить одно правило: все классы, которым требуется рефлексия, при определении должны содержать макрос `GX_OBJECT` и наследоваться от `PrimitiveObject` или `Object`.

## `PrimitiveObject` и `Object`

Объектная система фреймворка делится на два уровня:

**`PrimitiveObject`** — базовый класс для всех **управляемых объектов**. Наследующие его классы получают возможности фреймворка: рефлексию свойств, динамическое приведение типов, безопасное отложенное уничтожение и т.д. При этом сам `PrimitiveObject` **не имеет** древовидной структуры «родитель-потомок» — это просто «объект C++, о котором осведомлен фреймворк». Такие типы, как `AsyncSession` и `BindableObject`, наследуются от него, поскольку им не нужно объединяться в дерево.

**`Object`** наследует `PrimitiveObject` и добавляет **древовидную структуру «родитель-потомок»**: при создании передается указатель `parent`, и при уничтожении родительского объекта все дочерние объекты также рекурсивно уничтожаются. Дерево элементов интерфейса (Widget Tree) организовано именно с помощью этого механизма.

::: tip Аналогия с другими фреймворками
Если у вас есть опыт разработки на Qt, метаобъектную систему Glyphix можно сравнить с системой MOC в Qt: `GX_OBJECT` соответствует `Q_OBJECT`. Однако есть и множество различий: например, Glyphix разделяет возможности `QObject` из Qt на два слоя; кроме того, `Signal` — это просто обычный шаблонный класс, не зависящий от метаобъектного компилятора.

Другие фреймворки, такие как UCLASS в Unreal Engine, также имеют похожие системы рефлексии.
:::

Выбор базового класса зависит от того, должен ли ваш класс являться частью дерева:

```cpp
// Требуется участие в объектном дереве → наследуем Object
class MySensor : public Object {
    GX_OBJECT
public:
    explicit MySensor(Object *parent = nullptr) : Object(parent) {}
};

// Требуется только осведомленность фреймворка, без участия в дереве → наследуем PrimitiveObject
class MyNetworkSession : public PrimitiveObject {
    GX_OBJECT_KINDS(ExplicitDeleteKind)
public:
    MyNetworkSession() = default;
};
```

Вызов `GX_OBJECT_KINDS(ExplicitDeleteKind)` в коде — это дополнительное объявление. Подобно макросу `GX_OBJECT`, оно объявляет метаобъектный класс, но сообщает фреймворку, что за жизненный цикл этого объекта отвечает разработчик, и он не будет автоматически удален JavaScript. Такие чувствительные к жизненному циклу типы, как `AsyncSession`, используют именно его.

## Свойства и сигналы

Макрос **`GX_PROPERTY`** используется для объявления свойства, доступного для фреймворка, с привязкой соответствующих геттеров (getter) и сеттеров (setter). После объявления свойство может управляться реактивной системой фреймворка: при изменении значения зависящий от него интерфейс автоматически обновляется, а система анимации может выполнять его интерполяцию:

```cpp
class MyWidget : public Widget {
    GX_OBJECT
public:
    int value() const { return m_value; }
    void setValue(int v) { m_value = v; update(); }

    GX_PROPERTY(int value, get value, set setValue)

private:
    int m_value = 0;
};
```

### Сигналы (Signal)

**`Signal<>`** представляет собой механизм уведомления о событиях, объявляемый непосредственно как член класса. Событие «испускается» (emitted) в момент своего возникновения, а другие объекты принимают уведомления путем «подключения» ([лямбда-выражения](https://en.cppreference.com/w/cpp/language/lambda) в C++ являются синтаксисом анонимных функций):

```cpp
class MyWidget : public Widget {
    GX_OBJECT
public:
    Signal<int> valueChanged;

    void setValue(int v) {
        m_value = v;
        valueChanged(v);  // Испускание сигнала
    }
private:
    int m_value = 0;
};

// Подключение к методу класса
myWidget->valueChanged.connect(this, &MyClass::onValueChanged);

// Или подключение к лямбда-функции
auto slot = make_slot([](int v) { /* Реакция на изменение */ });
myWidget->valueChanged.connect(slot);
```

::: tip Сравнение с сигналами и слотами в Qt
Классический механизм сигналов и слотов в Qt требует поддержки генерации кода с помощью MOC, в то время как `Signal<>` — это чистый шаблонный класс C++, не зависящий от метакомпилятора. Поэтому использовать объект `Signal<...>` необязательно в каком-то конкретном классе, вы можете применять его где угодно.

Поскольку `Signal` является классом, он занимает память (даже при отсутствии подключений). Поэтому для экономии памяти рекомендуется по возможности использовать перечисления типов событий и единые переменные-члены для сигналов, вместо объявления отдельного члена `Signal` под каждое событие.
:::

### Полная форма `GX_PROPERTY`

Помимо `get` и `set`, макрос `GX_PROPERTY` поддерживает объявление связанного сигнала изменения (`signal`), который служит стандартным интерфейсом для подписки реактивного фреймворка на изменения свойств:

```cpp
class ProgressRing : public Widget {
    GX_OBJECT
public:
    int value() const { return m_value; }
    void setValue(int v) {
        if (m_value == v) return;
        m_value = v;
        update();
        valueChanged(v);
    }

    Signal<int> valueChanged;

    GX_PROPERTY(int value, get value, set setValue, signal valueChanged)

private:
    int m_value = 0;
};
```

Изменения свойств, у которых объявлен параметр `signal`, автоматически передаются через реактивный фреймворк выражениям JavaScript, привязанным к этим свойствам. Это основа двунаправленной синхронизации между свойствами элементов управления и данными приложения.

Поле `signal` в макросе `GX_PROPERTY` не зависит от типов параметров `Signal<T>` — фреймворку важно лишь то, существует ли он и когда испускается. Напротив, в этом случае обязательно предоставление поля `get`, чтобы фреймворк мог считывать значение свойства на стороне JavaScript.

## Защищенные указатели и безопасность памяти

В GUI-фреймворках асинхронные сценарии легко приводят к сбоям из-за висячих указателей. Типичный пример:
```cpp
void onNetworkResponse(const String &data) {
    // Сетевой запрос возвращает данные через 2 секунды
    // Однако за эти 2 секунды пользователь мог покинуть текущую страницу, и label был уничтожен
    this->label->setText(data); // Segmentation Fault!
}
```
С тем же риском сталкиваются все асинхронные сценарии, такие как колбэки таймеров, колбэки ввода-вывода и т.д. В фреймворках со скриптовым языком такой сценарий структурно неизбежен, поэтому необходимо обеспечить надежный механизм наблюдения за жизненным циклом.

### `Pointer<T>` — защищенный указатель

Glyphix встраивает поддержку подсчета слабых ссылок для всех производных классов `PrimitiveObject`. Использование `Pointer<T>` для хранения невладеющих межобъектных ссылок гарантирует, что при уничтожении целевого объекта `Pointer<T>` автоматически обнуляется, и безопасное использование достигается простой проверкой перед разыменованием:

```cpp
Pointer<Label> m_label; // Объявлено как переменная-член

// ...присваивание после конструирования...
m_label = label;

// В любом асинхронном колбэке, способном привести к уничтожению label:
void onNetworkResponse(const String &data) {
    if (!m_label)
        return; // label был уничтожен, безопасный выход
    m_label->setText(data); // Теперь доступ безопасен
}
```

::: tip Когда применять
Используйте `Pointer<T>` вместо "голого" указателя `T *` для отслеживания жизненного цикла при хранении ссылок на другие объекты без владения ими. Механизм `connect` у класса `Signal` также опирается на защищенные указатели: когда получатель (объект, содержащий слот) уничтожается, соединение автоматически разрывается, предотвращая вызов висячих колбэков.
:::

::: warning Ограничения потоков
Защищенные указатели не поддерживают межпоточный доступ — как правило, они ограничены использованием только в UI-потоке. Кроме того, они не являются абстракцией с нулевыми накладными расходами, поскольку каждое создание сопряжено с операциями подсчета ссылок.
:::

### `SharedRef<T>` — интрузивный подсчет ссылок

Для обычных объектов-значений, не наследующихся от `PrimitiveObject` (например, пользовательских структур данных), фреймворк предоставляет интрузивный разделяемый подсчет ссылок. Унаследовав тип-значение от `SharedValue` и обернув его в `SharedRef<T>`, вы получаете семантику разделения, аналогичную [`std::shared_ptr`](https://en.cppreference.com/w/cpp/memory/shared_ptr), избегая при этом выделения памяти под дополнительный управляющий блок:

```cpp
class MyData : public SharedValue {
public:
    int x = 0;
    String name;
};

auto ref1 = make_shared<MyData>();
ref1->x = 42;

SharedRef<MyData> ref2 = ref1; // Количество ссылок увеличивается, объект разделяется
```

`SharedRef` также поддерживает семантику Copy-on-Write (копирование при записи): перед модификацией скопированной версии создается независимая копия, гарантирующая отсутствие взаимных помех между несколькими владельцами. Этот механизм реализуется с помощью атомарного подсчета ссылок для обеспечения потокобезопасности.

## Динамическое приведение типов

[`dynamic_cast`](https://en.cppreference.com/w/cpp/language/dynamic_cast) в стандартном C++ опирается на RTTI (информацию о типах во время выполнения), в то время как в средах embedded-разработки компиляция обычно выполняется с флагом `-fno-rtti`. `dyn_cast` использует метаобъектную систему для обеспечения эквивалентной способности безопасного нисходящего приведения типов (downcasting) в рантайме.

Целевой тип `T` для `dyn_cast<T *>()` должен удовлетворять двум условиям:
1. Наследоваться от `PrimitiveObject`.
2. Содержать макрос `GX_OBJECT`/`GX_OBJECT_KINDS`.

```cpp
PrimitiveObject *obj = getSomeObject();

// Безопасное нисходящее приведение, при неудаче возвращает nullptr
auto *btn = dyn_cast<Button *>(obj);
if (btn)
    btn->setText("OK");

// Поддерживается и версия с const
const auto *constBtn = dyn_cast<const Button *>(obj);
```

::: warning `GX_OBJECT` — обязательное условие
Проверка типов в `dyn_cast` опирается на статическую метаобъектную информацию целевого класса (`staticMetaObject`). Если целевой класс не объявляет макрос `GX_OBJECT`, у него отсутствует необходимая информация о типе в рантайме, что приводит к ошибке компиляции.
:::

При разработке Native Module `dyn_cast` используется особенно часто: фреймворк регулярно передает объекты по указателю на базовый класс (`PrimitiveObject *` или `Object *`), и для безопасного приведения к конкретному типу перед выполнением операций требуется `dyn_cast`.

Учитывая, что политика безопасности песочницы не доверяет объектам, поступающим из скриптов, нельзя предполагать, что переданный в рантайме указатель на объект имеет правильный тип, поэтому для проверки типа и безопасного обращения к его членам обязательно применение `dyn_cast`.

### Ловушка утечки памяти

Типичный паттерн использования `dyn_cast` таит в себе риск утечки памяти, например:
```cpp
auto *session = dyn_cast<Session *>(takeObjectOwnership());
if (session) {
    // Успешное приведение, обращение к членам session и передача владения
}
```
Проблема заключается в том, что если объект, возвращаемый `takeObjectOwnership()`, не имеет типа `Session`, `dyn_cast` вернет `nullptr`, однако владение исходным объектом уже передано — если нет иного механизма для утилизации этого объекта, произойдет утечка памяти.

При разработке API для Native Module иногда возникают подобные проблемы, и соответствующие фреймворки предоставляют лучшие API для их предотвращения. Тем не менее, разработчики должны осознавать этот потенциальный риск и не поддаваться иллюзии безопасности `dyn_cast`.

### Необходимость макроса `GX_OBJECT`

Не все классы, наследующие `PrimitiveObject`, обязаны содержать `GX_OBJECT`. Назначение макроса `GX_OBJECT` заключается в регистрации класса в метаобъектной системе, активации рефлексии, привязки свойств, возможностей `dyn_cast` и т.д. Если ваш класс:

- не нужно экспортировать в JavaScript;
- не требует механизмов рефлексии вроде `GX_PROPERTY`, `GX_METHOD`;
- не нуждается в безопасном приведении через `dyn_cast`.

Тогда вы можете опустить макрос `GX_OBJECT`, унаследовав базовый класс и используя стандартные возможности C++:

```cpp
// Внутренний вспомогательный класс, не требующий метаобъектных возможностей, опускаем GX_OBJECT
class InternalBufferManager : public PrimitiveObject {
public:
    explicit InternalBufferManager() = default;
    void flush();
private:
    // ...
};
```

Классы без `GX_OBJECT` по-прежнему обладают базовыми возможностями `PrimitiveObject`, включая `deleteLater()` и поддержку защищенных указателей, теряя лишь рефлексию и идентификацию типов в рантайме.

Другой случай: если вашему конечному типу требуются метаобъектные возможности, но некоторым промежуточным базовым классам — нет, то в промежуточных классах можно не объявлять `GX_OBJECT`. Это приведет к потере части информации о типе во время выполнения, но уменьшит объем кода.

::: tip
Если вы сомневаетесь в необходимости `GX_OBJECT`, обычно рекомендуется добавить его на всякий случай.
:::

Последнее важное отличие: будучи помеченным макросом `GX_OBJECT`, класс обязан находиться в заголовочном файле (`*.h`) и регистрироваться в системе сборки с помощью макроса CMake `glyphix_add_meta_objects()`. Для классов без `GX_OBJECT` это требование отсутствует, их можно определять непосредственно в файлах `.cpp`.

## Система типов времени выполнения

Во всех предшествующих обсуждениях `GX_PROPERTY` оставался один безмолвный вопрос:

```cpp
GX_PROPERTY(int value, get value, set setValue)
```

Откуда JavaScript знает, что такое `int`? Когда на стороне JavaScript пишется `widget.value = 42`, это значение `42` имеет тип `number` в JavaScript. А метод `setValue(int v)` принимает `int` из C++. Что происходит между ними? И наоборот, как `int`, возвращаемый функцией `getValue()`, превращается в `number` в JavaScript?

При отсутствии какого-либо связующего кода фреймворку очевидно требуется выполнять определенную работу за кулисами для сопряжения статических типов C++ и динамических типов скриптов. Это довольно прозрачный процесс, и в данном разделе объясняется, что происходит «под капотом».

### Универсальный контейнер типов `Variant`

Ответ кроется в классе `Variant`. Это контейнер со стертым типом (type erasure), способный вмещать значения произвольных типов. Он выступает в роли ключевого моста, соединяющего статическую систему типов C++ и динамические типы JavaScript.

Всякий раз, когда фреймворку необходимо преодолеть эту границу, используется `Variant`:

1. **Промежуточный слой чтения и записи свойств**: когда свойства, объявленные через `GX_PROPERTY`, читаются или записываются через API рефлексии, значения передаются в виде `Variant`. Фреймворк преобразует `JsValue` из JavaScript в `Variant`, а затем из `Variant` в фактический тип параметра для сеттера C++; при чтении направление меняется на противоположное.
2. **Маршалинг параметров вызова методов**: параметры и возвращаемые значения `GX_METHOD` перед передачей в C++ также предварительно представляются через `Variant`.

```cpp
Variant v1;                  // Пустое значение (null)
Variant v2{42};              // Хранит int
Variant v3{3.14};            // Хранит double
Variant v4{String("Hello")}; // Хранит String
// Variant должен конструироваться явно, неявное преобразование не поддерживается
// Variant v5 = 42; // Ошибка, необходимо писать Variant v5{42};

// Проверка типов
if (v2.is<int>()) { /* ... */ }
// Проверять совместимость типов не рекомендуется, лучше сразу вызвать to<T>() и проверить на недопустимое значение
if (v3.convertible<double>()) { /* ... */ }

// Чтение по ссылке (быстрее всего, требуется точное совпадение типов)
int n = v2.as<int>();
// Чтение по ссылке, при несоответствии типов возвращает значение по умолчанию
double d = v2.as<double>(0.0); // int != double, возвращает 0.0
// Чтение с преобразованием типов (по значению)
int fromDouble = v3.to<int>();   // 3.14 -> 3
String fromInt = v2.to<String>(); // 42 -> "42"
```

::: tip
Это не [`std::variant`](https://en.cppreference.com/w/cpp/utility/variant) из C++17, а скорее аналог [`std::any`](https://en.cppreference.com/w/cpp/utility/any), поддерживающий идентификацию типов в рантайме и автоматическое преобразование типов.

Обычно вам не требуется напрямую взаимодействовать с `Variant` в бизнес-коде — фреймворк осуществляет все преобразования автоматически. Непосредственная работа с ним необходима лишь при реализации низкоуровневых расширений фреймворка, написании универсальных вспомогательных функций или при прямом обращении к API рефлексии рантайма.
:::

### Встроенные маппинги типов

Фреймворк имеет встроенные двунаправленные маппинги распространенных базовых типов C++ с JavaScript:

| Тип C++ | Тип JavaScript | Примечание |
|:---:|:---:|:---:|
| `int`, `float`, `double` и т.д. | `number` | Численные типы маппятся напрямую |
| `bool` | `boolean` | |
| `String` | `string` | |
| Производные от `PrimitiveObject *` | Ссылка на объект JavaScript | Управление жизненным циклом объекта осуществляется фреймворком |
| Типы-значения `Color`, `Length` и др. | `string` | Представление в виде строки заданного формата |

Именно поэтому после написания `GX_PROPERTY(int value, ...)` на стороне JS можно напрямую присвоить `widget.value = 42`: тип `int` присутствует во встроенной таблице маппингов, и фреймворк знает, как выполнить преобразование.

::: note Не используйте C-строки
`Variant` требует, чтобы сохраняемый тип `T` обладал правом владения, поэтому невладеющие типы, такие как C-строки (`const char *`) и срезы строк (`String::View`), не могут храниться в `Variant`. Для представления текстовых данных всегда используйте `String`, выполняя при необходимости явное преобразование в `String` перед сохранением в `Variant`.

Использование неподдерживаемого типа строк приведет к ошибке компиляции.
:::

::: important
Таблица встроенных маппингов типов не содержит регистраций для `std::string`, поэтому хранить `std::string` в `Variant` также не рекомендуется. Незамаппленные типы могут успешно сохраняться, но будут обрабатываться как непрозрачные объекты C++, недоступные для использования в JavaScript.
:::

### Рефлексия сложных типов

Для классов, объявленных с использованием макроса `GX_OBJECT`, можно задействовать `GX_ENUM` и `GX_STRUCT` для экспорта перечислений (enum) и типов членов структур, делая их доступными в JavaScript интуитивным образом. Экспорт таких типов происходит автоматически, без необходимости вручную писать дополнительный код связывания.

#### Рефлексия перечислений `GX_ENUM`

Когда тип параметра свойства или метода является перечислением C++, его прямое экспортирование в JavaScript в виде целого числа неудобно и чревато ошибками. Макрос `GX_ENUM` экспортирует перечисления в виде строковых констант, позволяя JavaScript оперировать читаемыми строками, а не «магическими числами»:

```cpp
class ScrollArea : public Widget {
    GX_OBJECT
public:
    enum GX_ENUM ScrollBarStyle {
        RemoveScrollBar GX_ALIAS("hidden"),
        LinearScrollBar GX_ALIAS("line"),
        DotsScrollBar   GX_ALIAS("dots")
    };

    GX_PROPERTY(ScrollBarStyle indicator, set setScrollBar)
};
```

Макрос `GX_ENUM` помещается после ключевого слова `enum`, сообщая метакомпилятору, что данное перечисление подлежит экспорту. `GX_ALIAS("...")` задает видимое в JavaScript строковое имя для каждого члена перечисления — если опустить его, по умолчанию используется исходное имя члена C++. Разработчики приложений используют это на стороне JavaScript следующим образом:

```js
scroll.indicator = "hidden"; // Соответствует RemoveScrollBar
scroll.indicator = "dots";   // Соответствует DotsScrollBar
```

При чтении свойства `indicator` фреймворк преобразует строку `"dots"` в значение перечисления `DotsScrollBar` перед передачей сеттеру; при чтении значения перечисление обратно конвертируется в строку. Весь этот процесс полностью прозрачен для стороны C++, чей код неизменно оперирует конкретным типом перечисления.

#### Рефлексия параметров структур `GX_STRUCT`

Для параметров методов порой требуется передать несколько связанных конфигурационных элементов в рамках одной операции. В таком случае параметры можно инкапсулировать в структуру и экспортировать с помощью `GX_STRUCT`, позволяя передавать на стороне JavaScript литерал объекта:

```cpp
class Scroll : public ScrollArea {
    GX_OBJECT
public:
    struct GX_STRUCT ScrollOptions {
        Length left;
        Length top;
        ScrollBehavior behavior;
    };
    struct GX_STRUCT IndexOptions {
        int index;
        ScrollBehavior behavior;
    };

    GX_METHOD void scrollTo(const ScrollOptions &options);
    GX_METHOD void scrollBy(const ScrollOptions &options);
    GX_METHOD void setIndex(const IndexOptions &options);
};
```

Макрос `GX_STRUCT` ставится после ключевого слова `struct`, и каждое поле структуры автоматически экспортируется в соответствии с его типом (также через встроенные маппинги типов или вложенные `GX_ENUM`). На стороне JS можно напрямую передавать объект:

```js
scroll.scrollTo({ left: 0, top: 200, behavior: "smooth" });
scroll.setIndex({ index: 3, behavior: "instant" });
```

Функция `scrollTo` на стороне C++ всегда получает строго типизированный объект `ScrollOptions`, избавляя от необходимости выполнять какой-либо парсинг на стороне C++.

::: warning Не забывайте разметку
При объявлении `GX_PROPERTY` или `GX_METHOD`, если связанный тип представляет собой пользовательское перечисление или структуру, обязательно корректно проставляйте макросы `GX_ENUM` или `GX_STRUCT`. В противном случае эти свойства или методы будут недоступны на стороне JavaScript, причем без каких-либо предупреждений об ошибках компиляции.
:::

### Существует ли «промежуточное представление»?

При использовании `Variant` для связи C++ и JavaScript транслирует ли фреймворк объекты JavaScript в универсальное промежуточное представление, такое как сериализованная структура, напоминающая JSON?

Ответ — нет. `Variant` напрямую хранит объекты C++ (включая `JsValue`), что также охватывает всю информацию о типах и семантику операций этих объектов. Система корректно выполняет преобразования типов и вызовы методов на основе меток типов рантайма у значений `Variant`, обходясь без специфических промежуточных представлений или процессов сериализации.
