# Практика создания пользовательских виджетов

`slider-demo` — это полноценный пример, поставляемый с Glyphix SDK, который демонстрирует, как реализовать **кастомный элемент управления** `WaveSlider` с нуля на C++. Этот виджет добавляет эффект волновой заливки и анимированную рябь при нажатии поверх стандартного `Slider`. Пример также затрагивает кастомизацию `StyleEngine`, создание UI интерфейса непосредственно на C++ и многое другое.

В данной статье этот пример используется в качестве основы для демонстрации всех шагов, необходимых для создания нового виджета, в сочетании с ключевыми концепциями из [Руководства по разработке виджетов](./widget.md).

## Структура примера

Структура файлов примера выглядит следующим образом:

```
app/slider-demo/
├── CMakeLists.txt
├── main.cpp           # Точка входа в приложение, UI создается напрямую на C++
├── styleengine.h/.cpp # Кастомизация StyleEngine
└── waveslider.h/.cpp  # Реализация виджета WaveSlider
```

Вы можете напрямую скомпилировать и запустить цель `slider-demo`, чтобы увидеть результат в действии, без необходимости настройки фронтенд-проекта.

### Инструкции по сборке

После [настройки SDK](sdk-setup.md#准备工作) соберите и запустите пример с помощью следующих команд:

```bash
mkdir build && cd build
cmake .. && cmake --build . -j
bin/slider-demo
```

::: important Хост-система
Для сборки и запуска этого примера требуется поддерживающая графическую среду система Linux.
:::

## Создание UI напрямую на C++

В `main.cpp` пользовательский интерфейс приложения полностью собирается в конструкторе с помощью кода на C++, что по стилю напоминает Qt Widgets или LVGL: дочерние виджеты создаются через `new` с передачей указателя на родительский виджет, без использования декларативных шаблонов.

```cpp
int main() {
    Application app(new BSPPlatform(500, 500));
    app.setFont(Font(GX_EXAMPLE_ASSETS "/roboto.ttf", 32));
    app.setStyleEngine(new MyStyleEngine);

    Window window;
    window.setFlowLayout(true);

    MyWidget widget(&window);
    StyleModifier(&widget)->setSize(
      Length::fromPercent(100), Length::fromPercent(100));
    StyleModifier(&widget)->setMargin(Margin(10));
    return app.exec();
}
```

`Application` принимает объект бэкенда платформы (`BSPPlatform`) и разрешение экрана. `Window` — это корневой виджет; при включении `setFlowLayout(true)` его дочерние элементы автоматически упорядочиваются с помощью потокового компоновщика (Flow Layout).

Метод `setStyleEngine` подключает пользовательский движок стилей (необязательно, если используется стиль по умолчанию). Свой собственный движок требуется только тогда, когда вам нужно изменить внешний вид элементов управления (как в случае с модернизацией `Switch` ниже).

### Класс `MyWidget`

`MyWidget` наследуется от `ScrollArea` и создает дочерние элементы внутри своего конструктора:

```cpp
class MyWidget : public ScrollArea {
public:
    explicit MyWidget(Widget *parent = nullptr) : ScrollArea(parent) {
        addItem(&m_switch);
        addItem(&m_label);
        addItem(&m_slider);
        // ...
    }
    // ...
private:
    Label  m_label;
    Switch m_switch;
    Slider m_slider;
};
```

Дочерние элементы объявляются как члены класса и инициализируются автоматически при конструировании (родительский виджет устанавливается в `addItem`). Жизненный цикл членов класса управляется самим `MyWidget`, ручной вызов `delete` не требуется.

`ScrollArea` «из коробки» предоставляет возможности прокрутки, инерции и отскока, поэтому `MyWidget` не нужно писать собственную логику скроллинга.

::: tip Назначение `addItem()`
В общем случае вы можете добавлять дочерние виджеты к родительскому напрямую через `setParent()`. Однако `ScrollArea` внутри себя содержит специальный контейнер содержимого (`contentWidget()`), и обычные элементы нельзя добавлять напрямую на `ScrollArea` — их нужно добавлять в контейнер содержимого с помощью метода `addItem()`.

Для простых контейнеров `setParent()` и `addItem()` эквивалентны, но для таких специальных контейнеров, как `ScrollArea`, **обязательно** следует использовать `addItem()`.
:::

### Подключение сигналов

Состояние между элементами управления синхронизируется с помощью сигналов:

```cpp
m_slider.changed.connect(this, &MyWidget::onSlider);
m_switch.checked.connect(this, &MyWidget::onSwitch);

// Двусторонняя синхронизация значений двух слайдеров
waveSlider->changed.connect<AbstractSlider>(&m_slider, &Slider::setValue);
m_slider.changed.connect<AbstractSlider>(waveSlider, &WaveSlider::setValue);

// Переключатель управляет волновым режимом WaveSlider
m_switch.checked.connect(waveSlider, &WaveSlider::setWaveMode);
```

::: tip Использование Signal
Синтаксис подключения сигналов: `signal.connect(receiver, &Type::method)`. Если сигнатуры `Slider::setValue` и `WaveSlider::setValue` не полностью совпадают, для разрешения неоднозначности можно указать общий базовый класс (`AbstractSlider`) в качестве шаблонного параметра.

Если вы не уверены в типе, которому фактически принадлежит слот-функция, это можно проверить с помощью подсказок IDE. Например, при проверке `Slider::setValue` IDE обычно подскажет:
```cpp
public method
void setValue(int value) in class AbstractSlider 
```
Это означает, что `setValue` фактически объявлен в классе `AbstractSlider`. При подключении необходимо явно указать `AbstractSlider`, чтобы устранить неоднозначность:
```cpp
m_slider.changed.connect<AbstractSlider>(waveSlider, &WaveSlider::setValue);
```
:::

### Настройка стилей с помощью StyleModifier

`StyleModifier` — это инструмент для программной настройки стилей виджетов в C++, действие которого эквивалентно конфигурации свойств стиля в шаблоне:

```cpp
StyleModifier m(waveSlider);
m->setSize(120, 300);
m->setMargin(Style::Margin{Length::fromAuto(), 20});
m->setColor(Color{"#35a7ff"});
```

Метод `setColor` задает цвет переднего плана для `WaveSlider`, который считывается в `paintEvent` и используется для заливки прогресса.

## Кастомизация StyleEngine

Встроенный компонент [`Switch`](/components/switch.md) — это полнофункциональный переключатель, но его стандартный внешний вид напоминает [Fluent 2](https://fluent2.microsoft.design/components/web/react/core/switch/usage), что может не подойти под визуальный стиль конкретного устройства или бренда.

Механизм `StyleEngine` создан для решения этой задачи. Производители устройств могут реализовать собственный `StyleEngine`, настраивая внешний вид всех встроенных элементов управления с сохранением их логики взаимодействия без необходимости изменения кода фреймворка.

Модифицированный `Switch` — это не просто смена темы или цвета. Вся анимация переключателя (перемещение ползунка, цветовой переход, масштабирование при нажатии) реализуется с помощью **программной интерполяции**, а не предварительно записанных последовательностей кадров (кадровых спрайтов). Это означает:

- Анимация полностью плавная, ее частота кадров совпадает с системой рендеринга;
- Цвета и размеры могут переопределяться разработчиками приложений через свойства стиля (`StyleEngine` предоставляет значения по умолчанию, которые можно переопределить);
- Нет необходимости готовить различные графические ассеты для каждого разрешения экрана.

### Обязанности `StyleEngine`

`StyleEngine` является ядром системы стилей Glyphix и отвечает за три задачи:

1. **Предоставление палитры** (palette): глобальные цветовые переменные (аналоги пользовательских свойств CSS), считываемые всеми встроенными и кастомными виджетами.
2. **Отрисовка внешнего вида элементов управления** (paint): визуальное оформление встроенных во фреймворк виджетов (таких как `Switch`, `Slider`) полностью делегируется `StyleEngine::paint()`. Разработчики могут переопределить этот метод в производном классе для создания совершенно другого внешнего вида.
3. **Рекомендуемые размеры** (size hint): рекомендуемые размеры виджета в различных состояниях стиля, используемые компоновщиком (layout system) в качестве ориентира.

### Определение MyStyleEngine

Унаследуйте класс от `StyleEngine` и переопределите методы `sizeHint()` и `paint()`:

```cpp
class MyStyleEngine : public StyleEngine {
public:
    MyStyleEngine();
    Size sizeHint(StyleOption::Type type, const Widget *widget) const override;
    void paint(Painter &painter, Widget *widget, StyleOption &option) override;
};
```

В конструкторе задается палитра:

```cpp
MyStyleEngine::MyStyleEngine() {
    setPalette(SwitchDark,  Color(0xff565656));
    setPalette(SwitchLight, Color(0xff2f5cff));
    setPalette(SwitchThumb, Color(0xffffffff));
}
```

`SwitchDark`, `SwitchLight` и `SwitchThumb` — это семантические цветовые ключи, предварительно определенные в перечислении `StyleEngine`. Различные движки тем могут присваивать им разные цвета, а элементы управления всегда считывают их по именам ключей, избегая жестко закодированных значений цветов.

### Переопределение метода `sizeHint()`

Метод `sizeHint()` сообщает фреймворку **рекомендуемый размер** встроенного виджета для заданного состояния стиля. На примере `Switch` его ширина и высота должны быть пропорциональны размеру шрифта в пикселях:

```cpp
Size MyStyleEngine::sizeHint(StyleOption::Type type, const Widget *widget) const {
    // Пропорции размера кастомного Switch могут отличаться от встроенной стратегии
    if (type == StyleOption::OptionSwitch) {
        float f = widget->font().pixelSize();
        int d = int(round(f));
        return {int(round(f * SwitchAspectRatio)), d};
    }
    return StyleEngine::sizeHint(type, widget); // Остальные типы делегируем базовому классу
}
```

В конце функции обязательно вызывайте `StyleEngine::sizeHint(type, widget)` для возврата к реализации по умолчанию, иначе виджеты других типов получат нулевой размер.

### Переопределение метода `paint()`

Метод `paint()` распределяет логику отрисовки на основе типа опции из `StyleOption`, а необработанные типы точно так же передает в базовый класс:

```cpp
void MyStyleEngine::paint(Painter &painter, Widget *widget, StyleOption &option) {
    switch (option.option()) {
    case StyleOption::OptionSwitch:
        drawSwitch(this, painter, widget, static_cast<StyleOptionSwitch &>(option));
        break;
    default:
        StyleEngine::paint(painter, widget, option);
    }
}
```

`StyleOptionSwitch` — это производный класс от `StyleOption`, добавляющий специфичные для переключателя поля состояния. Он содержит два ключевых значения прогресса анимации:

- `option.transition`: прогресс перехода состояния `Switch` (`0.0` — выключено, `1.0` — включено, промежуточные значения означают процесс анимации).
- `option.scale`: коэффициент масштабирования при нажатии для отображения обратной связи (эффекта нажатия).

Используя эти два значения, в `drawSwitch` можно реализовать плавный переход состояния:

```cpp
// Интерполяция между цветом включенного и выключенного состояний
color = color.blend(checked.background().color(), option.transition);

// Положение индикатора thumb перемещается в соответствии с прогрессом перехода
float pos = option.transition * (box.width() - size - len);
```

`StyleEngine` отвечает за запуск анимации, а разработчику достаточно выполнить интерполяцию в `paint()` на основе значения прогресса для получения полноценного плавного перехода.

::: tip Настройка только отдельных виджетов
Стандартный `StyleEngine` реализует логику отрисовки всех встроенных виджетов, и часть из них довольно сложна. Если вас не устраивает внешний вид лишь некоторых элементов управления, в производном классе следует переопределить отрисовку только этих виджетов, а для остальных вызывать реализацию базового класса.

В первую очередь для кастомизации цветов следует использовать палитру, а переопределять `paint()` — только тогда, когда требуется принципиально иной визуальный эффект.
:::

### Отрисовка закругленной капсулы с помощью VectorPath

Фон и thumb стандартного переключателя `Switch` имеют форму закругленной капсулы. В примере для их отрисовки используется `VectorPath` в сочетании с двумя дугами. Это более гибкий подход по сравнению с `drawRoundedRect`, который подходит для сценариев, требующих раздельного контроля радиусов скругления для каждого из концов:

```cpp
static void indicatorBar(Painter &p, const RectF &rect) {
    float radius = rect.height() * 0.5f;
    float x1 = rect.left() + radius;
    float x2 = rect.right() - radius;
    float y = rect.top() + radius;
    VectorPath path;
    path.arcTo(PointF(x1, y), radius, radius, 90, 270);   // Полукруг слева
    path.arcTo(PointF(x2, y), radius, radius, -90, 90);   // Полукруг справа
    p.fillPath(path);
}
```

Две дуги соединяются концами, а `arcTo` автоматически соединяет линии внутри пути, исключая необходимость в дополнительных вызовах `lineTo`.

## WaveSlider: практика создания полноценного кастомного виджета

`WaveSlider` — это ядро данного примера, демонстрирующее полный цикл разработки кастомного виджета. Подобно кастомизации `StyleEngine`, описанной выше, дизайн `WaveSlider` направлен на **наложение** новых визуальных эффектов без нарушения уже существующих возможностей:

- **Режим волновой заливки** (`Wave fill`): область прогресса заполняется динамическими волнами вместо стандартной прямоугольной шкалы прогресса;
- **Эффект ряби от нажатия** (`Click ripple`): при нажатии возникает волнообразное расходящееся колебание, на короткое время усиливающее волны с последующим восстановлением;
- **Свойство `waveMode`**: позволяет переключать волновой режим и обычный режим во время выполнения программы, поддерживая привязку на стороне приложения (Data Binding) и анимацию свойств;
- **Полная обратная совместимость (fallback)**: при отключении волнового режима `WaveSlider` напрямую вызывает `Slider::paintEvent()`, возвращая стандартный внешний вид и полностью переиспользуя логику перетаскивания, свойства `value`/`changed` родительского класса без изменений в коде приложения.

### Определение и наследование класса

`WaveSlider` наследуется от `Slider` (а не напрямую от `Widget`), что позволяет переиспользовать логику жестов перетаскивания, свойства `minimum`/maximum`/value` и сигнал `changed`:

```cpp
// waveslider.h
#include "gx_slider.h"
#include "gx_valueanimation.h"

class WaveSlider : public Slider {
    GX_OBJECT
public:
    explicit WaveSlider(Widget *parent = nullptr);
    ~WaveSlider() override = default;

    GX_NODISCARD bool isWaveMode() const { return m_waveMode; }
    void setWaveMode(bool enabled);
    bool event(Event *event) override;

    GX_PROPERTY(bool waveMode, get isWaveMode, set setWaveMode)
    // ...
};
```

Макрос `GX_OBJECT` должен располагаться в самом начале определения класса; он инициирует генерацию метаданных для этого класса компилятором метаобъектов. `GX_PROPERTY` делает свойство `waveMode` доступным для системы свойств, позволяя использовать его для привязки со стороны приложения (например, `<wave-slider :wave-mode="enabled"/>`) и управления через анимацию свойств.

### Члены класса

Состояние виджета во время выполнения хранится в членах класса:

```cpp
private:
    bool  m_waveMode = false;       // Включен ли сейчас волновой режим
    float m_rippleProgress = 1.0f;  // Прогресс ряби [0, 1], по умолчанию 1 (неактивна)
    float m_waveOffset = 0.0f;      // Фазовое смещение волны [0, 1], управляется анимацией
    ValueAnimation<float> m_animation;        // Циклическая анимация волн
    ValueAnimation<float> m_rippleAnimation;  // Анимация ряби
    friend struct EventTraits<WaveSlider>;    // Разрешает диспетчеру событий доступ к защищенным (protected) методам
```

`ValueAnimation<float>` объявлена как член класса (а не как указатель), ее жизненный цикл управляется самим `WaveSlider`, ручной вызов `delete` не нужен.

### Конструктор: инициализация анимации

Конструктор настраивает две анимации и устанавливает ориентацию:

```cpp
WaveSlider::WaveSlider(Widget *parent) : Slider(parent) {
    // Анимация волн: бесконечный цикл, полный период за 1 секунду
    m_animation.setRepeat(AbstractAnimation::Infinity);
    m_animation.setValueLimits(0.f, 1.f);
    m_animation.setDuration(1000);
    m_animation.value.connect(this, &WaveSlider::onWaveAnimation);
    m_animation.start();

    // Анимация ряби: проигрывается один раз при нажатии, длительность 800 мс
    m_rippleAnimation.setValueLimits(0.f, 1.f);
    m_rippleAnimation.setDuration(800);
    m_rippleAnimation.value.connect(this, &WaveSlider::onRippleAnimation);

    setVertical(true);  // Вертикальный слайдер
}
```

`m_animation` работает непрерывно после запуска, с каждым кадром переводя `m_waveOffset` от $0$ до $1$ с возвратом к $0$. Это значение в конечном итоге преобразуется в фазовое смещение волны, обеспечивая ее непрерывное движение.

`m_rippleAnimation` запускается только при нажатии, проигрывается один раз и останавливается (без флага `Infinity`). Обратные вызовы (callback-функции) двух анимаций выполняют лишь одно действие: обновляют переменную состояния и вызывают `update()` для запроса перерисовки.

```cpp
void WaveSlider::onWaveAnimation(float value) {
    m_waveOffset = value;
    update();
}
void WaveSlider::onRippleAnimation(float value) {
    m_rippleProgress = value;
    update();
}
```

### Обработка событий

#### Настройка EventDispatch

В методе `event()` для маршрутизации событий используется [`EventDispatch`](widget.md#处理事件), а шаблонные параметры перечисляют типы событий, которые текущий виджет обрабатывает фактически, обеспечивая проверку на этапе компиляции:

```cpp
bool WaveSlider::event(Event *event) {
    return EventDispatch<Widget,
        GestureEvent, PaintEvent>{}(this, event);
}
```

#### Обработка жестов: запуск ряби

Метод `gestureEvent()` перехватывает момент начала жест `Press` для запуска ряби, а остальные события делегирует обработчику жестов `Slider` (что реализует перетаскивание и изменение значения):

```cpp
bool WaveSlider::gestureEvent(GestureEvent *event) {
    if (!event->isHitTest() && event->gesture()->type() == Gesture::Press) {
        auto g = static_cast<PressGesture *>(event->gesture());
        if (g->isStarted())
            startRipple(g->clientPoint());
    }
    return Slider::gestureEvent(event); // Передаем событие дальше в Slider
}

void WaveSlider::startRipple(const Point &) {
    m_rippleProgress = 0.f;      // Сброс в начало
    m_rippleAnimation.start();   // Перезапуск воспроизведения
}
```

Если `isHitTest()` возвращает `true`, это означает проверку попадания (механизм фреймворка для определения того, попадает ли событие в данный виджет), что не является реальным взаимодействием пользователя и должно быть пропущено.

::: tip О методе `isHitTest()`
Проверка попадания — это предварительный шаг диспетчеризации событий. Метод `gestureEvent()` вызывается и на этапе проверки попадания, но в этот момент не должно происходить никаких побочных эффектов (например, запуска анимации). Всегда проверяйте `!event->isHitTest()` перед обработкой логики взаимодействия.
:::

#### Интерфейс чтения стилей

В методе `paintEvent()` считываются данные стилей, соответствующие виджету. Рассмотрим два задействованных интерфейса:

- `style()` / `style(Styles::Xxx)` возвращает объект `Style` для определенного псевдокласса стиля виджета, откуда можно считывать цвет, фон и другие свойства;
- `se->palette(StyleEngine::Xxx)` считывает глобальный цвет палитры из `StyleEngine`, используемый по умолчанию, когда для виджета не задан кастомный цвет.

Совместное использование этих двух интерфейсов реализует логику «если есть пользовательская конфигурация — использовать её, в противном случае откатываться к цвету темы по умолчанию»:

```cpp
auto contentStyle = style(Styles::Content);
p.setBrush(contentStyle.hasProperty(style::Background)
               ? contentStyle.background()
               : se->palette(StyleEngine::ProgressRange));
```

### Реализация отрисовки

Метод `paintEvent()` — это ядро `WaveSlider`. Путь отрисовки определяется на основе значения `m_waveMode`:

```cpp
void WaveSlider::paintEvent(PaintEvent *event) {
    discard(event);  // Само событие PaintEvent не несет полезной информации, явно сбрасываем его во избежание предупреждений компилятора

    if (!isWaveMode())
        return Slider::paintEvent(event);  // Обычный режим: вызываем отрисовку базового класса

    auto se = App()->styleEngine();
    RectF box = rect();
    float radius = min(box.width(), box.height()) * 0.5f;
    float progress = sliderRange ? float(value() - minimum()) / float(sliderRange) : 0.f;

    Painter p(this);

    // Отрисовка фона (пустая шкала)
    p.setBrush(/* Цвет фона */);
    p.fillRoundedRect(box, radius);

    // Отрисовка волновой заливки (область прогресса)
    p.setBrush(/* Цвет переднего плана */);
    VectorPath path;
    buildWaveFillPath(path, box, radius, progress, m_waveOffset, m_rippleProgress);
    if (!path.isEmpty())
        p.fillPath(path);
}
```

Процесс отрисовки состоит из двух шагов: сначала с помощью `fillRoundedRect` рисуется скругленный прямоугольник полного фона, а затем поверх него с помощью `fillPath` прорисовывается волновая заливка. Наложение этих двух слоев формирует «индикатор выполнения с волнами».

#### Генерация пути волны

`buildWaveFillPath()` — это отдельная вспомогательная функция (не входит в класс), отвечающая за построение контура волны при заданных геометрических ограничениях:

```cpp
static void buildWaveFillPath(VectorPath &path, const RectF &box, float radius,
                              float progress, float waveOffset, float rippleProgress)
```

Её основная логика состоит из трех шагов:

1. **Вычисление уровня воды и амплитуды**: `waterLevel` поднимается от нижней границы пропорционально `progress`. Амплитуда зависит от соотношения ширины и высоты и ограничивается пределами, находящимися достаточно далеко от верхней и нижней дуг закругления, во избежание выхода волны за границы.
2. **Дискретизация волны**: равномерная выборка точек слева направо, вычисление значения $y$ для каждой координаты $x$.
   Волна формируется наложением трех составляющих: обычной синусоиды (фаза управляется `m_waveOffset`), усиления от ряби (затухающие колебания под управлением `m_rippleProgress`) и ограничения по радиусу скругления (гарантирующего, что путь не выходит за границы прямоугольника со скругленными углами).
3. **Замкнутый контур**: возврат по нижней кромке от верха волны к низу прямоугольника со скругленными углами для формирования замкнутого многоугольника, заполняемого методом `fillPath`.

Детали алгоритма носят обучающий характер демонстрации эффекта; в реальных продуктах их можно заменить на любую логику генерации путей в соответствии с требованиями дизайна.

::: tip Эффективность построения путей
Количество точек дискретизации (`sampleCount`) пропорционально ширине виджета (примерно одна точка каждые `4px`), и нагрузка на производительность при типичных разрешениях экрана находится в допустимых пределах. Если процессор слабый, можно снизить плотность выборки или использовать аппроксимацию кривыми Безье.
:::

### Свойство waveMode

Реализация метода `setWaveMode()` проста: при изменении состояния обновляется значение члена класса и запрашивается перерисовка:

```cpp
void WaveSlider::setWaveMode(bool enabled) {
    if (m_waveMode != enabled) {
        m_waveMode = enabled;
        update();
    }
}
```

Объявление макроса `GX_PROPERTY` делает `waveMode` свойством, видимым для фреймворка:

```cpp
GX_PROPERTY(bool waveMode, get isWaveMode, set setWaveMode)
```

Поле `signal` здесь не объявлено, так как значение обычно задается внешней стороной, а не инициируется интерактивно.

### Производственная оптимизация

Реализация `WaveSlider` в основном ориентирована на обучающие демонстрации и не лишена некоторых недостатков:
- Анимация волн воспроизводится постоянно, даже когда `waveMode` выключен, что вызывает циклический вызов `paintEvent()`;
- Поддерживается только вертикальный слайдер, адаптация под горизонтальный режим отсутствует (реализуется по продуктовым требованиям);
- Жестко зафиксирована отрисовка трека в виде капсулы; в реальных продуктах может потребоваться прямоугольник со скругленными углами или другая форма.

## Взаимодействие компонентов

Ниже показано, как компоненты в `slider-demo` взаимодействуют во время выполнения:

```
Пользователь касается экрана
    ├─ WaveSlider::gestureEvent() обнаруживает Press.isStarted()
    │       └─ startRipple() сбрасывает m_rippleProgress и запускает m_rippleAnimation
    └─ Slider::gestureEvent() продолжает обработку, изменяя value в зависимости от позиции касания
            └─ испускается сигнал changed → MyWidget::onSlider() обновляет текст Label

Цикл рендеринга каждого кадра
    ├─ m_animation непрерывно продвигает m_waveOffset (цикл 0→1)
    │       └─ update() → paintEvent() перерисовывает волну с новым смещением
    └─ m_rippleAnimation продвигает m_rippleProgress (от 0 до 1, затем останавливается)
            └─ update() → paintEvent() перерисовывает затухающую рябь
   
Переключение Switch
    └─ waveSlider->setWaveMode(true/false)
            └─ update() → paintEvent() переключается в обычный или волновой режим
```

Подключения сигналов устанавливаются единожды в конструкторе `MyWidget`, после чего работа приложения полностью управляется событиями и сигналами, без прямых вызовов между виджетами.

## Сводка ключевых паттернов

На примере `slider-demo` можно выделить типичные паттерны реализации кастомных виджетов в Glyphix:

| Задача | Решение |
|---|---|
| Наследование существующего виджета, повторное использование логики взаимодействия | Наследовать соответствующий базовый класс (например, `Slider`), управлять откатом к базовому классу через `EventDispatch` |
| Кастомная отрисовка | Реализовать `paintEvent()`, вызывать `Slider::paintEvent()` для возврата к дефолтной отрисовке, когда `isWaveMode()` равен `false` |
| Непрерывная циклическая анимация | `ValueAnimation::setRepeat(Infinity)` |
| Однократный запуск анимации | Сохранить переменную состояния, вызвать `anim.start()` в `gestureEvent()` для перезапуска |
| Экспорт свойств на уровень приложения | Использовать макрос `GX_PROPERTY` в сочетании с геттерами/сеттерами и опциональными сигналами |
| Чтение пользовательских или темных цветов | Проверить с помощью `style().hasProperty()` с откатом к `se->palette()` |
| Кастомизация внешнего вида глобальных элементов управления | Наследовать `StyleEngine`, переопределить `paint()` и `sizeHint()` |

Все эти паттерны подробно описаны в [Руководстве по разработке виджетов](widget.md), а `slider-demo` является их комплексной практической реализацией.

## Сравнение с другими GUI фреймворками

::: important Назначение разработки виджетов на C++
Основным способом разработки на Glyphix является создание интерфейсов с помощью декларативных шаблонов на базе [однофайловых компонентов `.ux`](../tutorials/quick-orientation.md). Разработка виджетов на C++ применяется для создания **низкоуровневых библиотек виджетов на стороне устройства** (например, кастомизированного производителем устройства `WaveSlider`), которые затем используются фронтенд-приложениями через шаблоны и привязку данных. Создание полноценного UI непосредственно на C++ (как показано в `main.cpp`) во фреймворке **возможно, но не является рекомендуемым рабочим процессом**, так как поддержка соответствующего инструментария (отладка, «горячее» обновление, превью макета) развита хуже, чем на уровне приложений.

Поэтому при оценке общей эффективности разработки на Glyphix за базовую линию следует принимать фронтенд-уровень приложения. Описанный в этом разделе опыт разработки виджетов на C++ отражает лишь сценарии создания низкоуровневых библиотек компонентов.
:::

По своей ментальной модели разработка C++ виджетов в Glyphix ближе к Qt Widgets, чем к LVGL: механизм сигналов, макросы свойств, расширение через наследование, а также наименования и разделение обязанностей в `paintEvent` в целом соответствуют Qt Widgets, что позволяет разработчикам с опытом работы в Qt быстро адаптироваться.

Разработчикам LVGL придется перестроиться от стиля Си-дескрипторов к ООП-стилю C++, что потребует больших усилий, однако ключевые парадигмы, такие как организация дерева виджетов и инициирование перерисовки через `update()`, остаются общими. В этом разделе на базе `slider-demo` детально рассмотрены сходства и ключевые отличия между фреймворками.

### Сходства

Независимо от того, используются ли Qt Widgets, LVGL или Glyphix, все они разделяют проверенную временем базовую парадигму UI-фреймворков:

- **Дерево виджетов**: пользовательский интерфейс организуется в иерархическое дерево из родителей и потомков, где координаты дочерних элементов задаются относительно родителя. `MyWidget(&window)` концептуально эквивалентен `new QWidget(&parent)` в Qt и `lv_obj_create(parent)` в LVGL.
- **Кастомная отрисовка**: внешний вид виджета реализуется путем переопределения метода отрисовки. Qt переопределяет `paintEvent(QPaintEvent *)`, LVGL регистрирует обратный вызов `LV_EVENT_DRAW_MAIN`, а Glyphix реализует `paintEvent(PaintEvent *)`. Проектные подходы во всех трех случаях идентичны.
- **Механизм сигналов и слотов**: передача изменений состояния между виджетами осуществляется через сигналы, а принимающая сторона реагирует на них с помощью методов-членов.
  - Glyphix: `m_slider.changed.connect(this, &MyWidget::onSlider)`;
  - Qt: `connect(&slider, &QSlider::valueChanged, this, &MyWidget::onSlider)`;
  - LVGL: реализация аналогичного функционала через функции обратного вызова (callbacks) событий.
- **Расширение через наследование**: расширение существующих элементов управления реализуется путем наследования. `WaveSlider : public Slider` переиспользует всю логику перетаскивания и получения значений базового класса, переопределяя только часть отрисовки, что соответствует дизайну большинства ООП GUI-фреймворков.
- **Перерисовка по требованию**: при изменении состояния вызывается `update()` для отметки области как «грязной», после чего фреймворк выполняет единую перерисовку в следующем кадре вместо немедленного рисования. Эту стратегию используют все основные фреймворки во избежание избыточного рисования в пределах кадра.

### Отличия от Qt Widgets

#### Диспетчеризация событий

В Qt события распределяются через переопределение виртуальных функций, где каждый метод события является `virtual` и переопределяется в подклассе с помощью `override`:

```cpp
// Qt
class MySlider : public QSlider {
    void paintEvent(QPaintEvent *event) override { ... }
    void mousePressEvent(QMouseEvent *event) override { ... }
};
```

Функции обработки событий в Glyphix, такие как `paintEvent()` и `gestureEvent()`, **не являются виртуальными** и не используют ключевое слово `override`. Маршрутизация событий выполняется на этапе компиляции с помощью `EventDispatch`:

```cpp
// Glyphix
bool WaveSlider::event(Event *event) {
    return EventDispatch<Widget, GestureEvent, PaintEvent>{}(this, event);
}
// paintEvent и gestureEvent являются обычными методами-членами без override
```

Это сделано для исключения косвенных переходов по виртуальной таблице (vtable), что дает преимущество в производительности при обработке высокочастотных событий в встраиваемых устройствах. В то же время список шаблонных параметров выполняет роль документации на этапе компиляции и проверки пропущенных элементов. Если вы объявили обработку `PaintEvent`, но забыли реализовать `paintEvent()`, компилятор выдаст ошибку, вместо того чтобы молча передать управление базовому классу.

#### Система объектов и свойств

Qt использует макрос `Q_PROPERTY` в сочетании с MOC (компилятором метаобъектов) для генерации метаданных свойств. Glyphix использует `GX_PROPERTY` в сочетании с `GX_OBJECT`. Механизмы схожи, но отличаются способом генерации и интерфейсами времени выполнения:

```cpp
// Qt
Q_PROPERTY(int value READ value WRITE setValue NOTIFY valueChanged)
// Glyphix
GX_PROPERTY(int value, get value, set setValue, signal valueChanged)
```

Оба фреймворка поддерживают анимацию на основе имен свойств в виде строк (`QPropertyAnimation` / `PropertyAnimation`). Однако при реализации собственных элементов управления в Glyphix рекомендуется напрямую использовать `ValueAnimation<T>`, что исключает накладные расходы на поиск свойства по имени и предотвращает конфликты с анимацией свойств, управляемой со стороны приложения.

#### Сигналы и слоты

Как описано в [Системе объектов](object-system.html#信号-signal), в Glyphix также имеется механизм сигналов, но по устройству он ближе к `boost::signals2` и не зависит от генерации кода через MOC. Это осознанное проектное решение: поскольку [системы сборки](sdk-setup.md#其他构建系统) в экосистеме Glyphix могут быть фрагментированы, предполагается, что в нижестоящих проектах компилятор метаобъектов не используется вовсе.

#### Стилизация и кастомизация внешнего вида

Настройка внешнего вида виджетов в Qt идет по двум путям: подклассы `QStyle` (сложно) или таблицы стилей QSS (строки наподобие CSS, парсящиеся в рантайме). В Glyphix используется `StyleEngine`: производитель реализует подкласс `StyleEngine`, отрисовывая все встроенные элементы управления на C++ в методе `paint()` и предоставляя рекомендуемые размеры в `sizeHint()`. Такой подход оптимален для глобальной кастомизации системных стилей, а не для локальной настройки отдельных элементов.

Для настройки стилей отдельных виджетов в Glyphix применяется вспомогательный объект `StyleModifier` с программным присваиванием значений, вместо использования CSS-подобных строк:

```cpp
StyleModifier m(waveSlider);
m->setSize(120, 300);
m->setColor(Color{"#35a7ff"});

// Поддерживаются и строки инлайн-стилей
waveSlider->setStyle(Style{"background-color: #35a7ff; color: #cce;"});
```

Свойства стилей и компоновки в Glyphix задаются преимущественно через атрибуты стилей, а не прямым вызовом методов виджета. Это связано с тем, что C++ ориентирован главным образом на разработку низкоуровневых библиотек виджетов, а не на непосредственное создание приложений.

#### Память и жизненный цикл

В модели владения «родитель-потомок» в Qt после вызова `new QWidget(parent)` дочерний виджет уничтожается родительским. Glyphix поддерживает эту модель (после `new WaveSlider` через `addItem()`), но также рекомендует объявлять дочерние виджеты в качестве членов класса (например, `m_label`, `m_slider` в `MyWidget`). В этом случае их жизненный цикл автоматически привязывается к хост-объекту без ручного вызова `delete` и без зависимости от механизма разрушения дерева родитель-потомок.

### Отличия от LVGL

#### Модель программирования

LVGL — это фреймворк, написанный на C, где элементы управления управляются через дескрипторы `lv_obj_t *`, а наименования функций обычно подчиняются соглашению `lv_<тип>_<операция>()`:

```c
// LVGL
lv_obj_t *slider = lv_slider_create(parent);
lv_slider_set_value(slider, 50, LV_ANIM_ON);
lv_obj_add_event_cb(slider, my_event_cb, LV_EVENT_VALUE_CHANGED, NULL);
```

Glyphix — это нативный ООП-фреймворк на C++, где методы вызываются непосредственно у объектов, а указатель `this` неявно несет контекст:

```cpp
// Glyphix
auto *slider = new Slider(parent);
slider->setValue(50);
slider->changed.connect(this, &MyWidget::onSlider);
```

Для разработчиков LVGL главным изменением становится не сама концепция возможностей, а способ их выражения: если раньше функции вызывались снаружи объекта-дескриптора, то теперь состояние, события и логика отрисовки инкапсулируются внутри класса виджета. Система типов также помогает избежать части ошибок с неверными типами дескрипторов на этапе компиляции.

#### Система событий

Обработка событий в LVGL обычно принимает различные типы событий через единую функцию обратного вызова, внутри которой выполняется ветвление по коду события через `lv_event_get_code()`:

```c
// LVGL
static void event_cb(lv_event_t *e) {
    lv_event_code_t code = lv_event_get_code(e);
    if (code == LV_EVENT_PRESSED) { ... }
    else if (code == LV_EVENT_VALUE_CHANGED) { ... }
}
```

В Glyphix события распределяются по отдельным функциям-обработчикам, изолирующим разные типы событий друг от друга и предоставляющим аргументы с корректными типами данных:

```cpp
// Glyphix
bool WaveSlider::gestureEvent(GestureEvent *event) { ... }
void WaveSlider::paintEvent(PaintEvent *event) { ... }
```

Кроме того, механизм `isHitTest()` в Glyphix не имеет прямого полного аналога в LVGL. В LVGL для решения похожих задач можно использовать `LV_EVENT_HIT_TEST`, но обычно в рамках одного колбэка все равно требуется ветвление логики.

::: tip Внутренний механизм диспетчеризации событий Glyphix
Под капотом `EventDispatch` также использует оператор switch-case, однако разработчикам не рекомендуется писать switch-ветвления вручную — всегда следует использовать стандартный паттерн `EventDispatch<Widget, ...>{}(this, event)` для облегчения код-ревью.
:::

#### Анимация

Анимации в LVGL настраиваются через структуру `lv_anim_t`, а целевые значения передаются через указатели на функции и пользовательские данные `void *`:

```c
// LVGL
lv_anim_t a;
lv_anim_init(&a);
lv_anim_set_exec_cb(&a, anim_cb);
lv_anim_set_var(&a, obj);
lv_anim_set_values(&a, 0, 100);
lv_anim_set_time(&a, 800);
lv_anim_start(&a);
```

Класс `ValueAnimation<T>` в Glyphix определяет типы интерполяции во время компиляции с помощью шаблонных параметров, исключая преобразования типов `void *` за счет подключения сигналов:

```cpp
// Glyphix
m_rippleAnimation.setValueLimits(0.f, 1.f);
m_rippleAnimation.setDuration(800);
m_rippleAnimation.value.connect(this, &WaveSlider::onRippleAnimation);
```

`ValueAnimation<T>` из коробки поддерживает интерполяцию составных типов, таких как `Color`, `Point` и `Transform`, в то время как LVGL нативно поддерживает только целочисленные диапазоны, а для комплексных типов требует реализации пользовательских колбэков интерполяции.

#### Отрисовка векторных путей

API рисования в LVGL ориентировано преимущественно на базовые примитивы, такие как прямоугольники и дуги, а поддержка векторных путей (`lv_draw_vector`) появилась относительно недавно и имеет более низкоуровневые интерфейсы. `VectorPath` в Glyphix представляет собой стандартный интерфейс построения путей с поддержкой `moveTo`, `lineTo`, `arcTo`, `conicTo` и `cubicTo`, полностью покрывающий распространенные типы кривых. Волны в `WaveSlider` реализованы полностью на базе этого интерфейса без подключения дополнительных графических библиотек.

#### Память и жизненный цикл

Оба фреймворка поддерживают управление деревом объектов: дочерние элементы прикрепляются к родительским и уничтожаются вместе с ними при удалении родительского объекта.

В Glyphix дочерние элементы, анимации и состояния времени выполнения также могут напрямую объявляться как члены класса и управляться автоматически средствами C++ RAII. Например, `m_label`, `m_slider` в `MyWidget`, а также две анимации `ValueAnimation<float>` в `WaveSlider` конструируются и уничтожаются вместе с хост-объектом, избавляя от необходимости организации состояния вокруг дескрипторов, `user_data` и контекста колбэков, как это принято в LVGL.
