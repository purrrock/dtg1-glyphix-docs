# Практическое руководство по созданию пользовательских виджетов

`slider-demo` — это полноценный пример, поставляемый с Glyphix SDK, который демонстрирует, как реализовать **кастомный элемент управления** `WaveSlider` на C++ с нуля. Этот элемент расширяет стандартный `Slider` эффектами волновой заливки и анимированной ряби при нажатии. Кроме того, пример затрагивает темы кастомизации `StyleEngine` и создания пользовательского интерфейса непосредственно на C++.

В данной статье этот пример используется в качестве основы для демонстрации всех шагов, необходимых для создания нового виджета, в сочетании с ключевыми концепциями из [Руководства по разработке виджетов](./widget.md).

## Структура примера

Структура файлов примера выглядит следующим образом:

```
app/slider-demo/
├── CMakeLists.txt
├── main.cpp           # Точка входа приложения, построение UI на C++
├── styleengine.h/.cpp # Кастомизация StyleEngine
└── waveslider.h/.cpp  # Реализация виджета WaveSlider
```

Вы можете напрямую скомпилировать и запустить цель `slider-demo`, чтобы увидеть результат в действии без необходимости использования фронтенд-проекта.

### Инструкции по сборке

После [настройки SDK](sdk-setup.md#准备工作) выполните следующие команды для сборки и запуска примера:

```bash
mkdir build && cd build
cmake .. && cmake --build . -j
bin/slider-demo
```

Для сборки и запуска этого примера требуется система Linux с поддержкой среды рабочего стола (Desktop Environment).
:::

## Создание UI непосредственно на C++

В `main.cpp` пользовательский интерфейс приложения полностью собирается в конструкторе с помощью кода на C++, что по стилю напоминает Qt Widgets или LVGL: дочерние виджеты создаются через `new` с передачей указателя на родительский виджет, без использования декларативных шаблонов.

```cpp
int main() {
    Application app(new BSPPlatform(500, 500));
    app.setFont(Font(GX_EXAMPLE_ASSETS "/roboto.ttf", 32));
    app.setStyleEngine(new MyStyleEngine);

    Window window;
    window.setFlowLayout(true);

    MyWidget widget(&window);
    StyleModifier(&widget)->setSize(
      Length::fromPercent(100), Length::fromPercent(100));
    StyleModifier(&widget)->setMargin(Margin(10));
    return app.exec();
}
```

`Application` принимает объект бэкенда платформы (`BSPPlatform`) и разрешение экрана. `Window` является корневым виджетом. При включении `setFlowLayout(true)` его дочерние элементы автоматически выстраиваются с использованием потокового компоновщика (flow layout).

Вызов `setStyleEngine` подключает пользовательский движок стилей. Это необязательный шаг (в противном случае используется стиль по умолчанию) и требуется только тогда, когда вам нужно изменить внешний вид элементов управления (например, модифицировать `Switch`, как показано ниже).

### Класс `MyWidget`

`MyWidget` наследуется от `ScrollArea` и создает дочерние виджеты в своем конструкторе:

```cpp
class MyWidget : public ScrollArea {
public:
    explicit MyWidget(Widget *parent = nullptr) : ScrollArea(parent) {
        addItem(&m_switch);
        addItem(&m_label);
        addItem(&m_slider);
        // ...
    }
    // ...
private:
    Label  m_label;
    Switch m_switch;
    Slider m_slider;
};
```

Дочерние элементы объявляются как члены класса и автоматически инициализируются при создании (родительский виджет устанавливается внутри метода `addItem`). Время жизни этих членов класса управляется самим `MyWidget`, ручной вызов `delete` не требуется.

`ScrollArea` «из коробки» предоставляет возможности прокрутки, инерции и отскока (bounce-back), поэтому в `MyWidget` не нужно писать собственную логику скроллинга.

::: tip Назначение `addItem()`
Обычно дочерние виджеты можно напрямую привязывать к родительскому с помощью `setParent()`. Однако внутри `ScrollArea` имеется специальный контейнер содержимого (`contentWidget()`), и обычные элементы нельзя добавлять в `ScrollArea` напрямую — их нужно добавлять в этот контейнер через `addItem()`.

Для простых контейнеров эффекты от `setParent()` и `addItem()` одинаковы; но для специальных контейнеров вроде `ScrollArea` **обязательно** использовать `addItem()`.
:::

### Подключение сигналов

Состояние между элементами управления синхронизируется через сигналы:

```cpp
m_slider.changed.connect(this, &MyWidget::onSlider);
m_switch.checked.connect(this, &MyWidget::onSwitch);

// Двусторонняя синхронизация значений двух слайдеров
waveSlider->changed.connect<AbstractSlider>(&m_slider, &Slider::setValue);
m_slider.changed.connect<AbstractSlider>(waveSlider, &WaveSlider::setValue);

// Переключатель управляет волновым режимом WaveSlider
m_switch.checked.connect(waveSlider, &WaveSlider::setWaveMode);
```

::: tip Использование Signal
Синтаксис подключения сигналов: `signal.connect(receiver, &Type::method)`. Если сигнатуры `Slider::setValue` и `WaveSlider::setValue` не полностью совпадают, можно указать общий базовый класс (`AbstractSlider`) в качестве шаблонного параметра для разрешения неоднозначности.

Если вы не уверены в точном типе, которому принадлежит слот-функция, это можно проверить с помощью подсказок IDE. Например, при проверке `Slider::setValue` IDE обычно подскажет:
```cpp
public method
void setValue(int value) in class AbstractSlider 
```
Это указывает на то, что `setValue` фактически объявлен в классе `AbstractSlider`. При подключении необходимо указать `AbstractSlider` для устранения неоднозначности:
```cpp
m_slider.changed.connect<AbstractSlider>(waveSlider, &WaveSlider::setValue);
```
:::

### Настройка стилей с помощью StyleModifier

`StyleModifier` — это инструмент для программной настройки стилей виджетов на C++, эквивалентный конфигурации через свойства стиля в шаблонах:

```cpp
StyleModifier m(waveSlider);
m->setSize(120, 300);
m->setMargin(Style::Margin{Length::fromAuto(), 20});
m->setColor(Color{"#35a7ff"});
```

Метод `setColor` задает цвет переднего плана для `WaveSlider`, который считывается внутри `paintEvent` и используется для отрисовки цвета заполнения прогресса.

## Кастомизация StyleEngine

Встроенный [`Switch`](/components/switch.md) — это полнофункциональный переключатель, но его стандартный внешний вид напоминает стиль [Fluent 2](https://fluent2.microsoft.design/components/web/react/core/switch/usage), который может не подойти под визуальный стиль конкретного устройства или бренда.

Механизм `StyleEngine` создан для решения этой задачи. Производители оборудования могут реализовать собственный `StyleEngine` для кастомизации внешнего вида всех встроенных элементов управления, сохраняя при этом их логику взаимодействия и не изменяя код фреймворка.

Модифицированный `Switch` — это не просто смена темы. Напротив, вся анимация переключателя (смещение ползунка, цветовой переход, масштабирование при нажатии) реализуется с помощью **программной интерполяции**, а не заранее записанных последовательностей кадров (кастомных картинок). Это означает, что:

- Анимация абсолютно плавная, а частота кадров совпадает с системой рендеринга;
- Разработчики приложений могут переопределять цвета и размеры с помощью свойств стилей (`StyleEngine` предоставляет значения по умолчанию, которые можно переопределять);
- Нет необходимости готовить различные графические материалы под каждое разрешение экрана.

### Обязанности `StyleEngine`

`StyleEngine` является ядром системы стилей Glyphix и отвечает за три вещи:

1. **Предоставление палитры** (palette): глобальные цветовые переменные (аналог пользовательских свойств CSS), которые считывают все встроенные и пользовательские виджеты.
2. **Отрисовка внешнего вида элементов** (paint): визуальное оформление встроенных виджетов фреймворка (таких как `Switch`, `Slider`) полностью делегируется `StyleEngine::paint()`. Разработчики могут переопределить этот метод в производном классе для достижения совершенно иного внешнего вида.
3. **Рекомендуемый размер** (size hint): рекомендуемые размеры виджетов в различных состояниях стилей, используемые системой компоновки в качестве справочных данных.

### Определение `MyStyleEngine`

Наследуйтесь от `StyleEngine` и переопределите методы `sizeHint()` и `paint()`:

```cpp
class MyStyleEngine : public StyleEngine {
public:
    MyStyleEngine();
    Size sizeHint(StyleOption::Type type, const Widget *widget) const override;
    void paint(Painter &painter, Widget *widget, StyleOption &option) override;
};
```

Палитра задается в конструкторе:

```cpp
MyStyleEngine::MyStyleEngine() {
    setPalette(SwitchDark,  Color(0xff565656));
    setPalette(SwitchLight, Color(0xff2f5cff));
    setPalette(SwitchThumb, Color(0xffffffff));
}
```

`SwitchDark`, `SwitchLight` и `SwitchThumb` — это предопределенные ключи семантических цветов в перечислении `StyleEngine`. Разные движки тем могут сопоставлять им разные цвета, а элементы управления всегда считывают цвета по имени ключа, а не используют жестко закодированные значения.

### Переопределение `sizeHint()`

Метод `sizeHint()` сообщает фреймворку **рекомендуемый размер** встроенного виджета для заданного состояния стиля. На примере `Switch`: его ширина и высота должны быть пропорциональны размеру шрифта в пикселях:

```cpp
Size MyStyleEngine::sizeHint(StyleOption::Type type, const Widget *widget) const {
    // Пропорции размеров кастомного Switch могут отличаться от встроенной стратегии
    if (type == StyleOption::OptionSwitch) {
        float f = widget->font().pixelSize();
        int d = int(round(f));
        return {int(round(f * SwitchAspectRatio)), d};
    }
    return StyleEngine::sizeHint(type, widget); // Остальные типы передаем базовому классу
}
```

В конце функции обязательно вызовите `StyleEngine::sizeHint(type, widget)` для возврата к реализации по умолчанию, иначе элементы управления других типов получат нулевой размер.

### Переопределение `paint()`

Метод `paint()` выполняет диспетчеризацию в соответствии с типом `option()` из `StyleOption` в соответствующую логику отрисовки. Необработанные типы также должны возвращаться к базовой реализации:

```cpp
void MyStyleEngine::paint(Painter &painter, Widget *widget, StyleOption &option) {
    switch (option.option()) {
    case StyleOption::OptionSwitch:
        drawSwitch(this, painter, widget, static_cast<StyleOptionSwitch &>(option));
        break;
    default:
        StyleEngine::paint(painter, widget, option);
    }
}
```

`StyleOptionSwitch` — это производный класс от `StyleOption`, добавляющий поля состояния, специфичные для Switch. Он содержит два ключевых значения прогресса анимации:

- `option.transition`: прогресс перехода состояния переключателя (`0.0` — выключено, `1.0` — включено, промежуточные значения означают процесс анимации).
- `option.scale`: коэффициент масштабирования при нажатии, используемый для визуальной обратной связи.

Используя эти два значения в `drawSwitch`, можно реализовать плавный переход состояний:

```cpp
// Интерполяция между цветами включенного и выключенного состояний
color = color.blend(checked.background().color(), option.transition);

// Позиция индикатора (thumb) смещается в зависимости от прогресса перехода
float pos = option.transition * (box.width() - size - len);
```

`StyleEngine` управляет анимацией, а разработчику достаточно выполнить интерполяцию на основе значений прогресса внутри `paint()`, чтобы получить полноценный анимированный переход.

::: tip Кастомизация только части виджетов
Стандартный `StyleEngine` реализует логику отрисовки для всех встроенных элементов управления, причем некоторые из них довольно сложны. Если вас не устраивает внешний вид лишь некоторых элементов, вам следует переопределить логику отрисовки только для них в своем производном классе, а для остальных элементов напрямую вызывать реализацию базового класса.

Для настройки цветов в первую очередь следует рассматривать использование палитры, и прибегать к переопределению `paint()` только тогда, когда требуется принципиально иной визуальный эффект.
:::

### Отрисовка скругленной капсулы с помощью VectorPath

Фон и бегунок (thumb) стандартного `Switch` имеют форму капсулы со скругленными углами. В примере для этого используется `VectorPath` в сочетании с двумя дугами. Это более гибкий подход по сравнению с `drawRoundedRect`, подходящий для сценариев, где требуется раздельное управление радиусами закругления для обоих концов:

```cpp
static void indicatorBar(Painter &p, const RectF &rect) {
    float radius = rect.height() * 0.5f;
    float x1 = rect.left() + radius;
    float x2 = rect.right() - radius;
    float y = rect.top() + radius;
    VectorPath path;
    path.arcTo(PointF(x1, y), radius, radius, 90, 270);   // Левая полусфера
    path.arcTo(PointF(x2, y), radius, radius, -90, 90);   // Правая полусфера
    p.fillPath(path);
}
```

Две дуги соединяются последовательно, а `arcTo` автоматически соединяет линии в пути без необходимости вызывать `lineTo` отдельно.

## WaveSlider: полноценная практика создания кастомного виджета

`WaveSlider` — это центральный элемент данного примера, демонстрирующий полный процесс разработки кастомного виджета. По аналогии с кастомизацией `StyleEngine`, цель создания `WaveSlider` заключается в **наложении** новых визуальных эффектов без нарушения уже существующих возможностей:

- **Режим волновой заливки** (`WaveFill`): область прогресса заполняется динамическими волнами вместо обычной прямоугольной полосы прогресса;
- **Эффект ряби при нажатии** (`Ripple`): при нажатии генерируется диффузное затухающее колебание, заставляющее волну кратковременно усиливаться и затем возвращаться в исходное состояние;
- **Свойство `waveMode`**: позволяет переключать волновой и обычный режимы во время выполнения, а также поддерживает привязку на уровне приложения и анимацию свойств;
- **Полная обратная совместимость (fallback)**: при отключении волнового режима `WaveSlider` напрямую вызывает `Slider::paintEvent()` для возврата к стандартному внешнему виду, полностью переиспользуя возможности родительского класса (перетаскивание, свойства `value`/`changed` и т.д.) без необходимости изменять какой-либо код на стороне приложения.

### Определение класса и наследование

`WaveSlider` наследуется от `Slider` (а не напрямую от `Widget`), что позволяет повторно использовать существующую логику перетаскивания жестами, свойства `value`/`minimum`/`maximum`, а также сигнал `changed`:

```cpp
// waveslider.h
#include "gx_slider.h"
#include "gx_valueanimation.h"

class WaveSlider : public Slider {
    GX_OBJECT
public:
    explicit WaveSlider(Widget *parent = nullptr);
    ~WaveSlider() override = default;

    GX_NODISCARD bool isWaveMode() const { return m_waveMode; }
    void setWaveMode(bool enabled);
    bool event(Event *event) override;

    GX_PROPERTY(bool waveMode, get isWaveMode, set setWaveMode)
    // ...
};
```

Макрос `GX_OBJECT` должен располагаться в самом начале определения класса; он заставляет компилятор метаобъектов (MOC) генерировать метаданные для данного класса. `GX_PROPERTY` делает свойство `waveMode` доступным для системы свойств, позволяя применять привязку на уровне приложения (например, `<wave-slider :wave-mode="enabled"/>`) и управлять им с помощью анимации свойств.

### Члены класса

Состояние виджета во время выполнения хранится в членах класса:

```cpp
private:
    bool  m_waveMode = false;       // Включен ли волновой режим в данный момент
    float m_rippleProgress = 1.0f;  // Прогресс ряби [0, 1], по умолчанию 1 (неактивна)
    float m_waveOffset = 0.0f;      // Фазовое смещение волны [0, 1], управляется анимацией
    ValueAnimation<float> m_animation;        // Циклическая анимация волн
    ValueAnimation<float> m_rippleAnimation;  // Анимация ряби
    friend struct EventTraits<WaveSlider>;    // Разрешает EventDispatch доступ к защищенным методам
```

`ValueAnimation<float>` объявляется как член класса (а не как указатель), ее время жизни управляется `WaveSlider`, ручной вызов `delete` не требуется.

### Конструктор: инициализация анимации

Конструктор настраивает две анимации и устанавливает ориентацию:

```cpp
WaveSlider::WaveSlider(Widget *parent) : Slider(parent) {
    // Анимация волн: бесконечный цикл, один полный период в секунду
    m_animation.setRepeat(AbstractAnimation::Infinity);
    m_animation.setValueLimits(0.f, 1.f);
    m_animation.setDuration(1000);
    m_animation.value.connect(this, &WaveSlider::onWaveAnimation);
    m_animation.start();

    // Анимация ряби: проигрывается один раз при нажатии, длительность 800мс
    m_rippleAnimation.setValueLimits(0.f, 1.f);
    m_rippleAnimation.setDuration(800);
    m_rippleAnimation.value.connect(this, &WaveSlider::onRippleAnimation);

    setVertical(true);  // Вертикальный слайдер
}
```

`m_animation` работает непрерывно после запуска, продвигая `m_waveOffset` от $0$ до $1$ за каждый кадр с возвратом к $0$. Это значение в конечном итоге преобразуется в фазовое смещение волны, заставляя ее непрерывно течь.

`m_rippleAnimation` запускается только при нажатии, проигрывается один раз и останавливается (без флага `Infinity`). Обратные вызовы (callbacks) обеих анимаций выполняют только одно действие: обновляют переменные состояния и вызывают `update()` для запроса перерисовки.

```cpp
void WaveSlider::onWaveAnimation(float value) {
    m_waveOffset = value;
    update();
}
void WaveSlider::onRippleAnimation(float value) {
    m_rippleProgress = value;
    update();
}
```

### Обработка событий

#### Настройка EventDispatch

В методе `event()` для маршрутизации событий используется [`EventDispatch`](widget.md#处理事件). Шаблонные параметры перечисляют типы событий, которые фактически обрабатываются текущим виджетом, что обеспечивает проверку на этапе компиляции:

```cpp
bool WaveSlider::event(Event *event) {
    return EventDispatch<Widget,
        GestureEvent, PaintEvent>{}(this, event);
}
```

#### Обработка жестов: запуск ряби

Метод `gestureEvent()` перехватывает момент начала жеста `Press` для запуска ряби, а во всех остальных случаях делегирует обработку жестов базовому `Slider` (реализуя перетаскивание и изменение значения):

```cpp
bool WaveSlider::gestureEvent(GestureEvent *event) {
    if (!event->isHitTest() && event->gesture()->type() == Gesture::Press) {
        auto g = static_cast<PressGesture *>(event->gesture());
        if (g->isStarted())
            startRipple(g->clientPoint());
    }
    return Slider::gestureEvent(event); // Передаем событие дальше в Slider
}

void WaveSlider::startRipple(const Point &) {
    m_rippleProgress = 0.f;      // Начинаем сначала
    m_rippleAnimation.start();   // Перезапускаем воспроизведение
}
```

Если `isHitTest()` возвращает `true`, это означает, что выполняется проверка попадания (фреймворк проверяет, попадает ли событие в этот элемент управления), что не является реальным взаимодействием пользователя, и такие события следует пропускать.

::: tip О методе `isHitTest()`
Проверка попадания — это предварительный шаг диспетчеризации событий. `gestureEvent()` также вызывается на этапе проверки попадания, но в этот момент не должно происходить никаких побочных эффектов (таких как запуск анимации). Всегда проверяйте `!event->isHitTest()` перед обработкой логики взаимодействия.
:::

#### Интерфейс чтения стилей

Внутри `paintEvent()` считываются данные стилей, соответствующие элементу управления. Здесь мы рассмотрим два используемых интерфейса:

- `style()` / `style(Styles::Xxx)` возвращает объект `Style` для определенного псевдокласса стиля текущего виджета, из которого можно считывать такие свойства, как цвет и фон;
- `se->palette(StyleEngine::Xxx)` считывает цвет из глобальной палитры `StyleEngine`. Он используется в качестве значения по умолчанию, если для виджета не задан пользовательский цвет.

Совместное использование этих двух методов реализует логику «если есть пользовательская конфигурация, использовать ее, иначе возвращаться к цвету темы по умолчанию»:

```cpp
auto contentStyle = style(Styles::Content);
p.setBrush(contentStyle.hasProperty(style::Background)
               ? contentStyle.background()
               : se->palette(StyleEngine::ProgressRange));
```

### Реализация отрисовки

Метод `paintEvent()` является ядром WaveSlider. Путь отрисовки определяется на основе значения `m_waveMode`:

```cpp
void WaveSlider::paintEvent(PaintEvent *event) {
    discard(event);  // PaintEvent сам по себе не содержит полезной информации, явно отбрасываем его для устранения предупреждений компилятора

    if (!isWaveMode())
        return Slider::paintEvent(event);  // Обычный режим: вызываем отрисовку базового класса

    auto se = App()->styleEngine();
    RectF box = rect();
    float radius = min(box.width(), box.height()) * 0.5f;
    float progress = sliderRange ? float(value() - minimum()) / float(sliderRange) : 0.f;

    Painter p(this);

    // Отрисовка фона (пустая дорожка)
    p.setBrush(/* Цвет фона */);
    p.fillRoundedRect(box, radius);

    // Отрисовка волновой заливки (область прогресса)
    p.setBrush(/* Цвет переднего плана */);
    VectorPath path;
    buildWaveFillPath(path, box, radius, progress, m_waveOffset, m_rippleProgress);
    if (!path.isEmpty())
        p.fillPath(path);
}
```

Весь процесс отрисовки состоит из двух шагов: сначала с помощью `fillRoundedRect` рисуется полный фоновый прямоугольник со скруглянными углами, а затем поверх него с помощью `fillPath` прорисовывается волновая заливка. Наложение этих двух слоев формирует «полосу прогресса с волнами».

#### Генерация волнового пути

`buildWaveFillPath()` — это отдельная вспомогательная функция (не входящая в класс), которая отвечает за построение волнового контура в заданных геометрических ограничениях:

```cpp
static void buildWaveFillPath(VectorPath &path, const RectF &box, float radius,
                              float progress, float waveOffset, float rippleProgress)
```

Её основная логика состоит из трех шагов:

1. **Вычисление уровня воды и амплитуды**: `waterLevel` поднимается снизу пропорционально значению `progress`. Амплитуда зависит от соотношения ширины и высоты и ограничивается пределами, находящимися достаточно далеко от скругленных углов вверху и внизу, чтобы волна не выходила за границы.
2. **Дискретизация волны**: выполняется равномерная выборка слева направо, для каждой координаты $x$ вычисляется значение $y$.
   Волна формируется путем наложения трех частей: обычной синусоиды (`m_waveOffset` управляет фазой) + усиления от ряби (`m_rippleProgress` управляет затухающими колебаниями) + ограничений скругленных углов (для гарантии, что путь не выходит за границы прямоугольника со скруглениями).
3. **Замыкание пути**: путь возвращается вдоль нижнего края от верхней точки волны к нижней части скругленного прямоугольника, образуя замкнутый многоугольник для заполнения методом `fillPath`.

Детали алгоритма носят обучающий характер демонстрации эффекта. В реальном продукте их можно заменить на любую пользовательскую логику генерации путей в соответствии с требованиями дизайна.

::: tip Эффективность отрисовки путей
Количество точек выборки (`sampleCount`) пропорционально ширине виджета (примерно одна точка на каждые `4px`), что обеспечивает приемлемые затраты производительности при типичных разрешениях экрана. Если процессор слабый, можно снизить плотность выборки или заменить ее приближением кривыми Безье.
:::

### Свойство waveMode

Реализация `setWaveMode()` очень проста: при изменении состояния обновляется значение члена класса и запрашивается перерисовка:

```cpp
void WaveSlider::setWaveMode(bool enabled) {
    if (m_waveMode != enabled) {
        m_waveMode = enabled;
        update();
    }
}
```

Объявление макроса `GX_PROPERTY` делает `waveMode` видимым свойством для фреймворка:

```cpp
GX_PROPERTY(bool waveMode, get isWaveMode, set setWaveMode)
```

Поле `signal` здесь не объявлено, поскольку это свойство обычно управляется пользователем (извне), а не инициируется взаимодействием.

### Оптимизация для продакшена

Реализация `WaveSlider` в основном ориентирована на демонстрацию учебного примера и лишена некоторых оптимизаций, например:
- Анимация волн воспроизводится постоянно, даже когда `waveMode` выключен, вызывая `update()`, что многократно инициирует `paintEvent()`;
- Поддерживается только вертикальный слайдер, горизонтальный режим не адаптирован (реализуется в зависимости от требований продукта);
- Статично рисуется дорожка капсулевидной формы, в то время как в реальном продукте может потребоваться прямоугольник со скругленными углами или другая форма.

## Взаимодействие компонентов

Ниже показано, как компоненты в `slider-demo` взаимодействуют во время выполнения программы:

```
Пользователь нажимает на экран
    ├─ WaveSlider::gestureEvent() фиксирует Press.isStarted()
    │       └─ startRipple() сбрасывает m_rippleProgress и запускает m_rippleAnimation
    └─ Slider::gestureEvent() продолжает обработку, изменяя value в зависимости от позиции касания
            └─ испускается сигнал changed → MyWidget::onSlider() обновляет текст Label

Цикл рендеринга каждого кадра
    ├─ m_animation непрерывно продвигает m_waveOffset (цикл 0→1)
    │       └─ update() → paintEvent() перерисовывает волну с новым смещением
    └─ m_rippleAnimation продвигает m_rippleProgress (0→1 до завершения, затем останавливается)
            └─ update() → paintEvent() перерисовывает затухание ряби с новым rippleProgress

Переключение Switch
    └─ waveSlider->setWaveMode(true/false)
            └─ update() → paintEvent() переключается в обычный или волновой режим
```

Все подключения сигналов устанавливаются один раз в конструкторе `MyWidget`. В дальнейшем выполнение полностью управляется событиями и сигналами, элементы управления не вызывают друг друга напрямую.

## Резюме ключевых паттернов

На основе `slider-demo` можно выделить типичные паттерны для реализации кастомных виджетов в Glyphix:

| Требование | Подход |
|---|---|
| Наследование существующего виджета, повторное использование логики взаимодействия | Наследуйтесь от соответствующего базового класса (например, `Slider`), управляйте откатом к базовому классу через `EventDispatch` |
| Кастомная отрисовка | Реализуйте `paintEvent()`, вызывайте `Slider::paintEvent()` для отката, если `isWaveMode()` равен `false` |
| Непрерывная циклическая анимация | `ValueAnimation::setRepeat(Infinity)` |
| Однократная анимация по триггеру | Сохраняйте переменную состояния, вызывайте `anim.start()` в `gestureEvent()` для перезапуска |
| Экспорт свойств на уровень приложения | Макрос `GX_PROPERTY` в сочетании с геттерами/сеттерами и опциональными сигналами |
| Чтение пользовательских или темных цветов | Проверка через `style().hasProperty()` с возвратом к `se->palette()` при отсутствии |
| Кастомизация внешнего вида элементов глобально | Наследуйтесь от `StyleEngine`, переопределите `paint()` и `sizeHint()` |

Все эти паттерны подробно описаны в [Руководстве по разработке виджетов](widget.md), а `slider-demo` выступает в роли их комплексного практического применения.

## Сравнение с другими GUI-фреймворками

::: important Позиционирование разработки C++ виджетов
Основным способом разработки в Glyphix является создание интерфейсов с помощью декларативных шаблонов в виде [одиночных файлов `.ux`](../tutorials/quick-orientation.md). Разработка виджетов на C++ предназначена для реализации **низкоуровневых библиотек элементов управления на стороне устройства** (например, кастомного `WaveSlider`, создаваемого производителем оборудования), которые затем используются прикладным уровнем фронтенда через шаблоны и привязку данных. Создание полноценного интерфейса непосредственно на C++ (как показано в `main.cpp`) в рамках фреймворка **возможно, но не является рекомендуемым рабочим процессом**, а поддержка со стороны инструментария (отладка, «горячее» обновление, предпросмотр компоновки) развита хуже, чем на прикладном уровне.

Поэтому при оценке общей эффективности разработки в Glyphix за базовую линию следует брать прикладной фронтенд-уровень; опыт разработки C++ виджетов, обсуждаемый в этом разделе, отражает сценарии создания исключительно низкоуровневых библиотек компонентов.
:::

По своей ментальной модели разработка C++ виджетов в Glyphix ближе к Qt Widgets, чем к LVGL: механизм сигналов, макросы свойств, расширение через наследование, а также именование и разделение обязанностей методов `paintEvent` практически полностью соответствуют Qt Widgets, что позволяет разработчикам с опытом работы в Qt быстро выработать интуитивное понимание.

Разработчикам на LVGL потребуется совершить переход от парадигмы дескрипторов (handles) в стиле C к объектно-ориентированному подходу C++, что потребует больших усилий. Тем не менее, основные парадигмы, такие как организация дерева виджетов и триггеры перерисовки через `update()`, являются общими. В этом разделе в качестве ориентира используется `slider-demo` для демонстрации сходств и ключевых различий между фреймворками.

### Сходства

Независимо от того, используются ли Qt Widgets, LVGL или Glyphix, все они разделяют проверенную временем базовую парадигму UI-фреймворков:

- **Дерево виджетов**: Пользовательский интерфейс организуется в древовидную структуру «родитель-потомок», где координаты дочерних элементов задаются относительно родителя. `MyWidget(&window)` концептуально эквивалентен `new QWidget(&parent)` в Qt и `lv_obj_create(parent)` в LVGL.
- **Кастомная отрисовка**: Внешний вид элементов настраивается путем «переопределения» методов отрисовки. Qt переопределяет `paintEvent(QPaintEvent *)`, LVGL регистрирует обратный вызов `LV_EVENT_DRAW_MAIN`, а Glyphix реализует `paintEvent(PaintEvent *)`. Проектирование во всех трех случаях одинаково.
- **Механизм сигналов/слотов**: Состояние передается между элементами управления через сигналы, а получатели реагируют на них с помощью методов-членов.
  - Glyphix: `m_slider.changed.connect(this, &MyWidget::onSlider)`;
  - Qt: `connect(&slider, &QSlider::valueChanged, this, &MyWidget::onSlider)`;
  - LVGL: аналогичный функционал реализуется через функции обратного вызова событий.
- **Расширение через наследование**: Расширение существующих элементов управления реализуется путем наследования. `WaveSlider : public Slider` повторно использует всю логику перетаскивания и получения значений родительского класса, переопределяя только часть отрисовки, что совпадает с дизайном большинства ООП GUI-фреймворков.
- **Перерисовка по требованию**: При изменении состояния вызывается метод `update()`, помечающий область как «грязную», после чего фреймворк выполняет общую перерисовку в следующем кадре, вместо немедленной отрисовки. Эту стратегию используют все основные фреймворки во избежание многократной отрисовки в пределах одного кадра.

### Отличия от Qt Widgets

#### Диспечеризация событий

Qt распределяет события через переопределение виртуальных функций, где каждый метод события помечен как `virtual`, а подклассы используют `override`:

```cpp
// Qt
class MySlider : public QSlider {
    void paintEvent(QPaintEvent *event) override { ... }
    void mousePressEvent(QMouseEvent *event) override { ... }
};
```

Функции обработки событий в Glyphix, такие как `paintEvent()` и `gestureEvent()`, **не являются виртуальными** и не могут содержать ключевое слово `override`. Маршрутизация событий выполняется на этапе компиляции с помощью `EventDispatch`:

```cpp
// Glyphix
bool WaveSlider::event(Event *event) {
    return EventDispatch<Widget, GestureEvent, PaintEvent>{}(this, event);
}
// paintEvent и gestureEvent являются обычными методами-членами без override
```

Это сделано для того, чтобы избежать косвенных переходов по виртуальной таблице (vtable), что дает преимущество в производительности при обработке высокочастотных событий на встраиваемых устройствах. В то же время список шаблонных параметров выполняет роль документации во время компиляции и проверки пропущенных элементов. Если вы объявили обработку `PaintEvent`, но забыли реализовать `paintEvent()`, компилятор выдаст ошибку, вместо того чтобы молча откатиться к базовому классу.

#### Система объектов и свойств

Qt использует макрос `Q_PROPERTY` в сочетании с MOC (метаобъектным компилятором) для генерации метаданных свойств. Glyphix использует макрос `GX_PROPERTY` в сочетании с `GX_OBJECT`. Механизмы схожи, но способы генерации и интерфейсы времени выполнения различаются:

```cpp
// Qt
Q_PROPERTY(int value READ value WRITE setValue NOTIFY valueChanged)
// Glyphix
GX_PROPERTY(int value, get value, set setValue, signal valueChanged)
```

Обе системы поддерживают управление анимацией по строковым именам свойств (`QPropertyAnimation` / `PropertyAnimation`). Однако при реализации собственных элементов управления Glyphix настоятельно рекомендует напрямую использовать `ValueAnimation<T>`, чтобы избежать накладных расходов на поиск по имени свойства и предотвратить конфликты с анимацией свойств, управляемой на уровне приложения.

#### Сигналы и слоты

Как описано в [Системе объектов](object-system.html#信号-signal), в Glyphix также есть механизм сигналов, но он ближе к boost::signals2 и не зависит от генерации кода через MOC. Это осознанное проектное решение, поскольку [система сборки](sdk-setup.md#其他构建系统) в экосистеме Glyphix довольно фрагментирована, и предполагается, что низовой код может вообще не использовать метаобъектный компилятор.

#### Стили и кастомизация внешнего вида

Кастомизация внешнего вида виджетов в Qt имеет два пути: создание подкласса `QStyle` (довольно сложно) или таблицы стилей QSS (строки наподобие CSS, парсимые во время выполнения). Glyphix использует `StyleEngine`: производители реализуют подкласс `StyleEngine`, рисуя весь внешний вид встроенных элементов управления на C++ внутри метода `paint()`, и предоставляют рекомендуемые размеры в `sizeHint()`. Этот подход применим к глобальной кастомизации стилей на уровне системы, а не к точечной настройке отдельных виджетов.

Для настройки стилей отдельных виджетов Glyphix использует вспомогательный объект `StyleModifier` для программного присвоения значений вместо использования строк CSS:

```cpp
StyleModifier m(waveSlider);
m->setSize(120, 300);
m->setColor(Color{"#35a7ff"});

// Также поддерживается строка inline-стилей
waveSlider->setStyle(Style{"background-color: #35a7ff; color: #cce;"});
```

Свойства стилей и компоновки в Glyphix задаются преимущественно через атрибуты стилей, а не через прямой вызов методов виджета. Это связано с тем, что C++ ориентирован главным образом на разработку низкоуровневых библиотек компонентов, а не на непосредственное создание приложений.

#### Управление памятью и временем жизни

В модели владения «родитель-потомок» в Qt, после вызова `new QWidget(parent)`, родительский виджет отвечает за уничтожение дочернего. Glyphix также поддерживает эту модель (после вызова `new WaveSlider` через `addItem()`), но также рекомендует объявлять дочерние элементы в качестве членов класса (например, `m_label` и `m_slider` в `MyWidget`). Время их жизни автоматически управляется хост-объектом, исключая необходимость ручного вызова `delete` и не завися от механизмов уничтожения древовидных структур родитель-потомок.

### Отличия от LVGL

#### Модель программирования

LVGL — это фреймворк, реализованный на C. Элементы управления управляются через дескрипторы `lv_obj_t *`, а наименования функций обычно следуют соглашению `lv_<тип>_<операция>()`:

```c
// LVGL
lv_obj_t *slider = lv_slider_create(parent);
lv_slider_set_value(slider, 50, LV_ANIM_ON);
lv_obj_add_event_cb(slider, my_event_cb, LV_EVENT_VALUE_CHANGED, NULL);
```

Glyphix — это нативный ООП-фреймворк на C++, где методы вызываются через объекты, а указатель `this` естественным образом несет в себе контекст:

```cpp
// Glyphix
auto *slider = new Slider(parent);
slider->setValue(50);
slider->changed.connect(this, &MyWidget::onSlider);
```

Для разработчиков LVGL основное изменение заключается не в возможностях как таковых, а в способе выражения: если раньше вы вызывали функции извне дескриптора объекта, то теперь вы организуете состояние, события и логику отрисовки внутри класса виджета. Система типов также помогает избежать некоторых ошибок использования типов дескрипторов еще на этапе компиляции.

#### Система событий

Обработка событий в LVGL обычно принимает различные события через единую функцию обратного вызова, внутри которой выполняется ветвление по коду события с помощью `lv_event_get_code()`:

```c
// LVGL
static void event_cb(lv_event_t *e) {
    lv_event_code_t code = lv_event_get_code(e);
    if (code == LV_EVENT_PRESSED) { ... }
    else if (code == LV_EVENT_VALUE_CHANGED) { ... }
}
```

Glyphix распределяет события по независимым функциям-обработчикам в зависимости от их типа. Различные события полностью изолированы друг от друга, а их параметры содержат данные корректных типов:

```cpp
// Glyphix
bool WaveSlider::gestureEvent(GestureEvent *event) { ... }
void WaveSlider::paintEvent(PaintEvent *event) { ... }
```

Кроме того, в LVGL нет полного эквивалента механизма `isHitTest()` из Glyphix. LVGL может обрабатывать схожие вопросы через `LV_EVENT_HIT_TEST`, но обычно все равно требует самостоятельного ветвления в том же самом колбэке.

::: tip Внутренний механизм диспечеризации событий в Glyphix
`EventDispatch` внутри себя также представляет switch-case распределитель, однако мы не рекомендуем разработчикам писать switch-ветвления вручную, а всегда использовать фиксированный паттерн `EventDispatch<Widget, ...>{}(this, event)` для облегчения проверки кода.
:::

#### Анимация

Анимация в LVGL настраивается через структуру `lv_anim_t`, а целевые значения передаются через указатель на функцию и пользовательские данные `void *`:

```c
// LVGL
lv_anim_t a;
lv_anim_init(&a);
lv_anim_set_exec_cb(&a, anim_cb);
lv_anim_set_var(&a, obj);
lv_anim_set_values(&a, 0, 100);
lv_anim_set_time(&a, 800);
lv_anim_start(&a);
```

Класс `ValueAnimation<T>` в Glyphix определяет тип интерполяции на этапе компиляции с помощью шаблонных параметров и устраняет необходимость преобразования типов `void *` за счет подключения сигналов:

```cpp
// Glyphix
m_rippleAnimation.setValueLimits(0.f, 1.f);
m_rippleAnimation.setDuration(800);
m_rippleAnimation.value.connect(this, &WaveSlider::onRippleAnimation);
```

`ValueAnimation<T>` имеет встроенную поддержку интерполяции для составных типов, таких как `Color`, `Point`, `Transform`, в то время как LVGL из коробки поддерживает только диапазоны целых чисел, а для составных типов требуется самостоятельно реализовывать функции обратного вызова интерполяции.

#### Отрисовка векторных путей

API отрисовки LVGL ориентирован в первую очередь на базовые примитивы, такие как прямоугольники и дуги, а поддержка векторных путей (`lv_draw_vector`) появилась относительно недавно и имеет довольно низкоуровневый интерфейс. `VectorPath` в Glyphix — это стандартный интерфейс построения путей, где `moveTo`, `lineTo`, `arcTo`, `conicTo` и `cubicTo` полностью покрывают распространенные типы кривых. Волны в `WaveSlider` реализованы исключительно на базе этого интерфейса без подключения сторонних графических библиотек.

#### Память и время жизни

Обе системы поддерживают управление через дерево объектов: дочерние элементы привязываются к родительскому и уничтожаются вместе с ним.

Glyphix также позволяет объявлять дочерние элементы, анимации и состояние времени выполнения непосредственно в качестве членов класса, управляя ими автоматически с помощью идиомы RAII в C++. Например, `m_label` и `m_slider` в `MyWidget`, а также две анимации `ValueAnimation<float>` в `WaveSlider` могут создаваться и уничтожаться вместе с хост-объектом, избавляя разработчика от необходимости организовывать состояние вокруг дескрипторов, `user_data` и контекста обратных вызовов, как это принято в LVGL.
