# Разработка асинхронного функционала

В встраиваемых (embedded) системах множество операций занимают много времени: чтение флеш-памяти, обращение к сети, ожидание отклика оборудования. Если выполнять эти операции в потоке пользовательского интерфейса (UI, который также является потоком рендеринга), это приведет к зависанию UI и неотзывчивости приложения.

Glyphix решает эту проблему путем бесшовной интеграции асинхронных операций с механизмом `Promise` в JavaScript. Сторона C++ отвечает за реальную асинхронную логику (обычно в другом потоке или через управляемую событиями модель), сторона JavaScript ожидает результат с помощью `async/await` или `.then()`, а UI остается плавным во время ожидания.

## Основной механизм

Ядром асинхронного функционала является модель «сессии» (Session). При инициализации асинхронного вызова из JavaScript, сторона C++ создает **объект сессии** (`AsyncSession`) и немедленно возвращает `Promise` в JavaScript. Когда операция завершается, сессия инициирует резолв (resolve) или реджект (reject) `Promise`, после чего на стороне JavaScript выполняются методы `then/catch` или оператор `await`.

Объект сессии привязан к вызвавшему его `Applet`. При выходе из приложения сессия автоматически очищается, и разработчику не нужно вручную управлять памятью.

Реализация асинхронного фреймворка находится в файле `gx_async.h` и инкапсулирована в пространстве имен `gx::async`. Фреймворк предоставляет несколько полезных инструментов:
- **`async::ResultSession`**: используется для одиночных асинхронных запросов, подходит для чтения файлов, сетевых запросов и т.д.
- **`async::make_timeout()`**: используется для создания однократного таймера, добавляющего функционал таймаута к отдельной сессии.
- **`async::Signal<T>`**: используется для широковещательной рассылки глобальных событий (изменение состояния устройства, уведомления о внешних событиях и т.д.).

## Одиночный запрос: ResultSession

Класс `async::ResultSession<T>` подходит для сценариев «отправить запрос, дождаться единичного результата», например, чтение файла или отправка сетевого запроса. Это наиболее часто используемый асинхронный паттерн, работающий аналогично вызову асинхронной функции.

### Рабочая модель

Полный жизненный цикл `ResultSession` выглядит следующим образом:

1. **Создание**: функция модуля создает сессию с помощью `async::make<ResultSession<T>>(applet)`, при этом сессия автоматически привязывается к текущему `Applet`.
2. **Настройка**: через `session->client()` получается доступ к объекту клиента для установки необходимых для задачи параметров на чистом C++.
3. **Отправка**: вызывается `session->request(resolver)` для отправки задачи, после чего в JavaScript мгновенно возвращается `Promise`.
4. **Выполнение**: фреймворк передает метод `resolve()` клиента **асинхронному исполнителю** (по умолчанию — фоновому пулу потоков).
5. **Возврат результата**: после завершения `resolve()` результат **автоматически перенаправляется обратно в UI-поток**, где инициируется resolve или reject для `Promise`.
6. **Очистка**: объект сессии автоматически уничтожается после возврата результата либо очищается при выходе из `Applet`.

::: important Требования изоляции класса Client
Класс клиента (то есть шаблонный параметр `T`) работает в асинхронном контексте и **не должен содержать или использовать какие-либо объекты, взаимодействующие с JavaScript**, включая `JsValue`, `Applet *` и любые другие объекты, принадлежащие исключительно UI-потоку.

Класс клиента должен быть **чистым модулем обработки данных на C++**, хранящим только типы данных, необходимые для выполнения задачи (например, `String`, `int` или пользовательские структуры), и выполнять всю работу внутри метода `resolve()`. Все взаимодействия между UI-потоком и асинхронным потоком фреймворк обрабатывает автоматически.
:::

### Базовое использование

Сначала определите класс клиента, реализовав метод `resolve()`. Этот метод вызывается в асинхронном контексте и возвращает результат, завернутый в `async::Result<T>`:

```cpp
#include "gx_async.h"
#include "gx_file.h"

using namespace gx;

// Класс клиента: чистая обработка данных на C++, без хранения каких-либо JS-объектов
class ReadTextClient {
public:
    void setPath(const String &path) { m_path = path; }

    // Вызывается в асинхронном контексте, возвращает результат операции
    async::Result<String> resolve() {
        File file(m_path);
        if (!file.open(File::ReadOnly | File::Text))
            return async::Status(300);  // Ошибка ввода-вывода (IO error)
        int size = int(file.size());
        String text(size);
        text.resize(file.read(text.data(), size));
        return text;  // Успех: возвращаем содержимое файла
    }

    // Опционально: пользовательское сообщение об ошибке (используется при отклонении Promise)
    static const char *errorMessage(async::Status status) {
        switch (status.value()) {
        case 300: return "io error";
        default:  return "unknown error";
        }
    }

private:
    String m_path;  // Абсолютный путь, прошедший проверку безопасности
};
```

Затем создайте сессию в функции модуля и верните `Promise`. Внимание: путь, переданный из JavaScript, **обязательно** должен пройти проверку безопасности с помощью `Applet::resolveUri()`, нельзя слепо доверять строке от приложения:

```cpp
static JsValue readText(JsCtx ctx) {
    Applet *applet = Applet::current(ctx.vm());
    if (!applet || ctx.argc() < 1 || !ctx.arg(0).isObject())
        return {};

    // ✅ Безопасно: проверка и преобразование пути через resolveUri
    auto uri = applet->resolveUri(ctx.arg(0)["uri"].toString());
    if (uri.empty())
        return {};  // Ошибка проверки URI, доступ запрещен

    using Session = async::ResultSession<ReadTextClient>;
    auto *session = async::make<Session>(applet);
    session->client().setPath(uri);  // Передаем проверенный безопасный путь

    // Передаем асинхронную задачу вместе с полным объектом options для совместимости с интерфейсом колбэков QuickApp
    session->request(ctx.arg(0));
    return session->promise();
}
```

::: tip Зачем передавать `ctx.arg(0)`?
Метод `request()` принимает весь объект `options`, переданный со стороны JavaScript (то есть `ctx.arg(0)`), для автоматической адаптации к обоим [стилям вызовов асинхронных интерфейсов QuickApp](/api/README.md#快应用异步接口):

- Если `options` содержит свойства `success`, `fail` или `complete`, это интерпретируется как **стиль колбэков (callback style)**: соответствующая функция вызывается напрямую, а `request()` не возвращает значимого значения.
- В противном случае это интерпретируется как **стиль Promise (Promise style)**: создается новый `Promise`, а `session->promise()` возвращает этот объект для использования вызывающей стороной через `await`.

Это позволяет одной и той же реализации на C++ без какого-либо дополнительного кода поддерживать как стандартные интерфейсы колбэков QuickApp, так и современные интерфейсы Promise/async-await. Если вы уверены, что поддерживается только Promise-стиль, можно передать пустое значение `{}`.
:::

::: danger Не пропускайте проверку URI
Использование строки, переданной непосредственно из JavaScript, в качестве пути к файлу является серьезной уязвимостью безопасности:

```cpp
// ❌ Опасно! Обход проверки безопасности путей песочницы
session->client().setPath(ctx.arg(0)["uri"].toString());
```

Злонамеренное приложение может получить доступ к файловой системе вне песочницы с помощью обхода путей (path traversal, например `../../etc/passwd`). Все пути, поступающие из JavaScript, **должны** проходить процедуру дезинфекции через `Applet::resolveUri()`. Она обнаруживает атаки с обходом путей, несанкционированный кросс-аппликационный доступ и недопустимые форматы URI, а в случае неудачи возвращает пустую строку.
:::

Использование на стороне JavaScript:

```javascript
import file from '@system.file'

async function loadConfig() {
    try {
        const text = await file.readText({
          uri: 'internal://files/config.json'
        })
        console.log('config:', text)
    } catch (err) {
        console.error('read failed:', err.message)
    }
}
```

### Ошибки и коды состояния

Класс `async::Status` инкапсулирует целочисленный код состояния: `0` (или `async::OK`) означает успех, а остальные значения являются пользовательскими кодами ошибок бизнес-логики:

```cpp
// Успех: возвращаем значение напрямую, код состояния автоматически становится OK
return async::Result<String>{std::move(content)};
// Ошибка: возвращается только код состояния, поле значения игнорируется
return async::Status(404);
// Одновременная передача частичного результата и статуса, отличного от OK (например, HTTP 206 Partial Content)
return async::Result<ByteArray>{
  std::move(partialData),
  async::Status(206)
};
```

Когда `resolve()` возвращает статус ошибки, `Promise` отклоняется (reject), и блок `catch` в JavaScript получает объект ошибки, содержащий поля `message` и `code`. Поле `message` берется из статического метода `errorMessage()` класса клиента.

Метод `errorMessage()` поддерживает несколько сигнатур, которые фреймворк распознает автоматически:

```cpp
// Вариант 1: принимает Status (рекомендуется, лаконично)
static const char *errorMessage(async::Status status);

// Вариант 2: принимает полный Result, позволяя генерировать сообщение на основе значения и статуса
static String errorMessage(const async::Result<MyType> &result);
```

Если у класса клиента не определен метод `errorMessage()`, фреймворк использует стандартное сообщение по умолчанию: `"unknown async error"`.

### Типы значений и преобразование в JavaScript

Значение, возвращаемое методом `resolve()`, не передается в JavaScript в сыром виде: фреймворк автоматически преобразует тип C++ в `JsValue` с помощью функции `js_cast()`, после чего инициирует резолв `Promise`. Этот процесс происходит внутри фреймворка и выглядит «прозрачным», однако на практике он опирается на набор **неявных соглашений**: корректно преобразованы могут быть только типы, для которых реализована специализация `js_cast()`. Для пользовательских перечислений (enum), структур и других типов необходимо явно настроить отношения преобразования, иначе компиляция завершится с ошибкой.

#### Встроенные поддерживаемые типы

Следующие типы могут использоваться непосредственно в качестве шаблонных параметров `Result<T>` без каких-либо дополнительных действий:

| Тип C++ | Соответствующий тип JavaScript | Примечания |
| --- | --- | --- |
| `int`, `double`, `float` | `number` | Прямое сопоставление чисел |
| `bool` | `boolean` | Прямое сопоставление логических значений |
| `String`, `StringView`, `const char *` | `string` | Прямое сопоставление строк |
| `ByteArray` | `ArrayBuffer` | Бинарные данные |
| `JsonValue` | `object` / `array` | JSON-объект или массив |
| [`std::vector<T>`](https://en.cppreference.com/w/cpp/container/vector) | `Array` | Массив, элементы преобразуются рекурсивно (`T` также должен быть конвертируемым) |
| `JsValue` | Любой | Передается напрямую без преобразований |
| `void` (т.е. `Result<void>`) | `undefined` | Без возвращаемого значения |

Для всех этих типов во фреймворке JsVM встроены специализации `js_cast<T>()`. Часть из них — это типы, из которых можно напрямую сконструировать `JsValue`, а другая часть реализует логику преобразования через специализацию.

#### Добавление поддержки преобразования для пользовательских типов

Если используемый тип отсутствует в приведенном выше списке, компилятор выдаст ошибку о невозможности построения `JsValue`. Существует два способа решить эту проблему:

**Способ 1: Определение функции-члена `operator JsValue()`**

Это подходит для пользовательских структур, определение которых вы можете изменить. Преимущество заключается в том, что логика преобразования встроена в определение типа и тесно с ним связана:

```cpp
struct DeviceInfo {
    String model;
    int version;

    // Преобразование структуры в объект JavaScript
    // Внимание: преобразование выполняется в UI-потоке, где доступен валидный контекст JsVM
    operator JsValue() const {
        JsVM &vm = JsVM::current();
        JsValue obj = vm.newObject();
        obj["model"] = JsValue(model);
        obj["version"] = JsValue(version);
        return obj;
    }
};
```

После этого определения `Result<DeviceInfo>` можно использовать напрямую:

```cpp
async::Result<DeviceInfo> resolve() {
    return DeviceInfo{"ModelX", 3};  // Фреймворк автоматически вызывает operator JsValue()
}
```

Такие API, как `JsVM::current()` и `vm.newObject()`, используемые внутри `operator JsValue()`, относятся к слою моста JsVM. Подробнее см. в [Документации по разработке нативных модулей](./native-module.md#创建与返回对象).

**Способ 2: [Специализация](https://en.cppreference.com/w/cpp/language/template_specialization) `js_cast<T>` в пространстве имен `gx`**

Подходит для случаев, когда определение исходного типа изменить невозможно (например, типы из внешних определений или перечисления):

```cpp
// При необходимости объявите специализацию перед использованием
template<>
JsValue gx::js_cast<ConnectionState>(const ConnectionState &x);

// Специализация внутри пространства имен gx
template<>
JsValue gx::js_cast<ConnectionState>(const ConnectionState &x) {
    switch (x) {
    case ConnectionState::Connected:    return "connected";
    case ConnectionState::Connecting:   return "connecting";
    case ConnectionState::Disconnected: return "disconnected";
    default:                            return "unknown";
    }
}
```

После завершения специализации и `Result<ConnectionState>`, и `Signal<ConnectionState>` будут работать корректно.

::: tip Упрощенный подход для целочисленных перечислений
Если значения перечисления напрямую соответствуют целым числам, ручное преобразование в `int` внутри `resolve()` является самым простым вариантом, не требующим никаких специализаций:

```cpp
async::Result<int> resolve() {
    return async::Result<int>{int(myEnum)};
}
```
:::

#### Накладные расходы на преобразование во время выполнения

Функция `js_cast()` выполняется **после** того, как асинхронный результат передан обратно в UI-поток, а не в асинхронном потоке. Накладные расходы времени на преобразование полностью приходятся на UI-поток, поэтому для сложных структур необходимо обеспечивать достаточную скорость во избежание пропусков кадров (фризов). Реальные издержки для различных типов:

- **Типы с нулевыми накладными расходами**: `int`, `double`, `bool`, `String`, `const char *` сопоставляются напрямую через конструкторы `JsValue`, без дополнительных копирований или выделений памяти в куче. Способ `operator JsValue()` и специализация `js_cast<T>` также инлайнятся на этапе компиляции, не имея виртуальных вызовов или промежуточных уровней.
- **Типы с линейными накладными расходами**: `std::vector<T>` требует поэлементного вызова `setIndex()`, накладные расходы пропорциональны количеству элементов. Если возвращаемая структура представляет собой объект с фиксированными полями, предпочтительнее вручную сконструировать JS-объект через `operator JsValue()`, так как это эффективнее и читаемее массивов.
- **Типы с обходом дерева**: `JsonValue` при преобразовании рекурсивно обходит всю древовидную структуру, поочередно конструируя узлы JavaScript, что делает его самым ресурсоемким среди встроенных типов. Если структура данных известна на этапе компиляции, `operator JsValue()` для прямого конструирования объектов обычно работает быстрее и не имеет издержек сборки самого `JsonValue`.
- **Пользовательские структуры**: если используется `operator JsValue()` или специализация `js_cast()`, производительность преобразования зависит от накладных расходов на конвертацию каждого поля-члена, то есть от сложности конструирования объекта.

::: tip Простое правило оценки
Если ваша асинхронная структура данных проста (числа, простые структуры/объекты или небольшой `JsonValue`), накладные расходы на преобразование обычно не влияют на плавность UI.
:::

#### Отсутствие промежуточного слоя сериализации

Некоторые асинхронные фреймворки требуют обязательной сериализации результатов в JSON или другой самоописывающийся формат при передаче данных между рабочим (worker) потоком и UI-потоком с последующей десериализацией в UI-потоке. Это делается для обеспечения «стирания типов» при межпоточной передаче, однако платой за это являются постоянные издержки на конкатенацию, передачу и парсинг строк (или потоков бинарных данных) при каждом вызове. Хуже того, это может порождать несколько копий данных (промежуточные сериализованные данные, исходные данные и т.д.).

Асинхронный фреймворк **не зависит от промежуточного слоя сериализации.** Результаты передаются между потоками в виде нативных значений C++ через `async::Result<T>`, полностью минуя процесс сериализации:

```
worker thread                  UI thread
resolve(Result<MyType>{...}) → js_cast(result.value()) → JsValue (JavaScript)
                  ↑
             Прямое перемещение в памяти, без JSON-строк
```

Функция `js_cast()` выполняется только тогда, когда результат уже безопасно возвращен в UI-поток. Ее задача — смаппить значения C++ во внутреннее представление движка JavaScript, а не выступать в роли протокола межпоточной коммуникации.

Если вы сознательно выбираете `JsonValue` в качестве шаблонного параметра `Result<T>` (для снижения раздувания шаблонного кода), вы вводите накладные расходы на **построение и обход дерева** `JsonValue`, а не на строковую сериализацию. Сам `JsonValue` также представляет собой древовидную структуру в памяти, а не текстовый формат.

#### Объем шаблонного кода

`ResultSession<T>` является шаблонным классом, и компилятор генерирует отдельную копию кода для каждого уникального типа клиента `T`. Тем не менее, фреймворк вынес подавляющую часть логики, не зависящей от `T` (такую как управление `Promise`, доставка событий, привязка жизненного цикла `Applet`), в нешаблонный базовый класс `detail::ResultSession`. Таким образом, реальный объем дополнительного кода для каждого `T` в основном сосредоточен в тонком адаптере `Resolver`.

Тем не менее, если в проекте присутствует **огромное количество мелкозернистых клиентских типов, используемых всего по одному разу**, накопившееся число инстациаций все равно может привести к заметному увеличению объема кода.

Распространенным способом минимизации этого является использование `JsonValue` в качестве механизма стирания типов, объединяя несколько разрозненных мелких функций в единый клиентский класс:

```cpp
// До объединения: каждый оператор — это независимый класс клиента + независимая инстациация шаблона
struct GetVersionClient { ... };   // ResultSession<GetVersionClient>
struct GetModelClient   { ... };   // ResultSession<GetModelClient>
struct GetSerialClient  { ... };   // ResultSession<GetSerialClient>

// После объединения: разделение одной и той же инстациации шаблона, различение операций во время выполнения
struct DeviceQueryClient {
    enum Kind { Version, Model, Serial } kind;

    // Здесь для примера используется диспетчеризация через switch, на практике также можно использовать указатели на функции.
    // Однако не используйте BaseClient вместе с переопределением resolve() в производных классах для реализации полиморфизма:
    // это вызовет большее раздувание таблицы виртуальных методов (vtable), чем вариант с указателями на функции.
    async::Result<JsonValue> resolve() {
        switch (kind) {
        case Kind::Version: return JsonValue{getVersion()};
        case Kind::Model:   return JsonValue{getModel()};
        case Kind::Serial:  return JsonValue{getSerial()};
        }
    }
};

// Три функции модуля совместно используют единственную инстациацию ResultSession<DeviceQueryClient>
static JsValue getVersion(JsCtx ctx) {
    using Session = async::ResultSession<DeviceQueryClient>;
    auto *session = async::make<Session>(applet);
    session->client().kind = DeviceQueryClient::Version;
    return session->request(ctx.arg(0));
}
```

Цена такого подхода заключается в том, что возвращаемый тип деградирует до `JsonValue`, что влечет за собой дополнительные накладные расходы на преобразование во время выполнения (см. выше). Поэтому он подходит для сценариев с **маленьким объемом данных и большим количеством функций**, позволяя обменять небольшие накладные расходы времени выполнения на значительную выгоду в размере бинарного кода. Для операций с большим объемом данных или чувствительных к производительности следует по-прежнему сохранять независимые строго типизированные классы клиентов.

### Пользовательский асинхронный контекст

По умолчанию метод `session->request()` отправляет `resolve()` асинхронному исполнителю фреймворка — обычно это фоновый пул потоков. Однако в некоторых сценариях требуется использовать другой асинхронный контекст, например, собственный цикл событий или механизм мультиплексирования AIO, которые не должны расходовать ресурсы дополнительных потоков.

В этом случае можно пропустить `request()` и вручную контролировать процесс асинхронного выполнения, а классу клиента даже не потребуется реализовывать функцию выполнения `resolve()`. Ключевой момент: **после завершения работы в асинхронном контексте вызовите `session->resolve()`, чтобы отправить результат обратно в UI-поток**.

```cpp
// Класс клиента: не требует реализации resolve(), так как пул потоков по умолчанию не используется
struct FirmwareCheckClient {
    // Определяем только errorMessage() для описания ошибок
    static const char *errorMessage(async::Status status) {
        switch (status.value()) {
        case 1: return "firmware not found";
        case 2: return "check failed";
        default: return "unknown error";
        }
    }
};

static JsValue checkFirmwareUpdate(JsCtx ctx) {
    Applet *applet = Applet::current(ctx.vm());
    if (!applet || ctx.argc() < 1) return {};

    using Session = async::ResultSession<FirmwareCheckClient>;
    auto *session = async::make<Session>(applet);
    auto version = ctx.arg(0).asString();

    // Ручная установка резолвера (без вызова request, без использования пула потоков по умолчанию)
    session->setResolver(ctx.arg(0));
    JsValue promise = session->promise();

    // Отправка в собственный поток драйвера оборудования
    HardwareDriver::checkUpdate(
        version,
        // Колбэк может вызываться из любого потока — фреймворк автоматически перенаправит его в UI-поток
        [session](bool available) {
            session->resolve<bool>(available);
        },
        [session](int errorCode) {
            session->resolve<bool>(async::Status(errorCode));
        }
    );

    return promise;
}
```

 principales различия здесь:
- `request()` одновременно выполняет два действия: «установка резолверов» и «отправка асинхронному исполнителю»;
- В ручном режиме вам нужно самостоятельно вызвать `session->setResolver()` для настройки цели ответа, а затем в произвольный момент времени отправить результат или статус ошибки через `session->resolve()`.

Метод `resolve()` потокобезопасен: он упаковывает результат в событие и перенаправляет его обратно в UI-поток, после чего завершает резолв `Promise`.

::: tip Когда использовать пользовательский контекст
- Низкоуровневый драйвер уже предоставляет интерфейс колбэков, и вы не хотите создавать дополнительные потоки: просто вызывайте `resolve` прямо в колбэке драйвера.
- Необходимо интегрироваться с существующим циклом событий AIO/epoll: вызывайте `resolve` в колбэке завершения события.
- Требуется последовательное (serial) выполнение (операции должны идти строго по порядку): используйте собственный планировщик очереди задач, а по завершении вызывайте `resolve`.

Главное — убедиться, что метод `session->resolve()` в итоге вызывается ровно один раз. Фреймворку все равно, из какого потока был доставлен результат.
:::

### Семантика типов значений

Поскольку значение `async::Result<T>`, возвращаемое методом `resolve()` (или доставляемое вручную через пользовательский асинхронный контекст), пересылается в UI-поток для последующего преобразования в `JsValue`, тип данных `T` **обязан поддерживать перемещение (move-able)**. Все встроенные поддерживаемые типы удовлетворяют этому требованию. Для пользовательских типов:
- Если это структура, состоящая исключительно из полей со встроенной поддержкой, стандарт C++ гарантирует ее способность к перемещению.
- Если вы используете «голые» (raw) указатели и самостоятельно контролируете их владение, вам необходимо корректно реализовать [конструктор перемещения](https://en.cppreference.com/w/cpp/language/move_constructor).
- [Тривиальные типы](https://en.cppreference.com/w/cpp/named_req/TrivialType) (например, чистые структуры C, перечисления и т.д.) по умолчанию соответствуют семантике типов значений.

Стоит отметить, что нетривиальные типы обычно содержат ресурсы в куче (heap), и следующий код может столкнуться с проблемами пикового потребления памяти:

```cpp
auto *session = getFetchLargeDataSession();
std::vector<uint32_t> data = fetchDataFromNetwork(url);
session->resolve<decltype(data)>(data);  // Произойдет полное копирование data
```
Это происходит потому, что параметры метода `session->resolve()` передаются по значению, и при передаче `data` вызывается [конструктор копирования](https://en.cppreference.com/w/cpp/language/copy_constructor), что приводит к созданию полной копии. Если объем данных `data` велик, это удвоит потребление памяти. В таких случаях появляется следующее предупреждение компилятора:
```
'...' is deprecated:
avoid use copy semantics of Result<T> if T is not trivially copyable
```
Правильный подход заключается в явном включении семантики перемещения с помощью [`std::move()`](https://en.cppreference.com/w/cpp/utility/move):

```cpp
auto *session = getFetchLargeDataSession();
std::vector<uint32_t> data = fetchDataFromNetwork(url);
session->resolve<decltype(data)>(std::move(data));  // Используем семантику перемещения
```

### Контроль тайм-аута

Для асинхронных операций, которые могут долго не отвечать, используйте `async::make_timeout()`, чтобы добавить защиту по тайм-ауту для сессии. По истечении таймаута `Promise` будет автоматически отклонен (reject), что предотвратит зависание стороны JavaScript насовсем.

Следующий фрагмент кода демонстрирует базовый пример использования контроля тайм-аута в сетевых запросах:

```cpp
static JsValue fetchData(JsCtx ctx) {
    Applet *applet = Applet::current(ctx.vm());
    if (!applet || ctx.argc() < 1) return {};

    String url = ctx.arg(0)["url"].asString();
    int timeoutMs = ctx.arg(0)["timeout"].asInt(5000);

    using Session = async::ResultSession<HttpClient>;
    auto *session = async::make<Session>(applet);
    session->client().setUrl(url);
    session->setResolver(ctx.arg(0));
    JsValue promise = session->promise();

    // Создание защиты по таймауту: автоматический reject Promise по истечении времени
    auto handle = async::make_timeout(session, timeoutMs,
        [](Session *s) {
            // Обработка таймаута: здесь следует отменить выполняющуюся асинхронную операцию
            s->fulfill(async::Status(408));  // 408 Request Timeout
            
        });

    // Перемещение handle в асинхронный контекст выполнения
    NetworkDriver::fetch(url,
        [handle = std::move(handle)](auto &response) {
            // Если таймаут уже истек, вызов resolve будет безопасно проигнорирован
            handle->resolve<String>(std::move(response.body));
        });

    return promise;
}
```

#### Принцип работы

Ключевой рабочий процесс `make_timeout()`:

1. Данные клиента сессии `session` **перемещаются** в во внутренний класс, после чего доступ к `session->client()` запрещен.
2. Запускается однократный таймер, возвращающий дескриптор `SharedRef<SingleTimer>`.
3. **Нормальный путь**: до истечения таймаута вызывается `handle->resolve()`, внутри которого атомарно забирается владение сессией и отправляется событие результата. Позже при срабатывании таймера обнаруживается, что сессия уже пуста, и никаких действий не предпринимается.
4. **Путь по таймауту**: таймер срабатывает и выполняет колбэк **в UI-потоке**, где разработчик вызывает `session->fulfill()` для передачи статуса ошибки; после возврата из колбэка таймер отвечает за удаление сессии (`delete session`).
5. **Выход из приложения**: при уничтожении `Applet` таймер автоматически отвязывается, сессия удаляется, а колбэк не вызывается.

Этот механизм особенно полезен в сценариях, где асинхронная операция не имеет встроенной поддержки таймаутов (как в реализации некоторых сетевых запросов). Как известно, корректная реализация защиты по таймауту бывает сложной задачей, поскольку требует правильной обработки условий гонки (race conditions) и безопасности жизненного цикла на всех путях выполнения.

`make_timeout()` опирается на следующие предпосылки для обеспечения безопасности:
- Тип клиента (т.е. `T` в `ResultSession<T>`) **обязан поддерживать перемещение**, что можно считать историческим ограничением.
- Асинхронная операция должна поддерживать безопасную отмену в UI-потоке, что подразумевает удаление слушателя задачи и освобождение ссылки на `handle`.

#### Поток колбэка и `fulfill()`

Колбэк таймаута (третий параметр `make_timeout()`) **всегда выполняется в UI-потоке**, поскольку он инициируется таймером (`Timer`), а события таймера распределяются главным циклом событий.

Это обстоятельство определяет, что в колбэке **можно** использовать только `session->fulfill()`, но **нельзя** использовать `session->resolve()`:

| Метод | Допустимые потоки вызова | Влияние на сессию |
| --- | --- | --- |
| `resolve(result)` | Любой поток | Отправляет событие Consume, сессия обрабатывается в UI-потоке и **удаляется** |
| `fulfill(result)` | **Только UI-поток** | Напрямую диспатчит результат, сессия **не удаляется** |

Путь таймаута в `make_timeout()` отвечает за `delete session` силами самого таймера после завершения колбэка. Если вызвать `session->resolve()` внутри колбэка, он также отправит событие на удаление сессии, что приведет к **двойному освобождению памяти (double free)** совместно с операцией `delete` таймера, вызывая неопределенное поведение. Метод `fulfill()` лишь передает результат и не затрагивает жизненный цикл сессии, поэтому он является единственно безопасным выбором внутри колбэка.

`fulfill()` принимает `async::Result<R>` или напрямую `async::Status` (сокращение для случаев без результирующего значения):

```cpp
auto handle = async::make_timeout(session, 5000, [](Session *s) {
    s->fulfill(async::Status(408)); // Заполняем только статус ошибки
    // Или передаем значение и статус:
    s->fulfill(async::Result<String>{"partial", async::Status(206)});
    // ❌ Не вызывайте s->resolve(), это приведет к двойному освобождению сессии вместе с таймером
});
```

::: tip
Правило определения просто: где находится владение сессией, кто отвечает за ее удаление?
- **Нормальный путь**: `handle->resolve()` атомарно принимает владение сессией внутрь себя, сессия удаляется после обработки события Consume.
- **Колбэк таймута**: таймер владеет сессией и удаляет ее после завершения колбэка. Следовательно, в колбэке можно использовать только `fulfill()` для передачи результатов.
:::

#### Доступ к данным клиента

Если в колбэке тайм-аута требуется прочитать данные клиента для определения стратегии обработки ошибки, используйте расширенную сигнатуру колбэка `(Session *, const T &)`. **Не** вызывайте `session->client()` внутри колбэка — клиент уже перемещен в таймер:

```cpp
auto handle = async::make_timeout(session, 3000,
    [](Session *s, const HttpClient &client) { // Также можно использовать auto &client
        // ✅ Доступ к данным клиента через второй параметр
        LogWarn() << "request timeout: " << client.url();
        s->fulfill(async::Status(408));
    }
);
```

#### Управление жизненным циклом ресурсов

При наступлении тайм-аута вам необходимо отменить выполняющуюся асинхронную задачу в колбэке, чтобы освободить ссылку на `handle`. `SingleTimer` использует подсчет ссылок (reference counting) для управления жизненным циклом: если асинхронная операция удерживает ссылку на `handle`, но никогда не завершится, возникнет утечка памяти:

```cpp
auto task = AioTask::create();
auto handle = async::make_timeout(session, 5000,
    [task](auto *s) {
        task->cancel();     // Отменяем задачу, освобождая ссылку на handle
        s->fulfill(async::Status(408)); // Отклоняем Promise (reject)
    });

// Колбэк завершения задачи удерживает ссылку на handle
task->start([handle = std::move(handle)](auto &result) {
    handle->resolve(result);
});
```

::: important
Дескриптор `handle`, возвращаемый функцией `make_timeout()`, **обязан** удерживаться асинхронной задачей (в примере выше захвачен через лямбду), чтобы гарантировать, что таймер не будет уничтожен до завершения задачи. В противном случае тайм-аут сработает немедленно, вызвав колбэк и реджект `Promise`, из-за чего задача не сможет завершиться нормально.
:::

Подобные утечки памяти происходят по двум причинам:
1. **Утечка во фреймворке async**: ссылка на `handle` забыта, из-за чего сопутствующий объект сессии не может быть освобожден.
2. **Утечка низкоуровневой задачи**: сама асинхронная задача блокируется в незавершенном состоянии, и сопутствующие ресурсы также не очищаются.

### Автоматическая очистка при выходе из приложения

Когда `Applet` уничтожается (например, пользователь закрыл приложение, система выгрузила ресурсы), все привязанные к этому `Applet` асинхронные сессии автоматически очищаются:

- Вызывается метод `unbind()` сессии, который закрывает ее и освобождает ссылку на `Promise`.
- Если используется `make_timeout`, таймер также отвязывается, а внутренне удерживаемая сессия удаляется.
- `Promise` на стороне JavaScript никогда не получит resolve или reject, но поскольку к этому моменту само окружение JavaScript уже уничтожается, это безопасно.

Это означает, что вам **не нужно** вручную отслеживать и отменять асинхронные задачи — фреймворк гарантирует отсутствие следующих ситуаций:
- Доставка результатов в уже уничтоженный `Applet`, приводящая к обращению к висячим указателям (dangling pointers).
- Выполнение колбэков в уже освобожденном окружении JavaScript.
- Утечка асинхронных сессий после выхода из приложения.

В частности, когда фоновый поток вызывает `resolve()` для отправки результата в UI-поток, обработчик проверяет, остается ли `applet()` валидным. Если `Applet` уже уничтожен и `applet()` возвращает `nullptr`, фреймворк безопасно отбрасывает результат, не выполняя никаких операций с JavaScript.

::: tip Безопасный возврат из асинхронного контекста
Поскольку `resolve()` — это чистая доставка данных (через очередь событий), вызов `resolve()` в фоновом потоке не приведет к падению, даже если `Applet` уже уничтожен. Фоновому потоку не нужно заботиться о статусе жизнеспособности `Applet` — это обязанность фреймворка.
:::

Единственное, о чем следует помнить: если вы унаследовали `ResultSession` и добавили другие переменные-члены типа `JsValue`, вам потребуется очистить эти члены в методе `unbind()`, чтобы избежать утечек памяти:

```cpp
class MySession : public async::ResultSession<MyClient> {
public:
    void unbind() override {
        m_callbacks = {}; // Очищаем все удерживаемые JsValue во избежание утечек
        async::ResultSession::unbind(); // Вызываем очистку базового класса
    }

private:
    JsValue m_callbacks; // Член, требующий ручной очистки
};
```

::: important Продление жизненного цикла ResultSession
Если при выходе из приложения все еще существуют незавершенные асинхронные сессии, фреймворк очищает только ресурсы, связанные с приложением (такие как ссылки `Promise`, отношения привязки и т.д.), но **не уничтожает сам объект сессии**. Это выражается в том, что жизненный цикл `ResultSession` продлевается до момента завершения асинхронной операции.

Хотя само по себе это сделано ради обеспечения безопасности памяти, это приводит к преждевременному не освобождению части ресурсов. Поэтому асинхронные задачи должны гарантированно завершаться за ограниченное время и не могут зависать бессрочно.
:::

## Множественные запросы: ListenSession

API данного класса пока нестабильно и временно недоступно для использования.

## Широковещательная рассылка глобальных событий: async::Signal

Если событие C++ должно транслироваться **многим приложениям** (а не какому-то конкретному инициатору запроса), используйте `async::Signal<T>`. Оно осуществляет многоадресную рассылку («мультикаст») аппаратных или системных событий всем слушателям JavaScript, подписанным на него.

Назначение `async::Signal<T>` и `ResultSession` различается:

| Характеристика | ResultSession | Signal |
| --- | :---: | :---: |
| Направление связи | Один к одному (вызывающий → результат) | Один ко многим (источник событий → все подписчики) |
| Количество срабатываний | Одиночное | Многократное |
| Объект привязки | Один Applet | Между Applet |
| Область применения | Асинхронные запросы | Системные события, изменения состояний |

### Базовое использование

Предположим, существует событие изменения уровня заряда батареи, о котором необходимо уведомить всех подписчиков:

```cpp
// Определение глобального сигнала, обычно являющегося членом соответствующего сервиса
async::Signal<int> batteryChanged;

// Вызов сигнала при наступлении аппаратного события (может вызываться из любого потока)
void onBatteryLevelChanged(int newLevel) {
    batteryChanged(newLevel);  // Уведомление всех подписчиков
}
```

#### Подписка и отписка

Эта функция модуля позволяет стороне JavaScript подписаться на данный сигнал. Она также возвращает идентификатор привязки (binding ID), используемый стороной JavaScript для отписки:

```cpp
static JsValue subscribeBatteryChange(JsCtx ctx) {
    if (ctx.argc() < 1 || !ctx.arg(0).isFunction())
        return {};
    // Подписка возможна только в валидном окружении applet
    auto *applet = Applet::current(ctx.vm());
    if (applet == nullptr) return {};

    // Привязываем слот к приложению, подписка автоматически отменится при выходе из приложения
    auto *slot = batteryChanged.connect(ctx.arg(0));
    return applet->bindObject(slot); // Возвращаем ID слота для отписки из JS
}
```

Также необходимо реализовать функцию модуля для отписки. Независимо от типа `async::Signal`, реализация функции отвязки выглядит одинаково:

```cpp
static JsValue unsubscribeBatteryChange(JsCtx ctx) {
    auto *applet = Applet::current(ctx.vm());
    if (applet && ctx.argc()) {
        // slotId по умолчанию равен 0, его можно безопасно проигнорировать без выполнения действий
        auto slotId = ctx.arg(0).toInt();
        // После отвязки слота от applet также необходимо удалить объект слота
        delete applet->unbindObject<async::Slot>(slotId);
    }
    return {};
}
```

#### Экспорт в JavaScript

Достаточно определить [нативный модуль](./native-module.md) для экспорта этих функций:

```cpp
static JsModule *createBatteryModule(JsVM &vm) {
    auto mod = vm.newObject();
    // Модуль battery обычно также имеет функции вроде getLevel(), здесь они опущены
    mod["subscribe"] = subscribeBatteryChange;
    mod["unsubscribe"] = unsubscribeBatteryChange;
    return mod;
}
// Не забудьте импортировать модуль с помощью GX_JSVM_MODULE_IMPORT
GX_JSVM_MODULE(vendor_battery, "vendor.battery", createBatteryModule)
```

::: tip Переиспользование функции `unsubscribe`
Поскольку реализация функции отписки универсальна, вы можете определить одну общую функцию `unsubscribe` и импортировать ее в несколько модулей.
:::

Сторона JavaScript:

```js
import battery from '@vendor.battery'

const sid = battery.subscribe((level) => {
  console.log('battery level:', level)
})

// Вызов при необходимости отписаться
battery.unsubscribe(sid)
```

### Режимы доставки сигналов

`Signal` поддерживает два режима доставки, управляемых вторым параметром:

```cpp
// Обычный режим (по умолчанию): уведомление всех подписчиков
batteryChanged(newLevel, async::NormalSignal);

// Пропуск невидимых приложений: уведомление только передних видимых приложений для снижения избыточного расхода
batteryChanged(newLevel, async::SkipInvisible);
```

Режим `SkipInvisible` подходит для событий, имеющих смысл только тогда, когда интерфейс видим (например, уведомления об обновлении UI). Для событий, которые должны отслеживаться в фоне (например, предупреждение о низком заряде батареи), следует использовать стандартный `NormalSignal`.

### Типы значений сигналов

Параметр типа `T` в `Signal<T>` подчиняется тем же правилам преобразования, что и `ResultSession`: при срабатывании сигнала фреймворк преобразует значения C++ в аргументы JavaScript-колбэка через тот же механизм `js_cast()`. Такие встроенные типы, как `int`, `bool`, `String`, `JsonValue`, могут использоваться напрямую. Для передачи пользовательских структур или перечислений обратитесь к разделу [Типы значений и преобразование в JavaScript](#值类型与-javascript-转换).

## Инструкции по потокобезопасности

Модель потокобезопасности асинхронного фреймворка следует следующим правилам:

- **`resolve()` потокобезопасен**: `ResultSession::resolve()` и `SingleTimer::resolve()` могут вызываться из любого потока. Они доставляют результаты в UI-поток через систему событий и не взаимодействуют с объектами JavaScript напрямую.
- **`JsValue` не потокобезопасен**: Жизненный цикл `JsValue` управляется на основе подсчета ссылок, операции с которым не атомарны. Запрещено создавать, копировать, уничтожать или обращаться к `JsValue` в асинхронных потоках. Именно поэтому классам клиентов запрещено содержать `JsValue`.
- **Резолв `Promise` выполняется в UI-потоке**: Независимо от того, из какого потока был вызван `resolve()`, финальный колбэк JavaScript `Promise` всегда выполняется в UI-потоке, гарантируя безопасность операций с интерфейсом.
- **Уведомления `async::Signal` диспатчатся в UI-потоке**: Хотя `async::Signal::operator()` можно вызывать из разных потоков, JavaScript-колбэки всегда выполняются в UI-потоке.

Если классу клиента необходимо разделять состояние с UI-потоком (например, предоставлять флаг отмены), используйте атомарные операции [`std::atomic`](https://en.cppreference.com/w/cpp/atomic/atomic) или мьютексы для защиты общих данных:

```cpp
class CancellableClient {
public:
    void cancel() { m_cancelled.store(true); }

    async::Result<String> resolve() {
        for (int i = 0; i < 100 && !m_cancelled.load(); ++i) {
            // Выполнение пошаговой задачи с периодической проверкой флага отмены
            processChunk(i);
        }
        if (m_cancelled.load())
            return async::Status(499);  // Отменено клиентом
        return std::move(m_result);
    }

private:
    std::atomic_bool m_cancelled{false};
    String m_result;
};
```

В частности, многие типы значений фреймворка Glyphix **в рамках данного асинхронного фреймворка** могут безопасно передаваться между потоками, например:
- `String`: можно напрямую присваивать и читать в многопоточной среде без дополнительных механизмов синхронизации.
- `JsonValue`: этот класс также является типом-значением и обладает той же потокобезопасностью, что и `String`.
- `ByteArray`: аналогично `String`, поддерживает многопоточное использование.
- `SharedRef<T>`: сам по себе умный указатель с подсчетом ссылок может передаваться между потоками, но потокобезопасность управляемого объекта `T` зависит от его собственного определения.
- Не являющиеся владельцами типы вроде `String::View` **не могут** использоваться между потоками.

Именно поэтому во всех предыдущих примерах мы всегда напрямую захватывали и передавали такие типы, как `String`, между асинхронными контекстами без какой-либо специальной обработки и без применения механизмов синхронизации вроде мьютексов.

::: important
Потокобезопасность упомянутых выше типов фактически зависит от модели памяти конкретного асинхронного фреймворка, что означает, что они **не являются автоматически потокобезопасными** во всех сценариях. Асинхронный фреймворк в данном документе гарантирует это, но данное поведение нельзя экстраполировать на любые другие ситуации.
:::
