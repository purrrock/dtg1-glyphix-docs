# Разработка асинхронного функционала

В встраиваемых системах (embedded systems) многие операции требуют значительного времени: чтение из флеш-памяти, обращение к сети, ожидание ответа от аппаратного обеспечения. Если выполнять эти операции в потоке пользовательского интерфейса (UI-потоке, который также является потоком рендеринга), это приведет к зависанию UI и отсутствию отклика у приложения.

Glyphix решает эту проблему путем бесшовной интеграции асинхронных операций с механизмом `Promise` в JavaScript. Сторона C++ отвечает за реальную асинхронную логику (обычно в другом потоке или через событийную модель), сторона JavaScript ожидает результат с помощью `async/await` или `.then()`, в то время как UI остается плавным и отзывчивым во время ожидания.

## Основной механизм

Ядром асинхронной функциональности является модель «сессии» (Session). Когда инициируется асинхронный вызов из JavaScript, на стороне C++ создается **объект сессии** (`AsyncSession`), который немедленно возвращает `Promise` в JavaScript. Когда операция завершается, сессия инициирует резолв (resolve или reject) `Promise`, после чего на стороне JavaScript выполняются блоки `then/catch` или `await`.

Объект сессии привязан к вызвавшему его `Applet`. При выходе из приложения сессия автоматически очищается, и разработчику не нужно вручную управлять памятью.

Реализация асинхронного фреймворка находится в файле `gx_async.h` и инкапсулирована в пространстве имен `gx::async`. Фреймворк предоставляет несколько полезных утилит:
- **`async::ResultSession`**: используется для одиночных асинхронных запросов, подходит для чтения файлов, отправки сетевых запросов и т. д.
- **`async::make_timeout()`**: используется для создания однократного таймера и добавления функционала таймаута к отдельной сессии.
- **`async::Signal<T>`**: используется для глобальной рассылки событий, подходит для изменения состояния устройства, уведомлений о внешних событиях и т. д.

## Одиночные запросы: ResultSession

Класс `async::ResultSession<T>` подходит для сценариев «отправить запрос, дождаться единичного результата», например, чтение файла или выполнение сетевого запроса. Это наиболее часто используемый асинхронный паттерн, работающий по принципу вызова асинхронной функции.

### Рабочая модель

Полный жизненный цикл `ResultSession` выглядит следующим образом:

1. **Создание**: функция модуля создает сессию с помощью `async::make<ResultSession<T>>(applet)`, сессия автоматически привязывается к текущему `Applet`.
2. **Настройка**: через `session->client()` получается доступ к объекту клиента, где задаются чисто C++ параметры, необходимые для задачи.
3. **Отправка (Submit)**: вызывается `session->request(resolver)` для отправки задачи, после чего в JavaScript немедленно возвращается `Promise`.
4. **Выполнение**: фреймворк передает метод `resolve()` клиента **асинхронному исполнителю** (по умолчанию — фоновому пулу потоков) для выполнения.
5. **Возврат результата**: после завершения `resolve()` результат **автоматически планируется для возврата в UI-поток**, вызывая resolve или reject для `Promise`.
6. **Очистка**: объект сессии автоматически уничтожается после завершения возврата результата или автоматически очищается при выходе из `Applet`.

::: important Требования изоляции для класса Client
Класс клиента (то есть шаблонный параметр `T`) выполняется в асинхронном контексте и **не должен содержать или обращаться к каким-либо объектам, взаимодействующим с JavaScript**, включая `JsValue`, `Applet *` и любые другие объекты, специфичные для UI-потока.

Класс клиента должен быть **чистым блоком обработки данных на C++**, содержащим только типы данных со значениями, необходимыми для выполнения задачи (например, `String`, `int` или пользовательские структуры), и выполнять всю работу в методе `resolve()`. Все взаимодействия между UI-потоком и асинхронным потоком обрабатываются фреймворком автоматически.
:::

### Базовое использование

Сначала определите класс клиента, реализовав метод `resolve()`. Этот метод вызывается в асинхронном контексте и возвращает результат, обернутый в `async::Result<T>`:

```cpp
#include "gx_async.h"
#include "gx_file.h"

using namespace gx;

// Класс клиента: чистая обработка данных на C++, без хранения каких-либо JS-объектов
class ReadTextClient {
public:
    void setPath(const String &path) { m_path = path; }

    // Вызывается в асинхронном контексте, возвращает результат операции
    async::Result<String> resolve() {
        File file(m_path);
        if (!file.open(File::ReadOnly | File::Text))
            return async::Status(300);  // Ошибка ввода-вывода (IO error)
        int size = int(file.size());
        String text(size);
        text.resize(file.read(text.data(), size));
        return text;  // Успех: возвращаем содержимое файла
    }

    // Необязательно: пользовательское сообщение об ошибке (используется при отклонении Promise)
    static const char *errorMessage(async::Status status) {
        switch (status.value()) {
        case 300: return "io error";
        default:  return "unknown error";
        }
    }

private:
    String m_path;  // Абсолютный путь, прошедший проверку безопасности
};
```

Затем создайте сессию в функции модуля и верните `Promise`. Внимание: **необходимо** использовать `Applet::resolveUri()` для проверки безопасности пути, переданного из JavaScript, вместо того чтобы слепо доверять строке, предоставленной приложением:

```cpp
static JsValue readText(JsCtx ctx) {
    Applet *applet = Applet::current(ctx.vm());
    if (!applet || ctx.argc() < 1 || !ctx.arg(0).isObject())
        return {};

    // ✅ Безопасно: проверка и преобразование пути через resolveUri
    auto uri = applet->resolveUri(ctx.arg(0)["uri"].toString());
    if (uri.empty())
        return {};  // Ошибка проверки URI, доступ запрещен

    using Session = async::ResultSession<ReadTextClient>;
    auto *session = async::make<Session>(applet);
    session->client().setPath(uri);  // Передаем проверенный безопасный путь

    // Отправляем асинхронную задачу, передавая полный объект options для совместимости с интерфейсом обратных вызовов FastApp
    session->request(ctx.arg(0));
    return session->promise();
}
```

::: tip Зачем передавать `ctx.arg(0)`?
Метод `request()` принимает весь объект `options`, переданный со стороны JavaScript (то есть `ctx.arg(0)`), который используется для автоматической адаптации к двум [стилям вызова](/api/README.md#快应用异步接口) асинхронного интерфейса FastApp:

- Если `options` содержит любое из свойств `success`, `fail` или `complete`, это определяется как **стиль callback (обратного вызова)**. Вызывается соответствующая функция напрямую, а `request()` не возвращает значимого значения.
- В противном случае это определяется как **стиль Promise**. Создается новый `Promise`, а `session->promise()` возвращает этот объект для вызова через `await` на стороне вызывающего кода.

Это позволяет одной и той же реализации на C++ без какого-либо дополнительного кода одновременно поддерживать как стандартный интерфейс обратных вызовов FastApp, так и современные интерфейсы Promise/async-await. Если вы точно уверены, что поддерживается только стиль Promise, можно передать пустое значение `{}`.
:::

::: danger Не пропускайте проверку URI
Использование строки, переданной непосредственно из JavaScript, в качестве пути к файлу представляет собой серьезную уязвимость безопасности:

```cpp
// ❌ Опасно! Обход проверки безопасности путей песочницы
session->client().setPath(ctx.arg(0)["uri"].toString());
```

Злонамеренное приложение может получить доступ к файловой системе за пределами песочницы с помощью обхода путей (например, `../../etc/passwd`). Все пути, поступающие из JavaScript, **должны** проходить санитизацию через `Applet::resolveUri()`, который обнаруживает атаки обхода пути, несанкционированный кросс-аппликационный доступ и недопустимые форматы URI, возвращая пустую строку в случае сбоя проверки.
:::

Использование на стороне JavaScript:

```javascript
import file from '@system.file'

async function loadConfig() {
    try {
        const text = await file.readText({
          uri: 'internal://files/config.json'
        })
        console.log('config:', text)
    } catch (err) {
        console.error('read failed:', err.message)
    }
}
```

### Ошибки и коды состояния

`async::Status` инкапсулирует целочисленный код состояния. `0` (то есть `async::OK`) означает успех, а остальные значения являются пользовательскими кодами ошибок бизнес-логики:

```cpp
// Успех: возврат значения напрямую, код состояния автоматически равен OK
return async::Result<String>{std::move(content)};
// Ошибка: возвращается только код состояния, часть со значением игнорируется
return async::Status(404);
// Одновременная передача частичного результата и статуса, отличного от OK (например, HTTP 206 Partial Content)
return async::Result<ByteArray>{
  std::move(partialData),
  async::Status(206)
};
```

Когда `resolve()` возвращает статус ошибки, `Promise` отклоняется (rejected), и блок `catch` в JavaScript получает объект ошибки, содержащий поля `message` и `code`. Поле `message` берется из статического метода `errorMessage()` класса клиента.

`errorMessage()` поддерживает несколько сигнатур, которые фреймворк распознает автоматически:

```cpp
// Вариант 1: принимает Status (рекомендуется, лаконично)
static const char *errorMessage(async::Status status);

// Вариант 2: принимает полный Result, позволяет генерировать сообщение на основе значения и статуса
static String errorMessage(const async::Result<MyType> &result);
```

Если в классе клиента метод `errorMessage()` не определен, фреймворк использует стандартное сообщение `"unknown async error"`.

### Типы значений и преобразование в JavaScript

Значения, возвращаемые `resolve()`, не передаются в JavaScript «как есть». Фреймворк автоматически преобразует типы C++ в `JsValue` с помощью функции `js_cast()`, после чего инициирует резолв `Promise`. Этот процесс происходит внутри фреймворка и выглядит «прозрачным», но на самом деле он опирается на набор **неявных соглашений**: корректно преобразовываться могут только те типы, для которых реализована специализация `js_cast()`. Для пользовательских перечислений (enum), структур и других типов необходимо явно установить отношения преобразования, в противном случае сборка завершится ошибкой.

#### Встроенные поддерживаемые типы

Следующие типы могут использоваться непосредственно в качестве параметров шаблона `Result<T>` без каких-либо дополнительных действий:

| Тип C++ | Соответствующий тип JavaScript | Примечания |
| --- | --- | --- |
| `int`, `double`, `float` | `number` | Прямое сопоставление чисел |
| `bool` | `boolean` | Прямое сопоставление логических значений |
| `String`, `StringView`, `const char *` | `string` | Прямое сопоставление строк |
| `ByteArray` | `ArrayBuffer` | Бинарные данные |
| `JsonValue` | `object` / `array` | JSON-объект или массив |
| [`std::vector<T>`](https://en.cppreference.com/w/cpp/container/vector) | `Array` | Массив, элементы преобразуются рекурсивно (`T` также должен подлежать преобразованию) |
| `JsValue` | Любой | Передается напрямую, без преобразования |
| `void` (т. е. `Result<void>`) | `undefined` | Без возвращаемого значения |

Все эти типы имеют встроенные специализации `js_cast<T>()` во фреймворке JsVM. Часть из них — это типы, которые могут быть созданы непосредственно из `JsValue`, а другая часть реализует логику преобразования через специализацию.

#### Добавление поддержки преобразования для пользовательских типов

Если используемый тип отсутствует в списке выше, компилятор выдаст ошибку о том, что невозможно создать `JsValue`. Эту проблему можно решить двумя способами:

**Способ 1: Определение функции-члена `operator JsValue()`**

Этот способ подходит для пользовательских структур, определение которых вы можете изменить. Преимущество заключается в том, что логика преобразования встроена в определение типа и тесно с ним связана:

```cpp
struct DeviceInfo {
    String model;
    int version;

    // Преобразование структуры в объект JavaScript
    // Примечание: Преобразование выполняется в UI-потоке, где доступен легитимный контекст JsVM
    operator JsValue() const {
        JsVM &vm = JsVM::current();
        JsValue obj = vm.newObject();
        obj["model"] = JsValue(model);
        obj["version"] = JsValue(version);
        return obj;
    }
};
```

После определения `Result<DeviceInfo>` может использоваться напрямую:

```cpp
async::Result<DeviceInfo> resolve() {
    return DeviceInfo{"ModelX", 3};  // Фреймворк автоматически вызывает operator JsValue()
}
```

АПИ вроде `JsVM::current()` и `vm.newObject()`, используемые внутри `operator JsValue()`, принадлежат мостовому слою JsVM. Подробнее см. в [документации по разработке нативных модулей](./native-module.md#创建与返回对象).

**Способ 2: [Специализация](https://en.cppreference.com/w/cpp/language/template_specialization) `js_cast<T>` в пространстве имен `gx`**

Подходит для случаев, когда определение исходного типа не может быть изменено (например, типы или перечисления из внешних определений):

```cpp
// При необходимости объявите специализацию перед использованием
template<>
JsValue gx::js_cast<ConnectionState>(const ConnectionState &x);

// Специализация внутри пространства имен gx
template<>
JsValue gx::js_cast<ConnectionState>(const ConnectionState &x) {
    switch (x) {
    case ConnectionState::Connected:    return "connected";
    case ConnectionState::Connecting:   return "connecting";
    case ConnectionState::Disconnected: return "disconnected";
    default:                            return "unknown";
    }
}
```

После завершения специализации как `Result<ConnectionState>`, так и `Signal<ConnectionState>` будут работать нормально.

::: tip Простой способ для целочисленных перечислений (enum)
Если значения перечисления напрямую соответствуют целым числам, ручное преобразование в `int` внутри `resolve()` — это самый простой путь, не требующий никаких специализаций:

```cpp
async::Result<int> resolve() {
    return async::Result<int>{int(myEnum)};
}
```
:::

#### Накладные расходы на выполнение преобразования

Функция `js_cast()` выполняется **после** того, как асинхронный результат доставлен обратно в UI-поток, а не в асинхронном потоке. Затраты времени на преобразование происходят полностью в UI-потоке, и для сложных структур необходимо убедиться, что преобразование выполняется достаточно быстро, чтобы избежать пропусков кадров (фризов). Реальные издержки для различных типов выглядят следующим образом:

- **Типы с нулевыми накладными расходами**: `int`, `double`, `bool`, `String`, `const char *` сопоставляются напрямую через конструкторы `JsValue`, без дополнительных копирований или выделений памяти в куче. Подход `operator JsValue()` и специализации `js_cast<T>` также инлайнятся на этапе компиляции, не имея виртуальных вызовов или косвенных уровней.
- **Типы с линейными накладными расходами**: `std::vector<T>` требует вызова `setIndex()` для каждого элемента, затраты пропорциональны количеству элементов. Если возвращаемая структура представляет собой объект с фиксированными полями, предпочтительнее вручную конструировать JS-объект через `operator JsValue()`, что эффективнее и читаемее массива.
- **Типы с древовидным обходом**: `JsonValue` во время преобразования рекурсивно обходит всю древовидную структуру, поочередно конструируя узлы JavaScript. Это самый затратный тип среди встроенных. Если структура данных известна на этапе компиляции, прямое создание объекта через `operator JsValue()` обычно работает быстрее и не имеет затрат на построение самого `JsonValue`.
- **Пользовательские структуры**: При использовании `operator JsValue()` или специализации `js_cast()` производительность преобразования зависит от накладных расходов на преобразование каждого типа члена структуры, то есть от сложности конструирования объекта.

::: tip Простой критерий оценки
Если ваша асинхронная структура данных проста (числа, простые объекты структур или небольшой `JsonValue`), то накладные расходы на преобразование обычно не влияют на плавность UI.
:::

#### Отсутствие промежуточного слоя сериализации

Некоторые асинхронные фреймворки требуют, чтобы при передаче данных между потоком worker и UI-потоком результат сначала сериализовался в JSON или другой самоописывающийся формат, а затем десериализовался в UI-потоке. Это делается для реализации «стирания типов» при межпоточной передаче, но ценой за это являются затраты на конкатенацию, передачу и парсинг строк (или потоков бинарных данных) при каждом вызове. Хуже того, это может привести к созданию нескольких копий данных (промежуточные сериализованные данные и исходные данные и т. д.).

Асинхронный фреймворк **не зависит от промежуточного слоя сериализации.** Результаты перемещаются между потоками в виде нативных значений C++ через `async::Result<T>`, полностью обходя процесс сериализации:

```
worker thread                  UI thread
resolve(Result<MyType>{...}) → js_cast(result.value()) → JsValue (JavaScript)
                  ↑
             Прямое перемещение памяти, без JSON-строк
```

`js_cast()` выполняется только после того, как результат безопасно возвращен в UI-поток. Его обязанность — сопоставить значения C++ с внутренним представлением движка JavaScript, а не выступать в роли протокола межпоточной связи.

Если вы осознанно выбираете `JsonValue` в качестве шаблонного параметра `Result<T>` (для смягчения раздувания шаблонного кода), то вы вносите затраты на **построение и обход дерева** `JsonValue`, а не на сериализацию строк. Сам по себе `JsonValue` также представляет собой древовидную структуру в памяти, а не текстовый формат.

#### Объем шаблонного кода

`ResultSession<T>` является шаблонным классом, и компилятор будет генерировать отдельный экземпляр кода для каждого уникального типа клиента `T`. Тем не менее, фреймворк вынес подавляющее большинство логики, не зависящей от `T` (такой как управление `Promise`, доставка событий, привязка жизненного цикла `Applet`), в нешаблонный базовый класс `detail::ResultSession`. Таким образом, объем дополнительного кода для каждого `T` в основном сосредоточен в тонком адаптерном слое `Resolver`.

Однако, если в проекте присутствует **большое количество мелкозернистых типов клиентов, используемых только один раз**, накопленное количество инстанциаций все равно приведет к заметному росту объема кода.

Распространенным способом минимизации этого является использование `JsonValue` в качестве среды стирания типов, объединяя несколько разрозненных мелких функций в единый тип клиента:

```cpp
// До объединения: каждая операция представляет собой независимый класс клиента + независимая инстанциация шаблона
struct GetVersionClient { ... };   // ResultSession<GetVersionClient>
struct GetModelClient   { ... };   // ResultSession<GetModelClient>
struct GetSerialClient  { ... };   // ResultSession<GetSerialClient>

// После объединения: общий экземпляр шаблона, операции различаются во время выполнения
struct DeviceQueryClient {
    enum Kind { Version, Model, Serial } kind;

    // Здесь для примера используется switch-диспетчеризация, на практике можно использовать и указатели на функции. 
    // Однако не используйте BaseClient вместе с переопределением resolve() в производных классах для реализации полиморфизма,
    // так как это приведет к большему раздуванию таблицы виртуальных функций (vtable), чем вариант с указателями на функции.
    async::Result<JsonValue> resolve() {
        switch (kind) {
        case Kind::Version: return JsonValue{getVersion()};
        case Kind::Model:   return JsonValue{getModel()};
        case Kind::Serial:  return JsonValue{getSerial()};
        }
    }
};

// Три функции модуля совместно используют единственную инстанциацию ResultSession<DeviceQueryClient>
static JsValue getVersion(JsCtx ctx) {
    using Session = async::ResultSession<DeviceQueryClient>;
    auto *session = async::make<Session>(applet);
    session->client().kind = DeviceQueryClient::Version;
    return session->request(ctx.arg(0));
}
```

Цена такого подхода заключается в том, что возвращаемый тип деградирует до `JsonValue`, что влечет за собой дополнительные накладные расходы на преобразование во время выполнения (см. выше). Поэтому он подходит для сценариев с **небольшим объемом данных и большим количеством функций**, где за счет небольших накладных расходов во время выполнения достигается значительный выигрыш в размере кода. Для операций с большими объемами данных или чувствительных к производительности по-прежнему следует сохранять независимые строго типизированные классы клиентов.

### Пользовательские асинхронные контексты

По умолчанию `session->request()` отправляет `resolve()` в **асинхронный исполнитель** фреймворка, которым обычно является фоновый пул потоков. Однако в некоторых сценариях требуется использование другого асинхронного контекста, например, пользовательского цикла событий или механизма мультиплексирования AIO, которые не должны потреблять дополнительные ресурсы потоков.

В этом случае можно пропустить `request()` и вручную контролировать процесс выполнения асинхронной задачи. Классу клиента также не нужно реализовывать функцию выполнения `resolve()`. Ключевой момент: **после завершения работы в асинхронном контексте вызовите `session->resolve()` для доставки результата обратно в UI-поток**.

```cpp
// Класс клиента: реализация resolve() не требуется, так как пул потоков по умолчанию не используется
struct FirmwareCheckClient {
    // Определяется только errorMessage() для описания ошибок
    static const char *errorMessage(async::Status status) {
        switch (status.value()) {
        case 1: return "firmware not found";
        case 2: return "check failed";
        default: return "unknown error";
        }
    }
};

static JsValue checkFirmwareUpdate(JsCtx ctx) {
    Applet *applet = Applet::current(ctx.vm());
    if (!applet || ctx.argc() < 1) return {};

    using Session = async::ResultSession<FirmwareCheckClient>;
    auto *session = async::make<Session>(applet);
    auto version = ctx.arg(0).asString();

    // Ручная установка resolver (без вызова request, без использования пула потоков по умолчанию)
    session->setResolver(ctx.arg(0));
    JsValue promise = session->promise();

    // Передача в пользовательский поток аппаратного драйвера
    HardwareDriver::checkUpdate(
        version,
        // Callback может выполняться в любом потоке — фреймворк автоматически перенаправит его в UI-поток
        [session](bool available) {
            session->resolve<bool>(available);
        },
        [session](int errorCode) {
            session->resolve<bool>(async::Status(errorCode));
        }
    );

    return promise;
}
```

Основные отличия здесь:
- `request()` выполняет два действия одновременно: «установку resolver» и «отправку асинхронному исполнителю»;
- В ручном режиме вам необходимо самостоятельно вызвать `setResolver()` для настройки целевого объекта ответа, а затем в любой момент отправить результат или состояние ошибки через `session->resolve()`.

Метод `resolve()` является потокобезопасным: он упаковывает результат в виде события, доставляет его обратно в UI-поток и завершает резолв `Promise`.

::: tip Когда использовать пользовательский контекст
- Низкоуровневый драйвер уже предоставляет интерфейс обратных вызовов (callback), и вы не хотите создавать дополнительные потоки: просто вызывайте `resolve` прямо в callback-функции драйвера.
- Необходимо интегрироваться с существующим циклом событий AIO/epoll: вызывайте `resolve` в callback-функции завершения события.
- Требуется последовательное выполнение (например, операции должны выполняться строго по порядку): используйте собственную очередь задач для планирования, а после завершения вызывайте `resolve`.

Фреймворк не волнует, из какого потока доставлен результат, главное — гарантировать хотя бы один вызов `session->resolve()`.
:::

### Семантика типов значений

Поскольку значения `async::Result<T>`, возвращаемые `resolve()` (или доставляемые вручную в пользовательском асинхронном контексте), передаются в UI-поток, а затем преобразуются в `JsValue`, тип данных `T` должен быть перемещаемым (movable). Все встроенные поддерживаемые типы удовлетворяют этому требованию. Для пользовательских типов:
- Если это структура, содержащая только встроенные поддерживаемые типы, стандарт C++ гарантирует ее перемещаемость.
- Если используются «голые» (raw) указатели и вы самостоятельно управляете их владением, вам необходимо корректно реализовать [конструктор перемещения](https://en.cppreference.com/w/cpp/language/move_constructor).
- [Тривиальные типы](https://en.cppreference.com/w/cpp/named_req/TrivialType) (такие как чистые структуры C, перечисления и т. д.) по умолчанию удовлетворяют семантике типов значений.

Стоит отметить, что нетривиальные типы обычно содержат ресурсы в куче, и следующий код может столкнуться с проблемами пикового потребления памяти:

```cpp
auto *session = getFetchLargeDataSession();
std::vector<uint32_t> data = fetchDataFromNetwork(url);
session->resolve<decltype(data)>(data);  // Произойдет полное копирование data
```
Это происходит потому, что параметр `session->resolve()` передается по значению, и при передаче `data` вызывается [конструктор копирования](https://en.cppreference.com/w/cpp/language/copy_constructor), что приводит к полному дублированию данных. Если `data` имеет большой объем, это удвоит потребление памяти. В таких случаях компилятор выдает предупреждение следующего вида:
```
'...' is deprecated:
avoid use copy semantics of Result<T> if T is not trivially copyable
```
Правильный подход заключается в том, чтобы явно задействовать семантику перемещения с помощью [`std::move()`](https://en.cppreference.com/w/cpp/utility/move):

```cpp
auto *session = getFetchLargeDataSession();
std::vector<uint32_t> data = fetchDataFromNetwork(url);
session->resolve<decltype(data)>(std::move(data));  // Используем семантику перемещения
```

### Контроль таймаута

Для асинхронных операций, которые могут долго не отвечать, используйте `async::make_timeout()`, чтобы добавить защиту по таймауту к сессии. По истечении таймаута `Promise` будет автоматически отклонен (rejected), что предотвратит зависание стороны JavaScript на неопределенный срок.

Следующий фрагмент кода демонстрирует базовый пример использования контроля таймаута в сетевом запросе:

```cpp
static JsValue fetchData(JsCtx ctx) {
    Applet *applet = Applet::current(ctx.vm());
    if (!applet || ctx.argc() < 1) return {};

    String url = ctx.arg(0)["url"].asString();
    int timeoutMs = ctx.arg(0)["timeout"].asInt(5000);

    using Session = async::ResultSession<HttpClient>;
    auto *session = async::make<Session>(applet);
    session->client().setUrl(url);
    session->setResolver(ctx.arg(0));
    JsValue promise = session->promise();

    // Создание защиты по таймауту: автоматический reject Promise при истечении времени
    auto handle = async::make_timeout(session, timeoutMs,
        [](Session *s) {
            // Обработка таймаута: здесь следует отменить выполняющуюся асинхронную операцию
            s->fulfill(async::Status(408));  // 408 Request Timeout
            
        });

    // Перемещение handle в контекст асинхронного выполнения
    NetworkDriver::fetch(url,
        [handle = std::move(handle)](auto &response) {
            // Если таймаут уже истек, вызов resolve будет безопасно проигнорирован
            handle->resolve<String>(std::move(response.body));
        });

    return promise;
}
```

#### Принцип работы

Ключевой рабочий процесс `make_timeout()`:

1. Данные клиента `session` **перемещаются** (moved) во внутренний класс, после чего доступ к `session->client()` запрещен.
2. Запускается однократный таймер, возвращающий дескриптор `SharedRef<SingleTimer>`.
3. **Нормальный путь**: до истечения таймаута вызывается `handle->resolve()`, что атомарно забирает владение сессией и доставляет событие результата. Позже, когда сработает таймер, он обнаружит, что сессия уже пуста, и ничего не предпримет.
4. **Путь таймаута**: таймер срабатывает, выполняя callback **в UI-потоке**, где разработчик вызывает `session->fulfill()` для передачи статуса ошибки. После возврата из callback-функции таймер отвечает за `delete session`.
5. **Выход из приложения**: когда `Applet` уничтожается, таймер автоматически отвязывается, сессия удаляется, и callback не вызывается.

Этот механизм особенно полезен в сценариях, где асинхронная операция не имеет встроенного механизма таймаута (например, некоторые реализации сетевых запросов). Как известно, корректная реализация защиты по таймауту бывает сложной задачей, так как необходимо правильно обрабатывать условия гонки (race conditions) на всех путях и обеспечивать безопасность жизненного цикла.

`make_timeout()` опирается на следующие предпосылки для обеспечения безопасности:
- Тип клиента (то есть `T` в `ResultSession<T>`) должен быть **перемещаемым** (movable), что является своего рода историческим ограничением.
- Асинхронная операция должна поддерживать безопасную отмену в UI-потоке, что означает удаление прослушивателя задачи и освобождение ссылки на `handle`.

#### Потоки обратных вызовов и `fulfill()`

Callback-функция таймаута (третий параметр `make_timeout()`) **всегда выполняется в UI-потоке**, так как она инициируется таймером (`Timer`), а события таймера распределяются главным циклом событий.

Этот факт определяет, что в callback-функции **можно** использовать только `session->fulfill()`, но **нельзя** использовать `session->resolve()`:

| Метод | Допустимые потоки вызова | Влияние на сессию |
| --- | --- | --- |
| `resolve(result)` | Любой поток | Доставляет событие Consume, сессия обрабатывается в UI-потоке и **удаляется** |
| `fulfill(result)` | **Только UI-поток** | Напрямую распределяет результат, **не удаляет** сессию |

Путь таймаута в `make_timeout()` отвечает за то, чтобы таймер самостоятельно вызвал `delete session` после завершения callback-функции. Если вызвать `session->resolve()` внутри callback, это также приведет к доставке события удаления сессии, что создаст **двойное освобождение памяти (double free)** совместно с вызовом `delete` таймера, приводя к неопределенному поведению. Метод `fulfill()` доставляет только результат и не затрагивает жизненный цикл сессии, поэтому он является единственным безопасным выбором внутри callback-функции.

`fulfill()` принимает `async::Result<R>` или напрямую принимает `async::Status` (сокращение для случаев без результирующего значения):

```cpp
auto handle = async::make_timeout(session, 5000, [](Session *s) {
    s->fulfill(async::Status(408)); // Заполняется только статус ошибки
    // Или передача значения и статуса:
    s->fulfill(async::Result<String>{"partial", async::Status(206)});
    // ❌ Не вызывайте s->resolve(), это приведет к двойному освобождению памяти вместе с delete session таймера
});
```

::: tip
Правило определения очень простое: где находится владение сессией и кто отвечает за ее удаление?
- **Нормальный путь**: `handle->resolve()` атомарно принимает владение сессией, и сессия удаляется после обработки события Consume.
- **Callback таймаута**: таймер принимает владение сессией и удаляет ее после завершения callback. Поэтому в callback следует использовать только `fulfill()`.
:::

#### Доступ к данным клиента

Если в callback-функции таймаута необходимо прочитать данные клиента для определения стратегии обработки ошибок, используйте расширенную сигнатуру callback-функции `(Session *, const T &)`. **Не** вызывайте `session->client()` внутри callback — клиент уже был перемещен в таймер:

```cpp
auto handle = async::make_timeout(session, 3000,
    [](Session *s, const HttpClient &client) { // Можно также использовать auto &client
        // ✅ Доступ к данным клиента через второй параметр
        LogWarn() << "request timeout: " << client.url();
        s->fulfill(async::Status(408));
    }
);
```

#### Управление жизненным циклом ресурсов

При возникновении таймаута вам необходимо отменить выполняющуюся асинхронную задачу в callback-функции, чтобы освободить ссылку на `handle`. `SingleTimer` использует подсчет ссылок для управления жизненным циклом: если асинхронная операция удерживает ссылку на `handle`, но никогда не завершится, это приведет к утечке памяти:

```cpp
auto task = AioTask::create();
auto handle = async::make_timeout(session, 5000,
    [task](auto *s) {
        task->cancel();     // Отменяем задачу, освобождая ссылку на handle
        s->fulfill(async::Status(408)); // reject Promise
    });

// Callback завершения задачи удерживает ссылку на handle
task->start([handle = std::move(handle)](auto &result) {
    handle->resolve(result);
});
```

::: important
Дескриптор `handle`, возвращаемый `make_timeout()`, также **должен** удерживаться асинхронной задачей (захватываться лямбдой в примере выше), чтобы гарантии таймера не были разрушены до завершения задачи. В противном случае callback таймаута и отклонение `Promise` сработают немедленно, не позволив задаче нормально завершиться.
:::

Такие утечки памяти вызваны двумя причинами:
1. **Утечка асинхронного фреймворка**: ссылка `handle` забыта, из-за чего сопутствующий объект сессии не может быть освобожден.
2. **Утечка низкоуровневой задачи**: саму асинхронную задачу заклинило в незавершенном состоянии, и ее ресурсы также не очищаются.

### Автоматическая очистка при выходе из приложения

Когда `Applet` уничтожается (например, пользователь закрывает приложение или система выгружает ресурсы), все асинхронные сессии, привязанные к этому `Applet`, автоматически очищаются:

- Вызывается метод `unbind()` сессии, который закрывает сессию и освобождает ссылку на `Promise`.
- Если используется `make_timeout`, таймер также отвязывается, а внутренне удерживаемая сессия удаляется.
- `Promise` на стороне JavaScript никогда не получит resolve или reject, но окружение JavaScript в этот момент также уничтожается, поэтому это безопасно.

Это означает, что вам **не нужно** вручную отслеживать и отменять асинхронные задачи — фреймворк гарантирует отсутствие следующих ситуаций:
- Доставка результатов в уже уничтоженный `Applet`, приводящая к обращению к висячим указателям (dangling pointers).
- Выполнение callback-функций в уже освобожденном окружении JavaScript.
- Утечка асинхронных сессий после выхода из приложения.

В частности, когда фоновый поток вызывает `resolve()` для доставки результатов в UI-поток, обработчик проверяет, остается ли `applet()` действительным. Если `Applet` уже уничтожен, из-за чего `applet()` возвращает `nullptr`, фреймворк безопасно отбрасывает результат, не выполняя никаких операций с JavaScript.

::: tip Безопасный возврат из асинхронного контекста
Поскольку `resolve()` — это чистая доставка данных (через очередь событий), вызов `resolve()` в фоновом потоке не вызовет сбой даже в том случае, если `Applet` уже уничтожен. Фоновому потоку не нужно беспокоиться о состоянии выживания `Applet`, это обязанность фреймворка.
:::

Единственное, на что следует обратить внимание: если вы наследуете `ResultSession` и вводите другие переменные-члены `JsValue`, вам необходимо очистить эти члены в `unbind()`, чтобы избежать утечки памяти:

```cpp
class MySession : public async::ResultSession<MyClient> {
public:
    void unbind() override {
        m_callbacks = {}; // Очищаем любые удерживаемые JsValue во избежание утечек
        async::ResultSession::unbind(); // Вызываем очистку базового класса
    }

private:
    JsValue m_callbacks; // Член, требующий ручной очистки
};
```

::: important Продление жизненного цикла `ResultSession`
Если на момент выхода из приложения все еще существуют незавершенные асинхронные сессии, фреймворк очищает только ресурсы, связанные с приложением (такие как ссылки `Promise`, отношения привязки и т. д.), но **не уничтожает сам объект сессии**. Это проявляется в продлении жизненного цикла `ResultSession` до завершения асинхронной операции.

Хотя это сделано для обеспечения безопасности памяти, это приводит к тому, что часть ресурсов освобождается несвоевременно. Поэтому асинхронные задачи должны гарантировать завершение за ограниченное время и не зависать на неопределенный срок.
:::

## Глобальное вещание событий: async::Signal

Если событие C++ необходимо транслировать **нескольким приложениям** (а не какому-то конкретному инициатору), используйте `async::Signal<T>`. Оно осуществляет «многоадресную рассылку» (multicast) аппаратных или системных событий всем JavaScript-слушателям, подписанным на них.

Назначение `async::Signal<T>` и `ResultSession` различается:

| Характеристика | ResultSession | Signal |
| --- | :---: | :---: |
| Направление связи | Один к одному (инициатор → результат) | Один ко многим (источник событий → все подписчики) |
| Количество срабатываний | Однократно | Многократно |
| Привязанный объект | Один Applet | Кросс-Applet |
| Применимые сценарии | Асинхронные запросы, вызовы | Системные события, изменения состояния |

### Базовое использование

Предположим, есть событие изменения уровня заряда батареи, о котором нужно уведомить всех подписчиков:

```cpp
// Определение глобального сигнала, обычно являющегося членом соответствующего сервисного класса
async::Signal<int> batteryChanged;

// Запуск сигнала при возникновении аппаратного события (может вызываться из любого потока)
void onBatteryLevelChanged(int newLevel) {
    batteryChanged(newLevel);  // Уведомление всех подписчиков
}
```

#### Подписка и отписка

Эта функция модуля позволяет стороне JavaScript подписаться на данный сигнал, а также возвращает ID привязки для отписки на стороне JavaScript:

```cpp
static JsValue subscribeBatteryChange(JsCtx ctx) {
    if (ctx.argc() < 1 || !ctx.arg(0).isFunction())
        return {};
    // Для подписки необходимо находиться в валидном контексте applet
    auto *applet = Applet::current(ctx.vm());
    if (applet == nullptr) return {};

    // Привязываем слот к приложению, подписка автоматически отменяется при выходе из приложения
    auto *slot = batteryChanged.connect(ctx.arg(0));
    return applet->bindObject(slot); // Возвращаем slot ID для отписки в JavaScript
}
```

Также необходимо реализовать функцию модуля для отписки. Независимо от типа `async::Signal`, реализация функции отвязки весьма стандартна:

```cpp
static JsValue unsubscribeBatteryChange(JsCtx ctx) {
    auto *applet = Applet::current(ctx.vm());
    if (applet && ctx.argc()) {
        // slotId по умолчанию равен 0, его можно безопасно проигнорировать без выполнения каких-либо действий
        auto slotId = ctx.arg(0).toInt();
        // После отвязки слота от applet необходимо также удалить объект slot
        delete applet->unbindObject<async::Slot>(slotId);
    }
    return {};
}
```

#### Экспорт в JavaScript

Достаточно определить [нативный модуль](./native-module.md) для экспорта этих функций:

```cpp
static JsModule *createBatteryModule(JsVM &vm) {
    auto mod = vm.newObject();
    // Модуль battery обычно также содержит такие функции, как getLevel(), здесь они опущено
    mod["subscribe"] = subscribeBatteryChange;
    mod["unsubscribe"] = unsubscribeBatteryChange;
    return mod;
}
// Не забудьте импортировать модуль с помощью GX_JSVM_MODULE_IMPORT
GX_JSVM_MODULE(vendor_battery, "vendor.battery", createBatteryModule)
```

::: tip Повторное использование функции `unsubscribe`
Поскольку реализация функции отписки универсальна, вы можете определить одну общую функцию `unsubscribe`, а затем многократно импортировать ее в различные модули.
:::

На стороне JavaScript:

```js
import battery from '@vendor.battery'

const sid = battery.subscribe((level) => {
  console.log('battery level:', level)
})

// Вызывается при необходимости отписаться
battery.unsubscribe(sid)
```

### Режимы доставки сигналов

`Signal` поддерживает два режима доставки, управляемых вторым параметром:

```cpp
// Обычный режим (по умолчанию): уведомление всех подписчиков
batteryChanged(newLevel, async::NormalSignal);

// Пропуск невидимых приложений: уведомление только видимых на переднем плане приложений для снижения лишнего потребления
batteryChanged(newLevel, async::SkipInvisible);
```

Режим `SkipInvisible` применим к событиям, имеющим смысл только тогда, когда пользовательский интерфейс виден (например, уведомления об обновлении интерфейса). Для событий, требующих отслеживания в фоновом режиме (например, предупреждение о низком заряде батареи), следует использовать стандартный `NormalSignal`.

### Типы значений сигналов

Параметр типа `T` в `Signal<T>` подчиняется тем же правилам преобразования, что и `ResultSession`: при срабатывании сигнала фреймворк преобразует значения C++ в аргументы callback-функции JavaScript через тот же механизм `js_cast()`. Встроенные типы, такие как `int`, `bool`, `String`, `JsonValue`, могут использоваться напрямую. Для передачи пользовательских структур или перечислений см. методы в разделе [Типы значений и преобразование в JavaScript](#Типы-значений-и-преобразование-в-javascript).

## Замечания по потокобезопасности

Модель потокобезопасности асинхронного фреймворка следует следующим правилам:

- **`resolve()` является потокобезопасным**: `ResultSession::resolve()` и `SingleTimer::resolve()` могут вызываться из любого потока. Они доставляют результаты в UI-поток через систему событий и не взаимодействуют с объектами JavaScript напрямую.
- **`JsValue` не является потокобезопасным**: жизненный цикл `JsValue` управляется на основе подсчета ссылок, причем операции с этим счетчиком не являются атомарными. Создавать, копировать, уничтожать или обращаться к `JsValue` в асинхронных потоках запрещено. Именно поэтому классам клиентов запрещено хранить `JsValue`.
- **Резолв `Promise` выполняется в UI-потоке**: независимо от того, из какого потока был вызван `resolve()`, финальный callback `Promise` в JavaScript всегда выполняется в UI-потоке, что гарантирует безопасность операций с UI.
- **Уведомления `async::Signal` распределяются в UI-потоке**: хотя `async::Signal::operator()` может вызываться из разных потоков, callback-функции JavaScript всегда выполняются в UI-потоке.

Если классу клиента необходимо совместно использовать состояние с UI-потоком (например, предоставлять флаг отмены), используйте [`std::atomic`](https://en.cppreference.com/w/cpp/atomic/atomic) или мьютексы для защиты общих данных:

```cpp
class CancellableClient {
public:
    void cancel() { m_cancelled.store(true); }

    async::Result<String> resolve() {
        for (int i = 0; i < 100 && !m_cancelled.load(); ++i) {
            // Выполнение пошаговой задачи с периодической проверкой флага отмены
            processChunk(i);
        }
        if (m_cancelled.load())
            return async::Status(499);  // Отменено клиентом
        return std::move(m_result);
    }

private:
    std::atomic_bool m_cancelled{false};
    String m_result;
};
```

В частности, многие типы значений фреймворка Glyphix **в рамках данного асинхронного фреймворка** могут безопасно передаваться между потоками, например:
- `String`: может напрямую присваиваться и читаться в многопоточной среде без дополнительных механизмов синхронизации.
- `JsonValue`: этот класс также является типом значения и обладает теми же характеристиками потокобезопасности, что и `String`.
- `ByteArray`: аналогично `String`, поддерживает многопоточное использование.
- `SharedRef<T>`: сам умный указатель с подсчетом ссылок может передаваться между потоками, но потокобезопасность управляемого объекта `T` зависит от его определения.
- Не являющиеся владельцами типы, такие как `String::View`, **не могут** использоваться в разных потоках.

Именно поэтому во всех предыдущих примерах мы всегда напрямую захватываем и передаем типы вроде `String` через асинхронные контексты, и их использование не требует специальной обработки или применения механизмов синхронизации, таких как мьютексы.

::: important
Потокобезопасность вышеупомянутых типов фактически зависит от модели памяти конкретного асинхронного фреймворка, что означает, что они **не являются автоматически потокобезопасными** во всех сценариях. Асинхронный фреймворк в данном документе гарантирует это, но данное утверждение нельзя экстраполировать на любые другие ситуации.
:::
