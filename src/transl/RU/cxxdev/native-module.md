# Разработка Native Module

Native Module (нативный модуль) — это мост, соединяющий C++ и код JavaScript на уровне приложения. Когда вам необходимо предоставить приложению системные возможности — например, чтение данных датчиков, вызов сторонних SDK или подключение системных функций, — вам потребуется написать Native Module.

Фреймворк Glyphix уже реализовал множество встроенных модулей с помощью этого механизма, таких как файловая система (`@system.file`), маршрутизация (`@system.router`) и т. д. Вы можете добавить эксклюзивные возможности для своего устройства аналогичным образом.

На рисунке ниже показано положение Native Module во фреймворке: он находится на уровне реактивного фреймворка, через уровень моста JsVM предоставляет системные API для JavaScript-приложений вверх и вызывает C++ ядро фреймворка или платформенные возможности вниз:

Для написания Native Module используются три группы концепций: **уровень моста JsVM** предоставляет возможности преобразования типов и вызова функций между C++ и JavaScript; **макросы регистрации модулей** объединяют код C++ в модуль, который может импортировать (`import`) JavaScript; **песочница Applet** предоставляет модулю контекст уровня приложения и управление жизненным циклом ресурсов. Эта глава последовательно раскрывает эти темы в данном порядке.

::: warning Риски безопасности
Если вы планируете разрабатывать «системные расширения» для Glyphix, не забывайте, что это также влечет за собой высокие риски безопасности. Неосторожность может привести к появлению уязвимостей, позволяющих вредоносным приложениям использовать эти возможности для атак на систему или другие приложения. Обязательно соблюдайте стандарты безопасного кодирования, ограничивайте разрешения и область доступа модуля, а также проводите достаточное тестирование безопасности.
:::

## Уровень моста JsVM

Прежде чем писать конкретные модули, необходимо ознакомиться с инструментами взаимодействия между C++ и JavaScript. Уровень моста JsVM является инфраструктурой всего Native Module, он предоставляет систему типов `JsValue` и контекст вызова `JsCallContext`, позволяя коду C++ создавать, считывать значения JavaScript и манипулировать ими.

### Система типов `JsValue`

`JsValue` — это тип C++, представляющий значение JavaScript во фреймворке и охватывающий все базовые типы JavaScript. Он использует подсчет ссылок для управления жизненным циклом и может напрямую присваиваться и копироваться, как типы значений C++, такие как `int`, `String` и т. д.

Создание значений JavaScript из C++:

```cpp
JsValue undefined;               // undefined
JsValue boolVal{true};           // boolean
JsValue intVal{42};              // number (целое)
JsValue floatVal{3.14};          // number (с плавающей точкой)
JsValue strVal{"hello"};         // string
```

Все эти конструкторы неявные, поэтому функции модулей могут напрямую возвращать `return "hello"` или `return 42` без ручной упаковки.

При чтении значений C++ из `JsValue` используйте семейство методов `as*`. Они возвращают указанное значение по умолчанию в случае несоответствия типов, избавляя от необходимости выполнять ручную проверку типов:

```cpp
int    count  = value.asInt(0);       // Возвращает 0, если не число
double ratio  = value.asNumber(1.0);  // Возвращает 1.0, если не число
String label  = value.asString();     // Возвращает пустую строку, если не строка
```

Если вам нужно выполнить принудительное приведение типов по семантике JavaScript (например, преобразовать произвольное значение в логическое), используйте семейство методов `to*`:

```cpp
bool   enable = value.toBoolean();    // Любое значение может быть преобразовано в bool
int    num    = value.toInt();        // Преобразование в целое число по спецификации ECMAScript
String str    = value.toString();     // Преобразование в строку по спецификации ECMAScript
```

Если вам нужно определить конкретный тип значения, используйте семейство методов `is*`:

```cpp
value.isUndefined()   // Является ли undefined
value.isNumber()      // Является ли числом
value.isString()      // Является ли строкой
value.isObject()      // Является ли объектом
value.isArray()       // Является ли массивом
value.isFunction()    // Является ли функцией
```

### Контекст `JsCallContext`

Каждая вызываемая из JavaScript функция C++ имеет фиксированную сигнатуру:

```cpp
JsValue myFunction(JsCtx ctx);
```

`JsCtx` является псевдонимом для `const JsCallContext &`. `JsCallContext` предоставляет три ключевые возможности:

- **`ctx.argc()`**: получает количество аргументов, переданных из JavaScript;
- **`ctx.arg(index)`**: получает аргумент с индексом `index` (возвращает `const JsValue &`);
- **`ctx.vm()`**: получает текущий экземпляр движка JavaScript (`JsVM &`).

Типичный паттерн чтения аргументов:

```cpp
static JsValue setVolume(JsCtx ctx) {
    // Обязательно сначала проверьте количество аргументов, а затем проверьте тип, иначе ctx.arg(0) может выйти за границы
    if (ctx.argc() < 1 || !ctx.arg(0).isNumber())
        return JsValue();  // Аргумент недействителен, возвращаем undefined

    int level = ctx.arg(0).asInt(0);
    level = std::max(0, std::min(100, level));
    audioSetVolume(level);
    return JsValue(true);  // Возвращаем флаг успеха
}
```

Многие функции встроенных модулей принимают в качестве параметра объект. Это гибкое соглашение, которое позволяет аргументам иметь значения по умолчанию, а также облегчает будущее расширение:

```js
// Вызов со стороны JavaScript
setConfig({ brightness: 80, contrast: 50 })
```

Чтение свойств объекта со стороны C++ с помощью `operator[]`:

```cpp
static JsValue setConfig(JsCtx ctx) {
    if (ctx.argc() < 1) return {}; // Не забудьте проверить количество аргументов

    JsValue params = ctx.arg(0);
    int brightness = params["brightness"].asInt(100);
    int contrast   = params["contrast"].asInt(50);
    // ...
    return {}; // Возвращает undefined
}
```

### Экспорт функций в виде `JsValue`

Функции модулей не обязательно должны быть именованными статическими функциями. `JsValue` может быть сконструирован из любого вызываемого объекта: **лямбда без захвата** автоматически преобразуется в указатель на функцию, ее эффективность эквивалентна именованной функции; **лямбда с захватом** упаковывается в объект callable, что подходит для замыкания времени выполнения уровня модуля внутри фабричной функции:

```cpp
static JsValue createMathModule(JsVM &vm) {
    JsValue mod = vm.newObject();

    // Лямбда без захвата: автоматически деградирует до указателя на функцию, без дополнительных накладных расходов
    mod["double"] = +[](JsCtx ctx) -> JsValue {
        return ctx.arg(0).asInt(0) * 2;
    };

    // Лямбда с захватом: один раз считывает конфигурацию при создании модуля, последующие вызовы используют ее напрямую
    int factor = readScaleFactorFromConfig();
    mod["scale"] = [factor](JsCtx ctx) -> JsValue {
        return ctx.arg(0).asInt(0) * factor;
    };

    return mod;
}
```

Преимущество лямбда-форм заключается в том, что связанная логика может быть написана в непосредственной близости внутри фабричной функции, избегая распыления большого количества коротких именованных функций по всему файлу. Для логически простых функций, которые не нужно переиспользовать на стороне C++, рекомендуется в первую очередь использовать лямбда-выражения.

### Создание и возвращение объектов

Во многих сценариях требуется вернуть результирующий объект, содержащий несколько полей. Используйте `JsVM::newObject()` для создания нового объекта JavaScript, а затем установите свойства с помощью `operator[]`:

```cpp
static JsValue getSystemInfo(JsCtx ctx) {
    JsValue result = ctx.vm().newObject();
    result["model"] = "GX-Watch-2";
    result["firmware"] = "2.1.0";
    result["memory"] = 512; // КБ
    return result;
}
```

`JsVM` также предоставляет другие фабричные методы, такие как `newArray()`, `newArrayBuffer()`, `newPromise()` и т. д., которые позволяют создавать различные типы JavaScript по мере необходимости.

### Исключения и обработка ошибок

Если функция модуля сталкивается с ошибкой, вы можете выбросить исключение JavaScript с помощью `JsVM::newError()`:

```cpp
static JsValue setConfig(JsCtx ctx) {
    if (ctx.argc() < 1)
        return ctx.vm().newError("missing parameters");
    // ...
}
```

Тем не менее, мы обычно не используем исключения в простых сценариях, таких как проверка аргументов функций, потому что текст сообщения об ошибке увеличивает объем кода. Для некритических ошибок обычно предпочтительнее возвращать `undefined` или `false`.

### Межъязыковое взаимодействие функций

Если вам нужно активно выполнять функции JavaScript или методы объектов в C++, вы можете использовать `JsValue::call()` или `callMethod()`. Это так же просто, как вызывать функции JavaScript напрямую в C++, аргументы могут передаваться через списки инициализации, а также можно получать возвращаемые значения:

```cpp
static JsValue printDemo(JsCtx ctx) {
    JsVM &vm = ctx.vm();
    JsValue obj = vm.newObject();
    obj["value"] = 42;
    
    // Вызов метода объекта console, эквивалентно console.log("Object is:", obj) в JS
    auto result = vm.globalObject()["console"]
                    .callMethod("log", {"Object is:", obj});
    
    // print() можно использовать для прямого вывода содержимого JsValue в консоль для удобства отладки
    result.print(); // undefined 
    
    // Если вас интересует только процесс выполнения без возвращаемого значения и вы хотите вывести предупреждение в случае ошибки:
    result.reportError(); // Возвращает bool, указывающий, является ли это исключением
    
    return {}; // Возвращает undefined
}
```

Если вы вызываете отдельную функцию-объект, переданную через аргументы (а не метод, привязанный к объекту), вам нужно использовать `call()` и указать объект привязки `this`, обычно можно использовать глобальный объект `globalObject()`:

```cpp
static JsValue doMathAndCallback(JsCtx ctx) {
    if (ctx.argc() < 1 || !ctx.arg(0).isFunction()) return JsValue();
    
    auto &callback = ctx.arg(0); // Здесь можно взять ссылку, чтобы избежать накладных расходов на подсчет ссылок
    // Это объект this при вызове функции JS, если {}, то эквивалентно undefined
    JsValue thisObj = ctx.vm().globalObject();
    // Эквивалентно callback.call(globalThis, 10, 20) в JS
    JsValue result = callback.call(thisObj, { 10, 20 });
    
    return result;
}
```

::: warning Опасный антипаттерн: утечка асинхронных колбэков
Если ваше первоначальное намерение состояло в том, чтобы долгосрочно сохранить `callback`, переданный из JavaScript, например, передав его низкоуровневому оборудованию и используя для подписки на события, будьте предельно осторожны:

```cpp
// ❌ Пример ошибки: приведет к утечке памяти!
static JsValue onButtonPress(JsCtx ctx) {
    auto callback = callback = ctx.arg(0);
    // Получение колбэка JavaScript непосредственно из аргумента и захват его в лямбду, передача драйверу нижнего уровня
    HardwareButton::onPress([callback]() mutable {
        callback.call({}, {...});
    });
    return {};
}
```

Это типичная **серьезная ловушка**: `JsValue` имеет управление жизненным циклом на основе подсчета ссылок. Как только это замыкание будет постоянно удерживаться низкоуровневым драйвером вместе с глобальным состоянием и не будет предоставлен четкий механизм отмены (например, соответствующий метод отвязки `offPress`), этот колбэк JavaScript и весь связанный с ним контекст песочницы приложения будут **навсегда утеряны (утечка)**!

Для реализации долгоживущих колбэков в циклах событий (таких как подписка на события) необходимо использовать механизм жизненного цикла **песочницы приложения** для управления объектами C++ и безопасно отвязывать их при ненадобности, либо напрямую использовать специализированный инструмент `AsyncSession` (см. [Разработка асинхронного функционала](./async.md)).
:::

Для более сложных асинхронных сценариев (например, когда требуется вернуть Promise или нужны многократные колбэки) см. [Разработка асинхронного функционала](./async.md).

В этом разделе рассмотрены только наиболее часто используемые возможности моста JsVM. `JsVM` и `JsValue` также предоставляют множество интерфейсов, не затронутых в этом разделе, таких как: синтаксический анализ и сериализация JSON (`parseJSON()`, `stringifyJSON()`), перечисление свойств (`properties()`), операции с Promise (`newPromise()`, `promiseResolve()`/`promiseReject()`), а также прямое выполнение кода JS (`eval()`, `importModule()`) и т. д. Полное описание интерфейсов см. в документации API, поставляемой с SDK.

### Экспорт объектов C++

В предыдущих примерах функции возвращали базовые типы или обычные объекты JavaScript, что по сути является манипулированием JavaScript через API C++. Но иногда возникает необходимость **экспортировать объект C++ в JavaScript**, чтобы скрипт мог продолжать работу с одним и тем же низкоуровневым экземпляром в дальнейшем.

Существует несколько различных способов реализации:

- **`vm.newMetaObject(object)`**: наиболее прямой, автоматически экспортирующий `GX_PROPERTY` / `GX_METHOD` в JavaScript;
- **`vm.newObject(object)` + ручное навешивание функций**: ближе к «обычному объекту JS с нативным дескриптором»;
- **`vm.newProxy()`**: наиболее гибкий, но логика перехвата свойств рассредоточена, а стоимость обслуживания выше всего.

В большинстве бизнес-сценариев рекомендуется в первую очередь использовать `newMetaObject()`. Рассматривайте другие два метода только тогда, когда вам явно нужно вручную написать структуру JavaScript или перехватить очень динамичный доступ к свойствам.

#### Экспорт через `newMetaObject()`

Это самый простой способ. Сначала определите тип нативного объекта, а затем упакуйте его непосредственно в отражаемый (reflectable) объект JavaScript.

В следующем примере экспортируется объект счетчика с возможностью чтения и записи. Он должен наследоваться от `PrimitiveObject` и объявляться в системе метаобъектов с помощью `GX_OBJECT`:

```cpp
#include "gx_jsvm.h"
#include "gx_object.h"

using namespace gx;

class NativeCounter final : public PrimitiveObject {
    GX_OBJECT

public:
    explicit NativeCounter(int initial = 0) : m_value(initial) {}

    int value() const { return m_value; }
    void setValue(int value) { m_value = value; }

    GX_METHOD void reset() { m_value = 0; }

    // Необходимо предоставить JavaScript в качестве «конструктора».
    static JsValue constructor(JsCtx ctx) {
        int initial = ctx.argc() ? ctx.arg(0).asInt(0) : 0;
        auto *counter = new NativeCounter(initial);
        return ctx.vm().newMetaObject(counter);
    }

    GX_PROPERTY(int value, get value, set setValue)

private:
    int m_value = 0;
};
```

::: tip Типы GX_METHOD
Функции, помеченные `GX_METHOD`, могут иметь любые управляемые типы параметров и возвращаемых значений `Variant`, которые могут взаимозаменяться с `JsValue`, включая ссылки. Например: `int`, `const String &` и т. д.

Не забывайте, что сам `JsValue` также может использоваться.
:::

Затем экспортируйте этот «конструктор» в фабричной функции модуля:

```cpp
static JsValue createCounterModule(JsVM &vm) {
    JsValue mod = vm.newObject();
    mod["createCounter"] = NativeCounter::constructor;
    return mod;
}
```

Использование на стороне JavaScript:

```js
import counter from '@vendor.counter'

const c = counter.createCounter(10)
console.log(c.value) // 10
c.value = 42
c.reset()
console.log(c.value) // 0
```

Здесь `c` выглядит как обычный объект JavaScript, но на самом деле он связан с экземпляром `NativeCounter` на низком уровне. Поскольку используется `newMetaObject()`, JavaScript может напрямую читать и записывать свойства, объявленные через `GX_PROPERTY`, а также вызывать методы, предоставленные через `GX_METHOD`.

Если вам нужно лишь «естественным образом экспортировать объект C++ как объект JavaScript» (включая свойства и методы), этого обычно достаточно.

#### Обработка контекста Applet

У `newMetaObject()` есть общее ограничение: `GX_METHOD`, экспортируемые через систему метаобъектов, являются обычными функциями-членами C++, они не могут получить `JsCtx` / `JsCallContext`, и поэтому не могут напрямую писать `Applet::current(ctx.vm())`, как функции модулей.

Если методы вашего объекта должны иметь доступ к контексту текущего приложения, например:

- разрешение частных URI приложения;
- чтение разрешений или конфигурации приложения;
- привязка других ресурсов к текущей песочнице внутри метода объекта;

то более подходящим подходом будет заставить этот объект наследоваться от `BindableObject` и связываться с текущим `Applet` при создании объекта. Таким образом, методы `GX_METHOD` смогут получать доступ к хост-приложению напрямую через `applet()`.

Пример:

```cpp
#include "gx_applet.h"
#include "gx_bindableobject.h"
#include "gx_jsvm.h"

using namespace gx;

class NativeFile final : public BindableObject {
    GX_OBJECT_KINDS(NoneKind)

public:
    NativeFile(Applet *applet, const String &uri)
        : BindableObject(applet), m_uri(uri) {}

    GX_METHOD String resolvedUri() const {
        auto *host = applet();
        return host ? host->resolveUri(m_uri) : String();
    }

    static JsValue constructor(JsCtx ctx) {
        auto *applet = Applet::current(ctx.vm());
        if (!applet) return {};

        String uri = ctx.argc() ? ctx.arg(0).toString() : String();
        return ctx.vm().newMetaObject(new NativeFile(applet, uri));
    }

private:
    String m_uri;
};
```

::: warning Безопасность песочницы
Не реализуйте функцию вроде `resolvedUri()`, которая напрямую раскрывает пути к низкоуровневым ресурсам, это всего лишь пример. В реальной разработке обязательно выполняйте проверку разрешений и контроль доступа, чтобы избежать утечки конфиденциальной информации на сторону JavaScript.
:::

Использование на стороне JavaScript ничем не отличается от обычного объекта `newMetaObject()`:

```js
const file = native.createFile('internal://files/config.json')
console.log(file.resolvedUri())
```

В этом примере `resolvedUri()` не имеет параметра `JsCtx`, но он все равно может получить доступ к `applet()`, поскольку объект был привязан к текущему приложению при создании.

::: warning Два предварительных условия для `BindableObject`
При использовании `BindableObject` обратите особое внимание на два момента:

- `BindableObject` по умолчанию имеет `ExplicitDeleteKind`. Это означает, что он **не будет** автоматически уничтожен при сборке мусора (GC) объекта JavaScript. Если вы хотите, чтобы он вернулся к поведению обычного нативного объекта с GC, вы можете переопределить это поведение по умолчанию с помощью `GX_OBJECT_KINDS(NoneKind)`, как в примере выше.
- `BindableObject` должен быть привязан к `Applet`, иначе `applet()` всегда будет нулевым указателем, и говорить о контексте не придется. Простейший подход — вызвать `BindableObject(applet)` в конструкторе или связать с текущим `Applet` сразу после создания.
:::

::: important Поведение в старых версиях
До официального релиза v0.8.0 поведение `PrimitiveObject::objectKinds()` отличалось от описанного в этом документе, не ссылайтесь на детали реализации старых версий.
:::

`BindableObject` — это не замена [экспорту через `newMetaObject()`](#экспорт-через-newmetaobject), а специализированное решение для случаев, когда «методам объекта нужно помнить контекст приложения, которому они принадлежат». Вводите эту концепцию только тогда, когда вам действительно нужен доступ к `Applet` внутри `GX_METHOD`.

#### `newObject()` и ручной экспорт методов

Иногда вы не хотите выставлять наружу весь интерфейс метаобъекта, а хотите лишь закрепить объект C++ как непрозрачный дескриптор в объекте JavaScript и вручную решить, какие методы могут вызываться. В этом случае для экспорта объекта можно использовать `vm.newObject()`.

При таком подходе `GX_PROPERTY` и `GX_METHOD` **не** экспортируются автоматически, поэтому вам придется самостоятельно навешивать методы на объект:

```cpp
class CounterCore final : public PrimitiveObject {
    GX_OBJECT

public:
    explicit CounterCore(int initial = 0) : m_value(initial) {}

    int value() const { return m_value; }
    void add(int delta) { m_value += delta; }

private:
    int m_value = 0;
};

static JsValue createManualCounter(JsCtx ctx) {
    int initial = ctx.argc() > 0 ? ctx.arg(0).asInt(0) : 0;

    JsVM &vm = ctx.vm();
    JsValue obj = vm.newObject(new CounterCore(initial));

    obj["add"] = [](JsCtx ctx) -> JsValue {
        auto *counter = dyn_cast<CounterCore *>(ctx.thisObject().object());
        if (!counter)
            return {};
        counter->add(ctx.arg(0).asInt(0));
        return {};
    };

    obj["get"] = [](JsCtx ctx) -> JsValue {
        auto *counter = dyn_cast<CounterCore *>(ctx.thisObject().object());
        if (!counter)
            return {};
        return counter->value();
    };

    return obj;
}
```

Со стороны JavaScript это выглядит как обычный объект:

```js
const c = counter.createManualCounter(10)
c.add(5)
console.log(c.get()) // 15
```

Особенностью такого написания является то, что структура API JavaScript полностью определяется вами, но внутри каждого метода вам приходится самостоятельно извлекать низкоуровневый указатель C++ из объекта `this` и проверять тип с помощью `dyn_cast`. По сравнению с `newMetaObject()` здесь больше шаблонного кода, и легче пропустить проверку.

Тем не менее, у него есть и прямое преимущество: эти функции, навешенные вручную, по сути являются обычными колбэками `JsCtx`, поэтому они могут напрямую получать доступ к контексту текущего приложения через `Applet::current(ctx.vm())`, точно так же, как функции модулей. Это также важное отличие от `GX_METHOD`.

Этот метод пока не позволяет экспортировать аксессоры свойств (getter / setter), а может экспортировать только фиксированные значения свойств.

#### Экспорт объектов с помощью `newProxy()`

Если вам нужно полностью перехватить чтение и запись свойств, поиск методов, ленивую генерацию полей и другие действия, вы также можете использовать `vm.newProxy()`. Этот подход позволяет реализовать очень динамичные интерфейсы, такие как: перенаправление доступа к любому имени свойства в нижележащий словарь, создание дочерних объектов по требованию, перехват записи для проверки.

Но у него есть и очевидная цена:

- поведение чтения свойств, записи свойств и вызова методов рассредоточено по логике прокси;
- структура API больше не выражается напрямую определением класса, как в `newMetaObject()`;
- как только поведение становится сложным, устранение неполадок может стать затруднительным.

Поэтому `newProxy()` больше подходит для небольшого числа очень динамичных сценариев моста и не подходит для замены обычного экспорта объектов.

#### Правила жизненного цикла

Правила уничтожения Native Object определяются не отдельно `newMetaObject()`, а `objectKinds()` объекта C++:

- Если объект содержит `RootKind` и **не** содержит `ExplicitDeleteKind`, то при сборке мусора (GC) соответствующего объекта JavaScript объект C++ также будет автоматически уничтожен;
- Если объект является дочерним узлом другого объекта или объявил `ExplicitDeleteKind`, то его жизненный цикл по-прежнему находится в ведении стороны C++.

Для большинства «независимых упакованных объектов» прямое наследование от `PrimitiveObject` без дополнительного объявления `ExplicitDeleteKind` обычно позволяет получить подходящее поведение по умолчанию, то есть автоматическое уничтожение вместе с GC.

Если вы не знакомы с этими метками жизненного цикла объектов, рекомендуется сначала прочитать раздел об `PrimitiveObject` в [Системе объектов](./object-system.md), прежде чем решать, стоит ли передавать объект под управление JavaScript GC.

#### Извлечение Native Object из `JsValue`

Иногда функция другого Native Module получает этот объект в качестве параметра. В этом случае вы можете временно извлечь низкоуровневый указатель C++ из `JsValue`:

```cpp
static JsValue getCounterValue(JsCtx ctx) {
    if (ctx.argc() < 1 || !ctx.arg(0).isObject())
        return {};

    auto *counter = dyn_cast<NativeCounter *>(ctx.arg(0).object());
    if (!counter)
        return {};
    return counter->value();
}
```

`object()` обеспечивает только **временный доступ** и не передает право владения. Если вам действительно нужно «забрать» объект со стороны JavaScript, вам следует использовать шаблонную форму `moveObject<T>()`:

```cpp
auto *counter = value.moveObject<NativeCounter>();
```

**Не** пишите в следующем виде:

```cpp
auto *counter = dyn_cast<NativeCounter *>(value.moveObject());
```

Как только типы не совпадут, этот код потеряет право владения объектом после неудачного приведения типов, что приведет к утечке. Документация API также явно рекомендует отдавать предпочтение `moveObject<T>()`, объединяя «проверку типов» и «передачу права владения» в один шаг.

::: warning Когда не стоит экспортировать Native Object
Если вы хотите вернуть лишь простой результат (например, информацию об устройстве, результат однократного вычисления или снимок конфигурации), отдавайте предпочтение возврату обычных объектов JavaScript, созданных через `newObject()`. Нативный объект стоит вводить только тогда, когда JavaScript требуется продолжительное время работать с одним и тем же экземпляром C++ в дальнейшем.
:::

## Определение и регистрация модуля

Освоив базовые инструменты моста JsVM, вы можете объединить функции C++ в полноценный Native Module. Модуль состоит из двух частей: **фабричной функции**, которая отвечает за создание объекта модуля и привязку к нему функций C++, и **макроса регистрации**, который отвечает за регистрацию фабричной функции в системе модулей фреймворка.

::: tip
При разработке нестандартных системных расширений рекомендуется в первую очередь рассмотреть использование механизма [Library Loader](#library-loader).
:::

### Структура модуля

Рассмотрим в качестве примера реализацию модуля информации об устройстве `@vendor.device`:

```cpp
#include "gx_jsvm.h"

using namespace gx;

// Функции C++ в модуле
static JsValue getDeviceName(JsCtx ctx) {
    return "MyDevice-Pro";
}

static JsValue getBatteryLevel(JsCtx ctx) {
    int level = /* Чтение уровня заряда из драйвера */ 85;
    return level;
}

// Фабричная функция: построение объекта модуля и его возвращение
static JsValue createDeviceModule(JsVM &vm) {
    JsValue mod = vm.newObject();
    mod["getDeviceName"] = getDeviceName;
    mod["getBatteryLevel"] = getBatteryLevel;
    return mod;
}

// Регистрация модуля, чтобы он был доступен в JavaScript по пути @vendor.device
GX_JSVM_MODULE(vendor_device, "vendor.device", createDeviceModule)
```

Макрос `GX_JSVM_MODULE` принимает три параметра: имя переменной C++, путь к модулю JavaScript (без префикса `@`) и фабричную функцию. Фабричная функция вызывается при первом импорте (`import`) модуля, и возвращаемый объект `JsValue` является модулем, получаемым на стороне JavaScript.

На стороне JavaScript приложение использует этот модуль следующим образом:

```js
import device from '@vendor.device'

const name = device.getDeviceName()
const battery = device.getBatteryLevel()
```

::: tip Это демо!
Это выглядит довольно просто, за исключением одной большой проблемы: большинство API являются асинхронными! Мы абсолютно не должны читать уровень заряда батареи в контексте выполнения JavaScript, то есть в потоке пользовательского интерфейса, если только мы действительно не делаем демо. Для асинхронных API см. раздел [Разработка асинхронного функционала](./async.md), где приведены более подходящие паттерны и примеры.
:::

### Включение модуля

Мало просто объявить модуль, его также необходимо «установить» в движок JavaScript при инициализации фреймворка. Это делается с помощью макроса `GX_JSVM_MODULE_IMPORT`:

```cpp
GX_JSVM_MODULE_IMPORT(vendor_device)
```

`GX_JSVM_MODULE` объявляет глобальную переменную в области видимости файла, а `GX_JSVM_MODULE_IMPORT` находит и вызывает метод `install()` этой переменной. Имена (первые параметры) обоих макросов должны совпадать.

Обычным подходом является сосредоточение всех вызовов `GX_JSVM_MODULE_IMPORT` в одной функции для удобства управления:

```cpp
void installVendorModules() {
    GX_JSVM_MODULE_IMPORT(vendor_device)
    GX_JSVM_MODULE_IMPORT(vendor_sensor)
    GX_JSVM_MODULE_IMPORT(vendor_bluetooth)
}
```

Вызов `installVendorModules()` после инициализации `AppletKit` гарантирует, что модуль будет доступен при запуске приложения.

## Library Loader

Native Module подходит для реализации системных API уровня фреймворка, универсально доступных для всех приложений. Но для **нестандартных функций настройки системы**, таких как данные, специфичные для производителя, инкапсуляция закрытых SDK или возможности, открытые только для определенных авторизованных приложений, настоятельно рекомендуется использовать механизм **Library Loader**.

Library Loader загружается по имени с помощью метода [`loadLibrary()`](/api/system-app.md#loadlibrary), предоставляемого модулем `@system.app`:

```js
import app from '@system.app'

const lib = app.loadLibrary('custom-library')
lib.someFunction()
```

По сравнению с Native Module, Library Loader имеет два существенных преимущества:

- **Отсутствие необходимости в глобальной регистрации**: не зависит от макросов `GX_JSVM_MODULE` и `GX_JSVM_MODULE_IMPORT`, объект модуля создается по требованию при вызове;
- **Упрощенный откат в симуляторе**: приложение может изящно деградировать до заглушки (stub), реализованной в скрипте, в универсальной среде симулятора, проверяя, является ли возвращаемое значение `loadLibrary()` равным `undefined`, в то время как трюки с заглушками для импорта модулей вроде `import lib from '...'` являются более хакерскими и антипаттернными.

```js
import app from '@system.app'

// Попытка загрузить нативную библиотеку, откат к скриптовой заглушке в симуляторе
const nativeLib = app.loadLibrary('custom-library')
const lib = nativeLib || {
    someFunction() { /* Реализация для симулятора */ }
}
```

За исключением метода регистрации и способа использования на стороне JavaScript, Library Loader во всем остальном практически идентичен Native Module.

### Регистрация Library Loader

На стороне C++ загрузчик регистрируется через `AppletKit::setLibraryLoader()`. Загрузчик принимает экземпляр `Applet`, выполняющий вызов, и возвращает объект библиотеки (`JsValue`):

```cpp
#include "gx_appletkit.h"
#include "gx_jsvm.h"

using namespace gx;

static JsValue getDeviceName(JsCtx ctx) {
    return "MyDevice-Pro";
}

void installLibraries() {
    AppletKit::instance()->setLibraryLoader(
        "custom-library",
        [](Applet *applet) -> JsValue {
            JsVM &vm = JsVM::current();
            JsValue lib = vm.newObject();
            lib["someFunction"] = getDeviceName;
            return lib;
        }
    );
}
```

Достаточно вызвать `setLibraryLoader()` после инициализации `AppletKit`, повторная регистрация при каждом запуске приложения не требуется.

Загрузчик Library Loader получает `Applet *`, поэтому он может напрямую выполнять **проверку разрешений приложения** на входе, отказывая в предоставлении функций неавторизованным приложениям, вместо того чтобы повторять проверки внутри каждой функции модуля:

```cpp
AppletKit::instance()->setLibraryLoader(
    "custom-library",
    [](Applet *applet) -> JsValue {
        // Проверка разрешений: единый перехват неавторизованного доступа на входе
        if (!applet || !applet->permission(vendor::Permission::AccessCustomLib))
            return vm.newError("permissions denied"); // Возвращает undefined

        JsVM &vm = JsVM::current();
        JsValue lib = vm.newObject();
        lib["someFunction"] = getDeviceName;
        return lib;
    }
);
```

Если загрузчик возвращает `undefined` (то есть сконструированный по умолчанию `JsValue()`), `app.loadLibrary()` также получает `undefined` на стороне JavaScript, на основе чего приложение может выполнить откат (fallback).

::: tip
Не рекомендуется выбрасывать исключения в функции загрузчика при неудачной проверке разрешений, вместо этого лучше возвращать `undefined`. Помимо того, что это позволяет JavaScript-стороне просто деградировать, это также предотвращает утечку информации о существовании модуля (если вы не хотите, чтобы неавторизованное приложение знало о существовании этой библиотеки).
:::

## Взаимодействие с песочницей приложения

Функции модулей, описанные в предыдущих разделах, не имеют состояния — они принимают аргументы, возвращают результаты и не удерживают никакой контекст. Но во многих реальных сценариях модуль должен быть связан с текущим запущенным приложением: чтение путей к ресурсам приложения, настроек языка или размещение долгоживущего объекта C++ в песочнице приложения. Для этого требуются возможности, предоставляемые `Applet`.

### Получение контекста текущего приложения

Получите экземпляр приложения, к которому принадлежит вызывающая сторона, через `Applet::current()`:

```cpp
#include "gx_applet.h"

static JsValue readPreference(JsCtx ctx) {
    auto applet = Applet::current(ctx.vm());
    // Поскольку последующие операции зависят от applet, обязательно проверьте успешность получения контекста
    if (!applet) return JsValue();

    // Чтение приватного пути хранения приложения
    String storagePath = applet->resolveUri("internal://files/preferences.json");
    // ...
}
```

Экземпляр `Applet` управляется фреймворком автоматически, и каждое приложение работает в своем собственном независимом JavaScript Realm. `Applet::current()` выводит соответствующий экземпляр приложения через текущий Realm, поэтому при вызове одной и той же функции модуля в разных приложениях получаются независимые контексты.

### Управление жизненным циклом ресурсов

Если функции модуля необходимо выделить долгоживущий объект C++ (например, фоновую задачу, которая непрерывно отслеживает состояние оборудования), **никогда** не используйте глобальные переменные или «голые» указатели для удержания ресурсов между вызовами — это позволит ресурсам ускользнуть из-под контроля песочницы приложения, что приведет не только к невозможности освобождения ресурсов после выхода из приложения, но и к потере ключевых гарантий безопасности, предоставляемых песочницей.

Здесь существует серьезное требование безопасности: **Native Module должен гарантировать, что все пути доступа к объектам C++ проходят строгую проверку права собственности и типов**, а не просто предоставляют «легальные пути», оставляя лазейки для их обхода. Правильный способ добиться этого — полностью делегировать управление жизненным циклом объекта песочнице `Applet` и в обязательном порядке использовать `takeObject<T>()` для проверки в **каждой** функции модуля, принимающей целочисленные дескрипторы. Это неотъемлемое инвариантное правило, которое будет подробно рассмотрено ниже.

Давайте рассмотрим этот безопасный механизм привязки жизненного цикла на примере непрерывного отслеживания состояния датчика.

::: tip
Код в этом разделе фактически является примитивной заменой принципа `AsyncSession` из раздела [Разработка асинхронного функционала](./async.md) и используется исключительно для демонстрации концепции. В реальной разработке настоятельно рекомендуется напрямую использовать зрелые инструменты, связанные с `AsyncSession`, для обработки асинхронных задач, так как под капотом они также основаны на методах, описанных в этом разделе.
:::

Предположим, у нас есть датчик, и приложению необходимо включить прослушивание при инициализации, затем неоднократно считывать последние данные и вручную останавливать прослушивание, когда оно больше не нужно. Сначала мы определяем носитель для этой фоновой задачи:

```cpp
class SensorListener : public PrimitiveObject {
    GX_OBJECT
public:
    SensorListener() {
        // Запуск датчика, запрос аппаратных ресурсов низкоуровневого драйвера...
    }
    ~SensorListener() override {
        // Останов датчика, освобождение связанных аппаратных ресурсов...
    }
    int latestValue() const { return m_value; }

private:
    int m_value = 0;
};
```

#### Привязка объекта к песочнице

Используйте `Applet::bindObject()` для привязки экземпляра к песочнице текущего приложения, возвращая целочисленный дескриптор для хранения на стороне JavaScript:

```cpp
static JsValue startSensor(JsCtx ctx) {
    auto applet = Applet::current(ctx.vm());
    if (!applet) return {};

    auto *listener = new SensorListener();
    // Передача объекта под управление Applet и получение целочисленного дескриптора (ID)
    int bindId = applet->bindObject(listener);

    // Возврат ID в JavaScript в качестве уникального удостоверения для последующих операций с этим объектом
    return bindId;
}
```

Поскольку объект теперь находится под **управлением** песочницы, даже если приложение неожиданно завершится в процессе выполнения задачи или будет принудительно уничтожено системой, песочница автоматически очистит все привязанные объекты при своем уничтожении, предотвращая тем самым утечку ресурсов.

#### Безопасное извлечение объекта

Когда стороне JavaScript требуется операция с ранее созданным объектом, она **обязана** извлечь экземпляр через `Applet::takeObject<T>()` на основе дескриптора, а не выполнять какое-либо «голое приведение типов»:

```cpp
static JsValue readSensor(JsCtx ctx) {
    auto applet = Applet::current(ctx.vm());
    if (!applet || ctx.argc() < 1) return {};

    int bindId = ctx.arg(0).asInt();
    auto *listener = applet->takeObject<SensorListener>(bindId);
    if (!listener) return {}; // Если ID недействителен или типы не совпадают, возвращаем nullptr

    return listener->latestValue();
}
```

`applet->takeObject<T>()` обращается только к ID, принадлежащим **текущей песочнице** (предотвращая несанкционированный доступ между приложениями), а затем проверяет **соответствие типов** с помощью метаинформации объекта. Непустой указатель возвращается только в том случае, если пройдены оба уровня.

::: danger Обязательный доступ к объекту через `takeObject<T>()`
Целочисленный ID, поступающий из JavaScript, абсолютно ненадежен на стороне C++ — он может быть поддельным или просроченным. Подход без проверок приведет к серьезным уязвимостям безопасности:

```cpp
// ❌ Ни в коем случае так не делайте!
static JsValue readSensor(JsCtx ctx) {
    auto bindId = ctx.arg(0).asInt();
    // Использование только нешаблонной версии takeObject + static_cast обходит проверку типов и границ песочницы
    auto *binded = applet->takeObject(bindId);
    // Опасно: static_cast не имеет проверки во время выполнения, binded здесь может вообще не быть SensorListener!
    auto *listener = static_cast<SensorListener *>(binded);
    return listener->latestValue(); // Может привести к произвольному чтению/записи памяти
}
```
:::

#### Отвязка и уничтожение

Когда вам нужно активно завершить задачу со стороны C++ и полностью освободить ресурсы, сначала извлеките и проверьте тип с помощью `takeObject<T>()`, затем отмените привязку с помощью `unbindObject()`, и, наконец, уничтожьте вручную:

```cpp
static JsValue stopSensor(JsCtx ctx) {
    Applet *applet = Applet::current(ctx.vm());
    if (!applet || ctx.argc() < 1) return {};

    int bindId = ctx.arg(0).asInt();
    auto *listener = applet->takeObject<SensorListener>(bindId);
    if (listener) {
        applet->unbindObject(listener); // Отмена привязки из списка автоматического управления
        delete listener;                // Ручное уничтожение
    }
    return {};
}
```

Полный рабочий процесс на фронтенде JavaScript:

```javascript
import sensor from '@vendor.sensor'

// Запуск и сохранение удостоверения
const id = sensor.startSensor()
// ...многократное чтение
const value = sensor.readSensor(id)
// Задача завершена, освобождение ресурсов
sensor.stopSensor(id)
```

Благодаря гарантиям безопасности, предоставляемым `bindObject`, даже если приложение забудет вызвать `stopSensor()`, песочница автоматически освободит все привязанные объекты при завершении работы.


::: important Обязательная автоматическая отвязка
Поскольку код JavaScript ненадежен, нельзя предполагать, что он вызовет функцию освобождения ресурсов. Для вредоносного приложения утечка песочницы, вызванная утечкой ссылок JavaScript, является эффективным вектором атаки. Поэтому **все объекты, привязанные к песочнице, должны автоматически отвязываться при уничтожении песочницы**, чтобы гарантировать отсутствие утечек ресурсов независимо от действий JavaScript.

Любой дизайн, требующий отвязки со стороны JavaScript, является опасным и должен быть исключен.
:::

### Защита безопасности

Несмотря на множество упомянутых выше требований безопасности, этого может быть недостаточно для устранения всех рисков. Для дальнейшего укрепления линии защиты безопасности мы рекомендуем напрямую ограничивать права доступа к модулям расширения доверенными приложениями. Вы можете проверить флаги разрешений или информацию об идентичности `Applet` прямо в фабричной функции модуля и отклонять не соответствующие условиям запросы:

```cpp
static JsValue createDeviceModule(JsVM &vm) {
    auto applet = Applet::current(vm);
    if (!applet || !applet->permission(
                    vendor::Permission::AccessDeviceInfo)) {
        // Если нет разрешений, возвращаем пустой объект или выбрасываем исключение
        return vm.newError("permissions denied");
    }

    // Создавать объект модуля и выставлять функционал наружу можно только после авторизации
    JsValue mod = vm.newObject();
    mod["getDeviceName"] = getDeviceName;
    // ...
    return mod;
}
```

Такая стратегия может эффективно предотвратить несанкционированный доступ на входе. Даже если сама функция модуля недостаточно надежна, злоумышленник не сможет использовать ее для получения конфиденциальной информации или выполнения вредоносных операций.

Проверка разрешений на входе для Library Loader уже была рассмотрена в соответствующей документации.
