# Разработка нативных модулей (Native Module)

Нативный модуль — это мост, соединяющий C++ и прикладной слой кода JavaScript. Когда вам необходимо предоставить приложению системные возможности — например, чтение данных датчиков, вызов сторонних SDK или доступ к возможностям системы, — вам потребуется написать нативный модуль.

Фреймворк Glyphix уже реализовал множество встроенных модулей с помощью этого механизма, таких как файловая система (`@system.file`), роутинг (`@system.router`) и т. д. Вы можете использовать тот же подход для добавления эксклюзивных возможностей на ваше устройство.

На следующей диаграмме показано положение нативного модуля в фреймворке: он находится на уровне реактивного фреймворка, через уровень моста JsVM предоставляет системные API для JavaScript-приложений вверх, а вниз вызывает ядро C++ или возможности платформы:

Для написания нативного модуля используются три группы концепций: **уровень моста JsVM**, обеспечивающий преобразование типов и вызовы функций между C++ и JavaScript; **макросы регистрации модулей**, собирающие код C++ в модуль, доступный для `import` из JavaScript; и **песочница Applet**, предоставляющая модулю контекст уровня приложения и управление жизненным циклом ресурсов. В этой главе материал излагается последовательно в данном порядке.

::: warning Риски безопасности
Планируя разработку «системных расширений» для Glyphix, не забывайте, что это влечет за собой высокие риски безопасности. Малейшая неосторожность может привести к появлению уязвимостей, позволяя злоумышленникам использовать эти возможности для атак на систему или другие приложения. Обязательно соблюдайте стандарты безопасного кодирования, ограничивайте права и область доступа модулей, а также проводите тщательное тестирование безопасности.
:::

## Уровень моста JsVM

Прежде чем приступать к написанию конкретных модулей, необходимо ознакомиться с инструментами взаимодействия между C++ и JavaScript. Уровень моста JsVM является инфраструктурной основой всего нативного модуля; он предоставляет систему типов `JsValue` и контекст вызова `JsCallContext`, позволяя коду C++ создавать, читать и манипулировать значениями JavaScript.

### Система типов `JsValue`

`JsValue` — это тип C++, представляющий значения JavaScript в фреймворке и охватывающий все базовые типы JavaScript. Он использует подсчет ссылок для управления жизненным циклом и может напрямую присваиваться и копироваться, подобно типам значений C++, таким как `int` или `String`.

Создание значений JavaScript из C++:

```cpp
JsValue undefined;               // undefined
JsValue boolVal{true};           // boolean
JsValue intVal{42};              // number (целое)
JsValue floatVal{3.14};          // number (с плавающей точкой)
JsValue strVal{"hello"};         // string
```

Все эти конструкторы являются неявными (implicit), поэтому функции модулей могут напрямую возвращать `return "hello"` или `return 42` без ручной упаковки.

Для чтения значений C++ из `JsValue` используйте методы серии `as*`. При несоответствии типов они возвращают указанное значение по умолчанию, избавляя от необходимости выполнять ручную проверку типов:

```cpp
int    count  = value.asInt(0);       // Возвращает 0, если не число
double ratio  = value.asNumber(1.0);  // Возвращает 1.0, если не число
String label  = value.asString();     // Возвращает пустую строку, если не строка
```

Если требуется принудительное приведение типов по семантике JavaScript (например, преобразование произвольного значения в булево), используйте методы серии `to*`:

```cpp
bool   enable = value.toBoolean();    // Любое значение может быть преобразовано в bool
int    num    = value.toInt();        // Преобразование в целое число по спецификации ECMAScript
String str    = value.toString();     // Преобразование в строку по спецификации ECMAScript
```

Для определения конкретного типа значения используйте методы серии `is*`:

```cpp
value.isUndefined()   // Является ли undefined
value.isNumber()      // Является ли числом
value.isString()      // Является ли строкой
value.isObject()      // Является ли объектом
value.isArray()       // Является ли массивом
value.isFunction()    // Является ли функцией
```

### Контекст `JsCallContext`

Каждая функция C++, вызываемая из JavaScript, имеет фиксированную сигнатуру:

```cpp
JsValue myFunction(JsCtx ctx);
```

`JsCtx` — это псевдоним (alias) для `const JsCallContext &`. Класс `JsCallContext` предоставляет три ключевые возможности:

- **`ctx.argc()`**: получение количества аргументов, переданных из JavaScript;
- **`ctx.arg(index)`**: получение аргумента по индексу `index` (возвращает `const JsValue &`);
- **`ctx.vm()`**: получение экземпляра текущего движка JavaScript (`JsVM &`).

Типичный паттерн чтения аргументов:

```cpp
static JsValue setVolume(JsCtx ctx) {
    // Обязательно сначала проверяйте количество аргументов, а затем тип, иначе ctx.arg(0) может выйти за границы
    if (ctx.argc() < 1 || !ctx.arg(0).isNumber())
        return JsValue();  // Неверные аргументы, возвращаем undefined

    int level = ctx.arg(0).asInt(0);
    level = std::max(0, std::min(100, level));
    audioSetVolume(level);
    return JsValue(true);  // Возвращаем флаг успеха
}
```

Многие функции во встроенных модулях принимают в качестве аргумента объект. Это гибкое соглашение, которое позволяет аргументам иметь значения по умолчанию, а также облегчает расширение в будущем:

```js
// Вызов на стороне JavaScript
setConfig({ brightness: 80, contrast: 50 })
```

Чтение свойств объекта на стороне C++ через `operator[]`:

```cpp
static JsValue setConfig(JsCtx ctx) {
    if (ctx.argc() < 1) return {}; // Не забудьте проверить количество аргументов

    JsValue params = ctx.arg(0);
    int brightness = params["brightness"].asInt(100);
    int contrast   = params["contrast"].asInt(50);
    // ...
    return {}; // Возвращает undefined
}
```

### Экспорт функций в виде `JsValue`

Функции модулей не обязательно должны быть именованными статическими функциями. `JsValue` может быть создан из любого вызываемого объекта (callable): **лямбда-функции без захвата (no-capture lambda)** автоматически преобразуются в указатели на функции с производительностью, эквивалентной именованным функциям; **лямбда-функции с захватом** упаковываются в объекты callable, что подходит для замыкания времени выполнения уровня модуля внутри фабричных функций:

```cpp
static JsValue createMathModule(JsVM &vm) {
    JsValue mod = vm.newObject();

    // Лямбда без захвата: автоматически деградирует до указателя на функцию, без дополнительных накладных расходов
    mod["double"] = +[](JsCtx ctx) -> JsValue {
        return ctx.arg(0).asInt(0) * 2;
    };

    // Лямбда с захватом: конфигурация считывается один раз при создании модуля, последующие вызовы используют ее напрямую
    int factor = readScaleFactorFromConfig();
    mod["scale"] = [factor](JsCtx ctx) -> JsValue {
        return ctx.arg(0).asInt(0) * factor;
    };

    ;
}
```

Преимущество лямбда-выражений заключается в том, что связанную логику можно писать прямо внутри фабричной функции, избегая разброса множества коротких именованных функций по всему файлу. Для логики с простой структурой, не требующей повторного использования на стороне C++, рекомендуется в первую очередь использовать лямбда-выражения.

### Создание и возвращение объектов

Во многих сценариях требуется вернуть результирующий объект, содержащий несколько полей. Используйте `JsVM::newObject()` для создания нового объекта JavaScript, а затем задайте свойства с помощью `operator[]`:

```cpp
static JsValue getSystemInfo(JsCtx ctx) {
    JsValue result = ctx.vm().newObject();
    result["model"] = "GX-Watch-2";
    result["firmware"] = "2.1.0";
    result["memory"] = 512; // КБ
    return result;
}
```

`JsVM` также предоставляет другие фабричные методы, такие как `newArray()`, `newArrayBuffer()`, `newPromise()` и т. д., позволяющие создавать различные типы JavaScript по мере необходимости.

### Исключения и обработка ошибок

Если в функции модуля возникает ошибка, вы можете выбросить исключение JavaScript с помощью метода `JsVM::newError()`:

```cpp
static JsValue setConfig(JsCtx ctx) {
    if (ctx.argc() < 1)
        return ctx.vm().newError("missing parameters");
    // ...
}
```

Однако мы обычно не используем исключения в простых сценариях, таких как проверка параметров функций, поскольку текст сообщения об ошибке увеличивает объем кода. Для некритических ошибок возврата `undefined` или `false` обычно вполне достаточно.

### Межъязыковое взаимодействие функций

Если вам нужно выполнить функцию JavaScript или метод объекта из C++, вы можете использовать `JsValue::call()` или `callMethod()`. Это так же просто, как вызывать функции JavaScript напрямую в C++; аргументы могут передаваться через список инициализации, а также можно получать возвращаемое значение:

```cpp
static JsValue printDemo(JsCtx ctx) {
    JsVM &vm = ctx.vm();
    JsValue obj = vm.newObject();
    obj["value"] = 42;
    
    // Вызов метода объекта console, эквивалентно console.log("Object is:", obj) в JS
    auto result = vm.globalObject()["console"]
                    .callMethod("log", {"Object is:", obj});
    
    // print() может использоваться для прямого вывода содержимого JsValue в консоль для отладки
    result.print(); // undefined 
    
    // Если вас интересует только процесс выполнения без возвращаемого значения и вы хотите вывести предупреждение при возникновении ошибки:
    result.reportError(); // Возвращает bool, указывающий, является ли результат исключением
    
    return {}; // Возвращает undefined
}
```

Если вы вызываете отдельную функцию, переданную в качестве аргумента (а не метод, привязанный к объекту), вам нужно использовать `call()` и указать объект привязки `this`. Обычно для этого можно использовать глобальный объект `globalObject()`:

```cpp
static JsValue doMathAndCallback(JsCtx ctx) {
    if (ctx.argc() < 1 || !ctx.arg(0).isFunction()) return JsValue();
    
    auto &callback = ctx.arg(0); // Здесь можно взять ссылку, чтобы избежать накладных расходов на подсчет ссылок
    // Это объект this при вызове функции JS; если {}, то эквивалентно undefined
    JsValue thisObj = ctx.vm().globalObject();
    // Эквивалентно callback.call(globalThis, 10, 20) в JS
    JsValue result = callback.call(thisObj, { 10, 20 });
    
    return result;
}
```

::: warning Опасный антипаттерн: утечка асинхронных колбэков
Если ваша цель — долгосрочное сохранение переданного из JavaScript `callback`, например, передача его низкоуровневому оборудованию для подписки на события, будьте предельно осторожны:

```cpp
// ❌ Пример с ошибкой: приведет к утечке памяти!
static JsValue onButtonPress(JsCtx ctx) {
    auto callback = callback = ctx.arg(0);
    // Получение колбэка JS напрямую из аргументов и захват в лямбду, передача низкоуровневому драйверу
    HardwareButton::onPress([callback]() mutable {
        callback.call({}, {...});
    });
    return {};
}
```

Это типичная **серьезная ловушка**: `JsValue` использует управление жизненным циклом на основе подсчета ссылок. Как только это замыкание постоянно удерживается низкоуровневым драйвером вместе с глобальным состоянием и не предоставляет явного механизма отмены (например, соответствующего метода отписки `offPress`), этот колбэк JavaScript и весь контекст песочницы приложения, к которому он привязан, будут **навсегда утеряны (утечка памяти)**!

Для реализации долгоживущих колбэков, охватывающих циклы событий (например, подписки на события), вы должны использовать механизм жизненного цикла **песочницы приложения** для управления объектами C++ и безопасно отписываться при ненадобности, либо напрямую использовать специализированные средства `AsyncSession` (см. [Разработка асинхронного функционала](./async.md)).
:::

Для более сложных асинхронных сценариев (например, когда нужно вернуть Promise или требуется несколько колбэков) см. [Разработка асинхронного функционала](./async).

::: tip Полный справочник по API
В этом разделе описаны только наиболее часто используемые возможности моста JsVM. `JsVM` и `JsValue` также предоставляют множество интерфейсов, не затронутых здесь, таких как: парсинг и сериализация JSON (`parseJSON()`, `stringifyJSON()`), перечисление свойств (`properties()`), операции с Promise (`newPromise()`, `promiseResolve()`/`promiseReject()`), а также прямое выполнение кода JS (`eval()`, `importModule()`) и др. Полное описание интерфейсов см. в документации API, поставляемой с SDK.
:::

### Экспорт объектов C++

В предыдущих примерах функции возвращали базовые типы или обычные объекты JavaScript, что по сути сводилось к управлению JavaScript через C++ API. Но иногда возникает необходимость **экспортировать объект C++ в JavaScript**, чтобы скрипт мог в дальнейшем непрерывно работать с одним и тем же экземпляром на нижнем уровне.

Существует несколько различных способов реализации:

- **`vm.newMetaObject(object)`**: самый прямой, автоматически экспортирующий `GX_PROPERTY` / `GX_METHOD` в JavaScript;
- **`vm.newObject(object)` + ручное навешивание функций**: ближе к «обычному объекту JS с нативным дескриптором»;
- **`vm.newProxy()`**: наиболее гибкий, но логика перехвата свойств рассредоточена, а стоимость поддержки максимальна.

В большинстве бизнес-сценариев в первую очередь рекомендуется использовать `newMetaObject()`. Рассматривайте другие два метода только тогда, когда вам явно требуется вручную спроектировать структуру JavaScript или перехватить динамический доступ к свойствам.

#### Экспорт через `newMetaObject()`

Это самый простой способ. Сначала определите тип нативного объекта, а затем напрямую упакуйте его в рефлексивно доступный объект JavaScript.

В следующем примере экспортируется объект читаемого/записываемого счетчика. Он должен наследоваться от `PrimitiveObject` и быть объявлен в системе метаобъектов с помощью макроса `GX_OBJECT`:

```cpp
#include "gx_jsvm.h"
#include "gx_object.h"

using namespace gx;

class NativeCounter final : public PrimitiveObject {
    GX_OBJECT

public:
    explicit NativeCounter(int initial = 0) : m_value(initial) {}

    int value() const { return m_value; }
    void setValue(int value) { m_value = value; }

    GX_METHOD void reset() { m_value = 0; }

    // Требуется для экспорта в JavaScript в качестве «конструктора».
    static JsValue constructor(JsCtx ctx) {
        int initial = ctx.argc() ? ctx.arg(0).asInt(0) : 0;
        auto *counter = new NativeCounter(initial);
        return ctx.vm().newMetaObject(counter);
    }

    GX_PROPERTY(int value, get value, set setValue)

private:
    int m_value = 0;
};
```

::: tip Типы для GX_METHOD
Функции, помеченные как `GX_METHOD`, могут иметь любые управляемые типы параметров и возвращаемые значения типа `Variant`, которые могут конвертироваться в/из `JsValue`, включая ссылки (например, `int`, `const String &` и т. д.).

Не забывайте, что сам тип `JsValue` также может использоваться.
:::

Затем экспортируйте этот «конструктор» в фабричной функции модуля:

```cpp
static JsValue createCounterModule(JsVM &vm) {
    JsValue mod = vm.newObject();
    mod["createCounter"] = NativeCounter::constructor;
    return mod;
}
```

Использование на стороне JavaScript:

```js
import counter from '@vendor.counter'

const c = counter.createCounter(10)
console.log(c.value) // 10
c.value = 42
c.reset()
console.log(c.value) // 0
```

Здесь `c` выглядит как обычный объект JavaScript, но под капотом он на самом деле связан с экземпляром `NativeCounter`. Благодаря использованию `newMetaObject()`, JavaScript может напрямую читать и записывать свойства, объявленные через `GX_PROPERTY`, а также вызывать методы, предоставленные через `GX_METHOD`.

Если вам нужно лишь «естественным образом экспортировать объект C++ в виде объекта JavaScript» (включая свойства и методы), этого обычно достаточно.

#### Обработка контекста Applet (Applet Context)

У `newMetaObject()` есть одно распространенное ограничение: функции `GX_METHOD`, экспортируемые через систему метаобъектов, являются обычными функциями-членами C++ и не имеют доступа к `JsCtx` / `JsCallContext`, поэтому они не могут напрямую вызывать `Applet::current(ctx.vm())`, как функции модулей.

Если метод вашего объекта должен обращаться к контексту текущего приложения, например для:

- разрешения URI, приватных для приложения;
- чтения прав или конфигураций приложения;
- привязки других ресурсов к текущей песочнице внутри метода объекта;

более подходящим решением будет заставить этот объект наследоваться от `BindableObject` и привязываться к текущему `Applet` при создании объекта. Таким образом, внутри последующих `GX_METHOD` можно будет напрямую обращаться к хост-приложению через `applet()`.

Пример:

```cpp
#include "gx_applet.h"
#include "gx_bindableobject.h"
#include "gx_jsvm.h"

using namespace gx;

class NativeFile final : public BindableObject {
    GX_OBJECT_KINDS(NoneKind)

public:
    NativeFile(Applet *applet, const String &uri)
        : BindableObject(applet), m_uri(uri) {}

    GX_METHOD String resolvedUri() const {
        auto *host = applet();
        return host ? host->resolveUri(m_uri) : String();
    }

    static JsValue constructor(JsCtx ctx) {
        auto *applet = Applet::current(ctx.vm());
        if (!applet) return {};

        String uri = ctx.argc() ? ctx.arg(0).toString() : String();
        return ctx.vm().newMetaObject(new NativeFile(applet, uri));
    }

private:
    String m_uri;
};
```

::: warning Безопасность песочницы
Не реализуйте на практике функционал вроде `resolvedUri()`, который напрямую раскрывает пути к системным ресурсам — это всего лишь пример. В реальной разработке обязательно проводите проверку прав и контроль доступа во избежание утечки конфиденциальной информации в сторону JavaScript.
:::

Использование на стороне JavaScript ничем не отличается от обычного объекта `newMetaObject()`:

```js
const file = native.createFile('internal://files/config.json')
console.log(file.resolvedUri())
```

В этом примере `resolvedUri()` не имеет параметра `JsCtx`, но все равно может обращаться к `applet()`, поскольку объект был привязан к текущему приложению в момент создания.

::: warning Два предварительных условия для `BindableObject`
При использовании `BindableObject` следует учитывать две особенности:

- `BindableObject` по умолчанию имеет флаг `ExplicitDeleteKind`. Это означает, что он **не будет** автоматически уничтожен при сборке мусора (GC) объекта JavaScript. Если вы хотите вернуть ему поведение сборки мусора обычного нативного объекта, вы можете переопределить это поведение по умолчанию с помощью `GX_OBJECT_KINDS(NoneKind)`, как в примере выше.
- `BindableObject` должен быть привязан к `Applet`, иначе `applet()` всегда будет нулевым указателем (nullptr), и ни о каком контексте не может быть речи. Самый простой способ — вызывать `BindableObject(applet)` в конструкторе или выполнить привязку к текущему `Applet` сразу после создания.
:::

::: important Поведение в старых версиях
До официального релиза v0.8.0 поведение `PrimitiveObject::objectKinds()` отличалось от описанного в этом документе, пожалуйста, не опирайтесь на детали реализации старых версий.
:::

`BindableObject` — это не замена [экспорту через `newMetaObject()`](#экспорт-через-newmetaobject), а специализированное решение для тех случаев, когда методам объекта необходимо «помнить» контекст приложения, которому они принадлежат. Вводите эту концепцию только тогда, когда вам действительно нужен доступ к `Applet` изнутри `GX_METHOD`.

#### Создание `newObject()` и ручной экспорт методов

Иногда вы не хотите выставлять наружу весь интерфейс метаобъекта, а желаете использовать объект C++ просто как непрозрачный дескриптор, привязанный к объекту JavaScript, и вручную решать, какие методы могут вызываться. В этом случае для экспорта объекта можно использовать `vm.newObject()`.

При таком подходе `GX_PROPERTY` и `GX_METHOD` **не** экспортируются автоматически, поэтому вам придется самостоятельно вешать методы на объект:

```cpp
class CounterCore final : public PrimitiveObject {
    GX_OBJECT

public:
    explicit CounterCore(int initial = 0) : m_value(initial) {}

    int value() const { return m_value; }
    void add(int delta) { m_value += delta; }

private:
    int m_value = 0;
};

static JsValue createManualCounter(JsCtx ctx) {
    int initial = ctx.argc() > 0 ? ctx.arg(0).asInt(0) : 0;

    JsVM &vm = ctx.vm();
    JsValue obj = vm.newObject(new CounterCore(initial));

    obj["add"] = [](JsCtx ctx) -> JsValue {
        auto *counter = dyn_cast<CounterCore *>(ctx.thisObject().object());
        if (!counter)
            return {};
        counter->add(ctx.arg(0).asInt(0));
        return {};
    };

    obj["get"] = [](JsCtx ctx) -> JsValue {
        auto *counter = dyn_cast<CounterCore *>(ctx.thisObject().object());
        if (!counter)
            return {};
        return counter->value();
    };

    return obj;
}
```

На стороне JavaScript это выглядит как обычный объект:

```js
const c = counter.createManualCounter(10)
c.add(5)
console.log(c.get()) // 15
```

Особенность этого подхода заключается в том, что структуру JavaScript API вы определяете полностью самостоятельно, но внутри каждого метода вам приходится вручную извлекать лежащий в основе указатель C++ из объекта `this` и проверять тип с помощью `dyn_cast`. По сравнению с `newMetaObject()`, здесь больше шаблонного кода (boilerplate) и выше вероятность пропустить проверку.

Однако у этого подхода есть и явное преимущество: такие вручную добавленные функции по сути являются обычными колбэками `JsCtx`, поэтому они могут напрямую получать доступ к контексту текущего приложения через `Applet::current(ctx.vm())`, точно так же, как функции модулей. Это важное отличие от `GX_METHOD`.

Данный метод пока не позволяет экспортировать аксессоры свойств (getter / setter), а поддерживает только фиксированные значения свойств.

#### Экспорт объектов через `newProxy()`

Если вам нужно полностью перехватить чтение и запись свойств, поиск методов, ленивую генерацию полей и другие операции, вы можете использовать `vm.newProxy()`. Этот подход позволяет реализовывать очень динамичные интерфейсы, например: перенаправление доступа к произвольным именам свойств в базовый словарь, генерацию дочерних объектов по требованию или перехват записи для валидации.

Но у него есть и очевидная цена:

- поведение чтения свойств, записи свойств и вызовов методов рассредоточено по логике прокси;
- структура API больше не выражается напрямую через определение класса, как в `newMetaObject()`;
- при усложнении логики отладка становится более трудоемкой.

Поэтому `newProxy()` больше подходит для редких, высокодинамичных сценариев мостирования, а не для замены обычного экспорта объектов.

#### Правила жизненного цикла

Правила уничтожения нативных объектов (Native Object) определяются не отдельно `newMetaObject()`, а значением `objectKinds()` объекта C++:

- Если объект содержит `RootKind` и **не** содержит `ExplicitDeleteKind`, то при сборке мусора (GC) соответствующего объекта JavaScript объект C++ также уничтожается автоматически;
- Если объект является дочерним элементом другого объекта или явно объявил `ExplicitDeleteKind`, то его жизненный цикл по-прежнему управляется на стороне C++.

Для большинства «независимых оберток» простое наследование от `PrimitiveObject` без дополнительного объявления `ExplicitDeleteKind` обычно обеспечивает корректное поведение по умолчанию, то есть автоматическое уничтожение сборщиком мусора.

Если вы не знакомы с этими флагами жизненного цикла объектов, рекомендуется сначала прочитать раздел об `PrimitiveObject` в [Системе объектов](./object-system.md), прежде чем принимать решение о передаче объекта под управление сборщика мусора JavaScript.

#### Извлечение нативного объекта из `JsValue`

Иногда функция другого нативного модуля принимает этот объект в качестве аргумента. В этом случае вы можете временно извлечь базовый указатель C++ из `JsValue`:

```cpp
static JsValue getCounterValue(JsCtx ctx) {
    if (ctx.argc() < 1 || !ctx.arg(0).isObject())
        return {};

    auto *counter = dyn_cast<NativeCounter *>(ctx.arg(0).object());
    if (!counter)
        return {};
    return counter->value();
}
```

Метод `object()` предоставляет только **временный доступ** и не передает права владения. Если вам действительно нужно «забрать» объект сA стороны JavaScript, следует использовать шаблонную форму `moveObject<T>()`:

```cpp
auto *counter = value.moveObject<NativeCounter>();
```

**Не** пишите код в таком виде:

```cpp
auto *counter = dyn_cast<NativeCounter *>(value.moveObject());
```

При несоответствии типов этот код после сбоя приведения типов потеряет владение объектом, что приведет к утечке. Документация API также явно рекомендует отдавать предпочтение `moveObject<T>()`, объединяя «проверку типов» и «передачу владения» в один шаг.

::: warning Когда НЕ следует экспортировать нативные объекты
Если вы хотите вернуть лишь простые результирующие данные, такие как информация об устройстве, результат одноразового вычисления или снимок конфигурации, отдавайте приоритет возврату обычных объектов JavaScript, созданных через `newObject()`. Нативные объекты стоит внедрять только тогда, когда JavaScript должен непрерывно работать с одним и тем же экземпляром C++ в дальнейшем.
:::

## Определение и регистрация модуля

Освоив базовые инструменты моста JsVM, вы можете объединить функции C++ в полноценный нативный модуль. Модуль состоит из двух частей: **фабричной функции**, которая отвечает за создание объекта модуля и привязку к нему функций C++, и **макроса регистрации**, который регистрирует фабричную функцию в системе модулей фреймворка.

::: tip
При разработке нестандартных системных расширений рекомендуется в первую очередь рассмотреть механизм [Library Loader](#library-loader).
:::

### Структура модуля

Рассмотрим в качестве примера реализацию модуля информации об устройстве `@vendor.device`:

```cpp
#include "gx_jsvm.h"

using namespace gx;

// Функции C++ внутри модуля
static JsValue getDeviceName(JsCtx ctx) {
    return "MyDevice-Pro";
}

static JsValue getBatteryLevel(JsCtx ctx) {
    int level = /* чтение уровня заряда из драйвера */ 85;
    return level;
}

// Фабричная функция: конструирование объекта модуля и его возврат
static JsValue createDeviceModule(JsVM &vm) {
    JsValue mod = vm.newObject();
    mod["getDeviceName"] = getDeviceName;
    mod["getBatteryLevel"] = getBatteryLevel;
    return mod;
}

// Регистрация модуля, чтобы он был доступен в JavaScript по пути @vendor.device
GX_JSVM_MODULE(vendor_device, "vendor.device", createDeviceModule)
```

Макрос `GX_JSVM_MODULE` принимает три параметра: имя переменной C++, путь к модулю JavaScript (без префикса `@`) и фабричную функцию. Фабричная функция вызывается при первом импорте модуля (`import`), а возвращаемый объект `JsValue` становится модулем, получаемым на стороне JavaScript.

На стороне JavaScript приложение использует этот модуль следующим образом:

```js
import device from '@vendor.device'

const name = device.getDeviceName()
const battery = device.getBatteryLevel()
```

::: tip Это демо!
Это выглядит довольно просто, за исключением одной большой проблемы: большинство API являются асинхронными! Мы абсолютно не должны читать уровень заряда батареи в контексте выполнения JavaScript, то есть в потоке пользовательского интерфейса (UI thread), если только мы действительно не пишем демо. Для асинхронных API см. раздел [Разработка асинхронного функционала](./async.md), где приведены более подходящие паттерны и примеры.
:::

### Включение модуля

Простого объявления модуля недостаточно, его также необходимо «установить» в движок JavaScript при инициализации фреймворка. Это делается с помощью макроса `GX_JSVM_MODULE_IMPORT`:

```cpp
GX_JSVM_MODULE_IMPORT(vendor_device)
```

`GX_JSVM_MODULE` объявляет глобальную переменную в области видимости файла, а `GX_JSVM_MODULE_IMPORT` находит и вызывает метод `install()` этой переменной. Имена (первые параметры) в обоих макросах должны совпадать.

Распространена практика сбора всех вызовов `GX_JSVM_MODULE_IMPORT` в одной функции для удобства управления:

```cpp
void installVendorModules() {
    GX_JSVM_MODULE_IMPORT(vendor_device)
    GX_JSVM_MODULE_IMPORT(vendor_sensor)
    GX_JSVM_MODULE_IMPORT(vendor_bluetooth)
}
```

Вызов `install` после инициализации `AppletKit` гарантирует, что модули будут доступны при запуске приложения.

## Library Loader

Нативные модули отлично подходят для реализации системных API уровня фреймворка, которые общедоступны для всех приложений. Однако для **нестандартных функций кастомизации системы** (например, доступа к данным конкретного производителя, инкапсуляции частных SDK) или возможностей, доступных только определенным авторизованным приложениям, настоятельно рекомендуется использовать механизм **Library Loader**.

Library Loader загружает библиотеки по имени с помощью метода [`loadLibrary()`](/api/system-app.md#loadlibrary), предоставляемого модулем `@system.app`:

```js
import app from '@system.app'

const lib = app.loadLibrary('custom-library')
lib.someFunction()
```

По сравнению с нативными модулями, Library Loader имеет два существенных преимущества:

- **Отсутствие необходимости глобальной регистрации**: нет зависимости от макросов `GX_JSVM_MODULE` и `GX_JSVM_MODULE_IMPORT`, объект модуля создается по требованию в момент вызова;
- **Удобный откат (fallback) для эмулятора**: приложение на своей стороне может проверить, является ли возвращаемое значение `loadLibrary()` равным `undefined`, и изящно деградировать в среде общего симулятора до заглушки (stub), реализованной на скриптах. В то время как трюки с заглушками для импортируемых модулей вроде `import lib from '...'` являются довольно хакерскими и антипаттернными.

```js
import app from '@system.app'

// Попытка загрузить нативную библиотеку, откат к скриптовой заглушке в симуляторе
const nativeLib = app.loadLibrary('custom-library')
const lib = nativeLib || {
    someFunction() { /* реализация для симулятора */ }
}
```

За исключением способа регистрации и использования на стороне JavaScript, Library Loader во всем остальном схож с нативными модулями.

### Регистрация Library Loader

На стороне C++ функция загрузчика регистрируется через `AppletKit::setLibraryLoader()`. Загрузчик принимает экземпляр `Applet`, инициирующий вызов, и возвращает объект библиотеки (`JsValue`):

```cpp
#include "gx_appletkit.h"
#include "gx_jsvm.h"

using namespace gx;

static JsValue getDeviceName(JsCtx ctx) {
    return "MyDevice-Pro";
}

void installLibraries() {
    AppletKit::instance()->setLibraryLoader(
        "custom-library",
        [](Applet *applet) -> JsValue {
            JsVM &vm = JsVM::current();
            JsValue lib = vm.newObject();
            lib["someFunction"] = getDeviceName;
            return lib;
        }
    );
}
```

Достаточно вызвать `setLibraryLoader()` после инициализации `AppletKit`, повторная регистрация при каждом запуске приложения не требуется.

Загрузчик Library Loader принимает `Applet *`, что позволяет производить **проверку прав приложений** прямо на входе, отказывая в предоставлении функционала неавторизованным приложениям без необходимости повторять проверки внутри каждой функции модуля:

```cpp
AppletKit::instance()->setLibraryLoader(
    "custom-library",
    [](Applet *applet) -> JsValue {
        // Проверка прав: централизованный перехват неавторизованного доступа на входе
        if (!applet || !applet->permission(vendor::Permission::AccessCustomLib))
            return vm.newError("permissions denied"); // Возвращает undefined

        JsVM &vm = JsVM::current();
        JsValue lib = vm.newObject();
        lib["someFunction"] = getDeviceName;
        return lib;
    }
);
```

Если загрузчик возвращает `undefined` (т. е. стандартно сконструированный `JsValue()`), метод `app.loadLibrary()` на стороне JavaScript также получает `undefined`, на основе чего приложение может выполнить логику отката.

::: tip
В случае сбоя проверки прав в функции загрузчика не рекомендуется выбрасывать исключения — лучше просто вернуть `undefined`. Помимо возможности простого деградирования на стороне JavaScript, это позволяет избежать утечки информации о существовании модуля (если вы не хотите, чтобы неавторизованные приложения знали о наличии этой библиотеки).
:::

## Взаимодействие с песочницей приложения

Описанные в предыдущих разделах функции модулей были безгосударственными (stateless) — принимали аргументы, возвращали результаты и не хранили никакого контекста. Однако во многих реальных сценариях модулям необходимо взаимодействовать с текущим запущенным приложением: читать пути к ресурсам приложения, языковые настройки или удерживать долгоживущий объект C++ внутри песочницы приложения. Для этого требуются возможности, предоставляемые классом `Applet`.

### Получение контекста текущего приложения

Получите экземпляр приложения, к которому принадлежит вызывающая сторона, с помощью метода `Applet::current()`:

```cpp
#include "gx_applet.h"

static JsValue readPreference(JsCtx ctx) {
    auto applet = Applet::current(ctx.vm());
    // Поскольку дальнейшие операции зависят от applet, обязательно проверьте успешность получения контекста
    if (!applet) return JsValue();

    // Чтение приватного пути хранения данных приложения
    String storagePath = applet->resolveUri("internal://files/preferences.json");
    // ...
}
```

Экземпляр `Applet` управляется фреймворком автоматически, каждое приложение работает в своем собственном изолированном Realm JavaScript. Метод `Applet::current()` выводит соответствующий экземпляр приложения на основе текущего Realm, поэтому при вызове одной и той же функции модуля из разных приложений получаются независимые контексты.

### Управление жизненным циклом ресурсов

Если функции модуля требуется выделить объект C++ с длительным временем жизни (например, фоновую задачу, которая непрерывно отслеживает состояние оборудования), **ни в коем случае** не используйте глобальные переменные или «голые» указатели (raw pointers) для удержания ресурсов между вызовами — это позволит ресурсам ускользнуть из-под контроля песочницы приложения, что приведет не только к невозможности освобождения ресурсов после завершения работы приложения, но и к потере ключевых гарантий безопасности, предоставляемых песочницей.

Здесь действует строгое требование безопасности: **нативный модуль должен гарантировать, что все пути доступа к объектам C++ проходят строгую валидацию владения и типов**, а не просто предоставляют «легальные пути» с возможностью их обойти. Правильный способ добиться этого — полностью делегировать управление жизненным циклом объектов песочнице `Applet` и в **каждой** функции модуля, принимающей целочисленный дескриптор (handle), принудительно использовать `takeObject<T>()` для валидации. Это неизменяемый инвариант, который нельзя опускать (подробнее см. ниже).

В качестве примера рассмотрим функционал непрерывного мониторинга состояния датчика, демонстрирующий этот безопасный механизм привязки жизненного цикла.

::: tip
Код в этом разделе по сути является упрощенным аналогом принципа `AsyncSession` из главы [Разработка асинхронного функционала](./async.md) и используется исключительно для демонстрации концепции. В реальной разработке настоятельно рекомендуется использовать готовые средства, связанные с `AsyncSession`, для обработки асинхронных задач — под капотом они используют те же методы, которые описаны в данном разделе.
:::

Допустим, у нас есть датчик, мониторинг которого приложение должно запускать при инициализации, затем многократно считывать актуальные данные и вручную останавливать мониторинг при ненадобности. Сначала мы определяем носитель этой фоновой задачи:

```cpp
class SensorListener : public PrimitiveObject {
    GX_OBJECT
public:
    SensorListener() {
        // Запуск датчика, запрос аппаратных ресурсов низкоуровневого драйвера...
    }
    ~SensorListener() override {
        // Остановка датчика, освобождение связанных аппаратных ресурсов...
    }
    int latestValue() const { return m_value; }

private:
    int m_value = 0;
};
```

#### Привязка объекта к песочнице

Используйте метод `Applet::bindObject()` для привязки экземпляра к песочнице текущего приложения, возвращая целочисленный дескриптор, который удерживается на стороне JavaScript:

```cpp
static JsValue startSensor(JsCtx ctx) {
    auto applet = Applet::current(ctx.vm());
    if (!applet) return {};

    auto *listener = new SensorListener();
    // Передача объекта под управление Applet и получение целочисленного дескриптора (ID)
    int bindId = applet->bindObject(listener);

    // Возврат ID в JavaScript в качестве уникального удостоверения для последующих операций с этим объектом
    return bindId;
}
```

Поскольку объект теперь **управляется** песочницей, даже если приложение аварийно завершится или будет принудительно закрыто системой в процессе выполнения задачи, песочница автоматически очистит все привязанные объекты при своем уничтожении, предотвращая утечку ресурсов.

#### Безопасное извлечение объекта

Когда на стороне JavaScript требуется выполнить операцию с созданным ранее объектом, **обязательно** извлекайте экземпляр через `Applet::takeObject<T>()` по дескриптору, а не выполняйте никакие формы «голого приведения типов» (naked casting):

```cpp
static JsValue readSensor(JsCtx ctx) {
    auto applet = Applet::current(ctx.vm());
    if (!applet || ctx.argc() < 1) return {};

    int bindId = ctx.arg(0).asInt();
    auto *listener = applet->takeObject<SensorListener>(bindId);
    if (!listener) return {}; // Если ID недействителен или типы не совпадают, возвращаем nullptr

    return listener->latestValue();
}
```

Метод `applet->takeObject<T>()` обращается только к ID, принадлежащим **текущей песочнице** (что предотвращает несанкционированный кросс-аппликационный доступ), а затем проверяет **соответствие типов** с помощью метаинформации объекта. Непустой указатель возвращается только в том случае, если пройдены оба уровня проверки.

::: danger Обязательный доступ через `takeObject<T>()`
Целочисленный ID, поступающий из JavaScript, совершенно ненадежен на стороне C++ — он может быть поддельным или оказаться устаревшей ссылкой. Отсутствие валидации приводит к серьезным уязвимостям безопасности:

```cpp
// ❌ Категорически запрещено!
static JsValue readSensor(JsCtx ctx) {
    auto bindId = ctx.arg(0).asInt();
    // Использование только нешаблонной версии takeObject + static_cast обходит проверку типов и границ песочницы
    auto *binded = applet->takeObject(bindId);
    // Опасно: static_cast не выполняет проверки во время выполнения, переданный binded может вообще не быть SensorListener!
    auto *listener = static_cast<SensorListener *>(binded);
    return listener->latestValue(); // Может привести к произвольному чтению/записи памяти
}
```
:::

#### Отвязка и уничтожение

Когда необходимо активно завершить задачу со стороны C++ и полностью освободить ресурсы, сначала получите и проверьте тип с помощью `takeObject<T>()`, затем снимите с управления через `unbindObject()` и выполните ручное уничтожение:

```cpp
static JsValue stopSensor(JsCtx ctx) {
    Applet *applet = Applet::current(ctx.vm());
    if (!applet || ctx.argc() < 1) return {};

    int bindId = ctx.arg(0).asInt();
    auto *listener = applet->takeObject<SensorListener>(bindId);
    if (listener) {
        applet->unbindObject(listener); // Удаление из списка автоматического управления
        delete listener;                // Ручное уничтожение
    }
    return {};
}
```

Полный цикл использования на стороне фронтенда JavaScript:

```javascript
import sensor from '@vendor.sensor'

// Запуск и сохранение удостоверения (дескриптора)
const id = sensor.startSensor()
// ... многократное чтение
const value = sensor.readSensor(id)
// Задача завершена, освобождение ресурсов
sensor.stopSensor(id)
```

Благодаря гарантиям безопасности от `bindObject`, даже если приложение забудет вызвать `stopSensor()`, песочница автоматически освободит все привязанные объекты при завершении своей работы.

::: important Обязательная автоматическая отвязка
Поскольку код JavaScript не заслуживает доверия, нельзя полагаться на то, что он вызовет функции освобождения ресурсов. Для вредоносных приложений утечки песочницы, вызванные утечками ссылок JavaScript, являются эффективным вектором атак. Следовательно, **все объекты, привязанные к песочнице, должны автоматически отвязываться при уничтожении песочницы**, чтобы гарантировать, что независимо от действий JavaScript утечки ресурсов не произойдет.

Любой проект, требующий отвязки со стороны JavaScript, является небезопасным и должен быть исключен.
:::

### Защита безопасности

Несмотря на множество упомянутых выше требований безопасности, их может быть недостаточно для устранения всех рисков. Для дальнейшего укрепления обороны мы рекомендуем напрямую ограничивать права доступа к расширяемым модулям только доверенными приложениями. Вы можете проверять права или идентификационную информацию `Applet` прямо в фабричной функции модуля и отклонять несоответствующие запросы:

```cpp
static JsValue createDeviceModule(JsVM &vm) {
    auto applet = Applet::current(vm);
    if (!applet || !applet->permission(
                    vendor::Permission::AccessDeviceInfo)) {
        // При отсутствии прав возвращаем пустой объект или выбрасываем исключение
        return vm.newError("permissions denied");
    }

    // Создание объекта модуля и предоставление функционала возможно только после авторизации
    JsValue mod = vm.newObject();
    mod["getDeviceName"] = getDeviceName;
    // ...
    return mod;
}
```

Такая стратегия позволяет эффективно блокировать несанкционированный доступ на входе. Даже если сама функция модуля окажется недостаточно надежной, злоумышленники не смогут использовать ее для получения конфиденциальной информации или выполнения вредоносных операций.

Проверка прав на входе для Library Loader уже была рассмотрена в соответствующей документации.
