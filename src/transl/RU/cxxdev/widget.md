# Руководство по разработке контролов

В Glyphix все видимые UI-элементы являются `Widget` (контролами). Фреймворк содержит встроенные стандартные контролы, такие как кнопки, метки, изображения и области прокрутки, но производителям устройств часто требуется разрабатывать кастомные контролы с учетом особенностей своего продукта. Например, умные часы могут требовать особой анимации списков из-за маленького круглого экрана, а приборные панели — специализированных контролов для графиков. В этом документе описывается, как реализовать новый контрол на C++.

## Основы контролов

`Widget` представляет собой прямоугольную область, которая имеет такие базовые свойства, как позиция, размер, видимость и прозрачность, может принимать события и отвечает за отрисовку собственного содержимого. Контролы организованы в древовидную структуру: родительский контрол содержит несколько дочерних, а координаты дочернего контрола задаются относительно родительского.

Каждый контрол имеет **цикл логического обновления**: когда состояние контрола изменяется (например, обновились данные), вызывается метод `update()`, который помечает его как «требующий перерисовки». Фреймворк выполнит общую перерисовку всех помеченных контролов в следующем кадре рендеринга, а не мгновенно. Это позволяет избежать многократной избыточной перерисовки в пределах одного кадра.

### Контролы и система компонентов

UI-контролы обычно реализуются как C++ классы, наследуемые от `Widget`, и соответствуют стандартному объектно-ориентированному дизайну C++. Реактивный фреймворк и система компонентов Glyphix позволяют напрямую экспортировать эти C++ контролы в качестве нативных компонентов и использовать их в шаблонном, декларативном стиле.

Такой дизайн позволяет относительно независимо вести разработку контролов на стороне C++ и использование компонентов во фронтенде, сохраняя привычные для обеих сторон подходы к разработке. Например, на C++ вы можете создавать интерфейс способом, похожим на LVGL или Qt Widgets, не принимая при этом популярный во фронтенде декларативный стиль.

### Сравнение с другими фреймворками

По своему дизайну система контролов Glyphix похожа на традиционные C/C++ UI-фреймворки, такие как Qt Widgets или LVGL. Поэтому вы заметите, что подходы и система знаний для разработки нового контрола очень близки к этим фреймворкам:
- Создание нового класса контрола через наследование от `Widget`;
- Наличие ключевых механизмов, таких как система компоновки (layout), система событий и система отрисовки;
- Реализация привязки данных (data binding) и нотификации о событиях через систему свойств и механизм сигналов;
- Наличие геометрических понятий, таких как система координат и размеры, а также поддержка вложенных древовидных структур контролов.

::: tip Не рекомендуется использовать C++ контролы для разработки UI
Изначальный замысел Glyphix не предполагает прямую разработку UI на стороне C++, поэтому мы не предоставляем соответствующую документацию и примеры.
:::

## Создание кастомного контрола

В этом разделе на примере контрола кольцевого индикатора выполнения (`ProgressRing`) пошагово описаны все элементы, необходимые для разработки кастомного контрола.

::: tip Комплексный пример контрола
Пример [slider-demo](./widget-slider-demo.md), поставляемый с SDK, представляет собой полную практическую реализацию всех концепций из этого документа, включая наследование существующих контролов, отрисовку, обработку событий, объявление свойств, анимацию `ValueAnimation` и кастомизацию через `StyleEngine`. Рекомендуется ознакомиться с ним после прочтения данного документа.
:::

### Определение класса контрола

Создайте новый контрол, унаследовав его от `Widget`. В самом начале определения класса добавьте макрос `GX_OBJECT` и **переопределите** виртуальную функцию **`event()`** в качестве точки входа для обработки событий:

```cpp
// progressring.h
#include "gx_widget.h"

class ProgressRing : public Widget {
    GX_OBJECT
public:
    explicit ProgressRing(Widget *parent = nullptr)
        : Widget(parent), m_value(0) {}

    int value() const { return m_value; }
    void setValue(int v);
    bool event(Event *event) override;

    GX_PROPERTY(int value, get value, set setValue, signal valueChanged)
    Signal<int> valueChanged;

protected:
    void paintEvent(PaintEvent *event);

    // EventDispatch должен иметь доступ к protected методам, объявляемเพื่อน (friend)
    friend struct EventTraits<ProgressRing>;

private:
    int m_value;  // [0, 100]
};
```

Макрос `GX_OBJECT` обязателен: он запускает генератор метаобъектов (MOC) для создания метаданных этого класса, что позволяет фреймворку (системе свойств, анимации и компонентов) корректно распознавать контрол (подробнее см. в разделе [Система объектов](./object-system.md)).

### Отрисовка контрола

В `.cpp` файле подключите `gx_widgetevent.h` и реализуйте методы `event()` и `paintEvent()`:

```cpp
// progressring.cpp
#include "progressring.h"
#include "gx_widgetevent.h"

bool ProgressRing::event(Event *event) {
    return EventDispatch<Widget>{}(this, event);
}

void ProgressRing::paintEvent(PaintEvent *event) {
    Widget::paintEvent(event);
    Painter p(this);
    // ... см. подробности в главе об отрисовке
}
```

Кастомная отрисовка выполняется путем реализации метода `paintEvent()`. При создании объекта `Painter` передайте в него указатель `this`, чтобы получить контекст рисования, связанный с текущим контролом, после чего вызывайте различные методы отрисовки. Полное описание API `Painter` см. в разделе [Отрисовка](./painting.md).

### Обработка событий

Система событий Glyphix **не зависит от виртуального наследования** для диспетчеризации событий. Методы `paintEvent()`, `gestureEvent()` и другие **не** являются `virtual`, поэтому при объявлении **нельзя** использовать ключевое слово `override` (это вызовет ошибку компиляции). Фреймворк использует `EventDispatch` для маршрутизации вызовов к правильной функции-обработчику на **этапе компиляции** на основе типа события.

Единственная виртуальная функция, которую требуется (и необходимо) переопределить — это **`event()`**, в которой происходит делегирование в `EventDispatch`:

```cpp
bool ProgressRing::event(Event *event) {
    return EventDispatch<Widget>{}(this, event);
}
```

Первым шаблонным параметром `EventDispatch` обычно является **непосредственный базовый класс** (тот класс, от которого наследуется `ProgressRing`, в данном случае `Widget`). На этапе компиляции проверяется, объявил ли текущий класс соответствующую функцию-обработчик напрямую; если да, она вызывается, в противном случае происходит автоматический откат к реализации базового класса. Возвращаемое значение `bool` у функции-обработчика означает, было ли событие перехвачено (потреблено); возвращаемое значение `void` трактуется как событие, которое было обработано.

::: tip Совет по выбору базового класса
Выбор параметра базового класса для `EventDispatch` имеет некоторые оптимизационные нюансы. Обычно можно выбрать непосредственный базовый класс, но допускается и использование вышестоящих классов-предков, что приводит к незначительным различиям в размере кода и производительности. Тем не менее, обычно не стоит над этим сильно задумываться или бояться ошибок — если код компилируется, диспетчеризация событий будет работать корректно.
:::

::: important
Когда в дальнейшем тексте упоминается «переопределение метода `xxxEvent()`», обратите внимание, что речь идет лишь об **объявлении** в классе производного контрола функции-члена с такой же сигнатурой, как у обработчика базового класса, но **не виртуальной**. Это **не** виртуальная функция, к ней нельзя добавлять `override`, и она не зависит от механизма виртуальных функций для диспетчеризации событий.

IDE может выдавать подсказку изменить эти функции-члены на виртуальные — проигнорируйте эту подсказку.
:::

Если необходимо обрабатывать жесты ввода, объявите `gestureEvent()` и реализуйте её в классе:

```cpp
// Добавьте объявление в секции protected заголовочного файла:
bool gestureEvent(GestureEvent *event);

// Реализация в .cpp:
bool ProgressRing::gestureEvent(GestureEvent *event) {
    if (event->type() == Event::Press) {
        // ...
        return true;   // Возврат true означает, что событие обработано и не передается родительскому контролу
    }
    return false;
}
```

Поддерживаемые типы событий:

| Сигнатура метода | Момент срабатывания |
|---|---|
| `bool gestureEvent(GestureEvent *)` | События жестов, включая Press, Pan, Swipe и т.д. |
| `bool wheelEvent(WheelEvent *)` | Ввод с колесика или энкодера (например, вращающийся безель) |
| `bool keyEvent(KeyEvent *)` | Физические кнопки |
| `void resizeEvent(ResizeEvent *)` | Изменение размера контрола |
| `void moveEvent(MoveEvent *)` | Изменение позиции контрола |
| `bool focusEvent(FocusEvent *)` | Изменение фокуса |
| `void paintEvent(PaintEvent *)` | Запрос на перерисовку |
| `bool layoutEvent(LayoutEvent *)` | Запрос на компоновку |
| `void tickEvent(TickEvent *)` | Кадровый тикер (требуется явный вызов `requestNextTick()` для активации) |

Если для текущего контрола некоторые функции обработки событий являются **обязательными для реализации**, вы можете объявить их в шаблонных параметрах `EventDispatch`. В случае пропуска или несоответствия сигнатур возникнет ошибка компиляции:

```cpp
bool MyButton::event(Event *event) {
    // Если paintEvent или gestureEvent объявлены некорректно, компиляция завершится с ошибкой
    return EventDispatch<Widget, PaintEvent, GestureEvent>{}(this, event);
}
```

::: tip Объявление обязательных функций обработки событий
Хотя можно использовать `EventDispatch<Widget>` для автоматической диспетчеризации всех событий, **настоятельно рекомендуется** явно объявлять типы событий, которые должен обрабатывать текущий контрол. Это позволяет на этапе компиляции по максимуму выявлять пропуски или опечатки и снижает нагрузку при ручной проверке.
:::

### Свойства и сигналы

Используйте макрос `GX_PROPERTY` для экспорта свойств во фреймворк, чтобы их можно было связывать на уровне приложений или использовать в качестве целей для анимации свойств:

```cpp
// Объявление свойства value, геттер — value(), сеттер — setValue()
// Поле signal связывает сигнал изменения для подписки реактивным фреймворком
GX_PROPERTY(int value, get value, set setValue, signal valueChanged)
```

После объявления свойство `value` может:
- Напрямую связываться шаблонами уровня приложения (например, `<progress-ring :value="progress"/>`);
- Плавного анимироваться системой анимации свойств (когда тип свойства поддерживает интерполяцию).

Вызывайте метод `update()` в сеттере для запуска перерисовки и в нужный момент испускайте сигнал для уведомления внешнего кода:

```cpp
void ProgressRing::setValue(int v) {
    if (m_value == v) return;
    m_value = v;
    update();          // Помечаем для перерисовки в следующем кадре
    valueChanged(v);   // Испускаем сигнал
}
```

`Signal<T>` — это обычная шаблонная переменная-член, которая испускается точно так же, как вызов функции. Сигналы без аргументов используют `Signal<>` и вызываются без параметров. Полную семантику свойств и сигналов см. в соответствующем разделе [Системы объектов](./object-system.md).

### Компоновка (Layout)

После создания экземпляра контрола его позиция и размер задаются вручную через `setGeometry()`. Если родительский контрол использует автоматическую компоновку, переопределите `sizeHint()` для объявления желаемого размера контрола:

```cpp
Size ProgressRing::sizeHint() const {
    return Size(80, 80);
}
```

Для контейнерных контролов, которым требуется самостоятельно управлять компоновкой дочерних элементов, реализуйте расчет геометрических параметров в `LayoutEvent` или подключите предоставляемый фреймворком класс компоновки (например, `FlexLayout`) через `setLayout()`. Подробнее см. в разделе [Компоновка и размеры](#компоновка-и-размеры).

## Отрисовка

### Инициализация Painter

Для начала отрисовки создайте экземпляр `Painter` в функции-члене `paintEvent()` контрола:

```cpp
void ProgressRing::paintEvent(PaintEvent *event) {
    Painter p(this);
    // Все последующие операции рисования выполняются через p
}
```

Система координат рисования использует **левый верхний угол контрола в качестве начала координат** ($+x$ вправо, $+y$ вниз), единицы измерения — пиксели. Метод `rect()` возвращает локальный прямоугольник текущего контрола `(0, 0, width(), height())` и является наиболее часто используемой опорной областью при рисовании.

Если для контрола на уровне приложения или через `StyleModifier` заданы управляемые фреймворком стилевые свойства (например, цвет фона), вы можете вызвать базовый класс перед отрисовкой кастомного содержимого:

```cpp
void ProgressRing::paintEvent(PaintEvent *event) {
    Widget::paintEvent(event);  // Сначала рисуем фон, управляемый фреймворком (если есть)
    Painter p(this);
    // ...
}
```

Если вы не вызываете базовый класс, стили фона, управляемые фреймворком, будут проигнорированы, и за всё визуальное представление контрола будет отвечать исключительно его собственный метод `paintEvent`.

### Состояние рисования

`Painter` поддерживает набор текущих состояний рисования; каждый вызов рисования использует текущее состояние до тех пор, пока оно не будет изменено.

#### Кисть (Brush)

Кисть определяет цвета для методов **заполнения** (`fillRect`, `fillRoundedRect`, `fillPath` и др.), а также цвет **текста**:

```cpp
p.setBrush(Color(200, 200, 200));   // RGB серый
p.setBrush(Color{"#35a7ff"});       // Шестнадцатеричная строка
p.setBrush(Color::White);           // Предопределенная константа
p.setBrush(Color(0xff4486ff));      // ARGB шестнадцатеричное число (0xff — полная непрозрачность)
```

#### Перо (Pen)

Перо определяет цвет и толщину линии для методов **обводки** (`drawRect`, `drawArc`, `drawLine` и др.):

```cpp
Pen pen(Color(64, 156, 255));
pen.setSize(6);    // Ширина линии 6px
p.setPen(pen);
```

#### Другие состояния

```cpp
p.setFont(Font(18));     // Размер шрифта 18px, влияет на drawText()
p.setOpacity(127);      // Прозрачность [0, 255], влияет на все последующие операции рисования
```

Все состояния действуют только на текущий экземпляр `Painter`. Экземпляры `Painter`, созданные разными контролами, полностью независимы и не мешают друг другу.

### Базовые фигуры

#### Прямоугольник

```cpp
p.setBrush(Color::White);
p.fillRect(rect());                    // Заполнение всей области контрола
p.fillRect(Rect(10, 10, 60, 20));      // Заполнение указанного прямоугольника

p.fillRoundedRect(rect(), 8.0f);       // Заполнение скругленного прямоугольника, радиус скругления 8px
p.drawRoundedRect(rect(), 8.0f);       // Обводка скругленного прямоугольника (без заполнения, используется цвет пера Pen)
```

Когда радиус скругления равен половине меньшей из сторон (широты или высоты), прямоугольник превращается в капсулу, что очень часто используется в кнопках и индикаторах прогресса:

```cpp
float radius = min(box.width(), box.height()) * 0.5f;
p.fillRoundedRect(box, radius);
```

#### Линия

```cpp
p.drawLine(Point(0, cy), Point(width(), cy));   // Горизонтальная разделительная линия
```

#### Дуга

Метод `drawArc` принимает координаты центра и радиус для задания дуги. Упараметры `startAngle` / `endAngle` измеряются в градусах, причем $0^\circ$ соответствует положению на 3 часа, а значения увеличиваются по часовой стрелке:

```cpp
float cx = width() / 2.0f;
float cy = height() / 2.0f;
float radius = min(cx, cy) - 4.0f;

// Рисуем полную фоновую дугу (фоновое кольцо) от -90° (12 часов) на полный круг
Pen bgPen(Color(200, 200, 200));
bgPen.setWidth(6);
p.setPen(bgPen);
p.drawArc({cx, cy}, radius, -90.0f, -90.0f + 360.0f);

// Рисуем дугу прогресса (от 12 часов по часовой стрелке до позиции, соответствующей m_value)
if (m_value > 0) {
    Pen fgPen(Color(64, 156, 255));
    fgPen.setWidth(6);
    p.setPen(fgPen);
    p.drawArc({cx, cy}, radius, -90.0f, -90.0f + 360.0f * m_value / 100.0f);
}
```

Визуальная толщина дуги определяется толщиной линии текущего пера (`Pen`).

### Векторный путь (`VectorPath`)

Для сложных фигур, которые нельзя описать прямоугольниками и дугами, используйте `VectorPath` для построения произвольных контуров с последующей визуализацией через `fillPath()` или `drawPath()`.

```cpp
#include "gx_vectorpath.h"
```

Принцип работы `VectorPath` напоминает движение пера: вы опускаете перо с помощью `moveTo`, рисуете прямые линии с помощью `lineTo` и дуги с помощью `arcTo`, описывая контур, который затем рендерится единым вызовом `Painter`.

#### Путь из прямых линий

```cpp
VectorPath path;
path.moveTo(x0, y0);   // Опустить перо (без рисования)
path.lineTo(x1, y1);   // Прямая линия до (x1, y1)
path.lineTo(x2, y2);
path.lineTo(x0, y0);   // Возврат в начальную точку для формирования замкнутого треугольника

p.fillPath(path, Color(64, 156, 255)); // Заполнение замкнутой области
```

Метод `fillPath()` автоматически обрабатывает путь как замкнутую область, даже если в конце не был выполнен явный возврат в начальную точку. Метод `drawPath()` рисует только контур пути текущим пером (`Pen`) без заливки.

#### Путь из дуг

Параметры `arcTo` задают центр, радиусы по осям $x$ и $y$ (разные для эллипса), начальный угол и угол охвата (в градусах, по часовой стрелке):

```cpp
// Рисуем горизонтальную капсулу: полукруг слева + полукруг справа, arcTo автоматически соединяет отрезки линией
float r  = rect.height() * 0.5f;
float x1 = rect.left() + r;
float x2 = rect.right() - r;
float y  = rect.top() + r;

VectorPath path;
path.arcTo(PointF(x1, y), r, r, 90.0f, 270.0f);    // Левый полукруг (против часовой стрелки от 9 до 3 часов)
path.arcTo(PointF(x2, y), r, r, -90.0f, 90.0f);    // Правый полукруг (против часовой стрелки от 3 до 9 часов)
p.fillPath(path);
```

`arcTo` автоматически вставляет прямую линию между текущей конечной точкой пути и началом новой дуги, поэтому две дуги плавно соединяются на стыках без необходимости вызывать `lineTo` вручную.

#### Кривые

Используйте `conicTo` или `cubicTo` для построения квадратичных или кубических кривых Безье. В сочетании с `moveTo` и `lineTo` это позволяет описывать сложные контуры:

```cpp
VectorPath path;
path.moveTo(x0, y0);
// Квадратичная кривая Безье, где (cx, cy) — контрольная точка
path.conicTo(cx, cy, x1, y1);
// Кубическая кривая Безье, где (cx1, cy1) и (cx2, cy2) — контрольные точки
path.cubicTo(cx1, cy1, cx2, cy2, x2, y2);
// Заполнение пути указанной кистью
p.fillPath(path, brush);
```

#### Пример комбинированного пути

Комбинируя несколько команд, можно построить фигуру любой сложности. Рассмотрим заполненную волнистую область в `WaveSlider`: путь включает в себя верхнюю волнистую ломаную линию и нижнюю скругленную границу:

```cpp
VectorPath path;
path.moveTo(leftX, waveY(leftX));
for (int i = 1; i <= sampleCount; ++i) {
    float x = leftX + (rightX - leftX) * float(i) / sampleCount;
    path.lineTo(x, waveY(x));           // Контур верхней волны
}
path.lineTo(rightX, bottomEdge(rightX)); // Правый спуск
for (int i = sampleCount - 1; i >= 0; --i) {
    float x = leftX + (rightX - leftX) * float(i) / sampleCount;
    path.lineTo(x, bottomEdge(x));       // Нижняя граница (возврат вдоль низа скругленного прямоугольника)
}
path.lineTo(leftX, waveY(leftX));        // Возврат в начальную точку
p.fillPath(path);
```

### Текст

Метод `drawText()` упорядочивает и выводит текст в пределах заданного прямоугольника. Цвет текста определяется текущей кистью (`Brush`), а шрифт — методом `setFont()`:

```cpp
p.setFont(Font(18));
p.setBrush(Color(50, 50, 50));
p.drawText(rect(), format("{}%", m_value), AlignCenter);
```

::: tip Форматирование строк
`format()` — это функция форматирования, предоставляемая фреймворком. Ее синтаксис похож на [`std::format`](https://en.cppreference.com/w/cpp/utility/format/format) и доступен кроссплатформенно.
:::

Флаги выравнивания можно свободно комбинировать:

| Флаг | Значение |
|---|---|
| `AlignLeft` | Горизонтально по левому краю |
| `AlignHCenter` | Горизонтально по центру |
| `AlignRight` | Горизонтально по правому краю |
| `AlignTop` | Вертикально по верхнему краю |
| `AlignVCenter` | Вертикально по центру |
| `AlignBottom` | Вертикально по нижнему краю |
| `AlignCenter` | Горизонтально + вертикально по центру (эквивалентно `AlignHCenter \| AlignVCenter`) |

Метод `font()` возвращает текущий шрифт, унаследованный контролом от системы стилей. Использование его при отрисовке позволяет контролу автоматически подстраиваться под изменение размера шрифта в приложении:

```cpp
p.setFont(font());   // Используем шрифт из унаследованного стиля контрола, а не фиксированный размер
```

`drawText()` также поддерживает более сложную верстку текста, например, многострочный текст, автоматический перенос строк и т. д. Подробности см. в документации по API.

### Изображения

Метод `drawImage()` отрисовывает изображение внутри заданного прямоугольника:

```cpp
Image img{"file://path/to/icon.png"};
p.drawImage(widget->rect(), img); // Отрисовка изображения в указанной области без автоматического масштабирования
```

На практике изображения обычно загружаются из ресурсной системы, а способ их загрузки зависит от платформы и конфигурации сборки.

### Полный пример

Ниже приведен полный метод `paintEvent` для `ProgressRing`, объединяющий рассмотренные выше возможности отрисовки:

```cpp
void ProgressRing::paintEvent(PaintEvent *event) {
    // Если у контрола есть стиль фона, управляемый фреймворком, вызовите базовый класс
    // Widget::paintEvent(event);

    Painter p(this);

    float cx = width() / 2.0f;
    float cy = height() / 2.0f;
    float radius = min(cx, cy) - 4.0f;
    float startAngle = -90.0f;   // Начинаем с позиции 12 часов

    // Рисуем серое фоновое кольцо
    Pen bgPen(Color(200, 200, 200));
    bgPen.setWidth(6);
    p.setPen(bgPen);
    p.drawArc({cx, cy}, radius, startAngle, startAngle + 360.0f);

    // Рисуем цветную дугу прогресса
    if (m_value > 0) {
        Pen fgPen(Color(64, 156, 255));
        fgPen.setWidth(6);
        p.setPen(fgPen);
        p.drawArc({cx, cy}, radius,
          startAngle, startAngle + 360.0f * m_value / 100.0f);
    }

    // Выводим процентное значение в центре кольца
    p.setFont(Font(18));
    p.setBrush(Color(50, 50, 50));
    p.drawText(rect(), format("{}%", m_value), AlignCenter);
}
```

## Компоновка и размеры

Переопределите метод `sizeHint()`, чтобы сообщить системе компоновки «желаемый размер» контрола. Когда родительский контрол использует автоматическую компоновку, она будет опираться на это значение при распределении пространства:

```cpp
Size ProgressRing::sizeHint() const {
    return Size(80, 80);  // Рекомендуется отображать как 80×80px
}
```

Если высота контрола зависит от его ширины (например, изображение с фиксированным соотношением сторон), переопределите `heightForWidth()`:

```cpp
int AspectWidget::heightForWidth(int width) const {
    return width; // Квадратная пропорция
}
```

Для случаев, когда требуется вручную управлять компоновкой дочерних элементов, переопределите метод `layoutEvent()` и задайте геометрию дочерних элементов внутри него:

```cpp
bool ContainerWidget::layoutEvent(LayoutEvent *event) {
    // Располагаем дочерние элементы сверху вниз
    int y = 0;
    for (auto *child : children()) {
        auto *w = dyn_cast<Widget *>(child);
        if (w && w->isVisible()) {
            w->setGeometry(0, y, width(), w->sizeHint().height());
            y += w->height();
        }
    }
    return true;
}
```

Вы также можете использовать готовые классы компоновки, предоставляемые фреймворком (например, `FlexLayout`, `StackLayout`), подключив их через `setLayout(new FlexLayout())`.

::: tip Использование готовых классов компоновки
Если вы не создаете контейнерный контрол с нестандартной компоновкой, рекомендуется использовать готовые классы компоновки фреймворка для управления дочерними элементами. В этом случае переопределять `layoutEvent()` не требуется.

Реализация собственного полноценного алгоритма компоновки — задача довольно сложная: требуется корректно обрабатывать взаимодействие с `sizeHint()` и другими аспектами, а также учитывать оптимизацию производительности.
:::

## Анимация

Фреймворк предоставляет три типа механизмов анимации: **анимация стилей**, **анимация свойств** и **`ValueAnimation`**. Первые два типа в основном используются на **уровне приложений** (т. е. со стороны использования контролов), в то время как при реализации кастомных контролов чаще всего напрямую применяется `ValueAnimation`.

### ValueAnimation

`ValueAnimation<T>` — это класс анимации, выполняющий интерполяцию для произвольного типа `T`. На каждом кадре он вычисляет результат интерполяции на основе текущего прогресса и передает его через сигнал `value`. Вам достаточно лишь подключить этот сигнал к собственной логике обновления:

```cpp
#include "gx_valueanimation.h"

// Объявляем объект анимации в членах контрола, обычно в виде указателя для динамического создания и удаления при необходимости
ValueAnimation<int> *m_animation = nullptr;
```

```cpp
// Инициализация и запуск в подходящем месте
m_animation = new ValueAnimation<int>;
m_animation->setValueLimits(0, 100);  // Интерполяция от 0 до 100
m_animation->setDuration(800);        // 800 миллисекунд
m_animation->value.connect(this, &MyWidget::onAnimationValue);
m_animation->start();

// Обратный вызов кадра: прием интерполированного значения для текущего кадра
void MyWidget::onAnimationValue(int v) {
    m_currentValue = v;
    update();  // Запуск перерисовки
}
```

По завершении анимации испускается сигнал `finished`. Если вам не требуется вручную управлять жизненным циклом, вы можете использовать стратегию `DeleteOnStop`, чтобы анимация автоматически удалялась после завершения воспроизведения:

```cpp
// Объект анимации не требует внешнего доступа, сразу создаем через new и настраиваем автоудаление
auto *anim = new ValueAnimation<int>;
anim->setValueLimits(0, 100);
anim->setDuration(500);
anim->value.connect(this, &MyWidget::onValue);
anim->start(AbstractAnimation::DeleteOnStop);  // Автоматический delete после завершения
```

Фреймворк имеет встроенную поддержку интерполяции для следующих типов: `int`, `float` (и других числовых типов), `Color`, `Point`, `Pen`, `Brush`, `Length`, `Transform` и др.

Другие часто используемые настройки:

```cpp
// Бесконечный цикл воспроизведения
anim->setRepeat(AbstractAnimation::Infinity);

// Обратное воспроизведение «туда-обратно» (вперед → назад → вперед…)
anim->setDirection(AbstractAnimation::Alternate);

// Установка кривой замедления (easing curve)
#include "gx_easecurve.h"
anim->setEaseCurve(easing::make_curve<easing::Ease>());
```

### Анимация стилей и свойств

**Анимация стилей** (`StyleAnimation`) определяет эффекты перехода способом, похожим на CSS transition, и воспроизводится фреймворком автоматически при изменении стилевого состояния контрола. Она преимущественно используется в конфигурации стилей компонентов уровня приложения.

**Анимация свойств** (`PropertyAnimation`) управляет свойствами, объявленными через `GX_PROPERTY`, по строковому имени свойства. Она часто применяется на уровне приложения для анимации свойств контролов:

```cpp
#include "gx_propertyanimation.h"

auto *anim = new PropertyAnimation(widget, "value");
anim->setStartValue(Variant{0});
anim->setStopValue(Variant{100});
anim->setDuration(1000);
anim->start(AbstractAnimation::DeleteOnStop);
```

При реализации самого контрола использование анимации свойств, как правило, не требуется, поскольку `ValueAnimation` работает напрямую и не имеет накладных расходов на поиск свойств по имени.

## Контролы отображения текста

При реализации контролов, содержащих текстовый контент, помимо базовой логики отрисовки, необходимо решать задачи измерения текста, кэширования компоновки, взаимодействия со стилями и т. д. `Label` — самый типичный текстовый контрол во фреймворке, и его реализация может служить эталонным шаблоном для подобных контролов.

### Использование `updateLayout()`

Метод `update()` лишь помечает контрол как требующий **перерисовки** и не затрагивает систему компоновки. Однако при изменении текстового содержимого желаемый размер контрола (возвращаемое значение `sizeHint()`) обычно также меняется. В этом случае необходимо одновременно вызвать `updateLayout()`, чтобы инициировать пересчет компоновки родительским контролом:

```cpp
void MyTextWidget::setText(const String &text) {
    if (m_text == text)
        return;
    m_text = text;
    update();        // Запуск перерисовки
    updateLayout();  // Уведомление родительской компоновки о пересчете (так как изменился sizeHint)
}
```

Последствием вызова только `update()` станет то, что текстовое содержимое обновится, но размер контрола останется рассчитанным для старого текста, что приведет к искажению верстки.

### Измерение текста и `sizeHint()`

`FontMetrics` — основной инструмент для измерения текста. Используйте его для реализации `sizeHint()` и `heightForWidth()`:

```cpp
#include "gx_fontmetrics.h"

Size MyTextWidget::sizeHint() const {
    if (m_text.empty())
        return Size{0, int(font().pixelSize() * 1.2f)};
    FontMetrics fm(font());
    // Однострочный текст: напрямую измеряем ширину
    return Size{fm.width(m_text), int(font().pixelSize() * 1.2f)};
}
```

Для поддержки многострочного текста с автопереносом требуется также реализовать `heightForWidth()`, сообщая системе компоновки высоту контрола при заданной ширине:

```cpp
int MyTextWidget::heightForWidth(int width) const {
    if (width == 0) return 0;
    FontMetrics fm(font());
    float lineHeight = font().pixelSize() * 1.2f;
    // boundingRect вычисляет реальные границы текста при заданной ширине
    return fm.boundingRect(m_text, width, 1024 * 1024, 0, 0, lineHeight).height();
}
```

Если контрол строго однострочный (не переносится по ширине), метод `heightForWidth()` должен возвращать `-1`, сигнализируя об отсутствии зависимости от ширины:

```cpp
int SingleLineWidget::heightForWidth(int) const { return -1; }
```

### Реакция на стили и изменение размеров

При изменении стилевых свойств, таких как шрифт или цвет, результаты измерения текста также меняются. Переопределите `styleEvent()` для реакции на изменения стилей: вызовите реализацию базового класса, сбросьте кэши, связанные со стилями, и затем инициируйте обновление компоновки:

```cpp
void MyTextWidget::styleEvent(StyleEvent *event) {
  // Необходимо сначала вызвать базовый класс, он обновит внутренние стилевые данные
    Widget::styleEvent(event);
    // После изменения шрифта или других стилей возвращаемое значение sizeHint может измениться
    updateLayout();
}
```

Аналогично, если при изменении размера контрола выполняются вычисления переноса текста, зависящие от ширины, необходимо инициировать обновление в `resizeEvent()`:

```cpp
void MyTextWidget::resizeEvent(ResizeEvent *event) {
    Widget::resizeEvent(event); // Вызов базового класса
    update();                   // Перерисовка содержимого после изменения размера
}
```

::: important
Вызовы базового класса в таких функциях обработки событий, как `styleEvent()` и `resizeEvent()`, часто имеют побочные эффекты, которые нельзя пропускать, поэтому их **обязательно нужно вызывать**. Момент вызова зависит от логики вашего контрола: в большинстве случаев сначала вызывается базовый класс, а затем выполняется собственная логика.
:::

### Переопределение `event()`

Включите все типы событий, требующие обработки (`StyleEvent`, `ResizeEvent` и т. д.), в список шаблонных параметров `EventDispatch` для обеспечения проверки на этапе компиляции:

```cpp
bool MyTextWidget::event(Event *event) {
    return EventDispatch<Widget,
        PaintEvent, ResizeEvent, StyleEvent>{}(this, event);
}
```

### Потоковая компоновка и инлайн-элементы

Метод `setFlowLayout(true)` переводит **контейнерный контрол** в режим потоковой компоновки (flow layout), по своему эффекту похожему на блочный поток в CSS. Фреймворк автоматически располагает дочерние элементы по строкам без необходимости создания отдельных объектов компоновки через `setLayout()`. Класс `Label` включает этот режим прямо в своем конструкторе, что позволяет использовать его в качестве контейнера `SpanLabel` (содержащего несколько вложенных дочерних меток с разными стилями):

```cpp
Label::Label(Widget *parent) : Widget(parent) {
    setFlowLayout(true);
}
```

Метод `setInlineWidget(true)` предназначен для настройки **дочерних элементов**. Он помечает контрол как инлайн-элемент (inline), заставляя его встраиваться в текстовый поток родительского контейнера подобно тексту и участвовать в общей верстке. Например, встраивание иконки в поток богатого текста (ричтекста):

```cpp
auto *icon = new ImageBox(label);
// Смешивание с текстом в качестве инлайн-элемента. ImageBox по умолчанию уже является инлайн-элементом, здесь это показано для примера.
icon->setInlineWidget(true);
```

Когда `Label` используется в качестве контейнера `SpanLabel` для размещения инлайн-элементов, система компоновки автоматически координирует собственную логику измерения текста `Label` и размещение дочерних элементов как контейнера. Обе возможности используют единый механизм компоновки, и разработчику не требуется вручную вмешиваться в этот процесс.

## `AbstractScrollArea` и прокручиваемые контролы

Когда вашему контролу требуется поведение прокрутки, нет необходимости реализовывать распознавание жестов, инерционную прокрутку и отскок (bounce) с нуля — можно просто унаследовать его от `AbstractScrollArea`. Встроенные во фреймворк контролы `ScrollArea` (прокрутка списков) и `TextField` (однострочный ввод текста) реализованы на её основе.

### Базовая структура

Контрол, наследующий `AbstractScrollArea`, следует фиксированной структуре: сам контрол является «областью видимости» (viewport), а внутри него находится **контентный контрол** (content widget), который несет на себе реальное содержимое. При прокрутке перемещается именно контентный контрол, а не сама область видимости.

Инициализация выполняется в конструкторе:

```cpp
// myticker.h
#include "gx_abstractscorllarea.h"

class MyTicker : public AbstractScrollArea {
    GX_OBJECT
public:
    explicit MyTicker(Widget *parent = nullptr);
    bool event(Event *event) override;

protected:
    bool layoutEvent(LayoutEvent *event);
    friend struct EventTraits<MyTicker>;
};
```

```cpp
// myticker.cpp
#include "myticker.h"
#include "gx_widgetevent.h"

MyTicker::MyTicker(Widget *parent) : AbstractScrollArea(parent) {
    setDirection(Horizontal);     // Горизонтальная прокрутка
    setDamping(5);                // Настройка затухания (чем больше значение, тем сильнее трение)

    auto *content = new Widget;   // Создание контентного контрола
    setContentWidget(content);
}

bool MyTicker::event(Event *event) {
    return EventDispatch<AbstractScrollArea, LayoutEvent>{}(this, event);
}
```

Установка базового класса `AbstractScrollArea` (вместо `Widget`) для `EventDispatch` позволяет событиям, не обрабатываемым текущим классом (жесты, колесико мыши, изменение размера и т. д.), автоматически передаваться в реализацию `AbstractScrollArea`, сохраняя тем самым полноценное поведение прокрутки.

### Настройка параметров прокрутки

```cpp
setDirection(Vertical);          // Вертикальная прокрутка (по умолчанию)
setDirection(Horizontal);        // Горизонтальная прокрутка
setDamping(3);                   // Низкое затухание: более сильная инерция, большее расстояние скольжения
setDamping(20);                  // Высокое затухание: слабая инерция, практически без прокрутки по инерции
setScrollBar(true);              // Отображение полосы прокрутки
setBouncesPolicy(SnapType::SnapEdge);  // Стратегия отскока от краев
```

`AbstractScrollArea` также предоставляет метод `scrollTo(x, y, behavior)` для программного управления позицией прокрутки, где `behavior` может принимать значения `Instant` (мгновенный переход) или `Smooth` (с анимацией).

::: tip Инерционное затухание (Damping)
Для таких контролов, как `TextField`, где требуется точное управление позицией прокрутки, обычно задается высокое значение затухания для ослабления инерции. Для контролов вроде `ScrollArea`, ориентированных главным образом на просмотр контента, можно задать низкое затухание для более плавной прокрутки.

Не устанавливайте значение затухания слишком низким, так как прокрутка на сверхбольшие расстояния может привести к сбросу кэша содержимого и появлению подтормаживаний.
:::

### Вызов базового класса в диспетчеризации событий

Иногда возникает необходимость выполнить дополнительную обработку определенного события перед тем, как передать управление стандартной реализации `AbstractScrollArea`. Типичным паттерном является вызов метода базового класса прямо из функции-обработчика:

```cpp
// Подход в TextField: передавать жесты в область прокрутки только при наличии текста
bool TextField::gestureEvent(GestureEvent *event) {
    if (text().empty()) // Игнорировать, если текст пуст
        return false;
    // В остальных случаях передаем логике прокрутки базового класса
    return AbstractScrollArea::gestureEvent(event);
}
```

В этом режиме в качестве базового класса для `EventDispatch` используется `Widget`, и текущий класс самостоятельно решает, когда и какой метод базового класса вызывать:

```cpp
bool TextField::event(Event *event) {
    // Используя Widget в качестве базового класса, мы полностью контролируем момент вызова поведения AbstractScrollArea
    return EventDispatch<Widget, GestureEvent, ResizeEvent>{}(this, event);
}
```

### Фильтрация событий контентного контрола

Контентный контрол отвечает за компоновку и размещение дочерних элементов, но некоторые его события (например, запросы компоновки) иногда требуют перехвата и кастомной обработки со стороны контейнера. Зарегистрируйте контейнер в качестве фильтра событий контентного контрола с помощью `setEventFilter(this)`, а затем переопределите `eventFilter()` для обработки интересующих вас событий:

```cpp
// Регистрация в конструкторе
content->setEventFilter(this);

// Перехват запросов компоновки контентного контрола
bool MyTicker::eventFilter(Object *receiver, Event *e) {
    if (receiver == contentWidget() && e->type() == Event::Layout) {
        auto *lv = static_cast<LayoutEvent *>(e);
        if (lv->isLayoutRequest()) {
            // Кастомная логика компоновки…
            return true; // Возврат true предотвращает дальнейшую передачу события
        }
    }
    // В остальных случаях передаем базовому классу
    return AbstractScrollArea::eventFilter(receiver, e);
}
```

::: tip
Необработанные события должны передаваться обратно в `AbstractScrollArea::eventFilter()`, который отвечает за взаимодействие с внутренними механизмами, такими как полосы прокрутки.
:::

### Настройка инлайн-элементов

Вызов `setInlineWidget(true)` позволяет контролу участвовать в инлайн-компоновке (inline layout), что подходит для сценариев встраивания в текстовый поток. Именно так поступает `TextField`, чтобы иметь возможность встраиваться в строку подобно тексту.

### `ScrollArea` и производные классы

`ScrollArea` является производным классом от `AbstractScrollArea`, который добавляет к возможностям прокрутки **индексную навигацию** (`index()` / `setIndex()`), **режимы привязки** (snap) и **визуальные эффекты** (visual effect). Это предпочтительный базовый класс для списков, каруселей и других подобных сценариев. В свою очередь, `Swiper` расширяет `ScrollArea` функциями постраничной навигации (`pageLength`) и индикаторами, что делает его оптимальным для слайдеров и галерей.

Эти классы обычно **не требуют дальнейшего наследования**. Большинство задач кастомизации решается с помощью настройки параметров и подключения вспомогательных средств, без необходимости создавать подклассы.

#### Визуальные эффекты (VisualEffect)

`ScrollArea` поддерживает подключение объекта `VisualEffect` через метод `setVisualEffect()`. Он применяет визуальные трансформации (прозрачность, масштабирование, смещение и т. д.) к каждому дочернему элементу перед его отрисовкой, создавая динамические эффекты при прокрутке. Фреймворк содержит следующие встроенные эффекты:

| Имя класса | Эффект |
|---|---|
| `FisheyeVisualEffect` | Эффект «рыбьего глаза»: центральный элемент увеличивается, периферийные уменьшаются |
| `FadeVisualEffect` | Затухание по краям: чем дальше элемент от центра области видимости, тем ниже его прозрачность |
| `CollapseVisualEffect` | Эффект сворачивания: элементы сближаются и уменьшаются к верхнему (или нижнему) краю |
| `BlendVisualEffect` | Интерполяция по прогрессу между двумя эффектами |

```cpp
#include "gx_visualeffect.h"

scrollArea->setVisualEffect(make_shared<FisheyeVisualEffect>());
```

Если требуется создать собственный эффект, унаследуйте его от `VisualEffect` и реализуйте метод `resolve()`. Метод `resolve()` принимает целевой дочерний контрол, прямоугольник области видимости (viewport) и центр дочернего контрола, а возвращает объект `PaintModifier`, в котором можно настроить свойства `opacity`, `scale`, `translate` и др.

Подробное описание параметров `ScrollArea` и `Swiper`, а также инструкции по реализации кастомного `VisualEffect` рассматриваются в отдельной главе [Область прокрутки](./scroll-area.md).

## Дерево контролов и жизненный цикл

При создании контролов на C++ иерархия родитель-ребенок устанавливается через параметр конструктора `parent`:

```cpp
// При уничтожении parent уничтожается и child
auto *parent = new Widget(window);
auto *child  -> new ProgressRing(parent);
child->setGeometry(10, 10, 80, 80);
```

Независимо от того, удаляете ли вы родительский контрол вручную через `delete` или фреймворк очищает дерево контролов при выходе из приложения, все дочерние контролы будут удалены автоматически. Вам не нужно вызывать `delete` для дочерних контролов в деструкторе.

Если требуется отложенное удаление (например, изнутри функции обработки событий), используйте метод `deleteLater()`. Он уничтожит объект по завершении текущей обработки событий, избегая проблем вроде «самоуничтожения изнутри callback-функции».

В реактивном фреймворке дерево контролов поддерживается компонентом фреймворка, и при разработке кастомизаций требуется лишь [зарегистрировать класс контрола](./widget-export.md).
