# Руководство по разработке контролов

В Glyphix все видимые UI-элементы являются `Widget` (контролами). Фреймворк содержит встроенные стандартные контролы, такие как кнопки, метки, изображения, области прокрутки и т. д., но производителям устройств часто требуется разрабатывать кастомные контролы с учетом особенностей своего продукта. Например, умные часы могут иметь особую анимацию списка из-за небольшого круглого экрана, а приборные панели — специализированные графические контролы. В этом документе описывается, как реализовать новый контрол на C++.

## Базовые сведения о контролах

`Widget` представляет собой прямоугольную область, которая имеет такие базовые свойства, как положение, размер, видимость и прозрачность, может принимать события и отвечает за отрисовку собственного содержимого. Контролы организованы в древовидную структуру: родительский контрол содержит несколько дочерних, а координаты дочернего контрола задаются относительно родительского.

Каждый контрол имеет **цикл логического обновления**: когда состояние контрола изменяется (например, обновляются данные), вызывается метод `update()`, помечающий контрол как «требующий перерисовки». Фреймворк выполняет общую перерисовку всех помеченных контролов в следующем кадре рендеринга вместо немедленной перерисовки — это позволяет избежать многократной избыточной отрисовки в рамках одного кадра.

### Контролы и система компонентов

UI-контролы обычно реализуются как классы C++, наследуемые от `Widget` и соответствующие стандартному объектно-ориентированному проектированию C++. Реактивный фреймворк и система компонентов Glyphix позволяют напрямую экспортировать эти C++ контролы в качестве нативных компонентов и использовать их в шаблонном, декларативном стиле.

Такой дизайн позволяет сделать разработку контролов на стороне C++ и использование фронтенд-компонентов относительно независимыми, сохраняя при этом привычные для обеих сторон способы разработки. Например, на C++ вы можете создавать интерфейс способом, аналогичным LVGL или Qt Widgets, не принимая при этом популярный во фронтенд-фреймворках декларативный стиль.

### Сравнение с другими фреймворками

По своему дизайну система контролов Glyphix похожа на традиционные C/C++ UI-фреймворки, такие как Qt Widgets или LVGL. Поэтому вы обнаружите, что подход к разработке нового контрола и система знаний очень близки к этим фреймворкам:
- Создание нового класса контрола путем наследования от `Widget`;
- Наличие ключевых механизмов, таких как система компоновки (layout), система событий и система отрисовки;
- Реализация привязки данных (data binding) и нотификации о событиях с помощью системы свойств и механизма сигналов;
- Наличие геометрических концепций (система координат, размеры) и поддержка древовидной структуры вложенных контролов.

::: tip Не рекомендуется разрабатывать UI на C++
Изначальный замысел Glyphix не предполагает разработку пользовательского интерфейса напрямую на стороне C++, поэтому мы не предоставляем соответствующую документацию и примеры.
:::

## Создание кастомного контрола

В этом разделе на примере контрола кольцевого индикатора выполнения (`ProgressRing`) по шагам рассматриваются все элементы, необходимые для разработки кастомного контрола.

::: tip Комплексный пример контрола
Пример [slider-demo](./widget-slider-demo.md), поставляемый вместе с SDK, представляет собой полную практическую реализацию всех концепций из этого документа, включая наследование существующих контролов, отрисовку, обработку событий, объявление свойств, анимацию `ValueAnimation` и кастомизацию с помощью `StyleEngine`. Рекомендуется ознакомиться с ним после прочтения этого документа.
:::

### Определение класса контрола

Создайте новый контрол, унаследовав его от `Widget`, добавьте макрос `GX_OBJECT` в самом начале определения класса и **переопределите виртуальную функцию `event()`** в качестве точки входа для обработки событий:

```cpp
// progressring.h
#include "gx_widget.h"

class ProgressRing : public Widget {
    GX_OBJECT
public:
    explicit ProgressRing(Widget *parent = nullptr)
        : Widget(parent), m_value(0) {}

    int value() const { return m_value; }
    void setValue(int v);
    bool event(Event *event) override;

    GX_PROPERTY(int value, get value, set setValue, signal valueChanged)
    Signal<int> valueChanged;

protected:
    void paintEvent(PaintEvent *event);

    // EventDispatch должен иметь доступ к protected методам, объявляем дружественным
    friend struct EventTraits<ProgressRing>;

private:
    int m_value;  // [0, 100]
};
```

Макрос `GX_OBJECT` обязателен: он запускает компилятор метаобъектов для генерации метаданных для этого класса, что позволяет системным свойствам, системе анимации и компонентам фреймворка корректно распознавать контрол (подробнее см. в разделе [Система объектов](./object-system.md)).

### Отрисовка контрола

В файле `.cpp` подключите `gx_widgetevent.h` и реализуйте функции `event()` и `paintEvent()`:

```cpp
// progressring.cpp
#include "progressring.h"
#include "gx_widgetevent.h"

bool ProgressRing::event(Event *event) {
    return EventDispatch<Widget>{}(this, event);
}

void ProgressRing::paintEvent(PaintEvent *event) {
    Widget::paintEvent(event);
    Painter p(this);
    // ... см. главу про отрисовку
}
```

Кастомная отрисовка выполняется путем реализации `paintEvent()`; при создании `Painter` передайте в него указатель `this`, чтобы получить контекст рисования, связанный с текущим контролом, а затем вызовите различные методы рисования. Полное описание API `Painter` см. в главе [Отрисовка](./painting.md).

### Обработка событий

Система событий Glyphix **не зависит от наследования виртуальных функций** для диспетчеризации событий. Методы `paintEvent()`, `gestureEvent()` и другие **не являются** `virtual`, и их **не нужно** помечать ключевым словом `override` (это вызовет ошибку компиляции). Фреймворк маршрутизирует вызовы к правильной функции-обработчику во время **компиляции** на основе типа события с помощью `EventDispatch`.

Единственная виртуальная функция, которую нужно (и обязательно) переопределить — это **`event()`**, в которой происходит делегирование в `EventDispatch`:

```cpp
bool ProgressRing::event(Event *event) {
    return EventDispatch<Widget>{}(this, event);
}
```

Первым шаблонным параметром `EventDispatch` обычно является **непосредственный базовый класс** (тот, от которого наследуется `ProgressRing`, в данном случае — `Widget`). На этапе компиляции он проверяет, объявил ли текущий класс соответствующий метод-обработчик напрямую: если да, то вызывает его, в противном случае автоматически возвращается к реализации базового класса. Возвращаемое значение функции-обработчика `bool` указывает, было ли событие перехвачено (обработано); возвращаемое значение `void` трактуется как обработанное.

::: tip Совет по выбору базового класса
Выбор параметра базового класса для `EventDispatch` имеет некоторые оптимизационные нюансы. Обычно можно выбрать непосредственный базовый класс, но допускается использовать и более высокоуровневый родительский класс, что приведет к незначительным отличиям в размере кода и производительности. Однако, как правило, не стоит излишне ломать над этим голову или бояться ошибок — если код компилируется, диспетчеризация событий будет работать корректно.
:::

::: important
Когда далее по тексту упоминается «переопределение `xxxEvent()`», обратите внимание, что речь идет исключительно об **объявлении** в классе производного контрола функции-члена с той же сигнатурой, что и у обработчика базового класса, но **не виртуальной**. Это **не** виртуальная функция, к ней нельзя добавлять `override`, и она не зависит от механизма виртуальных функций для диспетчеризации событий.

IDE может выдавать подсказку о необходимости сделать эти функции-члены виртуальными, не обращайте на нее внимания.
:::

Если требуется обрабатывать жесты ввода, объявите `gestureEvent()` и реализуйте её в классе:

```cpp
// Добавьте объявление в секцию protected заголовочного файла:
bool gestureEvent(GestureEvent *event);

// Реализуйте в .cpp:
bool ProgressRing::gestureEvent(GestureEvent *event) {
    if (event->type() == Event::Press) {
        // ...
        return true;   // Возврат true означает, что событие обработано и не передается родительскому контролу
    }
    return false;
}
```

Типы обрабатываемых событий:

| Сигнатура метода | Момент срабатывания |
|---|---|
| `bool gestureEvent(GestureEvent *)` | События жестов, включая Press, Pan, Swipe и др. |
| `bool wheelEvent(WheelEvent *)` | Ввод с колесика или кругового регулятора (например, коронки часов) |
| `bool keyEvent(KeyEvent *)` | Аппаратные кнопки |
| `void resizeEvent(ResizeEvent *)` | Изменение размера контрола |
| `void moveEvent(MoveEvent *)` | Изменение положения контрола |
| `bool focusEvent(FocusEvent *)` | Изменение фокуса |
| `void paintEvent(PaintEvent *)` | Запрос на перерисовку |
| `bool layoutEvent(LayoutEvent *)` | Запрос на компоновку |
| `void tickEvent(TickEvent *)` | Потактовый tick (требует явного вызова `requestNextTick()` для активации) |

Если какие-то функции обработки событий **обязательны** для текущего контрола, вы можете указать их в шаблонных параметрах `EventDispatch`, и в случае пропуска или несовпадения сигнатур компилятор выдаст ошибку:

```cpp
bool MyButton::event(Event *event) {
    // Если paintEvent или gestureEvent не объявлены корректно, сборка завершится с ошибкой
    return EventDispatch<Widget, PaintEvent, GestureEvent>{}(this, event);
}
```

::: tip Объявление обязательных обработчиков событий
Хотя можно использовать `EventDispatch<Widget>` для автоматической диспетчеризации всех событий, **настоятельно рекомендуется** явно объявлять типы событий, которые должен обрабатывать текущий контрол. Это позволяет максимально отлавливать пропуски или опечатки на этапе компиляции и снижает нагрузку при ручной проверке.
:::

### Свойства и сигналы

Используйте макрос `GX_PROPERTY`, чтобы экспортировать свойства во фреймворк, делая их доступными для биндинга на уровне приложения или в качестве целей для анимации свойств:

```cpp
// Объявление свойства value, где getter — value(), а setter — setValue()
// Поле signal связывает сигнал изменения для подписки реактивным фреймворком
GX_PROPERTY(int value, get value, set setValue, signal valueChanged)
```

После объявления свойство `value` может:
- Напрямую привязываться шаблонами уровня приложения (например, `<progress-ring :value="progress"/>`);
- Плавно анимироваться системой свойств (если тип поддерживает интерполяцию).

Вызывайте `update()` в сеттере для запуска перерисовки и вовремя испускайте сигнал для уведомления внешнего мира:

```cpp
void ProgressRing::setValue(int v) {
    if (m_value == v) return;
    m_value = v;
    update();          // Пометка для перерисовки в следующем кадре
    valueChanged(v);   // Испускание сигнала
}
```

`Signal<T>` — это обычная шаблонная переменная-член, которая испускается прямо как вызов функции. Сигналы без аргументов используют `Signal<>` и вызываются без параметров. Подробную семантику свойств и сигналов см. в соответствующем разделе [Системы объектов](./object-system.md).

### Компоновка (Layout)

После создания экземпляра контрола его положение и размер задаются вручную с помощью `setGeometry()`. Если родительский контрол использует автоматическую компоновку, переопределите `sizeHint()`, чтобы объявить желаемый размер контрола:

Size ProgressRing::sizeHint() const {
    return Size(80, 80);
}

Для контейнерных контролов, которым требуется самостоятельно управлять компоновкой дочерних элементов, выполните вычисления геометрии дочерних элементов в `layoutEvent()` или подключите предоставляемый фреймворком класс компоновки (например, `FlexLayout`) через `setLayout()`. Подробнее см. в разделе [Компоновка и размеры](#компоновка-и-размеры).

## Отрисовка

### Инициализация Painter

Для начала отрисовки создайте экземпляр `Painter` в функции-члене `paintEvent()` контрола:

```cpp
void ProgressRing::paintEvent(PaintEvent *event) {
    Painter p(this);
    // Все последующие операции рисования выполняются через p
}
```

Система координат рисования использует **левый верхний угол контрола в качестве начала координат**, ось $+x$ направлена вправо, ось $+y$ — вниз, а единица измерения — пиксели. Метод `rect()` возвращает локальный прямоугольник текущего контрола `(0, 0, width(), height())` и является наиболее часто используемой опорной областью при рисовании.

Если для контрола установлены управляемые фреймворком свойства стиля (например, цвет фона) через стили уровня приложения или `StyleModifier`, вы можете вызвать метод базового класса перед отрисовкой кастомного содержимого:

```cpp
void ProgressRing::paintEvent(PaintEvent *event) {
    Widget::paintEvent(event);  // Сначала рисуем фон, управляемый фреймворком (если есть)
    Painter p(this);
    // ...
}
```

Если не вызывать базовый класс, стили фона, управляемые фреймворком, будут проигнорированы, и контрол будет полностью отвечать за свое визуальное представление через `paintEvent`.

### Состояние отрисовки

`Painter` поддерживает набор текущих состояний отрисовки: каждый вызов рисования использует текущее состояние до его следующего изменения.

#### Кисть (Brush)

Кисть определяет цвет для **методов заполнения** (`fillRect`, `fillRoundedRect`, `fillPath` и др.), а также цвет **текста**:

```cpp
p.setBrush(Color(200, 200, 200));   // Серый цвет RGB
p.setBrush(Color{"#35a7ff"});       // Шестнадцатеричная строка
p.setBrush(Color::White);           // Предопределенная константа
p.setBrush(Color(0xff4486ff));      // Шестнадцатеричное число ARGB (0xff — полная непрозрачность)
```

#### Перо (Pen)

Перо определяет цвет и толщину линии для **методов обводки** (`drawRect`, `drawArc`, `drawLine` и др.):

```cpp
Pen pen(Color(64, 156, 255));
pen.setSize(6);    // Толщина линии 6px
p.setPen(pen);
```

#### Другие состояния

```cpp
p.setFont(Font(18));     // Размер шрифта 18px, влияет на drawText()
p.setOpacity(127);      // Прозрачность [0, 255], влияет на все последующие операции рисования
```

Все состояния действуют только на текущий экземпляр `Painter`. Экземпляры `Painter`, созданные разными контролами, полностью независимы и не мешают друг другу.

### Базовые фигуры

#### Прямоугольник

```cpp
p.setBrush(Color::White);
p.fillRect(rect());                    // Заливка всей области контрола
p.fillRect(Rect(10, 10, 60, 20));      // Заливка указанного прямоугольника

p.fillRoundedRect(rect(), 8.0f);       // Заливка со скругленными углами, радиус 8px
p.drawRoundedRect(rect(), 8.0f);       // Обводка со скругленными углами (без заливки, используется цвет Pen)
```

Когда радиус скругления равен половине меньшего из размеров (широты или высоты), прямоугольник превращается в форму капсулы, что очень часто используется в кнопках и индикаторах выполнения:

```cpp
float radius = min(box.width(), box.height()) * 0.5f;
p.fillRoundedRect(box, radius);
```

#### Прямая линия

```cpp
p.drawLine(Point(0, cy), Point(width(), cy));   // Горизонтальная разделительная линия
```

#### Дуга

Метод `drawArc` определяет дугу по координатам центра и радиусу; параметры `startAngle`/`endAngle` задаются в градусах, где $0°$ соответствует позиции на $3$ часа, а значения увеличиваются по часовой стрелке:

```cpp
float cx = width() / 2.0f;
float cy = height() / 2.0f;
float radius = min(cx, cy) - 4.0f;

// Рисование полной дуги (фоновое кольцо), от -90° (12 часов) на полный круг
Pen bgPen(Color(200, 200, 200));
bgPen.setWidth(6);
p.setPen(bgPen);
p.drawArc({cx, cy}, radius, -90.0f, -90.0f + 360.0f);

// Рисование дуги прогресса (от 12 часов по часовой стрелке до позиции, соответствующей progress)
if (m_value > 0) {
    Pen fgPen(Color(64, 156, 255));
    fgPen.setWidth(6);
    p.setPen(fgPen);
    p.drawArc({cx, cy}, radius, -90.0f, -90.0f + 360.0f * m_value / 100.0f);
}
```

Визуальная толщина дуги определяется текущей толщиной линии `Pen`.

### Векторный путь `VectorPath`

Для сложных форм, которые невозможно описать прямоугольниками и дугами, используется `VectorPath` для построения произвольных контуров с последующим рендерингом через `fillPath()` или `drawPath()`.

```cpp
#include "gx_vectorpath.h"
```

Принцип работы `VectorPath` напоминает «траекторию пера»: с помощью `moveTo` перо опускается (перемещается), с помощью `lineTo` рисуются прямые линии, а с помощью `arcTo` — дуги окружности, описывая контур, который затем единовременно рендерится `Painter`.

#### Путь из прямых линий

```cpp
VectorPath path;
path.moveTo(x0, y0);   // Перемещение пера (без отрисовки)
path.lineTo(x1, y1);   // Прямая до (x1, y1)
path.lineTo(x2, y2);
path.lineTo(x0, y0);   // Возврат в начальную точку, образуя замкнутый треугольник

p.fillPath(path, Color(64, 156, 255)); // Заливка замкнутой области
```

Метод `fillPath()` автоматически обрабатывает путь как замкнутую область, даже если в конце не был явно вызван возврат в исходную точку. `drawPath()` рисует контур пути с помощью текущего `Pen` без заливки.

#### Дуговые сегменты пути

Параметры `arcTo` включают в себя центр, радиусы по осям $x/y$ (различаются для эллипсов), начальный угол и угол охвата (в градусах, по часовой стрелке):

```cpp
// Рисование горизонтальной капсулы: левый полукруг + правый полукруг, arcTo автоматически соединяет их линией
float r  = rect.height() * 0.5f;
float x1 = rect.left() + r;
float x2 = rect.right() - r;
float y  = rect.top() + r;

VectorPath path;
path.arcTo(PointF(x1, y), r, r, 90.0f, 270.0f);    // Левый полукруг (против часовой стрелки от 9 до 3 часов)
path.arcTo(PointF(x2, y), r, r, -90.0f, 90.0f);    // Правый полукруг (против часовой стрелки от 3 до 9 часов)
p.fillPath(path);
```

`arcTo` автоматически вставляет прямую линию между текущей конечной точкой пути и началом новой дуги, поэтому две дуги естественно стыкуются своими концами без необходимости вызывать `lineTo` отдельно.

#### Кривые

Использование `conicTo` или `cubicTo` позволяет строить квадратичные или кубические сегменты кривых Безье, которые в сочетании с `moveTo` и `lineTo` могут описывать сложные контуры:

```cpp
VectorPath path;
path.moveTo(x0, y0);
// Квадратичная кривая Безье, (cx, cy) — контрольная точка
path.conicTo(cx, cy, x1, y1);
// Кубическая кривая Безье, (cx1, cy1) и (cx2, cy2) — контрольные точки
path.cubicTo(cx1, cy1, cx2, cy2, x2, y2);
// Заливка пути заданной кистью
p.fillPath(path, brush);
```

#### Пример комбинированного пути

Комбинируя несколько команд, можно построить фигуру любой сложности. На примере области заливки волны в `WaveSlider` путь содержит верхнюю ломаную линию волны и нижнюю границу со скругленными углами:

```cpp
VectorPath path;
path.moveTo(leftX, waveY(leftX));
for (int i = 1; i <= sampleCount; ++i) {
    float x = leftX + (rightX - leftX) * float(i) / sampleCount;
    path.lineTo(x, waveY(x));           // Контур верхней волны
}
path.lineTo(rightX, bottomEdge(rightX)); // Спуск по правому краю
for (int i = sampleCount - 1; i >= 0; --i) {
    float x = leftX + (rightX - leftX) * float(i) / sampleCount;
    path.lineTo(x, bottomEdge(x));       // Нижняя граница (возврат вдоль нижней части прямоугольника со скругленными углами)
}
path.lineTo(leftX, waveY(leftX));        // Возврат в начальную точку
p.fillPath(path);
```

### Текст

Метод `drawText()` располагает и отрисовывает текст в пределах прямоугольной области. Цвет текста определяется текущей кистью (`Brush`), а шрифт задается через `setFont()`:

```cpp
p.setFont(Font(18));
p.setBrush(Color(50, 50, 50));
p.drawText(rect(), format("{}%", m_value), AlignCenter);
```

::: tip Форматирование строк
`format()` — это функция форматирования, предоставляемая фреймворком. Ее синтаксис аналогичен [`std::format`](https://en.cppreference.com/w/cpp/utility/format/format) и доступен на всех платформах.
:::

Флаги выравнивания можно свободно комбинировать:

| Флаг | Значение |
|---|---|
| `AlignLeft` | По горизонтали по левому краю |
| `AlignHCenter` | По горизонтали по центру |
| `AlignRight` | По горизонтали по правому краю |
| `AlignTop` | По вертикали по верхнему краю |
| `AlignVCenter` | По вертикали по центру |
| `AlignBottom` | По вертикали по нижнему краю |
| `AlignCenter` | По горизонтали + по вертикали по центру (эквивалентно `AlignHCenter \| AlignVCenter`) |

Метод `font()` возвращает текущий шрифт, унаследованный контролом из системы стилей. Его использование при рисовании позволяет контролу автоматически подстраиваться под изменение размера шрифта приложения:

```cpp
p.setFont(font());   // Использование шрифта стиля, унаследованного контролом, вместо фиксированного размера
```

Метод `drawText()` также поддерживает более сложную компоновку текста, такую как многострочный текст, автоматический перенос строк и т. д. Подробности см. в документации по API.

### Изображения

Метод `drawImage()` отрисовывает изображение внутри заданной прямоугольной области:

```cpp
Image img{"file://path/to/icon.png"};
p.drawImage(widget->rect(), img); // Отрисовка изображения в указанной области без автоматического масштабирования
```

В реальном использовании изображения обычно поступают из системы ресурсов, а способ их загрузки зависит от платформы и конфигурации сборки.

### Полный пример

Ниже приведен полный метод `paintEvent` для `ProgressRing`, объединяющий описанные выше возможности отрисовки:

```cpp
void ProgressRing::paintEvent(PaintEvent *event) {
    // Если у контрола есть фоновый стиль, управляемый фреймворком, вызываем базовый класс
    // Widget::paintEvent(event);

    Painter p(this);

    float cx = width() / 2.0f;
    float cy = height() / 2.0f;
    float radius = min(cx, cy) - 4.0f;
    float startAngle = -90.0f;   // Начиная с позиции 12 часов

    // Рисование серого фонового кольца
    Pen bgPen(Color(200, 200, 200));
    bgPen.setWidth(6);
    p.setPen(bgPen);
    p.drawArc({cx, cy}, radius, startAngle, startAngle + 360.0f);

    // Рисование цветной дуги прогресса
    if (m_value > 0) {
        Pen fgPen(Color(64, 156, 255));
        fgPen.setWidth(6);
        p.setPen(fgPen);
        p.drawArc({cx, cy}, radius,
          startAngle, startAngle + 360.0f * m_value / 100.0f);
    }

    // Отрисовка процентов в центре кольца
    p.setFont(Font(18));
    p.setBrush(Color(50, 50, 50));
    p.drawText(rect(), format("{}%", m_value), AlignCenter);
}
```

## Компоновка и размеры

Переопределите `sizeHint()`, чтобы подсказать системе компоновки «желаемый размер» контрола. Когда родительский контрол использует автоматическую компоновку, система компоновки будет опираться на это значение при распределении пространства:

```cpp
Size ProgressRing::sizeHint() const {
    return Size(80, 80);  // Рекомендуется отображать как 80×80px
}
```

Если высота контрола зависит от его ширины (например, изображение с фиксированным соотношением сторон), переопределите `heightForWidth()`:

```cpp
int AspectWidget::heightForWidth(int width) const {
    return width; // Квадратные пропорции
}
```

В случаях, когда требуется вручную управлять компоновкой дочерних элементов, переопределите `layoutEvent()` и задайте геометрию дочерних элементов внутри него:

```cpp
bool ContainerWidget::layoutEvent(LayoutEvent *event) {
    // Расположение дочерних элементов сверху вниз
    int y = 0;
    for (auto *child : children()) {
        auto *w = dyn_cast<Widget *>(child);
        if (w && w->isVisible()) {
            w->setGeometry(0, y, width(), w->sizeHint().height());
            y += w->height();
        }
    }
    return true;
}
```

Вы также можете использовать готовые классы компоновки, предоставляемые фреймворком (например, `FlexLayout`, `StackLayout`), подключив их через `setLayout(new FlexLayout())`.

::: tip Использование готовых классов компоновки
Если вы не создаете контейнерный контрол с нестандартной компоновкой, рекомендуется использовать готовые классы компоновки фреймворка для управления дочерними элементами. В этом случае переопределять `layoutEvent()` не требуется.

Реализация полноценного алгоритма компоновки — задача довольно сложная, требующая обработки взаимодействия с `sizeHint()` и другими аспектами, а также учета оптимизации производительности.
:::

## Анимация

Фреймворк предоставляет три типа механизмов анимации: **анимация стилей**, **анимация свойств** и **`ValueAnimation`**. Анимация стилей и анимация свойств в основном используются на **уровне приложения** (т. е. со стороны использования контролов), в то время как при реализации кастомных контролов чаще всего напрямую применяется `ValueAnimation`.

### ValueAnimation

`ValueAnimation<T>` — это класс анимации для интерполяции значений произвольного типа `T`. Каждый кадр он вычисляет результат интерполяции на основе текущего прогресса и испускает его через сигнал `value`. Вам достаточно просто подключить этот сигнал к собственной логике обновления:

```cpp
#include "gx_valueanimation.h"

// Объявление объекта анимации в членах контрола, обычно используется указатель для динамического создания и удаления при необходимости
ValueAnimation<int> *m_animation = nullptr;
```

```cpp
// Инициализация и запуск в нужном месте
m_animation = new ValueAnimation<int>;
m_animation->setValueLimits(0, 100);  // Интерполяция от 0 до 100
m_animation->setDuration(800);        // 800 миллисекунд
m_animation->value.connect(this, &MyWidget::onAnimationValue);
m_animation->start();

// Обратный вызов кадра: получение интерполированного значения для каждого кадра
void MyWidget::onAnimationValue(int v) {
    m_currentValue = v;
    update();  // Запуск перерисовки
}
```

По завершении анимации испускается сигнал `finished`. Если вам не нужно вручную управлять жизненным циклом, вы можете использовать стратегию `DeleteOnStop`, чтобы анимация автоматически удалялась после окончания воспроизведения:

```cpp
// Объект анимации не требует внешнего доступа, сразу после new он удалится автоматически
auto *anim = new ValueAnimation<int>;
anim->setValueLimits(0, 100);
anim->setDuration(500);
anim->value.connect(this, &MyWidget::onValue);
anim->start(AbstractAnimation::DeleteOnStop);  // Автоматический delete после завершения
```

Фреймворк имеет встроенную поддержку интерполяции для следующих типов: `int`, `float` (и других числовых типов), `Color`, `Point`, `Pen`, `Brush`, `Length`, `Transform` и др.

Другие распространенные настройки:

```cpp
// Бесконечный цикл воспроизведения
anim->setRepeat(AbstractAnimation::Infinity);

// Двусторонее воспроизведение туда-обратно (вперед -> назад -> вперед...)
anim->setDirection(AbstractAnimation::Alternate);

// Установка кривой плавности (easing)
#include "gx_easecurve.h"
anim->setEaseCurve(easing::make_curve<easing::Ease>());
```

### Анимация стилей и анимация свойств

**Анимация стилей** (`StyleAnimation`) определяет эффекты перехода способом, похожим на CSS transition. Она автоматически воспроизводится фреймворком при переключении состояний стилей контрола и в основном используется в конфигурации стилей компонентов уровня приложения.

**Анимация свойств** (`PropertyAnimation`) управляет свойствами, объявленными с помощью `GX_PROPERTY`, по строковому имени свойства и часто используется на уровне приложения для анимации свойств контролов:

```cpp
#include "gx_propertyanimation.h"

auto *anim = new PropertyAnimation(widget, "value");
anim->setStartValue(Variant{0});
anim->setStopValue(Variant{100});
anim->setDuration(1000);
anim->start(AbstractAnimation::DeleteOnStop);
```

При реализации самого контрола анимация свойств обычно не требуется, так как `ValueAnimation` более прямая и не имеет накладных расходов на поиск свойств по имени.

## Контролы для отображения текста

При реализации контролов с текстовым содержимым, помимо базовой логики отрисовки, необходимо решать такие проблемы, как измерение текста, кэширование компоновки, взаимодействие со стилями и т. д. `Label` — самый типичный текстовый контрол во фреймворке, и его реализация может служить эталонным шаблоном для подобных контролов.

### Использование `updateLayout()`

Вызов `update()` лишь помечает, что контрол требует **перерисовки**, и не влияет на систему компоновки. Однако при изменении текстового содержимого желаемый размер контрола (возвращаемое значение `sizeHint()`) обычно также меняется, и в этот момент необходимо одновременно вызвать `updateLayout()`, чтобы инициировать пересчет компоновки родительского контрола:

```cpp
void MyTextWidget::setText(const String &text) {
    if (m_text == text)
        return;
    m_text = text;
    update();        // Запуск перерисовки
    updateLayout();  // Уведомление родительского лэаута о необходимости пересчета (так как изменился sizeHint)
}
```

Последствие вызова только `update()` заключается в том, что текстовое содержимое обновилось, но размер контрола остался прежним (рассчитанным для старого текста), из-за чего верстка нарушится.

### Измерение текста и `sizeHint()`

`FontMetrics` — основной инструмент для измерения текста, используемый для реализации `sizeHint()` и `heightForWidth()`:

```cpp
#include "gx_fontmetrics.h"

Size MyTextWidget::sizeHint() const {
    if (m_text.empty())
        return Size{0, int(font().pixelSize() * 1.2f)};
    FontMetrics fm(font());
    // Однострочный текст: измерение ширины напрямую
    return Size{fm.width(m_text), int(font().pixelSize() * 1.2f)};
}
```

Для многострочного текста, поддерживающего автоматический перенос строк, также необходимо реализовать `heightForWidth()`, чтобы сообщить системе компоновки высоту контрола при заданной ширине:

```cpp
int MyTextWidget::heightForWidth(int width) const {
    if (width == 0) return 0;
    FontMetrics fm(font());
    float lineHeight = font().pixelSize() * 1.2f;
    // boundingRect вычисляет фактические границы текста при заданной ширине
    return fm.boundingRect(m_text, width, 1024 * 1024, 0, 0, lineHeight).height();
}
```

Если контрол строго однострочный (не переносится по ширине), `heightForWidth()` возвращает `-1`, указывая, что ширина не учитывается:

```cpp
int SingleLineWidget::heightForWidth(int) const { return -1; }
```

### Реакция на изменение стилей и размеров

При изменении таких свойств стиля, как шрифт или цвет, результаты измерения текста также меняются. Переопределите `styleEvent()` для реагирования на изменения стиля: после вызова реализации базового класса обновите кэши, связанные со стилями, и затем инициируйте обновление компоновки:

```cpp
void MyTextWidget::styleEvent(StyleEvent *event) {
    // Обязательно сначала вызываем базовый класс, он обновит внутренние данные стилей
    Widget::styleEvent(event);
    // После изменения таких стилей, как шрифт, возвращаемое значение sizeHint может измениться
    updateLayout();
}
```

Аналогично, если при изменении размера контрола выполняются вычисления переноса текста, зависящие от ширины, необходимо инициировать обновление в `resizeEvent()`:

```cpp
void MyTextWidget::resizeEvent(ResizeEvent *event) {
    Widget::resizeEvent(event); // Вызов базового класса
    update();                   // Перерисовка содержимого после изменения размера
}
```

::: important
Реализации базового класса для таких обработчиков событий, как `styleEvent()`, `resizeEvent()` и т. д., обычно имеют побочные эффекты, которые нельзя пропускать, поэтому **их вызов обязателен**. Момент вызова зависит от потребностей вашей логики: в большинстве случаев сначала вызывается базовый класс, а затем выполняется собственная логика.
:::

### Переопределение `event()`

Включите все типы событий, которые необходимо обрабатывать (`StyleEvent`, `ResizeEvent` и др.), в шаблонные параметры `EventDispatch` для получения проверок на этапе компиляции:

```cpp
bool MyTextWidget::event(Event *event) {
    return EventDispatch<Widget,
        PaintEvent, ResizeEvent, StyleEvent>{}(this, event);
}
```

### Потоковая компоновка и строчные элементы

Вызов `setFlowLayout(true)` переводит **контейнерный контрол** в режим потоковой компоновки (flow layout), аналогичный блочному потоку в CSS. Фреймворк автоматически располагает дочерние элементы по строкам без необходимости создавать отдельный объект компоновки через `setLayout()`. Контрол `Label` активирует этот режим прямо в конструкторе, благодаря чему может выступать в роли контейнера `SpanLabel` (содержащего несколько дочерних меток с разными стилями):

```cpp
Label::Label(Widget *parent) : Widget(parent) {
    setFlowLayout(true);
}
```

`setInlineWidget(true)` — это настройка для **дочерних элементов**, которая помечает контрол как строчный (inline) элемент, заставляя его встраиваться в текстовый поток родительского контейнера для участия в верстке подобно обычному тексту. Например, встраивание контрола иконки в строку богатого текста (rich text):

```cpp
auto *icon = new ImageBox(label);
// Смешивание с текстом в качестве строчного элемента. ImageBox по умолчанию уже является строчным, здесь это приведено для примера.
icon->setInlineWidget(true);
```

Когда `Label` используется в качестве контейнера `SpanLabel`, вмещающего строчные дочерние элементы, система компоновки автоматически координирует собственную логику измерения текста `Label` и размещение дочерних элементов в качестве контейнера. Обе функции используют единый механизм компоновки, и разработчику не требуется вмешиваться в этот процесс вручную.

## AbstractScrollArea и прокручиваемые контролы

Когда контролу требуется поведение прокрутки, нет необходимости реализовывать распознавание жестов, инерционную прокрутку и пружинящий возврат (bounce) с нуля — достаточно унаследовать `AbstractScrollArea`, чтобы получить эти возможности. Встроенные во фреймворк `ScrollArea` (прокрутка списка) и `TextField` (однострочный ввод текста) реализованы на ее основе.

### Базовая структура

Контрол, наследующий `AbstractScrollArea`, следует фиксированной структуре: сам контрол является «областью видимости» (viewport), а внутри него находится **контентный контрол** (content widget), отвечающий за размещение фактического содержимого. При прокрутке перемещается именно контентный контрол, а не сама видимая область.

Инициализация выполняется в конструкторе:

```cpp
// myticker.h
#include "gx_abstractscorllarea.h"

class MyTicker : public AbstractScrollArea {
    GX_OBJECT
public:
    explicit MyTicker(Widget *parent = nullptr);
    bool event(Event *event) override;

protected:
    bool layoutEvent(LayoutEvent *event);
    friend struct EventTraits<MyTicker>;
};
```

```cpp
// myticker.cpp
#include "myticker.h"
#include "gx_widgetevent.h"

MyTicker::MyTicker(Widget *parent) : AbstractScrollArea(parent) {
    setDirection(Horizontal);     // Горизонтальная прокрутка
    setDamping(5);                // Настройка затухания (чем больше значение, тем сильнее трение)

    auto *content = new Widget;   // Создание контентного контрола
    setContentWidget(content);
}

bool MyTicker::event(Event *event) {
    return EventDispatch<AbstractScrollArea, LayoutEvent>{}(this, event);
}
```

Установка параметра базового класса для `EventDispatch` в значение `AbstractScrollArea` (вместо `Widget`) позволяет событиям, не обрабатываемым текущим классом (жесты, колесико мыши, изменение размера и т. д.), автоматически возвращаться к реализации `AbstractScrollArea`, сохраняя тем самым полноценное поведение прокрутки.

### Настройка параметров прокрутки

```cpp
setDirection(Vertical);          // Вертикальная прокрутка (по умолчанию)
setDirection(Horizontal);        // Горизонтальная прокрутка
setDamping(3);                   // Низкое затухание: более сильная инерция, больший выбег
setDamping(20);                  // Высокое затухание: слабая инерция, близко к ее отсутствию
setScrollBar(true);              // Отображение полосы прокрутки
setBouncesPolicy(SnapType::SnapEdge);  // Стратегия возврата у края
```

`AbstractScrollArea` также предоставляет метод `scrollTo(x, y, behavior)` для программного управления позицией прокрутки, где `behavior` может быть `Instant` (мгновенный переход) или `Smooth` (с анимацией).

::: tip Инерционное затухание
Для контролов вроде `TextField`, которым требуется точное управление позицией прокрутки, обычно устанавливают высокое значение затухания, чтобы ослабить инерцию; в то время как для контролов вроде `ScrollArea`, ориентированных на просмотр, можно установить низкое затухание для более плавного процесса прокрутки.

Не устанавливайте затухание слишком низким, иначе прокрутка на сверхбольшие расстояния может привести к сбросу кэша содержимого и вызвать лаги.
:::

### Вызов базового класса в диспетчеризации событий

Иногда требуется выполнить дополнительную обработку определенного события, а затем передать управление стандартной реализации `AbstractScrollArea`. Типичный подход заключается в вызове метода базового класса прямо из функции-обработчика:

```cpp
// Подход в TextField: перенаправлять жесты в область прокрутки только при наличии текста
bool TextField::gestureEvent(GestureEvent *event) {
    if (text().empty()) // Игнорировать, если текст пуст
        return false;
    // В остальных случаях передаем логике прокрутки базового класса
    return AbstractScrollArea::gestureEvent(event);
}
```

В таком паттерне в качестве базового класса для `EventDispatch` используется `Widget`, и текущий класс сам решает, когда и какой метод базового класса вызывать:

```cpp
bool TextField::event(Event *event) {
    // Используем Widget в качестве базового класса, полностью контролируя моменты вызова поведения AbstractScrollArea
    return EventDispatch<Widget, GestureEvent, ResizeEvent>{}(this, event);
}
```

### Фильтрация событий контентного контрола

Контентный контрол отвечает за компоновку и размещение дочерних элементов, но некоторые его события (например, запросы компоновки) иногда требуют перехвата и кастомной обработки со стороны контейнера. Вы можете зарегистрировать контейнер в качестве фильтра событий контентного контрола с помощью `setEventFilter(this)`, а затем переопределить `eventFilter()` для обработки интересующих событий:

```cpp
// Регистрация в конструкторе
content->setEventFilter(this);

// Перехват запросов компоновки контентного контрола
bool MyTicker::eventFilter(Object *receiver, Event *e) {
    if (receiver == contentWidget() && e->type() == Event::Layout) {
        auto *lv = static_cast<LayoutEvent *>(e);
        if (lv->isLayoutRequest()) {
            // Кастомная логика компоновки...
            return true; // Возврат true предотвращает дальнейшую передачу события
        }
    }
    // В остальных случаях передаем базовому классу
    return AbstractScrollArea::eventFilter(receiver, e);
}
```

::: tip
Необработанные события должны передаваться обратно в `AbstractScrollArea::eventFilter()`, который отвечает за взаимодействие с внутренними механизмами, такими как полосы прокрутки.
:::

### Установка строчных элементов

Вызов `setInlineWidget(true)` позволяет контролу участвовать в строчной компоновке (inline layout), что подходит для сценариев встраивания в текстовый поток. Именно так поступает `TextField`, чтобы встраиваться в строку подобно тексту.

### ScrollArea и производные классы

`ScrollArea` — это производный класс от `AbstractScrollArea`, который помимо прокрутки добавляет такие возможности, как **индексная навигация** (`index()`/`setIndex()`), **режимы привязки** (snap) и **визуальные эффекты** (visual effect), что делает его предпочтительным базовым классом для списков, бегущих строк и т. д. `Swiper` расширяет `ScrollArea`, добавляя постраничную навигацию (`pageLength`) и индикаторы (indicator), что делает его идеальным для каруселей изображений и подобных режимов.

Эти классы обычно **не требуют дальнейшего наследования**: большинство потребностей в кастомизации может быть удовлетворено с помощью конфигурации параметров и подключения вспомогательных средств без необходимости создания подклассов.

#### Визуальные эффекты VisualEffect

`ScrollArea` поддерживает подключение объекта `VisualEffect` через `setVisualEffect()`, который применяет визуальные трансформации (прозрачность, масштабирование, смещение и т. д.) к каждому дочернему контролу перед его отрисовкой, создавая динамические эффекты при прокрутке. Во фреймворк встроены следующие эффекты:

| Имя класса | Эффект |
|---|---|
| `FisheyeVisualEffect` | Эффект «рыбий глаз», центральный элемент увеличивается, края уменьшаются |
| `FadeVisualEffect` | Затухание по краям, прозрачность падает по мере удаления от центра области видимости |
| `CollapseVisualEffect` | Эффект свертывания, элементы сжимаются и группируются к верхнему (или нижнему) краю |
| `BlendVisualEffect` | Плавный переход между двумя эффектами на основе прогресса |

```cpp
#include "gx_visualeffect.h"

scrollArea->setVisualEffect(make_shared<FisheyeVisualEffect>());
```

Если вам нужен кастомный эффект, унаследуйте `VisualEffect` и реализуйте метод `resolve()`. Метод `resolve()` принимает целевой дочерний контрол, прямоугольник области видимости (viewport) и центр дочернего контрола, а возвращает `PaintModifier`, в котором можно настроить свойства `opacity`, `scale`, `translate` и др.

Подробное описание параметров `ScrollArea` и `Swiper`, а также способы реализации пользовательского `VisualEffect` будут рассмотрены отдельно в главе [Область прокрутки](./scroll-area.md).

## Древовидная структура контролов и жизненный цикл

При создании контролов в C++ отношения родитель-потомок устанавливаются через параметр `parent` в конструкторе:

```cpp
// Когда parent уничтожается, child также автоматически уничтожается
auto *parent = new Widget(window);
auto *child  = new ProgressRing(parent);
child->setGeometry(10, 10, 80, 80);
```

Независимо от того, удаляется ли родительский контрол вручную через `delete` или фреймворк очищает дерево контролов при выходе из приложения, все дочерние контролы уничтожаются автоматически. Вам не нужно вызывать `delete` для дочерних контролов в деструкторе.

Если требуется отложенное уничтожение (например, внутри функции обработки события), можно использовать `deleteLater()`, который уничтожит объект после завершения текущей обработки события, избегая проблем вроде «самоуничтожения изнутри колбэка».

В реактивном фреймворке дерево контролов поддерживается компонентом фреймворка, и при кастомной разработке требуется лишь [зарегистрировать класс контрола](./widget-export.md).
