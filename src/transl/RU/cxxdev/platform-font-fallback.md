# Платформенный фоллбек шрифтов

Фреймворк Glyphix содержит встроенный механизм загрузки и фоллбека шрифтов на основе `font-face` / `font-family`. Однако целевые платформы обычно имеют собственные развитые подсистемы шрифтов (например, Windows DirectWrite, macOS CoreText), в которых уже реализованы системный фоллбек шрифтов и сопутствующие оптимизации.

Чтобы в полной мере задействовать платформенный пайплайн шрифтов, Glyphix позволяет перехватить управление фоллбеком: если встроенные шрифты фреймворка не содержат нужного символа, запрос передается платформе для поиска и отрисовки подходящего системного шрифта. Эта статья предназначена для системных разработчиков Glyphix и проведет вас через все этапы интеграции.

Используемые публичные заголовочные файлы:
- `gx_unite.h`: содержит публичный интерфейс UniTE, а также функцию установки движка `installEngine()`;
- `gx_shapingadapter.h`: основной интерфейс;
- `gx_fontdriver.h`: предоставляет механизм инкапсуляции `FontDriver`;
- `gx_fontloader.h`: предоставляет интерфейс загрузчика шрифтов.

## Общая концепция

Чтобы текст отобразился на экране, он проходит через следующий конвейер: прикладной текст передается **движку разметки абзацев** для разбиения на строки и позиционирования; текст с одинаковым скриптом (письменностью) и направлением **шейпится** в глифы; при нехватке символов применяется **фоллбек шрифтов**; глифы передаются **драйверу шрифтов** для рендеринга в растровые изображения; при этом все шрифты поступают из слоя **управления шрифтами** (регистрация, загрузка и повторное использование).

Три выделенные на схеме части относятся к теме этой статьи:
1. Стратегия фоллбека `FontFallbackShaper`, используемая для поиска недостающих символов и повторного шейпинга;
2. Обертка `PlatformFont`, отвечающая за отрисовку глифов платформенного фоллбека (используется в паре с `FontFallbackShaper`);
3. `FontLoader` для загрузки обертки платформенного фоллбека, который регистрируется в `FontManager`.

Остальные слои фреймворка уже реализованы. Шейпинг текста (`ShapingAdapter`), как правило, не требует реализации с нуля — можно напрямую переиспользовать эталонную реализацию.

### Предварительные требования

Перед реализацией платформенного фоллбека шрифтов согласно данному документу необходимо:

- Включить текстовый движок UniTE (по сравнению с легковесным движком по умолчанию, он поддерживает шейпинг сложных скриптов и многоуровневый фоллбек).
- Целевая платформа должна поддерживать полноценный конвейер шрифтов и предоставлять расширенные возможности, такие как шейпинг системных шрифтов и сопоставление скриптов. Обычно это сложная подсистема, отсутствующая на большинстве платформ MCU RTOS.

::: important
По сравнению с легковесным движком LiTE, включение UniTE и полноценного конвейера шрифтов требует больше памяти и места в ПЗУ. Кроме того, производительность этого движка ниже, чем у LiTE, поэтому необходимо оценить, оправдано ли его включение ради полноценной поддержки Unicode и требований интернационализации.
:::

## Переиспользование бэкенда шейпинга

`ShapingAdapter` отвечает за преобразование символов в глифы. Встроенный класс `HarfBuzzShaper` (`gx_harfbuzz_shaper.cpp`) уже реализует полноценный OpenType-шейпинг: он вызывает HarfBuzz, после чего записывает в вывод индексы глифов, величины advance (смещения шага) и смещения в соответствии с целевым размером в пикселях.

`HarfBuzzShaper` зависит от библиотеки FreeType для чтения файлов шрифтов, поэтому библиотеки HarfBuzz и FreeType должны быть подключены одновременно. Если на целевой платформе эти библиотеки уже присутствуют, убедитесь в совпадении их версий во избежание ошибок компоновки или выполнения.

::: tip
Подобно [зоне ответственности](https://harfbuzz.github.io/what-harfbuzz-doesnt-do.html) HarfBuzz, `ShapingAdapter` не обрабатывает текстовые run-фрагменты, состоящие из разных шрифтов, включая описанный ниже механизм «фоллбека шрифтов». Следовательно, если в шрифте, используемом при шейпинге, отсутствует символ, реализация `ShapingAdapter` возвращает глиф `.notdef` (индекс `0`), который затем обрабатывается стратегией фоллбека.
:::

## Реализация стратегии фоллбека

`FontFallbackShaper` — это ядро механизма фоллбека. Движок вызывает его каждый раз при шейпинге очередного фрагмента текста и ожидает на выходе последовательность глифов **без пропущенных символов** (`.notdef`). В отличие от `ShapingAdapter`, он выполняет шейпинг не для единственного font-face, а разработан для двухэтапного фоллбека.

### Двухэтапный каскад фоллбека

Метод `FontFallbackShaper::shape()` выполняет фоллбек в два этапа («от близкого к далекому»):

- **Первый этап**: взаимное дополнение символов другими шрифтами внутри текущего семейства (`family`). Уже реализовано во фреймворке, вам нужно лишь вызвать `builtinShape()`.
- **Второй этап**: символы, которые не удалось найти на первом этапе, передаются системным шрифтам платформы. Этот этап реализовываете вы.

Отсутствующий символ в данных представляется индексом глифа `0`, то есть `.notdef`. Возвращаемое значение функции `shape()`, тип `FallbackResult`, выражается битовыми флагами: если истинно `result & NotNeeded`, это означает отсутствие пропусков и завершение работы; в противном случае обычно возвращается `FullyResolved` (все обработано) или `PartiallyResolved` (остались неразрешенные `.notdef`).

### Структура функции `shape()`

Сначала вызывается первый этап; если пропущенных символов нет, происходит выход, иначе запускается второй этап платформенного фоллбека. `m_shaper` — это экземпляр `ShapingAdapter`, которым владеет данный класс фоллбека (обычно это `HarfBuzzShaper`).

```cpp
FallbackResult shape(GlyphRunBundle &storage,
                     TextSpan text,
                     FontDriver *font) override {
    // Первый этап: использование builtin API для обработки фоллбека внутри family
    auto r = builtinShape(storage, text, font, &m_shaper);
    if (r & NotNeeded)
        return r;                                  // Пропущенных символов нет, завершаем работу
    return resolveByPlatform(storage, text, font); // Второй этап, см. ниже
}
```

`builtinShape()` — единственное место, зависящее от `ShapingAdapter`. В этом случае реализацию `PlatformFallbackShaper` обычно оформляют следующим образом:
```cpp
class PlatformFallbackShaper : public FontFallbackShaper {
    HarfBuzzShaper m_shaper; // Объявляем напрямую как переменную-член, указатели не нужны

public:
    PlatformFallbackShaper() = default;
    FallbackResult shape(GlyphRunBundle &storage,
                         TextSpan text, FontDriver *font) override;
};
```
Обратите внимание, что `m_shaper` является лишь приватной переменной-членом вашей стратегии платформенного фоллбека и не требует внешнего экспорта. При вызове `builtinShape()` внутри `shape()` достаточно передать `&m_shaper`.

::: tip
В экстремальных случаях (например, на этапе первичной адаптации) можно проигнорировать фоллбек внутри семейства и сразу пропустить `builtinShape()`, выполняя только второй этап платформенного фоллбека. В этом случае можно обойтись без переменной-члена `m_shaper`.

В любом случае, конкретные классы `ShaperAdapter` обычно нельзя объявлять как локальные переменные, так как они могут хранить состояние кэша HarfBuzz, и их пересоздание при каждом вызове шейпинга приведет к серьезному падению производительности.
:::

### Получение платформенного шрифта

На втором этапе пропущенные символы передаются платформе, а рендеринг в конечном итоге выполняет обертка. Функция `fallbackFont(font)` возвращает ту самую обертку, которая зарегистрирована в качестве последнего элемента в `family` (см. далее). Ее статическим типом является `FontDriver *`, и вам потребуется привести его к типу вашей собственной обертки, чтобы иметь возможность вызывать пользовательские интерфейсы регистрации и запросов.

```cpp
// Для приведения можно использовать dyn_cast, но если тип обертки единственный, static_cast также безопасен
auto *wrapper = static_cast<PlatformFont *>(fallbackFont(font));
if (wrapper == nullptr)
    return PartiallyResolved; // Последний элемент family не содержит обертку, продолжение невозможно
```

::: warning Парная реализация обязательна
Стратегия фоллбека и обертка представляют собой взаимосвязанную пару: приведенный выше `static_cast` требует, чтобы `fallbackFont()` возвращала именно ваш тип обертки. Обязательно убедитесь, что установленный обработчик фоллбека и зарегистрированная обертка соответствуют друг другу.
:::

### Простой фоллбек-шейпинг

Наиболее распространенный и подходящий для старта сценарий: весь текстовый run целиком может быть зашейплен одним платформенным шрифтом (то есть файл некоторого системного шрифта полностью покрывает данный скрипт). В этом случае платформенный шрифт выбирается на основе `storage.run().spec.script`, для всего run выполняется повторный шейпинг, и вся последовательность записывается под одним `faceId`, **напрямую перезаписывая результат первого этапа** без необходимости слияния с уже разобранными глифами.

UniTE разбивает run-фрагменты по скриптам, поэтому латиница и CJK в одном тексте изначально попадают в разные run. Когда основной шрифт ориентирован на латиницу, а при встрече с CJK, Arabic, Devanagari и другими скриптами результат работы `builtinShape()` для всего run состоит из `.notdef`, повторный шейпинг и перезапись всего блока не приводят к потере уже разрешенных глифов. По этой причине подавляющее большинство сценариев многоязычной верстки используют именно этот путь, и он не является частным исключением.

```cpp
// Выбираем платформенный шрифт по скрипту (дескриптор платформенного шрифта, а не FontDriver), регистрируем faceId
auto sysFont = platformFontForScript(storage.run().spec.script);
uint32_t faceId = wrapper->registerFont(sysFont);
// Шаги вашего шейпинга порождают glyphCount глифов (здесь показано на примере вывода HarfBuzz)
auto &run = storage.resize(glyphCount);
for (int i = 0; i < glyphCount; ++i) {
    run.data.glyphIds[i]   = GlyphIds::encodeFallback(gid[i], faceId);
    run.data.xAdvances[i]  = uint16_t(scale(pos[i].x_advance));
    run.data.xOffsets[i]   = int16_t(scale(pos[i].x_offset));
    run.data.yOffsets[i]   = int16_t(scale(pos[i].y_offset));
    run.data.clusterMap[i] = static_cast<int>(info[i].cluster);
}
```

Поля `pos`, `info`, `gid` и `scale` получены в результате вашего этапа шейпинга (выше продемонстрировано на базе вывода HarfBuzz).

::: tip Возможности платформенного шейпинга
Платформы обычно имеют собственные средства шейпинга (например, DirectWrite, CoreText); использовать ли повторно HarfBuzz, зависит от конкретной платформы. Вывод HarfBuzz в примере может быть заменен на вывод платформенного шейпера. Для RTL run (`spec.bidiLevel & 1`) необходимо передать направление шейперу.
:::

Предпосылкой для этого метода является маппинг всего run-фрагмента на единственный платформенный шрифт. Он **не применим к общим скриптам (Common script)** (эмодзи, символы и т. д.), где различные символы в рамках одного run могут принадлежать разным платформам шрифтов, что требует использования следующего подхода — сложного фоллбека.

### Сложный фоллбек-шейпинг

Когда в рамках одного run требуются несколько платформ шрифтов или фоллбек необходим лишь для отдельных кластеров, простой подход не применим. Учитывая, что конкретные алгоритмы фоллбека и слияния зависят от API платформы, данный документ описывает лишь семантические требования к итоговому `GlyphRun`, которым должна удовлетворять реализация:

- Разобранные на первом этапе глифы **остаются без изменений**, на втором этапе заменяются только кластеры, оставшиеся `.notdef`.
- Каждый слот глифа должен содержать заполненные поля `glyphIds`, `xAdvances`, `xOffsets`, `yOffsets`, `clusterMap`; глифы фоллбека помечаются с помощью `encodeFallback(gid, faceId)`.
- `clusterMap[i]` задает смещение кодовой точки исходного текста относительно **данного run** (соответствует `spec.text`, диапазон `[0, text.length())`), которое используется при проецировании для отрисовки и обрезки по строкам.
- Количество глифов может изменяться: используйте `storage.resize()/reset()` для настройки хранилища с последующей послотовой записью. `GlyphRunBundle` автоматически обновляет `run().glyphCount`.
- При маппинге одного исходного кластера в несколько глифов порядок и сумма advance должны быть корректными; кодовые точки, поглощенные правилами GSUB при слиянии кластеров, должны порождать глифы с нулевым advance во избежание разрывов или смещений.
- `faceId` должен быть зарегистрированным в обертке стабильным в течение всего жизненного цикла ID; порядок глифов в RTL run должен соответствовать направлению шейпинга.
- Возвращаемое значение: если заполнены все символы — `FullyResolved`, если остались неразрешенные — `PartiallyResolved`.

До тех пор пока вывод удовлетворяет указанным ограничениям, фреймворк выполняет рендеринг корректно. Выбор конкретного способа реализации — поблочный опрос API платформы или повторный шейпинг каждого шрифта через HarfBuzz — остается за разработчиком платформы.

### Высота строки и кэширование

Высота строки определяется шрифтом, **которым фактически отрисовывается каждый конкретный глиф**. За символы внутри семейства отвечает `builtinLineMetrics()`; для глифов с признаком фоллбека (`isFallback()`) у обертки запрашиваются выступы (ascender/descender) их системного шрифта и интегрируются в общий результат. Глифы фоллбека кодируются в `GlyphIds` через `encodeFallback`, где `fontIndex()` содержит записанный `faceId`, по которому у обертки запрашивается соответствующий шрифт платформы.

```cpp
VerticalMetrics resolveLineMetrics(const GlyphIds *gids, int count,
                                   FontDriver *font) const override {
    // Обработка глифов внутри family
    VerticalMetrics m = builtinLineMetrics(gids, count, font);
    // Обработка глифов платформенного фоллбека
    auto *wrapper = static_cast<PlatformFont *>(fallbackFont(font));
    if (wrapper == nullptr)
        return m;
    // Для глифов с gids[i].isFallback() запрашиваем asc/descent у обертки и добавляем в m
    for (auto gid : utils::span<const GlyphIds>(gids, count)) {
        if (!gid.isFallback())
            continue; // Обрабатываем только глифы фоллбека
        uint32_t faceId = gid.fontIndex(); // fontIndex() глифа фоллбека — это faceId
        auto face = wrapper->fontForFaceId(faceId); // Дескриптор шрифта платформы (не FontDriver)
        if (face == nullptr)
            continue;
        m.ascent = max(face->ascender(), m.ascent);
        m.descent = min(face->descender(), m.descent);
    }
    return m;
}
```

Также допускается собрать шрифты фоллбека для всей строки и запросить их asc/descent за один раз, избегая запросов для каждого глифа в цикле.

Метод `flush()` служит для освобождения системных шрифтов, кэшированных оберткой:

```cpp
void flush(FontDriver *font) override {
    if (auto *w = static_cast<PlatformFont *>(fallbackFont(font)))
        w->releaseFonts();
}
```

::: tip
Метод `flush()` вызывается фреймворком при уничтожении абзаца или нехватке памяти; в нем необходимо очистить платформенные ресурсы, удерживаемые оберткой.
:::

## Обертка `FontDriver` для шрифта фоллбека

Обертка отвечает за рендеринг зашейпленных на предыдущем шаге глифов в растровые изображения. Она наследует `FontDriver` и при создании получает флаг `PlatformFallback`, информирующий фреймворк о том, что это шрифт фоллбека.

```cpp
class PlatformFont : public FontDriver {
public:
    PlatformFont(const String &family, const FontAttribute &attr)
        : FontDriver(family, attr, Vector | PlatformFallback) {}
    // ... bitmapOf / metricsOf ...
protected:
    void requestHandler(int) override {}
};
```

Данная обертка шрифта не предназначена для загрузки файлов шрифтов (в отличие от `FontDriverTTF`). Ее задача — передать глифы фоллбека на обработку в конвейер шрифтов платформы, при этом внутренняя реализация остается непрозрачной для Glyphix.

### Двухрежимный поиск

Передаваемый в обертку параметр `code` имеет два значения, которые различаются по биту `CodeAsGlyphId`:

- **С флагом**: поиск по индексу глифа, старшие биты содержат `faceId`, а младшие — индекс глифа. После извлечения запрос маршрутизируется к соответствующему платформенному шрифту, после чего по `glyphId` запрашивается `GlyphBitmap`.
- **Без флага**: поиск по символу Unicode, резервный поиск по кодовой точке среди зарегистрированных шрифтов платформы с последующим самостоятельным преобразованием в индекс глифа и запросом.

Типичная реализация `bitmapOf()` выглядит следующим образом:

```cpp
bool bitmapOf(uint32_t code, GlyphBitmap *bitmap) override {
    if (code & CodeAsGlyphId) { // Поиск по индексу глифа
        uint32_t faceId  = (code >> 16) & 0x3ff;
        uint32_t glyphId =  code & 0xffff;
        auto face = fontForFaceId(faceId); // Дескриптор шрифта платформы (не FontDriver)
        return face && face->bitmapOf(glyphId, bitmap);
    }
    // Поиск по Unicode символу, здесь перебираются зарегистрированные шрифты,
    // также можно использовать более эффективную таблицу маппинга
    for (auto *face : registeredFonts()) {
        uint32_t glyphId = face->glyphIndexOf(code);
        if (face->bitmapOf(glyphId, bitmap))
            return true;
    }
    return false;
}
```

::: tip
`fontForFaceId()` возвращает дескриптор шрифта платформы, **а не `FontDriver`**; вызовы `face->bitmapOf(...)` и `face->glyphIndexOf(...)` выше являются псевдокодом для операций над этим дескриптором, означающими получение `GlyphBitmap` по `glyphId` и получение `glyphId` по кодовой точке соответственно.
:::

Метод `metricsOf()` использует ту же двухрежимную логику; `advancesOf()`, `baseline()` и другие методы также вычисляются на основе платформенного шрифта. `duplicate()` может просто скопировать таблицу маппинга.

### Маппинг `faceId`

Обертка поддерживает маппинг `faceId` → шрифт платформы, используемый стратегией фоллбека при регистрации и при поиске во время рендеринга.

`faceId` представляет собой $10$-битное целое число ($[0, 1023]$), значение которого полностью определяется реализацией с единственным требованием: **стабильность в течение всего жизненного цикла**. Возможны два основных подхода:

- **Фиксация по скриптам**: значение перечисления `Script` используется напрямую в качестве `faceId`, обертка удерживает соответствующие шрифты платформы для каждого скрипта, а регистрация выполняется на основе скрипта без выделения памяти во время выполнения.
- **Динамическое выделение**: при обнаружении каждого нового шрифта платформы выделяется следующий индекс и поддерживается растущая таблица.

Пример фиксации по скриптам (где `faceId` равен значению скрипта):
```cpp
PlatformFontHandle fontForScript(Script script) {
    switch (script) {
    case Script::Han:    return sysHanFont;
    case Script::Arabic: return sysArabicFont;
    case Script::Latin:  return sysLatinFont;
    // ...
    }
    return sysDefaultFont;
}
```
Вам потребуется самостоятельно реализовать маппинг скрипт→шрифт, выделение `faceId` и кэширование объектов шрифтов платформы.

::: tip
`faceId` — это контракт между стратегией фоллбека и оберткой: `PlatformFallbackShaper` использует его для кодирования глифов, а `PlatformFont` — для декодирования обратно в системный шрифт. Интерпретация `faceId` с обеих сторон должна быть идентичной и умещаться в $10$-битное целое число.
:::

## Регистрация обертки

На заключительном этапе фреймворк подключает обертку к загрузке семейств (`family`). Реализуйте `FontLoader::load()`, чтобы для определенного общего имени семейства возвращалась обертка, после чего зарегистрируйте ее в `FontManager`:

```cpp
struct PlatformFontLoader : public FontLoader {
    FontDriver *load(const String &face, const FontAttribute &attr) override {
        if (face == "sans-serif")
            return new PlatformFont(face, attr);
        return nullptr;
    }
};

CoreApp()->fontManager()->install(new PlatformFontLoader);
```

Когда приложение запрашивает шрифт в формате `"<primary-face>,sans-serif"`, фреймворк последовательно объединяет компоненты в одно семейство (`family`), причем обертка становится последним элементом и выступает в роли резервного face, благодаря чему `fallbackFont()` может ее обнаружить.

Классы `PlatformFont` и `PlatformFontLoader` обычно регистрируются только для общих имен семейств, таких как `sans-serif`, а не для конкретных имен системных шрифтов. Это позволяет приложению использовать одно и то же имя семейств на разных платформах без необходимости знать конкретные шрифты системы.

::: warning Ограничение функциональности
Обертка всегда должна располагаться в качестве последнего элемента семейства шрифтов, а порядок указания семейства в запросе приложения должен соответствовать описанному выше. Механизм автоматического обеспечения такого порядка находится в разработке.
:::

## Установка и сборка

Функция `installEngine()` из заголовочного файла `gx_unite.h` подключает вашу стратегию фоллбека к движку:

```cpp
unite::installEngine(*CoreApp()->typesetCore(),
                     std::make_unique<PlatformFallbackShaper>());
```

Полная последовательность сборки:

1. `fontManager()->install(new PlatformFontLoader)`: регистрация загрузчика обертки.
2. `installEngine(...)`: установка стратегии фоллбека, владеющей бэкендом шейпинга.
3. Запрос шрифтов в формате `"<primary-face>,sans-serif"`, с последующей обычной разметкой и отрисовкой.

##Примечания

- Значения advance и смещений всегда задаются в виде фиксированной точки Q26.6 (значение = пиксели × 64).
- Неразрешенные `.notdef` (индексы глифов равны $0$) пропускаются при рендеринге, а на их месте отображается пустота или «квадрат».
- Поле `faceId` имеет размер всего $10$ бит, поэтому максимальное количество одновременно активных системных шрифтов в одном семействе (`family`) ограничено $1024$ штуками.
- Стратегия фоллбека и обертка должны быть реализованы в паре с сохранением一致ности типов (зависит от `static_cast`).
- Обязательно освобождайте кэш платформенных шрифтов, удерживаемый оберткой, внутри метода `flush()`.
