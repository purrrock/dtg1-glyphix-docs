# Пример асинхронной разработки

Если вы считаете, что глава [Разработка асинхронного функционала](async.md) содержит слишком много информации и недостаточно интуитивна, этот документ предлагает несколько типичных и более простых примеров, которые помогут вам справиться с распространенными сценариями асинхронной разработки.

Эти сценарии не являются предельно сложными, но они фокусируются на следующих аспектах:
- Типичный шаблон асинхронного вызова с акцентом на межпоточные и межъязыковые отношения вызовов;
- Эти сценарии могут быть более рутинными, включая большое количество системных API, с которыми необходимо взаимодействовать, что делает код чувствительным к раздуванию (code bloat);
- Наличие типичных требований к взаимодействию с C API, а не со стандартными интерфейсами C++.

Вы можете найти полную реализацию этих сценариев в примерах SDK и запустить их в симуляции прямо на ПК.

## Сценарий: Интеграция с C-интерфейсом будильника

Распространенным асинхронным паттерном в встраиваемых системах является «C-колб» (C Callback): вызывающий код передает задачу и указатель на функцию в качестве уведомления о завершении, а после завершения операции рабочий поток (worker thread) вызывает этот колб.

::: important async поддерживает только потоковую модель
Асинхронный функционал фреймворка Glyphix поддерживает только обычный контекст потоков и не может использоваться в прерываниях (interrupts). Если ваш асинхронный контекст представляет собой обработчик прерывания, вам следует выделить отдельный поток для передачи данных.
:::

В качестве примера рассмотрим службу будильника. Предоставляемый ею асинхронный C-интерфейс выглядит следующим образом:

```c
// На примере alarm_async_create, остальные операции выглядят аналогично
void alarm_async_create(AlarmService *svc, uint32_t interval_ms, ...,
                        alarm_create_cb_t done_cb, void *done_ctx);

// Тип указателя на функцию колба завершения, вызывается в рабочем потоке
typedef void (*alarm_create_cb_t)(alarm_err_t err, alarm_id_t id, void *ctx);
```

Далее мы покажем, как связать подобные типичные C-интерфейсы с колбами в Promise JavaScript.

### Общий тип сессии для нескольких операций

Служба будильника имеет набор операций: `create`, `cancel`, `setEnabled`, `update`, `snooze`, `getInfo`, `list`, `count` и т.д. Если для каждой операции определять отдельный класс клиента (client), это приведет к созданию большого объема шаблонного кода (template instantiation).

Для таких сценариев, где «фактическая логика выполняется на C-уровне, а на стороне C++ происходит только передача параметров», можно определить легковесный клиент, содержащий только маппинг кодов ошибок, и позволить всем операциям использовать один и тот же экземпляр `ResultSession`:

```cpp
struct AlarmClient {
    // Преобразует alarm_err_t с C-уровня в читаемую строку ошибки,
    // которая передается в catch на стороне JavaScript при отклонении (reject) Promise.
    static const char *errorMessage(async::Status status) {
        switch (status.value()) {
        case ALARM_OK:              return "ok";
        case ALARM_ERR_NOT_FOUND:   return "not_found";
        case ALARM_ERR_TABLE_FULL:  return "table_full";
        case ALARM_ERR_INVALID_ARG: return "invalid_arg";
        default:                    return "unknown_error";
        }
    }
};

// Все операции с будильником используют один и тот же тип сессии
using AlarmSession = async::ResultSession<AlarmClient>;
```

`AlarmClient` не нужно реализовывать метод `resolve()`, так как здесь не используется стандартный пул потоков (thread pool executor) — фактические асинхронные операции выполняются рабочим потоком службы будильника, а сторона C++ отвечает только за доставку результатов обратно в UI-поток.

### Базовый паттерн привязки (Binding Pattern)

На примере `alarm.create()` рассмотрим полный процесс привязки:

```cpp
static JsValue jsAlarmCreate(JsCtx ctx) {
    auto *applet = Applet::current(ctx.vm());
    if (!applet || ctx.argc() < 1 || !ctx.arg(0).isObject())
        return JsValue{};

    // Чтение параметров из объекта options, переданного из JavaScript
    const JsValue &opts = ctx.arg(0);
    uint32_t intervalMs = static_cast<uint32_t>(opts["interval"].toInt());
    String label        = opts["label"].toString();
    alarm_repeat_t mask = parseRepeatMask(opts["repeat"]);

    // Создание сессии и извлечение колбов resolve/reject из объекта options (поддерживается два стиля асинхронности)
    auto *session = async::make<AlarmSession>(applet);
    session->setResolver(opts);

    // C-колб: вызывается в рабочем потоке, уведомляет JavaScript через resolve() кросс-поточно
    auto done = +[](alarm_err_t err, alarm_id_t id, void *data) {
        auto *s = static_cast<AlarmSession *>(data);
        s->resolve(err == ALARM_OK
            ? async::Result<int>(id) // Успех: resolve с ID нового будильника
            : async::Status(err));   // Ошибка: reject, сообщение об ошибке берется из errorMessage()
    };

    // Вызов асинхронного C-интерфейса создания будильника, передача колба и указателя на сессию
    alarm_async_create(AppletAlarmService::instance(),
                       intervalMs, mask, label.c_str(), /*...*/,
                       onAlarmFired, nullptr, done, session);
    // Возвращает объект Promise в JavaScript, фреймворк автоматически разрешит его при вызове resolve()
    return session->promise();
}
```

Здесь есть несколько фиксированных шаблонов, которые можно напрямую копировать и использовать:

- `async::make<AlarmSession>(applet)` создает сессию и привязывает ее к текущему Applet для соблюдения требований жизненного цикла.
- `session->setResolver(opts)` позволяет использовать один и тот же код как в [стиле колбов, так и в стиле Promise](/api/README.md#快应用异步接口) для асинхронных вызовов.
- `+[](... void *data)` преобразует лямбду в обычный указатель на функцию с помощью унарного оператора `+`, удовлетворяя требованиям типа C-колба.
- Передача `session` в качестве `void *` в C API с последующим приведением типов обратно в колбе и вызовом `resolve()`.
- `resolve()` является потокобезопасным: он упаковывает результат в событие, отправляет его обратно в UI-поток и затем запускает разрешение (resolution) Promise.

::: tip Использование лямбда-выражений для написания колбов
В C колб-функции обычно являются статическими функциями. Вы можете использовать лямбда-выражения C++ для непосредственного и вложенного определения колб-функций рядом с местом их вызова, например:
```cpp
auto done = +[](alarm_err_t err, alarm_id_t id, ...) { ... }
alarm_async_create(..., done, session);
```
Это позволяет избежать определения большого количества отдельных статических функций, делая код более компактным и понятным.
:::

Структура остальных операций (`cancel`, `setEnabled`, `snooze` и т.д.) абсолютно одинакова, отличаются только чтение параметров и вызовы C API:

```cpp
static JsValue jsAlarmCancel(JsCtx ctx) {
    auto *applet = Applet::current(ctx.vm());
    if (!applet || ctx.argc() < 1)
        return JsValue{};

    alarm_id_t id = ctx.arg(0).toInt();

    auto *session = async::make<AlarmSession>(applet);
    session->setResolver(ctx.arg(0));

    auto done = +[](alarm_err_t err, void *data) {
        // Когда нет возвращаемого значения, достаточно использовать resolve<void>
        static_cast<AlarmSession *>(data)->resolve<void>(async::Status(err));
    };
    alarm_async_cancel(AppletAlarmService::instance(), id, done, session);

    return session->promise();
}
```

::: important Не пропускайте проверку параметров
`session->setResolver(ctx.arg(0))` зависит от проверки `ctx.argc()`. Если в начале функции нет проверки количества параметров, проверьте их при вызове `setResolver()`:
```cpp
session->setResolver(ctx.argc() ? ctx.arg(0) : JsValue{});
```
:::

### Регистрация преобразования типов для пользовательских C-структур

`alarm.getInfo()` возвращает структуру `alarm_info_t`, которую необходимо преобразовать в объект JavaScript. Для этого сначала специализируйте `js_cast<T>` в пространстве имен `gx`:

```cpp
template<> JsValue gx::js_cast<alarm_info_t>(const alarm_info_t &info) {
    JsValue obj = JsVM::current().newObject();
    obj["id"]          = info.id;
    obj["label"]       = info.label;
    obj["interval"]    = double(info.interval_ms);
    obj["repeatMask"]  = info.repeat_mask;
    obj["enabled"]     = bool(info.enabled);
    obj["remaining"]   = double(info.remaining_ms);
    obj["fireCount"]   = int(info.fire_count);
    obj["snooze"]      = int(info.snooze_ms);
    obj["snoozed"]     = bool(info.snoozed);
    return obj;
}
```

После завершения специализации просто передайте экземпляр структуры в `resolve()` внутри функции привязки:

```cpp
auto done = +[](alarm_err_t err, const alarm_info_t *info, void *data) {
    auto *s = static_cast<AlarmSession *>(data);
    if (err != ALARM_OK || !info) {
        // Путь ошибки: возврат статуса ошибки для вызова reject, сообщение берется из errorMessage()
        s->resolve<alarm_info_t>(async::Status(err));
        return;
    }
    s->resolve<alarm_info_t>(*info);  // Фреймворк автоматически вызывает js_cast в UI-потоке
};
alarm_async_get_info(AppletAlarmService::instance(), id, done, session);
```

::: tip
`js_cast()` вызывается фреймворком после того, как результат возвращается в UI-поток, и не выполняется в рабочем потоке. Это означает, что внутри `js_cast()` можно безопасно использовать API, предназначенные исключительно для UI-потока, такие как `JsVM::current()`.
:::

Для таких случаев, как `alarm.list()`, возвращающих массив, можно напрямую сконструировать `std::vector<int>` и вызвать resolve без определения дополнительных преобразований типов:

```cpp
auto done = +[](alarm_err_t /*err*/, const alarm_id_t *ids, int count, void *data) {
    auto *s = static_cast<AlarmSession *>(data);
    s->resolve<std::vector<int>>(std::vector<int>{ids, ids + count});
};
alarm_async_list(AppletAlarmService::instance(), done, session);
```

### Колб срабатывания будильника: отправка событий обратно в JavaScript

Когда будильник срабатывает, C-уровень вызывает колб `alarm_fire_cb_t` из рабочего потока. Этот сценарий несколько отличается от предыдущего «результата запроса» и требует специального проектирования механизма уведомления о событиях.

#### Почему не используются функции обратного вызова JavaScript

Интуитивно кажется разумным позволить приложению передавать функцию обратного вызова при регистрации будильника:

```javascript
// ❌ Это не будет работать в сценарии с будильником
alarm.create({ interval: 60000, onFired: (event) => { /* ... */ } })
```

Проблема в том, что будильники выходят за рамки жизненного цикла приложения: после создания будильника приложение может быть уничтожено в любой момент до срабатывания будильника; кроме того, многие устройства поддерживают срабатывание будильника после перезагрузки.

Функция обратного вызова JavaScript (`JsValue`) действительна только в среде выполнения JavaScript текущего экземпляра приложения. Как только приложение закрывается, эта среда выполнения вместе со всеми `JsValue` уничтожается. В этот момент у стороны C++ нет возможности продолжать удерживать этот колб JavaScript, не говоря уже о том, чтобы вызвать его при срабатывании будильника.

Это проблема не только будильников: **любые события, которые могут происходить в течение жизненного цикла за пределами приложения, не могут быть решены с помощью колбов JavaScript**, например, задачи по расписанию, отправка офлайн-сообщений, уведомления о завершении фоновой загрузки и т.д.

#### Использование согласованных имен методов вместо ссылок на колбы

Самое простое решение: вместо того чтобы приложение «регистрировало колб», система сама **запускает** приложение при возникновении события и вызывает метод обработки на объекте приложения по заранее согласованному имени.

Это согласуется с идеей функций жизненного цикла приложения (`onCreate`, `onShow` и т.д.) — система запускает приложение по требованию, вызывая известный входной метод, а не удерживая предварительно зарегистрированный колб. Приложение реализует соответствующий метод согласно соглашению:

```javascript
// app.js — метод обработки, экспортируемый объектом модели приложения (реализуется по соглашению)
export default {
  onAlarmFired(event) {
    // event: { id, label, interval, ... }
    console.log('alarm fired:', event)
  }
}
```

Реализация на стороне C++: сначала прочитать снимок (snapshot) в рабочем потоке, затем переключиться обратно в главный поток, чтобы запустить приложение и вызвать метод:

```cpp
static void onAlarmFired(alarm_id_t id, void * /*user_data*/) {
    // Чтение снимка в рабочем потоке во избежание межпоточного доступа к таблице будильников
    alarm_info_t info{};
    alarm_get_info(id, &info);

    // Переключение обратно в главный поток для работы с JavaScript
    App()->postTask([info] {
        auto *svc = AppletAlarmService::instance();
        // Запуск (или пробуждение) целевого приложения с помощью launch(), даже если оно в данный момент не запущенно
        auto *applet = AppletKit::instance()->launch(svc->alarmAppletName);
        if (!applet) return;

        auto &vm = JsVM::current();
        // Вызов согласованного метода на экспортированном объекте app.js, параметры события — объект JS с информацией о будильнике
        JsValue event = js_cast(info);
        applet->modelObject().callMethod("onAlarmFired", {event}).reportError();
    });
}
```

Ключевые моменты:

- **Не** манипулируйте `JsValue` напрямую и не вызывайте никаких API JavaScript в рабочем потоке; они могут использоваться только в UI-потоке.
- Используйте `App()->postTask()` для отправки замыкания в главный цикл событий для выполнения — это самый простой способ вернуться в UI-поток.
- Используйте `AppletKit::launch()` вместо поиска существующего экземпляра; `launch()` перезапускает приложение, если оно не существует, и возвращает существующий экземпляр, если оно уже запущенно.
- Метод `.reportError()` для возвращаемого значения `callMethod()` запишет возможные исключения JavaScript в лог вместо их молчаливого игнорирования.

::: tip Согласованные имена методов — самый простой способ обработки событий
Этот паттерн можно понимать так: экспортированный объект app.js — это «набор точек входа», предоставляемых приложением системе. Система вызывает методы внутри него при необходимости, точно так же, как вызывает `onCreate` или `onShow`.

Этот метод не является универсальным, но его вполне достаточно для контролируемых системных приложений. Он прост в реализации и не требует сложных механизмов персистентности и управления колбами.
:::

### Регистрация загрузчика библиотек

После написания всех функций привязки их необходимо «собрать» в [объект библиотеки](native-module.md#library-loader), который может импортировать JavaScript, и зарегистрировать во фреймворке.

Загрузчик библиотек — это функция C++, которая вызывается, когда приложение вызывает `app.loadLibrary('vendor.alarm')`. Она отвечает за создание и возврат объекта JavaScript, содержащего все экспортируемые методы:

```cpp
static JsValue libAlarmLoader(Applet *applet) {
    // Здесь можно проверить имя пакета приложения и отклонить неавторизованный доступ. Также можно проверять поля.
    if (!applet || applet->objectName() != "com.vendor.alarm")
        return JsValue{};

    JsValue lib = JsVM::current().newObject();

    // Монтирование функций привязки на объект библиотеки, имя свойства — это имя метода, вызываемого со стороны JavaScript
    lib["create"]     = jsAlarmCreate;
    lib["cancel"]     = jsAlarmCancel;
    lib["list"]       = jsAlarmList;
    lib["count"]      = jsAlarmCount;
    // ...
    return lib;
}
```

Затем зарегистрируйте загрузчик в `AppletKit` на этапе инициализации:

```cpp
AppletKit kit{&window};
kit.setLibraryLoader("vendor.alarm", libAlarmLoader);
```

На стороне JavaScript модуль импортируется через `app.loadLibrary()`, и возвращаемое значение является объектом библиотеки, возвращенным загрузчиком:

```javascript
const alarm = app.loadLibrary('vendor.alarm')

const id = await alarm.create({ interval: 60000, label: 'Подъем' })
```
