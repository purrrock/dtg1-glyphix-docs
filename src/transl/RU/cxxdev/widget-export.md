# Регистрация элементов управления и интеграция с фреймворком

В [Руководстве по разработке элементов управления](./widget.md) мы создали класс элемента управления на C++. Однако на данном этапе он представляет собой лишь обычный объект C++, и разработчики приложений не могут напрямую использовать его в коде страниц. В этой статье рассказывается, как зарегистрировать элемент управления в фреймворке, чтобы он стал компонентом, пригодным для использования в приложении. Многие концепции данного документа связаны с [Системой объектов](./object-system.md), поэтому рекомендуется предварительно ознакомиться с ней.

## Среда выполнения

Регистрация элементов управления зависит от набора **объектов среды выполнения**. Они являются обязательными зависимостями для работы реактивного фреймворка и должны быть явно созданы в функции `main()` или в коде инициализации платформы, а их жизненный цикл должен охватывать весь период работы приложения:

```cpp
Application app(/* platform */);
JsVM vm;
Window window;
AppletKit kit(&window, "pkgs.db");
```

Эти объекты отвечают за среду выполнения всего приложения:
- `Application` — объект приложения фреймворка, отвечающий за все низкоуровневые службы и поддержание цикла обработки событий. В самом конце инициализации вызывается `app.exec()` для запуска цикла обработки событий;
- `JsVM` — встроенный движок JavaScript, обеспечивающий работу реактивного фреймворка. Он **должен** быть создан *до* `AppletKit`;
- `Window` — окно верхнего уровня, выступающее в качестве цели для вывода рендеринга;
- `AppletKit` — менеджер приложений (Applet), отвечающий за жизненный цикл приложения и регистрацию элементов управления.

::: warning Не опускайте эти объекты
`vm`, `window`, `kit` и т.д. являются RAII-объектами, и фреймворк управляет средой выполнения через их конструкторы/деструкторы. Даже если в коде нет прямых вызовов `vm`, само её **существование** абсолютно необходимо — преждевременное уничтожение или отсутствие этих объектов приведет к неработоспособности фреймворка.
:::

Объект `Window window` в некоторых случаях можно заменить на `Widget window` и т.п. Разница заключается в том, что `Window` по умолчанию рисует непрозрачный фон, в то время как `Widget` по умолчанию прозрачен.

## Регистрация элементов управления

Регистрация элементов управления выполняется с помощью метода `AppletKit::installWidget<T>()`. Вызов должен осуществляться после инициализации `AppletKit`, но **до** запуска первого приложения с помощью `launch()`:

```cpp
// Регистрация кастомного элемента управления (до вызова launch)
kit.installWidget<ProgressRing>(); // Без параметров, регистрируется по имени класса, в шаблоне пишется как <progress-ring>
kit.installWidget<MySpecialChart>("SpecialChart"); // Или регистрация под кастомным именем (см. ниже)

kit.launch("com.example.app");     // Запуск приложения
return app.exec();                 // Вход в цикл обработки событий
```

::: tip Встроенные элементы управления зарегистрированы по умолчанию
Встроенные в фреймворк кнопки, метки и другие элементы управления регистрируются с помощью `installBuiltinWidgets()`. Если при сборке SDK включена опция CMake `GX_BUILTIN_BINDINGS` (по умолчанию `ON`), `AppletKit` **автоматически вызывает** этот метод при создании, и ручная обработка не требуется. Вызывать `kit.installBuiltinWidgets()` самостоятельно нужно только в том случае, если эта опция была явно отключена.
:::

После регистрации фреймворк на основе метаданных `GX_OBJECT` класса элемента управления автоматически экспортирует его свойства, события, методы, а также используемые ими типы перечислений (enum) и структур, делая их доступными на уровне приложения.

### Использование на страницах приложения

После успешной регистрации разработчики приложений могут использовать элемент управления в шаблонах страниц так же, как и встроенные:

```xml
<!-- На примере компонента progress-ring -->
<progress-ring
  class="ring"
  :value="progress"
  @completed="onDone">
</progress-ring>
```

Здесь `:value="progress"` связывает свойство `value` элемента управления с данными приложения `progress`; `@completed` прослушивает событие `completed`, экспортируемое элементом управления. Фреймворк автоматически выполняет взаимное преобразовывание значений JavaScript и свойств C++, избавляя разработчика от необходимости писать какой-либо «связующий код» (boilerplate).

### Пользовательские имена компонентов

По умолчанию элемент управления регистрируется под своим **именем класса**. Если имя класса не подходит для использования в качестве имени компонента, при регистрации можно указать пользовательское имя:

```cpp
// Регистрация VendorWaveformGraph под именем WaveformGraph, в шаблоне пишется как <waveform-graph>
kit.installWidget<VendorWaveformGraph>("WaveformGraph");
```

Пользовательское имя должно быть в формате **PascalCase** (большая верблюжья кавычка), в том же стиле, что и имена классов C++.

### Преобразование именования C++ ↔ UX

Имя тега компонента соответствует имени при регистрации (по умолчанию это **имя класса**, объявленное в `GX_OBJECT`, или пользовательское имя, указанное при регистрации). В шаблонах принято использовать дефисный стиль написания (kebab-case), а **инструмент сборки ux отвечает за преобразование имен на этапе компиляции**:

- Имя тега: kebab-case в шаблоне ↔ PascalCase зарегистрированного имени. Например, `<progress-ring>` соответствует классу `ProgressRing`. То же самое касается и имен пользовательской регистрации.
- Имя свойства: kebab-case в шаблоне ↔ camelCase в C++. Например, `ring-color` соответствует свойству `ringColor`.

Иными словами, во время выполнения фреймворк осуществляет точное сопоставление по исходным именам, объявленным в C++ (camelCase / PascalCase), в то время как написание через дефис — это лишь привычка написания на стороне шаблона, которая преобразуется инструментом ux для сопряжения.

В UX-компонентах также можно использовать те же PascalCase для тегов и camelCase для свойств, что и в C++, подробнее см. [Спецификация именования компонентов](/tutorials/name-spec.md).

## Экспорт свойств и событий

Свойства, объявленные с помощью макроса `GX_PROPERTY`, экспортируются автоматически по следующим правилам:

- Имя свойства совпадает с именем свойства в компоненте фреймворка, они напрямую соответствуют друг другу.
- Свойства, для которых объявлен сеттер (`set xxx`), могут получать значения из приложения.
- Свойства, для которых объявлен геттер (`get xxx`), могут считываться приложением.
- Когда объявлен сигнал (`signal xxxChanged`), сигнал об изменении свойства передается в привязку.

Пример полного объявления свойств:

```cpp
class ProgressRing : public Widget {
    GX_OBJECT
public:
    GX_PROPERTY(int value, get value, set setValue, signal valueChanged)
    GX_PROPERTY(Color ringColor, get ringColor, set setRingColor)
    GX_PROPERTY(bool showLabel, get showLabel, set setShowLabel)
    // ...
};
```

Соответствующее использование на стороне приложения:

```xml
<progress-ring
  :value="jobProgress"
  ring-color="#409EFF"
  :show-label="true">
</progress-ring>
```

Свойства в шаблоне пишется через дефис (kebab-case), что соответствует именам свойств в формате camelCase в C++: `ring-color` → `ringColor`, `show-label` → `showLabel` (преобразование выполняется инструментом сборки ux, см. выше). `:value` и `:show-label` — это динамические привязки (значения являются выражениями), в то время как литералы вроде `ring-color="#409EFF"` — статическое присваивание.

### Экспорт событий

События компонентов экспортируются через **свойства с сигналами изменения**, а не напрямую через члены типа `Signal<>`. Экспорт события состоит из двух шагов:

1. Объявление члена `Signal<...>` (используется внутри C++);
2. Ссылка на него в поле `signal` какого-либо макроса `GX_PROPERTY`.

Ключевое правило: имя события, прослушиваемого на стороне приложения, — это **имя свойства**, а **не** имя члена-сигнала.

### Событие изменения свойства со значением

```cpp
class ProgressRing : public Widget {
    GX_OBJECT
public:
    int value() const;
    void setValue(int v);

    Signal<int> valueChanged;   // Внутренний сигнал, это имя невидимо для приложения
    GX_PROPERTY(int value, get value, set setValue, signal valueChanged)
};
```

На стороне приложения изменения прослушиваются через `@имя_свойства`, поэтому здесь пишется `@value` (имя свойства), а **не** `@value-changed`: несмотря на то, что член-сигнал называется `valueChanged`, имя события, видимое приложением, всегда остается именем свойства `value`.

```xml
<progress-ring :value="progress" @value="onProgressChanged"></progress-ring>
```

Это полностью совпадает с поведением встроенных элементов управления фреймворка. Например, член-сигнал изменения значения `Slider` называется `changed`, но на стороне приложения прослушивается по-прежнему имя свойства `value` (`@value` или двунаправленная привязка `::value`).

### Чистое событие без значения

Для событий, которые не переносят числовых значений, а лишь обозначают «что-то произошло» (например, «завершено»), в качестве типа свойства используется `invalid_t` для объявления свойства, имеющего только сигнал и не имеющего значений чтения/записи:

```cpp
Signal<>  completed;   // Эмитируется при завершении прогресса
GX_PROPERTY(invalid_t completed, signal completed)
```

На стороне приложения прослушивание осуществляется следующим образом (без значения события):

```xml
<progress-ring @completed="onDone"></progress-ring>
```

Вы не можете объявить `GX_PROPERTY` с типом `void`, даже если у него вообще нет геттера/сеттера, поэтому в качестве типа-заглушки необходимо использовать `invalid_t`. Если вы хотите, чтобы событие переносило значение, вы должны объявить его как конкретный тип и предоставить метод `get` — тип параметра `Signal<T>` не становится автоматически значением события, оно всегда берется из геттера свойства.

::: warning `Signal<>` не становится событием автоматически
Если вы объявили только член `Signal<>`, но не сослались на него через поле `signal` ни в одном `GX_PROPERTY`, этот сигнал **невозможно** прослушивать на стороне приложения с помощью `@some-event`. Фреймворк экспортирует в качестве событий только «сигналы изменения свойств», то есть поле `signal`, а имя события всегда берется из имени свойства.
:::

## Экспорт методов

Функции-члены, объявленные с помощью `GX_METHOD`, экспортируются как методы компонента и могут вызываться приложением в JavaScript:

```cpp
class ProgressRing : public Widget {
    GX_OBJECT
public:
    GX_METHOD void reset();               // Метод без параметров
    GX_METHOD void animateTo(int target); // Метод с параметрами
};
```

В отличие от свойств и событий, методы используются не через теги шаблона, а путем предварительного получения объекта нативного компонента с помощью [`$element()`](../framework/component/component-apis.md#element) и последующего вызова метода на нем. В соответствующем шаблоне компоненту необходимо задать `id`:

```xml
<progress-ring id="ring" :value="progress"/>
```

```js
onReady() {
  const ring = this.$element('ring'); // 'ring' — это id компонента в шаблоне
  ring.reset();
  ring.animateTo(80);
}
```

Параметры и возвращаемые значения методов автоматически маршалятся фреймворком через `Variant`, написание кода преобразования вручную не требуется (подробности о сопряжении типов см. в разделе [Система объектов · Система типов времени выполнения](./object-system.md#运行时类型系统)). Обратите внимание, что `$element()` должен вызываться в жизненном цикле [`onReady()`](../framework/component/life-cycle.md#onready) или после него, подробнее см. в разделе [Нативный компонент](../framework/component/native-component.md).

## Типы перечислений и структур

Если типом свойства или параметра метода является пользовательское перечисление (enum) или структура C++, их можно экспортировать, просто отметив макросами `GX_ENUM` / `GX_STRUCT`. При [регистрации элемента управления](#注册控件) фреймворк автоматически установит соответствующие преобразователи типов, без необходимости писать код привязки вручную. Перечисления на стороне JavaScript представляются в виде строковых констант, а структуры — в виде объектных литералов:

```cpp
class ProgressRing : public Widget {
    GX_OBJECT
public:
    // Обратите внимание на определение псевдонимов для значений, иначе на стороне JavaScript
    // будут использоваться имена 'Solid' / 'Dashed' вместо ожидаемых 'solid' / 'dashed'
    enum GX_ENUM LineStyle {
        Solid GX_ALIAS("solid") = 0,
        Dashed GX_ALIAS("dashed"),
    };
    // Для структур не забывайте указывать значения по умолчанию, чтобы избежать появления неопр. полей при создании на стороне JS
    struct GX_STRUCT Range { int min = 0; int max = 100; };

    GX_METHOD void setRange(const Range &range);

    GX_PROPERTY(LineStyle lineStyle, get lineStyle, set setLineStyle)
};
```

```xml
<progress-ring line-style="dashed"/>
```

```js
this.$element('ring').setRange({ min: 0, max: 100 });
```

Полная семантика псевдонимов перечислений, маппинга полей структур, вложенных типов и т.д. описана в разделе [Система объектов · Отражение сложных типов](./object-system.md#复杂类型反射), здесь мы на этом останавливаться не будем.

::: warning Не забудьте аннотации
Когда в свойстве или методе используются пользовательские перечисления/структуры, обязательно отмечайте их макросами `GX_ENUM` / `GX_STRUCT`, иначе они будут недоступны на стороне JavaScript, и никаких сообщений об ошибках компиляции при этом не возникнет.
:::

## Контейнерные элементы управления (дочерние элементы)

Если элемент управления должен содержать дочерний контент, объявленный приложением, достаточно реализовать его как **контейнерный элемент управления**: на стороне C++ вы отвечаете за компоновку дочерних элементов, а фреймворк автоматически создаст вложенные в шаблон дочерние компоненты как дочерние элементы управления и смонтирует их под ним. В Glyphix нет именованных слотов (slots), как в HTML, и теги, вложенные в шаблон, напрямую становятся дочерними элементами управления данного компонента.

Компоновка контейнера может быть реализована двумя способами (подробнее см. в разделе «Компоновка и размеры» [Руководства по разработке элементов управления](./widget.md)):

- Использование готовых классов компоновки фреймворка, например, вызов `setLayout(new FlexLayout())` в конструкторе;
- Либо переопределение `layoutEvent()`, в котором перебираются `children()` для ручной установки геометрии каждого дочернего элемента управления.

На стороне приложения использование выглядит как вложенные дочерние теги (здесь `card-panel` — это реализованный и зарегистрированный разработчиком контейнерный элемент управления, а `text` — встроенный):

```xml
<card-panel>
  <text>Заголовок</text>
  <progress-ring :value="progress"/>
</card-panel>
```

## Полный пример

Ниже приведено определение простого элемента управления для отображения чисел с его последующей регистрацией в качестве компонента фреймворка:

```cpp
// number_display.h
#pragma once
#include "gx_widget.h"
#include "gx_color.h"

class NumberDisplay : public Widget {
    GX_OBJECT
public:
    explicit NumberDisplay(Widget *parent = nullptr);

    int value() const { return m_value; }
    Color textColor() const { return m_color; }

    void setValue(int v);
    void setTextColor(const Color &c);

    bool event(Event *event) override;   // Единственная виртуальная функция, требующая переопределения

    Signal<int> valueChanged;            // Внутренний сигнал; приложение прослушивает через имя свойства value

    GX_PROPERTY(int value, get value, set setValue, signal valueChanged)
    GX_PROPERTY(Color textColor, get textColor, set setTextColor)

protected:
    // paintEvent и sizeHint не являются виртуальными функциями, override ставить нельзя
    void paintEvent(PaintEvent *event);
    Size sizeHint() const;

    // EventDispatch требуется доступ к защищенным (protected) обработчикам
    friend struct EventTraits<NumberDisplay>;

private:
    int m_value = 0;
    Color m_color{0, 0, 0};
};
```

```cpp
// number_display.cpp
#include "number_display.h"
#include "gx_format.h"
#include "gx_painter.h"
#include "gx_widgetevent.h"   // EventDispatch

NumberDisplay::NumberDisplay(Widget *parent)
    : Widget(parent) {}

bool NumberDisplay::event(Event *event) {
    // Диспетчеризация событий в paintEvent; объявление PaintEvent позволяет проверить пропуски на этапе компиляции
    return EventDispatch<Widget, PaintEvent>{}(this, event);
}

void NumberDisplay::setValue(int v) {
    if (m_value == v) return;
    m_value = v;
    update();
    valueChanged(v);
}

void NumberDisplay::setTextColor(const Color &c) {
    if (m_color == c) return;
    m_color = c;
    update();
}

Size NumberDisplay::sizeHint() const {
    return Size(60, 30);
}

void NumberDisplay::paintEvent(PaintEvent *) {
    Painter p(this);
    p.setBrush(m_color);   // Цвет текста определяется кистью (Brush), а не пером (Pen)
    p.setFont(Font(20));
    p.drawText(rect(), format("{}", m_value), AlignCenter);
}
```

Регистрация:

```cpp
kit.installWidget<NumberDisplay>();
```

Использование на стороне приложения:

```xml
<number-display
  :value="count"
  text-color="#333333"
  @value="onCountChanged">
</number-display>
```

На этом весь процесс от реализации на C++ до использования в приложении завершен: тег `<number-display>` преобразуется инструментом ux в зарегистрированное имя `NumberDisplay` и успешно распознается.

Всякий раз, когда данные приложения `count` изменяются, привязка `:value` вызывает `NumberDisplay::setValue()`; когда элемент управления изнутри эмитирует сигнал `valueChanged`, фреймворк инициирует событие с именем `value` (имя события берется из имени свойства), тем самым вызывая метод приложения `onCountChanged`. Если вы хотите сделать синхронизацию `count` и элемента управления двунаправленной, вы можете заменить привязку на `::value="count"`.
