# C++ Нативная разработка

Glyphix — это прикладной фреймворк для встраиваемых устройств, который предоставляет опыт разработки приложений преимущественно на JavaScript в стиле, похожем на Vue Options API. Тем не менее, ядро рантайма фреймворка реализовано на C++, поэтому производители оборудования могут расширять и кастомизировать функционал фреймворка с помощью C++ — именно здесь в игру вступает «C++ нативная разработка».

Эта документация предназначена для C++ разработчиков с опытом встроенной разработки. Ее цель — помочь вам понять механизм C++ расширений Glyphix и научиться реализовывать следующие два типа функционала:

- **Native Module (Нативный модуль)**: Инкапсуляция функционала C++ в API, доступные из JavaScript, такие как системные возможности для доступа к файлам, чтения аппаратных датчиков, связи по Bluetooth и т. д.
- **Native Widget (Нативный элемент управления / виджет)**: Реализация пользовательских элементов интерфейса на C++ и их регистрация в качестве [компонентов](/framework/component/native-component.md) фреймворка, чтобы приложения могли использовать их прямо в интерфейсе, точно так же, как встроенные компоненты `div`, `image`, `button`.

::: tip
В разработке приложений мы используем термин «компонент» для обозначения элементов пользовательского интерфейса, в то время как на уровне C++ используется термин «виджет (Widget)». В этой документации эти два термина разграничиваются: **виджет** — это понятие на уровне C++, а **компонент** — на уровне реактивного фреймворка.
:::

Самый нижний уровень — это **слой адаптации платформы**, отвечающий за платформо-зависимые абстракции, такие как графический рендеринг, события ввода и файловая система. Этот слой обычно реализуется производителем устройства или предоставляется Glyphix в виде эталонной реализации для соответствующей платформы.

На нем располагается **ядро фреймворка C++**, включающее полную систему виджетов (`Widget`), диспетчеризацию событий, движок анимации, систему компоновки и движок стилей. Все элементы интерфейса в конечном итоге организуются и рендерятся в виде дерева виджетов C++.

Еще выше находится **реактивный фреймворк**, отвечающий за связывание базовых возможностей C++ с JavaScript-приложениями. Он содержит встроенный движок JavaScript (JerryScript или QuickJS) и осуществляет двунаправленное взаимодействие между C++ и JavaScript через классы `JsVM` и `JsValue`. AppletKit управляет полным жизненным циклом приложений (Applet), система компонентов реализует реактивную привязку данных и рендеринг шаблонов, а фреймворк асинхронных сессий сопоставляет асинхронные операции C++ с промисами (Promises) в JavaScript. Сам реактивный фреймворк также реализован на C++.

Самый верхний уровень — это **песочница приложения**: каждое запущенное приложение (Applet) имеет независимую среду выполнения JavaScript (Realm), полностью изолированную от остальных. При выходе из приложения все ресурсы в его песочнице автоматически высвобождаются.

### Принцип системного взаимодействия

Архитектурная схема отображает разделение модулей, но намеренно скрывает связи взаимодействия и сцепления между ними. На самом деле весь фреймворк работает за счет согласованной работы единого набора базовых механизмов. Понимание этих механизмов поможет вам на практике знать, «что вы делаете и почему вы это делаете».

Весь фреймворк пронизан единой **системой объектов**, которая наделяет классы способностью осознавать себя в рантайме, включая возможности рефлексии свойств классов C++, уведомления о событиях и необходимую безопасность жизненного цикла. Виджеты (Widget), нативные модули (Native Module), фреймворк приложений и асинхронные сессии — все они опираются на этот общий фундамент (подробнее см. в разделе [Система объектов](./object-system.md)).

**Виджеты** образуют скелет пользовательского интерфейса в виде дерева объектов, дополненного отрисовкой и диспетчеризацией событий; прикладной слой JavaScript использует декларативную модель программирования на основе **компонентов**, и обе эти стороны естественным образом стыкуются с помощью таких возможностей рефлексии, как свойства объектов. Сложные функции вроде **асинхронных сессий** также опираются на модель жизненного цикла системы объектов для обеспечения корректности.

Благодаря **компилятору метаобъектов** и другим механизмам абстракции, Glyphix не требует от разработчика вручную писать код связывания (binding) для экспорта классов виджетов, разработанных на C++, в JavaScript. В то же время на стороне C++ сохраняется полноценная функциональность: теоретически вы можете разработать полноценное приложение целиком на C++ (хотя это и не рекомендуется).

### Модель программирования

Проект Glyphix не накладывает ограничений на конкретные парадигмы программирования. Например, система объектов представляет собой классическую объектно-ориентированную модель, в то время как реактивный фреймворк предоставляет разработчикам приложений декларативный подход к компонентной разработке.

Мы не рекомендуем разработчикам следовать догме «все есть объект», слепо применять паттерны проектирования или гнаться за избыточными абстракциями. Наши принципы проектирования ближе к **прагматизму**, где во главу угла ставятся **ограничения ресурсов** встроенных систем и эффективность разработки.

## Соглашения документации

### Что это за документ?

Это руководство по нативной разработке на C++ в Glyphix, а **не** справочник по API. В нем рассказывается о концепциях проектирования фреймворка, его ключевых механизмах и процессе разработки. Оно поможет вам понять, как расширять функциональность фреймворка, и продемонстрирует конкретные детали реализации на примерах кода.

В процессе реальной разработки обязательно обращайтесь к документации по API, которая поставляется вместе с SDK (обратитесь к вашему вендору для получения доступа).

### О пояснениях к примерам кода

Весь код на C++ во фреймворке Glyphix находится в пространстве имен `gx`. В документации по умолчанию предполагается наличие директивы `using namespace gx;`, поэтому имена классов и функций указаны без префикса `gx::`. Например:

```cpp
#include "gx_widget.h"

using namespace gx; // В документации по умолчанию предполагается использование пространства имен gx

class MyWidget : public Widget {
    // ...
};
```

Здесь `Widget` фактически является `gx::Widget`, но для краткости префикс пространства имен опущен.

В них рассматривается только та часть C++, которая действительно необходима для нативной разработки на Glyphix, а также подобраны полезные внешние ресурсы для встраиваемых разработчиков.

## Путь разработки

Независимо от вашей цели, рекомендуется сначала бегло ознакомиться с [системой объектов](./object-system) и базовым использованием `GX_OBJECT`, `GX_PROPERTY` и `Signal` — они применяются во всех сценариях разработки.

В зависимости от ваших задач выберите подходящий раздел для дальнейшего чтения:

- [Настройка проекта SDK](./sdk-setup): Как настроить среду сборки проекта SDK, включая регистрацию через `glyphix_add_meta_objects()`, сборку для хоста и кросс-компиляцию.
- [Разработка Native Module](./native-module): Как предоставлять новые системные API для приложения, например, получение данных с датчиков или вызов функций низкоуровневого SDK.
- [Разработка асинхронного функционала](./async): Как расширять приложение асинхронными возможностями, такими как сетевые запросы, файловый ввод-вывод, ресурсоемкие вычисления и т. д.
- [Руководство по разработке виджетов](./widget.md): Как реализовать новые элементы интерфейса (например, кастомные графики, особые списки с анимацией и т. д.).
- [Регистрация и экспорт виджетов](./widget-export.md): Регистрация пользовательских виджетов в качестве компонентов фреймворка для прямого использования в приложениях.
