# C++ Нативная разработка

Glyphix — это прикладной фреймворк для встраиваемых устройств, который предоставляет опыт разработки приложений преимущественно на JavaScript в стиле, аналогичном Vue Options API. Тем не менее, ключевой рантайм фреймворка реализован на C++, поэтому производители оборудования могут расширять и настраивать функционал фреймворка с помощью C++ — именно в этом и заключается назначение «C++ нативной разработки».

Данная документация предназначена для C++ разработчиков с опытом встроенной разработки. Ее цель — помочь вам понять механизм C++ расширений Glyphix и научить реализовать следующие два типа функционала:

- **Native Module (Нативный модуль)**: Инкапсуляция функций C++ в API, доступные из JavaScript, такие как доступ к файловой системе, чтение аппаратных датчиков, Bluetooth-связь и другие системные возможности.
- **Native Widget (Нативный элемент управления)**: Реализация пользовательских UI-виджетов на C++ и их регистрация в качестве [компонентов](/framework/component/native-component.md) фреймворка для прямого использования в приложениях, точно так же, как встроенные компоненты `div`, `image`, `button`.

::: tip
В разработке приложений мы используем термин «компонент» для обозначения UI-элементов, в то время как на уровне C++ используется термин «виджет (Widget)». В данной документации эти два термина разграничиваются: **виджет** — это понятие уровня C++, а **компонент** — понятие реактивного фреймворка.
:::

Самый нижний уровень — это **слой адаптации платформы**, отвечающий за платформо-зависимые абстракции, такие как графический рендеринг, события ввода и файловая система. Этот уровень обычно реализуется производителем устройства или предоставляется Glyphix в виде эталонной реализации для соответствующей платформы.

На нем располагается **ядро фреймворка C++**, включающее полную систему виджетов (`Widget`), диспетчеризацию событий, движок анимации, систему компоновки и движок стилей. Все UI-элементы в конечном итоге организуются и рендерятся в виде дерева C++ виджетов.

Еще выше находится **реактивный фреймворк**, отвечающий за сопряжение возможностей ядра C++ с JavaScript-приложениями. Он встраивает JavaScript-движок (JerryScript или QuickJS) и реализует двунаправленное взаимодействие C++ и JavaScript с помощью классов `JsVM` и `JsValue`. AppletKit управляет полным жизненным циклом приложений (Applet), система компонентов реализует реактивную привязку данных и рендеринг шаблонов, а фреймворк асинхронных сессий отображает асинхронные операции C++ в JavaScript Promises. Сам реактивный фреймворк также написан на C++.

Самый верхний уровень — это **песочница приложения**: каждое запущенное приложение (Applet) имеет независимую среду выполнения JavaScript (Realm), полностью изолированную от остальных. При выходе из приложения все ресурсы в его песочнице автоматически высвобождаются.

### Принцип системного взаимодействия

Архитектурная схема отображает разделение модулей, но намеренно скрывает связи по взаимодействию и сцеплению между ними. Фактически весь фреймворк функционирует за счет слаженной работы единого набора базовых механизмов. Понимание этих механизмов поможет вам на практике знать, «что именно вы делаете и почему вы это делаете».

Весь фреймворк пронизан единой **системой объектов**, которая наделяет классы способностью к самоосознанию в рантайме, включая возможности рефлексии свойств C++ классов, уведомления о событиях, а также необходимую безопасность жизненного цикла. Виджеты, нативные модули, прикладной фреймворк и асинхронные сессии опираются на этот единый фундамент, подробнее см. в разделе [Система объектов](./object-system.md).

**Виджеты** формируют UI-каркас в виде дерева объектов, дополненного отрисовкой и диспетчеризацией событий; прикладной JavaScript-слой использует декларативную модель программирования на основе **компонентов**, и обе эти стороны естественным образом стыкуются через возможности рефлексии свойств объектов. Более сложные функции, такие как **асинхронные сессии**, также опираются на модель жизненного цикла системы объектов для обеспечения корректности.

Благодаря **компилятору метаобъектов** и другим механизмам абстракции, Glyphix освобождает разработчика от необходимости вручную писать код привязки для экспорта разработанных на C++ виджетов в JavaScript. В то же время на стороне C++ сохраняется полнота функционала, и теоретически вы можете разработать полноценное приложение целиком на C++ (хотя это и не рекомендуется).

### Модель программирования

Проект Glyphix не ограничивает какую-либо конкретную парадигму программирования: например, система объектов представляет собой классическую объектно-ориентированную модель, в то время как реактивный фреймворк предоставляет разработчикам приложений декларативный подход к компонентной разработке.

Мы не рекомендуем разработчикам следовать принципу «все есть объект», слепо применять паттерны проектирования или гнаться за избыточными абстракциям. Наши принципы проектирования более **прагматичны**, а первоочередными целями являются соблюдение **ресурсных ограничений** встроенных систем и эффективность разработки.

## Соглашения в документации

### Что это за документация?

Это руководство по нативной разработке на C++ для Glyphix, а **не** справочник по API. В нем рассказывается о дизайн-концепции, ключевых механизмах и процессе разработки фреймворка, чтобы помочь вам понять, как расширять его функциональность, а также продемонстрировать конкретные детали реализации на примерах кода.

В процессе реальной разработки обязательно обращайтесь к справочнику по API, который поставляется вместе с SDK (обратитесь к вашему вендору для получения доступа).

### О пояснениях к коду в примерах

Весь код на C++ во фреймворке Glyphix находится в пространстве имен `gx`. В документации по умолчанию предполагается наличие директивы `using namespace gx;`, поэтому имена классов и функций не содержат префикс `gx::`. Например:

```cpp
#include "gx_widget.h"

using namespace gx; // В документации по умолчанию предполагается подключение пространства имен gx

class MyWidget : public Widget {
    // ...
};
```

В примере выше `Widget` на самом деле является `gx::Widget`, но для краткости префикс пространства имен опущен.

Независимо от вашей цели, рекомендуется сначала ознакомиться с основами использования `GX_OBJECT`, `GX_PROPERTY` и `Signal` в разделе [Система объектов](./object-system) — они понадобятся вам во всех сценариях разработки.

- [Настройка проекта SDK](./sdk-setup): Как настроить окружение сборки проекта SDK, включая регистрацию через `glyphix_add_meta_objects()`, сборку под хост и кросс-компиляцию.
- [Разработка нативных модулей (Native Module)](./native-module): Как предоставить приложению новые системные API, такие как получение данных с датчиков или вызов функций низкоуровневого SDK.

- [Руководство по разработке виджетов](./widget.md): Как реализовать новые UI-виджеты (например, кастомные графики, особые списки с анимацией и т. д.).
