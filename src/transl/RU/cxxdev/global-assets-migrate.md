# Руководство по миграции глобальных ресурсов

Это руководство предназначено для проектов, интегрирующих Glyphix, и поможет вам обновить способ загрузки глобальных ресурсов в старых проектах до актуального решения. Это обеспечит простую в управлении и редактировании структуру глобальных ресурсов и избавит от необходимости зависеть от инструментов упаковки или конвертации производителя.

На ранних этапах Glyphix использовал бинарный архивный пакет `global.pkg` для управления глобальными ресурсами (файлами шрифтов, таблицами сопоставления шрифтов и т. д.). Позже система постепенно перешла на прямое использование распакованных файлов ресурсов, и в конечном итоге формат файла сопоставления шрифтов был также переведен из бинарного в стандартный JSON <version-badge since="0.9" />. Если в поддерживаемом вами коде точки входа все еще используются старые подходы, вы можете обновить его, следуя данному руководству.

::: tip
Использование старого режима создает трудности при обслуживании, управлении и редактировании глобальных ресурсов, поэтому настоятельно рекомендуется выполнить обновление незамедлительно.
:::

## Удаление `global.pkg`

### Признаки старого кода

Если в коде вашей точки входа присутствует любой из следующих шаблонов, это означает, что вы используете `global.pkg`:

```cpp
EnvPath::setEntry(EnvPath::GlobalPackage, "/global.pkg");
static String globalUri(const String &path) { return "pkg:///" + path; }
```

Эффект этих двух строк заключается в следующем: все запросы ресурсов с протоколом `pkg:///` маршрутизируются к файлам внутри бинарного архивного пакета `/global.pkg`.

Почему это нужно удалить:
- При каждой замене шрифтов или других ресурсов необходимо заново запускать утилиту упаковки для генерации файла `.pkg`.
- При отладке невозможно напрямую просмотреть или заменить отдельные файлы внутри `.pkg`, а также трудно сверять их содержимое.
- Процесс сборки зависит от специализированных инструментов, что увеличивает затраты на коммуникацию и поддержку.

### Процесс миграции

**Шаг 1: Извлечение ресурсов из `global.pkg`.**

Если у вас не осталось исходных файлов `.pkg`, вы можете извлечь содержимое из `global.pkg` (используя командную строку Glyphix или запросив исходные файлы ресурсов). Обычно необходимо извлечь следующее:

```
fonts/
    NotoSans-Regular.ttf
    NotoSansSC-Regular.ttf
    ...
    font-faces          ← файл сопоставления шрифтов (впоследствии будет обновлен до JSON)
```

Поместите извлеченный каталог в директорию ресурсов вашего проекта, например `/fonts/`.

**Шаг 2: Удаление кода, связанного с `global.pkg`.**

1. Удалите всю строку `EnvPath::setEntry(EnvPath::GlobalPackage, "/global.pkg")`.
2. Удалите вспомогательные функции вроде `globalUri()`.
3. Замените все ссылки на ресурсы `pkg:///xxx` на прямые пути к файлам, то есть `/xxx`.

**Шаг 3: Изменение кода загрузки шрифтов.**

Предположим, ваш исходный код инициализации выглядел примерно так:

```cpp
static String globalUri(const String &path) { return "pkg:///" + path; }

static void setupFont(const String &fontMap) {
    String uri = globalUri(fontMap);
    FontFaceMap &map = App()->fontManager()->faces();
    if (!map.readFile(uri))
        LogError() << "Failed to load font face map: " << fontMap;
}

int main() {
    Application app;
    EnvPath::setEntry(EnvPath::GlobalPackage, "/global.pkg");
    setupFont("font-faces");
    // ...
}
```

Измените его на прямое использование пути к файлу (без функции `globalUri()` и регистрации `GlobalPackage`):

```cpp
static void setupFont(const String &fontMap) {
    auto &map = App()->fontManager()->faces();
    if (!map.readFile(fontMap))
        LogError() << "Failed to load font face map: " << fontMap;
}

int main() {
    Application app;
    setupFont("/fonts/font-faces");
    // ...
}
```

Теперь структура ресурсов выглядит так:

```
/fonts/
    font-faces          ← бинарный формат
    NotoSans-Regular.ttf
    ...
```

На этом этапе вы все еще используете бинарный файл `font-faces`. В следующем разделе он будет обновлен до JSON.

## Переход на JSON-файлы сопоставления шрифтов

### Признаки старого кода

```cpp
FontFaceMap &map = App()->fontManager()->faces();
map.readFile("/fonts/font-faces");
```

Метод `readFile` считывает пользовательский бинарный формат файла. Этот бинарный файл нельзя отредактировать вручную — его необходимо конвертировать и генерировать из CSS-файла с помощью утилиты упаковки.

### Описание формата JSON

Теперь мы используем JSON-файлы для прямого описания отношений сопоставления шрифтов. Вам нужно лишь создать файл `font-faces.json` со следующей структурой:

```json
{
  "font-faces": [
    {
      "family": "sans-serif",
      "weight": 400,
      "style": "normal",
      "urls": [
        "NotoSans-Regular.ttf",
        "NotoSansSC-Regular.ttf",
        "NotoSansJP-Regular.ttf"
      ]
    },
    {
      "family": "sans-serif",
      "weight": 700,
      "style": "normal",
      "urls": [
        "NotoSans-Bold.ttf"
      ]
    },
    {
      "family": "serif",
      "weight": 400,
      "style": "normal",
      "urls": [
        "NotoSerif-Regular.ttf"
      ]
    }
  ]
}
```

Описание полей:

| Поле | Тип | Обязательное | По умолчанию | Описание |
|------|------|------|--------|------|
| `family` | Строка | Да | - | Имя семейств шрифтов, например `sans-serif`, `serif` |
| `weight` | Целое число | Нет | 400 | Значение жирности CSS (100–900), 400 — обычное, 700 — жирное |
| `style` | Строка | Нет | normal | Стиль шрифта, доступные значения `italic` или `oblique` |
| `urls` | Массив строк | Да | - | Пути к файлам шрифтов относительно директории, в которой находится JSON-файл |

Ниже приведено более подробное описание ключевых полей.

**Поле weight**

В поле `weight` указывается числовое значение жирности по CSS, которое округляется до ближайшего стандартного значения:

- `100` Thin (Тонкий)
- `400` Regular (Обычный — значение по умолчанию, можно не указывать)
- `700` Bold (Жирный)
- `900` Black (Черный)

**Разбор путей urls**

Пути в массиве `urls` разрешаются относительно директории, в которой находится JSON-файл. Например, если JSON-файл расположен по адресу `/fonts/font-faces.json`, то указание в `urls` значения `"fonts/NotoSans-Regular.ttf"` в итоге разрешится в `/fonts/fonts/NotoSans-Regular.ttf`.

Поэтому рекомендуется размещать JSON-файл непосредственно в той же директории, что и файлы шрифтов, чтобы в URL можно было указывать просто имя файла. Например, структура каталогов:

```
/fonts/
    font-faces.json
    NotoSans-Regular.ttf
    NotoSansSC-Regular.ttf
    NotoSans-Bold.ttf
```

В этом случае содержимое JSON выглядит так, как показано в примере выше.

### Изменение кода

Замените вызов `readFile` в коде инициализации на `readJSON`:

```cpp
#include "gx_fontmanager.h"

static void setupFont() {
    auto &map = App()->fontManager()->faces();
    if (!map.readJSON("/fonts/font-faces.json"))
        LogError() << "Failed to load font-faces.json";
    App()->setFont(Font("sans-serif", 24));
}

int main() {
    Application app;
    setupFont();
    // ...
}
```

Это единственное изменение вызова API, остальной код менять не требуется. После этого вы сможете напрямую редактировать `font-faces.json` для добавления/удаления шрифтов или настройки сопоставлений, не прибегая к каким-либо инструментам конвертации.

## Часто задаваемые вопросы (FAQ)

**Как поступить, если у одного семейства есть несколько вариантов: Regular, Bold, Italic и т. д.?**

Добавьте отдельную запись для каждого варианта в массив `font-faces`, различая их с помощью `weight` и `style`:

```json
{
  "font-faces": [
    {
      "family": "sans-serif",
      "weight": 400,
      "style": "normal",
      "urls": ["NotoSans-Regular.ttf"]
    },
    {
      "family": "sans-serif",
      "weight": 700,
      "style": "normal",
      "urls": ["NotoSans-Bold.ttf"]
    },
    {
      "family": "sans-serif",
      "weight": 400,
      "style": "italic",
      "urls": ["NotoSans-Italic.ttf"]
    }
  ]
}
```

В проектах для микроконтроллеров (MCU) обычно используется только нормальное начертание Regular для `sans-serif`, а система выполняет автоматический фоллбэк (fallback).

**Можно ли указать несколько файлов в массиве `urls`? Когда это нужно?**

Да, можно. Когда семейству шрифтов требуется поддержка нескольких языковых наборов символов, поместите несколько файлов шрифтов в один массив `urls`. Например, если `sans-serif` должен одновременно поддерживать латиницу, китайские/японские/корейские иероглифы и арабский язык:

```json
{
  "family": "sans-serif",
  "weight": 400,
  "style": "normal",
  "urls": [
    "NotoSans-Regular.ttf",
    "NotoSansSC-Regular.ttf",
    "NotoSansJP-Regular.ttf",
    "NotoSansArabic.ttf"
  ]
}
```

При рендеринге текста движок будет последовательно искать глифы символов в этих файлах, и будет использован первый найденный глиф.

**Обязательно ли файлы шрифтов должны находиться в той же директории, что и JSON?**

Нет. Пути в `urls` разрешаются относительно директории JSON-файла, поэтому вы можете использовать относительные пути, чтобы поместить шрифты в поддиректорию. Также можно использовать абсолютные пути, на которые расположение JSON-файла не влияет.

**Можно ли передать JSON-строку непосредственно в коде?**

Да. Используйте перегрузку с двумя параметрами:

```cpp
map.readJSON("/fonts/", R"({
  "font-faces": [
    {"family": "sans-serif", "urls": ["NotoSans-Regular.ttf"]}
  ]
})");
```

Первый параметр — это baseUri, который используется для разрешения относительных путей в `urls`.
