# Менеджер пакетов Node.js

Помимо автономного использования, утилита сборки `gx` может применяться совместно с менеджерами пакетов JavaScript, такими как npm, pnpm или yarn. Предварительным условием является установка пакета `glyphix`:

::: code-tabs
@tab npm
```bash
npm install -D glyphix
```

@tab pnpm
```bash
pnpm i -D glyphix
```

@tab yarn
```bash
yarn add -D glyphix
```
:::

В противном случае при выполнении команды `gx build` может возникнуть следующая ошибка:
```bash
$ gx build
fatal: glyphix not found, please install it by `npm install -D glyphix' or other package manager.
```

Использование менеджера пакетов JavaScript при разработке приложений Glyphix дает следующие основные преимущества:
- Использование TypeScript вместо JavaScript в качестве языка разработки, что обеспечивает типобезопасность и лучший опыт разработки
- Использование библиотек JavaScript из экосистемы Node.js, подходящих для встраиваемой разработки (например, библиотек алгоритмов, инструментов обработки данных и т. д.)
- Использование ESLint, Prettier и других инструментов для повышения качества кода и эффективности разработки
- Удобство командной работы и сопровождения проекта

::: warning
В настоящее время поддерживается управление только обычными зависимостями JavaScript или TypeScript, повторное использование компонентов Glyphix невозможно. При выборе сторонних библиотек убедитесь, что они подходят для встраиваемых сред, и избегайте использования библиотек, зависящих от DOM, специфичных API Node.js или чрезмерно громоздких решений.
:::

::: tip
Если инструменты разработчика [Glyphix.js](glyphix.js/README.md) установлены глобально, вы можете напрямую использовать такие команды, как `gx build`, в противном случае необходимо добавить скрипты (`scripts`) в файл `package.json`.
:::

## Конфигурация проекта

### Настройка `package.json`

При использовании менеджера пакетов Node.js рекомендуется добавить необходимые скрипты и конфигурацию в `package.json`:

```json
{
  "name": "my-glyphix-app",
  "version": "1.0.0",
  "scripts": {
    "build": "gx build",
    "emu": "gx emu",
    "clean": "gx clean"
  },
  "devDependencies": {
    "glyphix": "^1.0.41",
    "typescript": "^5.8.3"
  }
}
```

### Настройка `tsconfig.json`

Если вы используете TypeScript, вам нужно создать файл `tsconfig.json` в корневой директории проекта:

```json
{
  "compilerOptions": {
    "target": "ES2021",
    "module": "commonjs",
    "baseUrl": "./",
    "paths": {
      "/*": ["src/*"],
      "/assets": ["src/assets/*"]
    },
    "types": ["glyphix", "node"],
    "allowImportingTsExtensions": true,
    "checkJs": true,
    "declaration": true,
    "declarationMap": true,
    "emitDeclarationOnly": true,
    "esModuleInterop": true,
    "forceConsistentCasingInFileNames": true,
    "strict": true,
    "noImplicitAny": true,
    "noUnusedLocals": true,
    "noUnusedParameters": true,
    "skipLibCheck": true,
    "resolveJsonModule": true
  },
  "include": ["src/**/*.ts", "src/**/*.ux"]
}
```

::: info
Утилита сборки Glyphix автоматически обрабатывает компиляцию файлов TypeScript, а описанная выше конфигурация в основном используется для проверки типов в IDE и подсказок по коду.
:::

## Конфигурация `glyphix.config.js`

Рекомендуется создать файл `glyphix.config.js` в корневой директории проекта (там же, где находится `src/` или `package.json`), чтобы настроить параметры сборки:
```js
module.exports = {
  minify: false, // Отключение сжатия кода для удобства отладки и получения номеров строк исходного кода
};
```
Если вы используете TypeScript, вы можете создать файл `glyphix.config.ts` вместо этого.

::: tip
Обязательно создайте этот файл и настройте `minify: false`, иначе упакованный код будет сжат и обфусцирован, что сделает невозможным сопоставление номеров строк с исходным кодом при отладке.
:::

## Использование TypeScript

Фреймворк Glyphix обеспечивает экспериментальную поддержку TypeScript, позволяя вам наслаждаться преимуществами типобезопасности и современного синтаксиса JavaScript при разработке приложений.

### Пример базового компонента

Ниже приведен пример компонента, написанного на TypeScript:

```html
<template>
  <p on:click="onClick">{{count}}</p>
</template>

<script lang="ts">
import { defineComponent } from "glyphix"

export default defineComponent({
  data: {
    count: 0
  },
  onClick() {
    this.count++
  }
})
</script>
```

По сравнению со скриптами компонентов JavaScript по умолчанию, использование TypeScript требует следующих изменений:
1. В теге `<script>` используется `lang="ts"`, чтобы указать тип языка как TypeScript.
2. Функция `defineComponent` импортируется из модуля `glyphix`.
3. Экспортируемый объект компонента должен передаваться в качестве аргумента функции `defineComponent`, и экспортироваться должно возвращаемое значение этой функции.

После использования TypeScript функция `defineComponent` делает подсказки кода и проверку типов в IDE более точными.

### `app.ts`

Переименуйте `app.js` в `app.ts`, чтобы начать использовать TypeScript для файла точки входа приложения, а утилита сборки обработает его автоматически.

# Спецификация именования компонентов

В этом документе описаны обязательные правила именования и рекомендуемые стили для структуры компонентов. Обязательные правила являются строгими требованиями; их несоблюдение может привести к неожиданным результатам. Соблюдение рекомендуемых правил гарантирует максимальную совместимость.

## Правила именования шаблонов

Имена тегов в шаблонах должны быть в стиле kebab-case (через дефис) или PascalCase (паскальский регистр):
``` html
<Button></Button>
<button></button>
<scroll-area></scroll-area>
<ScrollArea></ScrollArea>
```

Имена свойств должны быть в стиле kebab-case или camelCase (верблюжий регистр):
``` html
<component prop-name="expr"></component>
<component propName="expr"></component>
```

Рекомендуется повсеместно использовать стиль kebab-case, соответствующий спецификации Web.

## Правила именования в коде JavaScript


Имена компонентов в коде JavaScript должны быть в стиле PascalCase, в то время как в шаблоне используется соответствующий им стиль kebab-case.

Имена свойств компонентов в коде JavaScript должны быть в стиле camelCase:
``` js
export default {
  data: {
    propName: 0 // Имя свойства в шаблоне будет prop-name
  }
}
```
Эти имена свойств автоматически преобразуются в соответствующие имена kebab-case при использовании в коде шаблона.

## Правила именования файлов

Файлы UX должны иметь то же имя, что и компонент, то есть в стиле PascalCase. В теге `<import>` атрибут `src` должен быть чувствительным к регистру URL-адресом файла, а для атрибута `name` следует использовать стиль PascalCase или kebab-case:
``` html
<import src="path/to/UxFile" name="UxFile"/>
<import src="path/to/UxFile" name="ux-file"/>
```
Фактически требования к именованию атрибута `name` совпадают с требованиями к именам тегов в шаблонах.

# Часто задаваемые вопросы

## Инструменты сборки

### Проблемы сборки проекта

#### Ошибка `Lisp Error: thread killed`

Конкретным проявлением является появление сообщения об ошибке, похожего на следующее:

``` log
[ 47%] Process image src/assets/images/frame1.png
error: Lisp Error: thread killed
```

Эта проблема возникает из-за того, что предыдущая ошибка сборки привела к отмене выполняющейся операции конвертации изображений. Для ее решения достаточно исправить операцию сборки, вызвавшую `fatal`-ошибку, и всё вернется в норму. Никаких дополнительных действий не требуется.

### Симулятор

#### Язык симулятора по умолчанию

Языком симулятора по умолчанию является `zh-CN`. Поэтому, если вы добавили конфигурацию [интернационализации](/framework/component/i18n.md), по умолчанию будет использоваться файл перевода `zh-CN.json`. Запустив симулятор с помощью команды `gx`, вы можете указать язык с помощью опции `-l` или `--language`:
``` shell
gx emu -l en-US # Использовать американский английский
```
Вы также можете динамически менять язык во время работы симулятора с помощью инструмента отладки inspector.

# 开发速览：从 Web 到 Glyphix

本文档专为熟悉 Web 前端（特别是 Vue.js）的开发者设计。我们将跳过基础语法教学，直接切入 Glyphix 框架的核心机制，帮助你快速建立正确的心智模型。

## 核心概念与运行环境

Glyphix 是一个运行在 MCU（微控制器）设备上的应用框架。虽然它使用 HTML/CSS/JS 进行开发，但它**不是**一个浏览器。本框架用于开发完整应用，而不是可刷新的页面，每个应用运行在独立的沙箱容器中。

你需要理解以下几个核心差异：
- **无 DOM**：底层由 C++ 原生引擎直接渲染，不存在 DOM 树。
- **无 Web API**：不支持 `window`、`document`、`localStorage` 等浏览器 API。系统能力（网络、存储、传感器）通过 `@system.*` 模块提供。
- **JS 引擎**：使用轻量级 JS 引擎（支持 ES6 标准），但内存极其受限。

### 资源限制

资源限制是与 Web 开发最大的不同点。MCU 设备的 RAM 通常仅有几 MB。这意味着不要使用网络请求加载超大 JSON 数据，或者直接 [`fetch`](../api/system-fetch.md) 一张图片。请牢记以下几点：
- 可以使用 [`@system.request`](../api/system-request.md) 模块将资源下载为文件，`fetch` 则会将响应加载到内存中。
- 图片资源通常存放在应用包内，尺寸尽可能与屏幕分辨率匹配。
- **后台冻结**：应用进入后台（`onHide`）后，通常会在几十秒内被系统挂起或销毁。请注意保存状态。

### 设备形态

Glyphix 应用通常运行在智能手表等小屏设备上。手表的屏幕尺寸通常为 1.5 到 2 英寸左右，典型分辨率为 466×466 像素，但存在圆形、矩形屏幕。低端设备的像素密度可能更低，但尺寸基本相似。这类设备常用触摸屏进行交互，可能支持物理按键或者旋钮，系统透明地处理了大部分交互细节。

通常使用模拟器进行开发和调试，因为真机部署和调试流程还比较碎片化，耗时较长。

### 典型项目结构

这是我们推荐的项目文件结构，这也是快应用标准的结构：
```bash
src/
├─ manifest.json  # 应用清单：配置权限、注册页面路由
├─ app.js         # 应用入口：全局生命周期 (onCreate, onDestroy)
├─ pages/         # 页面目录
│  └─ Main/
│     └─ index.ux # 页面组件
└─ assets/        # 公共资源
  └─ icon.png
```
你可以根据需要引入 [Node.js](nodejs.md) 工具链来管理依赖。也可以按照需要调整目录结构，但 [`src/manifest.json`](/framework/application/manifest.md) 和 `src/app.js` 必须固定在此位置。

## UI 开发

Glyphix 采用 [`.ux`](../framework/component/README.md) 单文件组件（类似 Vue SFC），风格接近 Vue Options API，但也有显著差异。

### Flexbox 布局优先

Web 默认是流式布局（Flow Layout），而 Glyphix 的页面默认为堆叠布局：如果你在页面中放两个 `div`，它们会**重叠**在一起，而不是上下排列。这是因为本框架支持在 `<template>` 中使用多个根节点，例如：
```html
<template>
  <image class="background" src="/assets/bg.png" />
  <div class="content"> ... </div>
</template>
```
默认的堆叠布局对于这种场景通常非常合适。

尽管 `div` 等容器默认使用流式布局，但推荐使用 Flexbox 来进行布局控制。绝大多数容器都应该显式声明 `display: flex`，再结合 `flex-direction` 控制子元素排列方式。

考虑到设备屏幕尺寸差异较大，请特别注意长度单位的使用：
- 在较小的尺寸中使用 `px` 单位，它是逻辑像素，会根据屏幕密度自动缩放。
- 字体应总是使用 `rem` 单位，它由设备厂商定义基准，更符合系统 UX 规范的一致性要求。
- 可以使用百分比（`%`）单位来实现响应式布局，但是目前限制和缺陷较多，请注意调试。

由于屏幕太小，你可能特别需要 [`scroll`](../components/scroll.md) 组件来实现滚动区域。和 Web 不同，`div` 容器本身不支持滚动，也无法使用 `overflow` 属性来控制。

### 模板语法差异

虽然长得像 Vue 模板，但请注意以下区别：
- 指令无 `v-` 前缀：如 `<div if="show">` 或 `<div for="item in items">`
- 事件绑定用 `on`、`@` 均可，如：`<p on:click="handler">`
- 必须使用 `<p>` 等文本组件：`<text>Hello</text>` 可以正常显示，但是 `<div>Hello</div>` 不会渲染任何内容。
- 支持用 `model:prop="state"` 或 `::prop="state"` [双向绑定](../framework/commands/model.md)任意组件属性，只要有和属性同名的事件触发即可。

### 样式限制

CSS 支持是子集：
- 支持类 (`.class`)、ID (`#id`)、标签 (`div`) 和后代 (`.a .b`)。**不支持** `~`、`+`、`>` 等复杂关系选择器。
- **效果限制**：不支持渐变、阴影等效果。暂不支持 `transition` 动画。
- **性能限制**：避免使用 `transform` 来移动或对齐元素。`object-fit` 默认为 `none` 并推荐保持默认。
- 目前不支持动态 `class` 绑定，也不支持 CSS 变量。

## 组件与逻辑

### 脚本模型

组件脚本非常接近 Vue Options API，以下示范指出了主要差异：
```js
export default {
  // 数据模型 (Data)，不需要声明属性，data 属性自动导出为属性
  data: {
    count: 0, // 修改 this.count 会自动触发视图更新
  },
  timer: null, // 非响应式字段直接定义在组件实例上，也可以不声明
  // 生命周期
  onInit() {}, // 数据已初始化，可发起网络请求
  onReady() {}, // 界面已渲染完成
  onDestroy() {}, // 务必在此清理定时器、订阅事件

  // 方法 (Methods)，直接定义在组件对象中
  handleTap() {
    this.count++
    // 触发自定义事件给父组件
    this.$emit('change', { value: this.count })
  }
}
```
其中 `data` 对象中的字段为响应式属性，它目前只支持 JSON 兼容的类型（不支持 `Date`、`Map`、`Set` 等）。如果不需要响应式更新，推荐将字段定义在组件实例（`this`）上。

::: tip
不要使用 `methods` 对象包裹方法，直接定义在组件对象中即可。也不需要使用 `props` 定义属性，`data` 对象中的字段会自动导出为属性。

也不能用 `document.getElementById` 等 DOM API 查找元素。可以使用 [`this.$element()`](../framework/component/component-apis.md#element) 方法获取指定 ID 的元素实例。
:::

### 页面与路由

Glyphix 应用由多个页面组成，页面间通过路由导航。所有页面均需在 `manifest.json` 中的 [`router.pages`](../framework/application/manifest.md#pages) 字段中静态注册。页面组件与普通组件类似，但支持 `onShow` 和 `onHide` 生命周期钩子。

使用 `system.router` 系统模块进行跳转：
```js
import router from '@system.router'

// 跳转并传递参数
router.push({ uri: 'pages/Detail', params: { id: 123 } })
```
::: tip
不要使用其他的路由库，也不要假装在开发单页面应用（SPA）。否则将无法利用转场动效、页面栈管理等现有功能。
:::

### TypeScript 支持

如果使用 Node.js 脚手架创建项目，使用 npm、pnpm 等安装 `glyphix` 和 `typescript` 等依赖后，可以在项目中使用 TypeScript 进行开发。

对于 `.ux` 单文件组件，可以在 `<script>` 标签上添加 `lang="ts"` 属性启用 TypeScript 支持。例如：
```html
<script lang="ts">
import { defineComponent } from 'glyphix'

export default defineComponent({
  data() {
    count: 0: number
  },
  increment() { this.count++ },
})
</script>
```

## 系统能力集成

不要尝试使用浏览器 API，请使用 Glyphix [标准库](../api/README.md)。

### 常用模块速查

| 功能 | Glyphix 模块 | 说明 |
| :--- | :--- | :--- |
| **网络** | [`@system.fetch`](../api/system-fetch.md) | 必须处理异步回调或 Promise |
| **弹窗** | [`@system.prompt`](../api/system-prompt.md) | 提供 Toast 和 Dialog |
| **存储** | [`@system.storage`](../api/system-storage.md) | 同步本地存储，直接读写对象而非字符串 |
| **路由** | [`@system.router`](../api/system-router.md) | 管理页面栈 |
| **日志** | `console.log` | 输出到调试终端，和浏览器一样 |

### 异步编程模式

系统 API 通常支持异步回调和 Promise 两种风格。推荐使用 `async/await` 以保持代码整洁。

```js
import fetch from '@system.fetch'
import prompt from '@system.prompt'

export default {
  onReady() { this.loadData() },
  async loadData() {
    try {
      const response = await fetch.fetch({
        url: 'https://api.example.com/data',
        method: 'GET', // 默认为 GET
        responseType: 'json', // 这样不需要 JSON.parse 手动解析
      })

      if (response.data.code === 200)
        this.data = response.data.data
    } catch (err) {
      prompt.showToast({ message: 'Network Error' })
    }
  }
}
```

## Что такое Glyphix

Glyphix — это эффективный и легковесный фреймворк для разработки приложений, предназначенный для устройств на базе MCU (микроконтроллеров). Он предоставляет разработчикам декларативную парадигму разработки пользовательского интерфейса, аналогичную веб-экосистеме: с помощью HTML-шаблонов, CSS и JavaScript разработчики могут с легкостью создавать страницы и компоненты, а также публиковать приложения на различных интеллектуальных устройствах (например, умных часах).  

Для получения дополнительной информации обратитесь к разделу [Фреймворк](/framework/README.md).

### Веб-подобный фреймворк

В отличие от традиционной разработки прошивок для MCU, Glyphix ближе к фреймворкам на базе веб-стека технологий. Разработчикам приложений необходимо быть знакомыми с JavaScript, CSS и основами HTML. Вам не нужно досконально знать полный стек веб-разработки, такой как DOM браузера, стандартные теги HTML и сложные цепочки инструментов сборки. Однако, если вы знакомы с веб-фреймворками пользовательского интерфейса, такими как [Vue.js](https://vuejs.org/) ([Options API](https://vuejs.org/guide/introduction#options-api)), вам будет очень легко освоить Glyphix.

::: tip
Стоит отметить, что Glyphix не является платформой «low-code». В процессе разработки вы всё равно столкнетесь с такими задачами, как абстрагирование логики, организация интерфейса, пользовательский опыт и компромиссы в производительности. Поэтому прочные базовые знания JavaScript и правильное мышление фронтенд-разработчика помогут вам полностью раскрыть потенциал Glyphix.
:::

### Декларативный UI-фреймворк

Традиционная разработка интерфейсов обычно носит императивный характер: требуется пошагово вызывать функции для создания элементов управления, обновления состояния и перерисовки интерфейса. Такой подход очень гибкий, но бизнес-логика и логика интерфейса в нем сильно связаны, и по мере роста масштаба приложения код быстро становится сложным и трудным в обслуживании. Появление таких паттернов, как MVC и MVVM, было направлено именно на решение этой проблемы сложности.  

Glyphix же использует парадигму декларативного пользовательского интерфейса. Разработчику достаточно описать, «как должен выглядеть интерфейс», а фреймворк автоматически выполнит рендеринг и обновление на основе изменений данных и состояния. Такой подход значительно снижает сложность логики интерфейса и управления состоянием, а также позволяет разработчикам сосредоточиться на функционале и интерактивном дизайне, а не на поддержании иерархии UI и процессах обновления.

### Контейнер приложений

Glyphix — это не просто UI-фреймворк, он также предоставляет такие возможности, как управление жизненным циклом приложений, изоляция прав и системные API. Приложения запускаются в независимом контейнере и изолированы друг от друга, что обеспечивает стабильность и безопасность системы.

Пожалуйста, прочитайте руководство [Быстрый старт](getting-started.md), чтобы сразу приступить к разработке приложений на Glyphix.

## Другие вопросы

### Нужно ли разбираться в MCU и встраиваемой разработке?

Разработчикам приложений обычно не требуется глубокое понимание специфических знаний об MCU и встраиваемой разработке. Тем не менее, следует иметь представление об ограничении ресурсов устройств. Например, объем памяти MCU обычно составляет всего несколько мегабайт, и память для выполнения кода JavaScript также ограничена. Это означает, что могут возникнуть ситуации, когда невозможно запросить из сети очень большой JSON-документ или закодировать целое изображение в Base64 и получить его через GET-запрос.

Эти ограничения, кардинально отличающиеся от веб-разработки, действительно обусловлены ограниченными ресурсами устройств MCU, однако они не входят в типичный набор знаний по работе с микроконтроллерами.

Интуитивно понятный способ убедиться в том, что приложение работает достаточно хорошо — запустить его непосредственно на устройстве. Вы можете использовать реальное устройство на разных этапах разработки, чтобы гарантировать качество работы.

### Нужно ли использовать C/C++ для разработки приложений?

Разработка приложений на Glyphix полностью осуществляется с использованием HTML, CSS и JavaScript, поэтому языки C/C++ не требуются.

### Как разработчикам встраиваемых систем приступить к разработке на Glyphix?

Разработчики встраиваемых систем могут начать с учебника [Быстрый старт](getting-started.md), чтобы постепенно разобраться с основными концепциями Glyphix. Фреймворк использует механизм компонентности и привязки данных, похожий на Vue Options API, что может несколько отличаться для читателей, привыкших к императивным GUI вроде [LVGL](https://lvgl.io/) или виджетов Qt, однако декларативный дизайн Glyphix также обеспечивает более интуитивное управление интерфейсом.

Разработчикам не обязательно полностью осваивать HTML, CSS и JavaScript, однако знакомство с базовым синтаксисом JavaScript (таким как переменные, условные операторы, вызовы функций) поможет понять логику рендеринга и обработку событий в Glyphix. Вы можете ознакомиться с этими аспектами с помощью примеров кода и практических заданий в учебниках и документации, чтобы ускорить процесс освоения разработки.

### Стоит ли уделять внимание оптимизации производительности приложений?

Наш фреймворк уже прошел глубокую оптимизацию с учетом ограничений ресурсов встраиваемых систем и отлично адаптирован к различным аппаратным средам. Большинство приложений при настройках по умолчанию работают достаточно плавно и стабильно, поэтому обычно не требуется тратить дополнительное время на оптимизацию производительности.

Если в будущем возникнет необходимость углубиться в специфические сценарии оптимизации, мы предоставим специализированную документацию по производительности, которая поможет разработчикам еще больше повысить эффективность работы приложений.

### Есть ли разница между средой Glyphix и браузером?

Да, среда Glyphix имеет существенные отличия от браузера. В Glyphix отсутствует структура DOM, а также нет таких объектов, как `window` или `document`. Вместо этого она напрямую и исключительно предоставляет набор декларативных интерфейсов, с помощью которых разработчики могут создавать компоненты и осуществлять взаимодействие с интерфейсом. Такой дизайн упрощает процесс разработки и лучше подходит для встраиваемых сред.

# Основы компонентов

В предыдущем документе «[Быстрый старт](getting-started)» было кратко представлено понятие компонентов. Данное руководство познакомит вас с компонентами более подробно. Прежде чем приступить к чтению этого документа, вам необходимо знать, как создавать и собирать проекты, а также как редактировать исходные файлы. Если вы этого не знаете, пожалуйста, прочитайте руководство «[Быстрый старт](getting-started)».

## Введение

В разработке приложений Glyphix все интерфейсы представляют собой компоненты — от маленьких кнопок до целых страниц. Компонентный подход позволяет разрабатывать интерфейсы с использованием простого языка шаблонов:
``` html
<!-- main/index.ux -->
<template>
  <p>{{text}}</p>
</template>

<style>
  * {
    text-align: center;
  }
</style>

<script>
  export default {
    data: {
      text: "Hello, World!"
    }
  }
</script>
```
По сути, это файл `main/index.ux` из шаблона проекта по умолчанию. Вы можете посмотреть результат отображения, выполнив команду `gx emu`. Содержимое тега `<template>` является шаблоном компонента, который описывает его внешний вид. В данном случае узел `<p>` будет отображать свойство `text` объекта модели компонента. Обратите внимание, что внутренний фреймворк компонентов связывает содержимое узла `<p>` со свойством `text` модели компонента: как только значение свойства `text` изменяется, интерфейс синхронно обновляется.

Мы можем протестировать это с помощью таймера:
``` js
export default {
  data: { text: "begin!" },
  onInit() {
    let count = 0
    setInterval(() => this.text = "timeout: " + count++, 1000)
  }
}
```
Теперь вы увидите, что отображаемое значение счетчика увеличивается на 1 каждую секунду.

## Программная модель компонентов

 Одной из важных функций GUI-программ является изменение своего внешнего вида на основе данных и пользовательского ввода для реализации интерактивности. В традиционном программировании GUI и нативном HTML разработчикам необходимо найти целевой элемент узла в дереве интерфейса, а затем вызвать API для его обновления. Как показывает практика, разработка интерфейсов таким способом очень сложна, поэтому появились шаблоны проектирования, подходящие для GUI, такие как MVC, MVP, MVVM, а в сфере веб-разработки появились новые фреймворки. Все эти технологии значительно снизили сложность разработки интерфейсов.

Программная модель компонентов Glyphix очень похожа на фронтенд-фреймворки вроде Vue. Основная идея этих фреймворков заключается в вычислении нового интерфейса на основе состояния модели интерфейса, а не в принудительном обновлении элементов интерфейса при изменении состояния. По сравнению с традиционными технологиями, часть представления интерфейса в таком решении не имеет собственного состояния (stateless), что делает его гораздо проще. Давайте продолжим использовать предыдущий пример для иллюстрации:
``` html
<template>
  <p>{{ text }}</p>
</template>
```
Как мы уже знаем, интерфейс автоматически обновляется при изменении свойства `text` модели компонента. Однако в традиционных GUI-фреймворках часто требуется вручную обновлять узел `<p>` после обновления свойства `text` в модели (что обычно происходит из-за ввода данных или изменения внутренних данных). Такие фреймворки, как MVC, могут упростить эти операции, но не делают их предельно простыми.

Теперь рассмотрим очень простой подход: мы пишем функцию `render()`, которая генерирует дерево интерфейса на основе текущего состояния модели. Если бы мы заменяли исходное дерево интерфейса результатом функции `render()` на каждом кадре, то любые изменения модели отражались бы в интерфейсе. Это решение очень простое, но вы бы отвергли его из-за низкой эффективности. На самом деле традиционная модель программирования GUI зародилась именно для решения проблемы эффективности этого подхода: изменять только те элементы в интерфейсе, которые действительно изменились. Однако это привносит состояние на уровень представления, что также влечет за собой немалую сложность.

Фреймворк компонентов Glyphix основан на этой простой идее: содержимое внутри тега `<template>` выполняет роль функции `render()`, в то время как JS-код сосредоточен на поддержке модели, а изменения данных модели автоматически отражаются в связанном интерфейсе. Вы можете считать, что фреймворк компонентов Glyphix всегда вычисляет новый интерфейс на основе состояния модели, поэтому нам не нужно вручную обновлять элементы интерфейса.

::: tip
Под капотом Glyphix нет дерева DOM, и, соответственно, нет API для манипуляции элементами DOM. Фактически, именно фреймворк компонентов и является нативным JavaScript API для Glyphix.
:::

## Реакция на ввод

Некоторые компоненты могут реагировать на события ввода пользователя. В этом случае вы можете использовать директиву `on` для указания обработчика событий. Например, прослушивание события клика по текстовому компоненту:
``` html
<template>
  <p on:click="text += ' click'">{{text}}</p>
</template>

<style>
  * {
    text-align: center;
  }
</style>

<script>
  export default {
    data: {
      text: "Text "
    }
  }
</script>
```
Клик по тексту автоматически обновит отображаемое содержимое. Значение атрибута `on:click` — `text += ' click'` — является JavaScript-выражением, и Glyphix автоматически свяжет `this` переменных в выражении с объектом компонента.

## Условный рендеринг

Директива `if` используется для условного рендеринга содержимого компонента. Область содержимого, управляемая этой директивой, будет отображаться только тогда, когда значение выражения в директиве `if` истинно (true).
``` html
<p if="display">Hello World</p>
```

Следующий пример реализует эффект взаимоисключающего переключателя: при последовательных кликах интерфейс будет попеременно отображать текст "Component A" или "Component B".
``` html
<template>
  <p if="display" on:click="display = false">Component A</p>
  <p if="!display" on:click="display = true">Component B</p>
</template>

<style>
  * {
    font-size: 48;
    text-align: center;
  }
</style>

<script>
  export default {
    data: {
      display: true
    }
  }
</script>
```

## Рендеринг списков

Используйте директиву `for` для многократного рендеринга компонента с целью создания списка. Базовое использование директивы `for`:
``` html
<p for="(index, value) in list">{{index}}: {{value}}</p>
```
Здесь `list` — это свойство-список в модели компонента (обязательно должно быть типа `Array`), `index` и `value` — две переменные итерации, где `index` — это индекс текущего элемента, а `value` — значение текущего элемента.

Директива `for` может быть записана в нескольких сокращенных формах:
``` html
<p for="list">{{$idx}}: {{$item}}</p>
<p for="value in list">{{$idx}}: {{value}}</p>
<p for="index, value in list">{{$idx}}: {{value}}</p>
```
Первый сокращенный вариант заключается в указании только выражения для итерации, при этом в качестве имен переменных итерации по умолчанию используются `$idx` и `$item`. Второй вариант явно определяет переменную итерации для значения, в то время как имя переменной индекса использует значение по умолчанию `$idx`. Третий вариант — это стандартная запись с опущенными круглыми скобками.

::: tip
Из-за особенностей области видимости (scope), переменные, используемые для итерации при написании директивы `for`, будут работать только при использовании после директивы `for`.
:::

``` html
<!-- correct -->
<button for="list" text="{{$item}}"/>
<!-- error -->
<button text="{{$item}}" for="list"/>
```

### Одновременное использование директив `if` и `for`

Вы можете одновременно использовать директивы `if` и `for` на одном и том же элементе, причем директива `if` имеет более высокий приоритет. В этом примере, когда свойство `display` ложно, весь список компонентов `button` не будет отрендерен:
```html
<button for="value in items" if="display">Hello {{value}}</button>
<p if="!display">Paragraph 1</p>
```

Если же ваша цель — условно отрендерить только некоторые узлы в списке, созданном директивой `for`, вам нужно поместить директиву `if` на внутренний элемент по отношению к директиве `for`.
```html
<button for="value in items">
  <p if="display">item: {{value}}</p>
</button>
```

::: tip
Не рекомендуется использовать директивы `if` и `for` на одном и том же элементе, так как это снижает читаемость кода.
:::

## Слоты

Подобно распространению контента в других фреймворках, в Glyphix также реализован API распространения контента. Мы можем использовать компонент `slot` в качестве точки выхода для распределяемого контента.

В дочернем компоненте используйте компонент `slot` для размещения контента, определенного в родительском компоненте. При рендеринге компонент `slot` заменяется элементами, переданными из родительского компонента.

```html
<div>
  <slot/>
</div>
```

## Комбинирование компонентов

Комбинирование нескольких компонентов в более крупные интерфейсы — это способ построения интерфейсов в фреймворке компонентов Glyphix. Если у вас есть компонент с именем `Menu`, вы можете импортировать его, используя тег `<import>` в корневом узле UX-файла, где он требуется:
``` html
<import src="path/to/Menu" name="Menu"/>
```
Атрибут `src` — это путь к компоненту, пожалуйста, не добавляйте суффикс `.ux`. Атрибут `name` является необязательным именем компонента; если этот атрибут не заполнен, в качестве имени компонента будет использоваться имя файла компонента.

Используйте тег `<import>` несколько раз для импорта всех зависимых компонентов:
``` html
<import src="path/to/ComA"/>
<import src="path/to/ComB"/>
<import src="path/to/ComC"/>
```

Вы можете использовать кастомные компоненты так же, как и нативные:
``` html
<div>
  <menu for="menus" on:click="clickMenu($idx, $item)">
    <p>Menu {{$item}}</p>
  </menu>
</div>
```

``` css
div {
  display: flex;
  flex-direction: column;
}

text {
  text-align: center;
}
```

``` js
export default {
  data: {
    menus: ["Dog", "Cat", "Pig", "Fish"],
  },
  clickMenu(id, name) {
    console.log(`clicked id: ${id}, name: ${name}.`)
  }
}
```

Это интерфейс меню, и мы хотим, чтобы при клике пользователя по меню выводилась информация о текущем элементе меню с помощью метода `clickMenu`. Поэтому компонент `Menu` должен уметь отображать содержимое меню и передавать свое событие клика через слушатель `on:click`.

Вот содержимое файла `Menu.ux`:
``` html
<template>
  <div on:click="$emit('click')"> <slot /> </div>
</template>

<style>
  div { display: flex; }
</style>

<script>
  export default {}
</script>
```
Мы просто используем нативный компонент `div`, чтобы реагировать на клики пользователя и передавать событие наверх. Внутри компонента `div` также будет отображаться дочерний компонент, переданный ранее, что в итоге позволит отобразить список меню.

## Структура проекта

Вы можете использовать файловый менеджер для просмотра структуры директории `myapp`. В текущей версии она выглядит следующим образом:
``` bash
<app-name>
├─ README.md         # Файл с описанием проекта (README)
└─ src               # Директория с исходным кодом проекта
    ├─ app.js        # Корневой скрипт приложения
    ├─ manifest.json # Конфигурация основных сведений о приложении
    ├─ assets        # Хранилище общих ресурсов (шрифты, изображения и т.д.)
    │  ├─ fonts      # Шрифты
    │  └─ images     # Изображения
    └─ main          # Директория главной страницы
        └─ index.ux  # Файл описания интерфейса главной страницы
```

В шаблоне проекта по умолчанию исходный код находится в директории `<app-name>/src`. Документация и другие ресурсы проекта, не требующие упаковки, могут размещаться в других директориях.

Мы рекомендуем выделять отдельную директорию для каждой страницы (используя имя страницы в качестве имени директории) и размещать ее в корне директории исходного кода. Исходные файлы компонентов, используемых только на определенной странице (файлы `*.ux`), должны находиться в директории этой страницы, в то время как общие файлы могут размещаться по следующим правилам:
- Общие UX-файлы и скрипты могут размещаться в директории `common`.
- Файлы скриптов, используемые исключительно на странице, хранятся непосредственно в директории страницы.
- Файлы шрифтов хранятся в директории `assets/fonts`.
- Файлы изображений хранятся в директории `assets/images`.
- Остальные ресурсы могут быть размещены в подходящих местах внутри директории `assets`.

### Файлы проекта

Теперь вы видите, что внутри `myapp` есть несколько файлов. Обратите внимание на файлы с расширением `*.ux` и файл `manifest.json` — это файлы, с которыми чаще всего приходится сталкиваться при разработке. В следующем руководстве будет приведено краткое описание каждого из них.

## Файл `manifest.json`

Файл `manifest.json` является конфигурационным файлом приложения и используется при его сборке. Он содержит основные сведения о приложении, такие как имя и версия, а также описание всех страниц и информацию о маршрутизации. Другими словами, описание страницы нужно добавить в `manifest.json`, прежде чем переходить к ней в коде.

Вот содержимое файла `manifest.json` для шаблона приложения, сгенерированного командой `gx`:
``` json
{
  "package": "com.example.app",
  "name": "Example App",
  "versionName": "1.0.0",
  "versionCode": 1,
  "features": [],
  "router": { // Информация о маршрутизации страниц
    "entry": "main", // Начальная страница приложения
    "pages": { // Описание страниц
      "main": {
        "component": "index"
      }
    }
  }
}
```

::: warning
В учебных целях данный фрагмент кода `manifest.json` содержит комментарии, однако формат JSON не поддерживает комментарии. Пожалуйста, не добавляйте комментарии в файл `manifest.json` вашего проекта.
:::

### Заполнение информации о приложении

Вы можете указать информацию о своем приложении в файле `manifest.json`.

### Добавление описания страниц

В корневых полях файла `manifest.json` поля `router` и `pages` связаны с описанием страниц. Поле `router` представляет собой таблицу маршрутизации страниц приложения и должно содержать как минимум поле `entry`, определяющее начальную страницу приложения. Обычно в качестве начальной страницы используется `main`.

Если вам нужно добавить новую страницу, вам потребуется внести изменения в поле `pages`. Например, если мы хотим создать новую страницу с именем `NewPage`, а ее корневым компонентом является `NewPage/index.ux`, то поле `pages` будет выглядеть следующим образом:
``` json
"pages": {
  "main": {
    "component": "index"
  },
  "NewPage": { // Это новодобавленная страница
    "component": "index"
  }
}
```
Поле `pages` представляет собой объект JSON, где каждый ключ является именем страницы, которое по умолчанию также совпадает с путем к директории страницы. Значением для имени страницы является объект, у которого поле `component` указывает на имя корневого компонента страницы. Этот компонент должен находиться внутри директории страницы. Поле `component` содержит имя файла корневого компонента страницы (без расширения). Все имена чувствительны к регистру.

При добавлении или удалении страниц не забывайте обновлять соответствующие поля в файле `manifest.json`.

Подробное описание структуры файла `manifest.json` смотрите в соответствующей документации.

## Знакомство с UX-файлами

UX (UI XML) — это файл описания интерфейса в Glyphix. На примере исходного шаблона проекта, файл `main/index.ux` имеет следующее содержимое:
``` html
<template>
  <p>{{text}}</p>
</template>

<style>
  * {
    text-align: center;
  }
</style>

<script>
  export default {
    data: {
      text: "Hello, World!"
    }
  }
</script>
```

UX-файл фактически представляет собой XML-файл с тремя корневыми узлами: `<template>`, `<style>` и `<script>`. Содержимое узла `<template>` описывает структуру интерфейса, в узле `<style>` определены таблицы стилей, а содержимое узла `<script>` представляет собой JavaScript-скрипт, реализующий логику взаимодействия компонента.

::: tip
VS Code не подсвечивает синтаксис UX-файлов автоматически. Вы можете переключить язык в правом нижнем углу на «HTML», чтобы включить удобную подсветку.
:::

### Введение в компоненты

Объект, соответствующий UX-файлу во время выполнения, называется **компонентом**. Компоненты являются важнейшей концепцией в структуре JavaScript-приложений Glyphix. Каждый компонент представляет собой элемент интерфейса со следующими характеристиками:
- Компонент имеет собственное визуальное представление.
- Некоторые компоненты могут реагировать на ввод пользователя.
- Некоторые компоненты могут отображать результаты в зависимости от данных и состояния.
- Компоненты могут быть встроены в другие компоненты.

Распространенные элементы интерфейса в фреймворке JavaScript-приложений Glyphix являются компонентами, например:
- Текст: используется для отображения текстовой информации.
- Кнопка: кнопка также может отображать текст, но самое главное — она может реагировать на события нажатия (и, конечно же, визуально отображать момент нажатия).
- Список: список вмещает другие компоненты и располагает их вертикально. Кроме того, с помощью жестов прокрутки можно перемещать дочерние элементы списка.

Компоненты, способные вмещать другие компоненты, такие как списки, также называются **компонентами-контейнерами**.

Как можно догадаться, компонент состоит из двух основных элементов: внешнего вида и логики поведения. Тег `<template>` в UX-файле определяет внешний вид компонента. На примере `main/index.ux`:
``` html
<template>
  <p>{{text}}</p>
</template>
```
Компонент `main/index.ux` отображает содержимое с помощью компонента `<p>`, который предназначен для показа текста. Значение выражения `{{text}}` определяет отображаемый текст.

JavaScript-скрипт внутри тега `<script>` реализует логику поведения компонента. Этот тег всегда использует `export default` для экспорта **объекта компонента**. В первую очередь стоит обратить внимание на свойство `data` объекта компонента, которое обычно представляет собой объект:
``` js
export default {
  data: {
    text: 'Hello, World!'
  }
}
```
Здесь у объекта `data` есть свойство `text`, значение которого будет использоваться в качестве отображаемого содержимого упомянутого ранее компонента `<text>` (прим. переводчика: в оригинале упоминается `<p>`).

### Модель компонентов и обновление состояния

Предположим, нам нужно разработать компонент, который меняет отображаемый текст при нажатии. В таком случае нам потребуется отслеживать событие ввода на компоненте и обновлять отображаемое содержимое. Следующий код отслеживает событие нажатия на компоненте `<p>`:
``` html
<template>
  <p on:click="text += '!'">{{text}}</p>
</template>
```
Выражение в атрибуте `on:click` будет выполняться при нажатии на текст. В результате при клике в конце текста `text`, отображаемого в компоненте `<p>`, будет добавляться символ `'!'`:

<glyphix id="getting-started-click-p" height="120" width="360" title="Событие клика">

``` html
<p on:click="text += '!'">{{text}}</p>
```

``` js
export default {
  data: {
    text: "Hello, World!"
  }
}
```

``` css
p {
  font-size: 32px;
  text-align: center;
}
```

</glyphix>

В следующих руководствах мы подробно рассмотрим механизм обновления компонентов.

# Управление изображениями

Инструмент сборки glyphix.js управляет всеми ресурсами PNG-изображений в проекте (в каталоге `src`). Соответствующие модули в основном предоставляют следующие функции:
- Поддержка файлов конфигурации для ресурсов изображений и предоставление соответствующего интерфейса настройки;
- Преобразование изображений в размеры и форматы, оптимизированные для конкретного устройства, во время сборки.

Разработчикам приложений нужно лишь настроить параметры сборки ресурсов изображений в соответствии со своими потребностями, в то время как поставщикам устройств необходимо определить конкретные стратегии конвертации изображений для своих устройств.

## Конфигурация разработки приложений

При разработке приложений необходимо настроить параметры сборки изображений для корректной генерации пакета ресурсов.
Настройка `config/image-rules.json`, а также таких свойств, как `config.designWidth` в файле `src/manifest.json` при разработке приложений, влияет на процесс сборки ресурсов изображений. Файл `config/image-rules.json` обычно используется для настройки параметров качества и производительности, в то время как поля в `manifest.json` влияют на глобальный масштаб изображений (используется для адаптации к устройствам с различным разрешением).

::: tip
Файл `config/image-rules.json` можно настроить с помощью команды `gx config` или другими способами, однако не рекомендуется редактировать его напрямую в текстовом редакторе.
:::

При использовании команды `gx config` разработчики будут в основном концентрироваться на двух параметрах: `transparent` (прозрачность) и `quality` (качество).

### Параметр Transparent

Параметр Transparent указывает, содержит ли изображение прозрачные пиксели. Если установлено значение «нет» (`false`), а исходное изображение содержит прозрачные пиксели, то при генерации эти пиксели будут преобразованы в непрозрачные (обычно путем наложения на черный фон).因此, необходимые изображения должны быть помечены как сохраняющие прозрачные пиксели, иначе эффект наложения будет отображаться некорректно. Поскольку на некоторых платформах производительность непрозрачных изображений выше, а объем данных таких изображений меньше, опция transparent по умолчанию отключена.

### Параметр Quality

Параметр Quality представляет качество изображения после сборки и является целым числом в диапазоне $[0, 100]$. Тем не менее, обычно используется только 3 примерных уровня качества:
- High: 100, максимальное качество;
- Middle: 50, среднее качество, значение по умолчанию;
- Low: 0, низкое качество.

При конвертации ресурсов изображений оптимизация выполняется на основе параметра качества. Как правило, среднее качество — это стратегия конвертации на целевой платформе, которая сбалансирована по таким факторам, как визуальный эффект, производительность рендеринга/загрузки и использование памяти, поэтому оно рекомендуется к использованию. Высокое качество может обеспечить лучшую детализацию, но может привести к снижению производительности. Низкое качество может использоваться для изображений, где допускается потеря качества ради повышения производительности (например, для фотографий). Конкретные целевые платформы также могут игнорировать параметр quality и использовать единую стратегию.

## Адаптация устройств и платформ

Предположим, что разработчики устройств и платформ уже реализовали оптимизированные форматы ресурсов изображений для конкретной целевой платформы и поддерживают различные форматы качества и пикселей. Чтобы эти форматы изображений могли генерироваться в glyphix.js, необходимо выполнить следующие действия:
- Реализовать инструмент командной строки для конвертации **одного изображения**
  - Необходимо предоставить интерфейс командной строки для конвертации PNG-изображения в пользовательский формат с поддержкой вывода по указанному пути (включая перезапись исходного файла).
  - Желательно предоставить интерфейс командной строки для конвертации из пользовательского формата обратно в PNG с поддержкой вывода по указанному пути (включая перезапись исходного файла). Без этой функции предварительный просмотр на ПК будет невозможен.
- Написать файл описания устройства и скрипт конвертации изображений.

### Скрипт конвертации изображений

Скрипт конвертации изображений представляет собой файл scheme. Когда требуется конвертировать изображение, glyphix.js вызывает этот скрипт, который может определить порядок конвертации на основе следующих переменных:
- `env.image-path`: абсолютный путь к конвертируемому изображению. Сконвертированное изображение перезаписывается по этому пути;
- `env.transparent`: параметр прозрачности данного изображения;
- `env.quailty`: параметр качества данного изображения;
- `env.target`: целевой режим конвертации, описанный далее;
- `env.verbose`: включен ли режим подробного вывода (verbose). Если да, можно выводить детальные логи, в противном случае логи выводить не следует;
- `env.script-dir`: абсолютный путь к каталогу текущего скрипта. Если команда, необходимая для конвертации, находится относительно этого скрипта, а не в переменной окружения `PATH`, этот параметр можно использовать для конкатенации путей.

`env.target` представляет **целевой режим** конвертации изображений. Его значение определяет, какой именно способ конвертации применять:
- `"device"`: выполнение полного процесса конвертации для целевого устройства, например, удаление альфа-канала непрозрачных изображений с последующим преобразованием в формат PGF (формат изображений Glyphix) в соответствии с параметром качества;
- `"emulator"`: выполнение процесса конвертации для эмулятора. Поскольку эмулятор не поддерживает специфические форматы текстур аппаратного обеспечения (например, ETC2 и т. д.), для обеспечения нормального отображения изображений в эмуляторе можно только удалить альфа-канал непрозрачных изображений без дальнейшего преобразования в формат целевого устройства (или преобразовать в формат PGF, поддерживаемый программно);
- `"preprocess"`: выполнение только этапа предварительной обработки, то есть удаление альфа-канала непрозрачных изображений с выводом результата в формате PNG;
- `"preview"`: генерация PNG-изображения для предварительного просмотра. Сначала изображение конвертируется в пользовательский целевой формат в соответствии с процессом конвертации для цели `"device"`, а затем полученное изображение преобразуется обратно в PNG для предварительного просмотра.

::: tip
Если инструмент командной строки для конвертации изображений не поддерживает конвертацию пользовательского формата в PNG, не реализуйте целевые режимы `"preprocess"` и `"preview"`.
:::

### Инструмент командной строки image-forge

image-forge — это инструмент командной строки для работы с форматом изображений PGF, предоставляемый Glyphix, который обладает следующими функциями:
- Поддержка конвертации PNG-изображений в формат PGF, а также PGF-изображений в формат PNG;
- Поддержка распространенных форматов пикселей ARGB и PAL с различием режима предварительно умноженного альфа-канала (premultiplied alpha);
- Поддержка смешивания прозрачных ARGB-изображений с указанным сплошным фоном для преобразования их в непрозрачные изображения (без простого отбрасывания альфа-канала);
- Поддержка выравнивания строк по пикселям или байтам;
- Поддержка сжатия LZ4 с возможностью установки минимального порога сжатия (данные изображений ниже порогового значения не сжимаются).

Платформы, использующие другие пользовательские форматы изображений, также могут использовать image-forge для удаления канала прозрачности.

## Пример скрипта конвертации изображений

В следующем примере показано, как использовать такие команды, как image-forge, для конвертации PNG в PGF-изображения с приоритетным использованием формата таблицы цветов (PAL).

Сначала определим правила целевого формата для непрозрачного и прозрачного случаев:
``` scheme
; Определяем правила формата пикселей для непрозрачных цветов
(define (opaque-formats q)
  (cond ((<= q 50) "pal-rgb")
        (else "rgb24")))

; Определяем правила формата пикселей для прозрачных цветов
(define (transparent-formats q)
  (cond ((<= q 50) "pal-argb-premul")
        (else "argb32-premul")))

; Вычисляем целевой формат пикселей под воздействием параметров прозрачности и качества
(define pixel-format
  ((if env.transparent
      transparent-formats opaque-formats)
    env.quailty))

; Преобразовывать ли изображение в формат таблицы цветов
(define palette (<= env.quailty 50))
```

Приведенный выше код будет использовать формат таблицы цветов, когда качество меньше или равно 50, и использовать `pal-rgb` или `pal-argb` в зависимости от наличия прозрачности. При качестве выше 50 используются форматы пикселей с 8-битной выборкой RGB или ARGB. В конечном итоге переменная `pixel-format` представляет собой фактически используемое имя формата пикселей, а `palette` указывает, используется ли формат таблицы цветов.

Далее определим команды, необходимые для различных сценариев:

``` scheme
; Добавлять ли параметр командной строки --verbose
(define if-verbose (if env.verbose "--verbose " ""))

; Вызов команды pngquant для сокращения цветов изображения до 256 или менее. В системе должен быть установлен pngquant
(define color-reduction
  (string-append "pngquant --ext=.png --force " if-verbose env.image-path))

; Конвертация изображения в формат PGF
(define convert (string-append "image-forge "
  "--format=" pixel-format " " ; Указываем выходной формат пикселей
  "--compress --min-compress-ratio=5 " ; Сжимаем данные изображения для уменьшения размера файла, минимальная степень сжатия равна 5
  "--align=16 --pixel-align " ; Выравнивание изображения по 16 пикселям
  if-verbose
  env.image-path))

; Удаление альфа-канала изображения и добавление фона
(define remove-alpha (string-append "image-forge --bypass "
  ; На часах bes2500ibp для непрозрачных изображений можно удалить альфа-канал и выполнить смешивание с черным фоном, что может улучшить качество изображения после сокращения цветов PAL
  (if env.transparent "" "--background black ")
  if-verbose
  env.image-path))

; Команда для декодирования PGF-изображения обратно в PNG
(define decode
  (string-append "image-forge --decode " if-verbose env.image-path))
```

В следующем коде `execute-try` вызывает указанную функцию `f`, если код выхода команды отличен от 0, а функция `execute` выводит лог ошибки и аварийно завершает скрипт, если код выхода команды отличен от 0. Функция `run-convert` выполняет полный процесс конвертации изображения для целевого устройства (вызывает команды `remove-alpha` и `convert`).

``` scheme
; Выполняет команду и выводит ее содержимое в режиме verbose. Если команда завершается с ненулевым кодом ошибки, вызывает функцию f
(define (execute-try cmd f)
  (begin
    (if env.verbose ; Если включен режим verbose, выводим содержимое команды
      (display (string-append "Run command: " cmd "\n")))
    (let ((r (system (string-append env.script-dir "/bin/" cmd))))
      (if (= r 0) 0 (f r)))
  ))

; Выполняет команду и выводит ее содержимое в режиме verbose. Если команда завершается с ошибкой, прерывает выполнение программы
(define (execute cmd)
  (execute-try cmd (lambda (x)
    (begin ; При сбое выводим код ошибки и аварийно завершаем работу
      (display (string-append "subprocess failed (" (number->string x) "): " cmd "\n"))
      (exit-fail)
  ))))

; Конвертация изображения
(define (run-convert)
  (begin
    (execute remove-alpha) ; Сначала удаляем прозрачный канал
    (if palette (execute color-reduction)) ; Если используется формат таблицы цветов, сокращаем количество пикселей изображения
    (execute convert) ; Выполняем команду конвертации изображения
  ))
```

Макрос `targets` определяет методы обработки для всех целевых режимов, например, режим `"device"` вызовет функцию `run-convert` и т. д.

``` scheme
; Определяем стратегии конвертации для соответствующих целей
(targets env.target
  ; Режим устройства: процесс конвертации изображений, в конечном итоге используемый на целевом устройстве
  ("device" (run-convert))
  ; Режим эмулятора: удаление альфа-канала только для непрозрачных изображений, без конвертации формата
  ("emulator" (execute remove-alpha))
  ; Режим предварительной обработки: удаление альфа-канала непрозрачных изображений и добавление фона
  ("preprocess" (execute remove-alpha))
  ; Режим предварительного просмотра: генерация PNG-изображения для предварительного просмотра с эффектом отображения, идентичным реальному устройству
  ("preview" (begin
    (run-convert) ; Сначала конвертируем изображение в формат PGF
    (decode))) ; Затем конвертируем изображение обратно в PNG
  )
```

Чтобы использовать скрипт конвертации изображений, необходимо добавить поле в файл описания модели устройства:

``` yaml

  width: 454 # пиксели
  height: 454 # пиксели
  dpi: 326 # пикселей на дюйм

#...

```

### Более сложные стратегии

Поскольку скрипт конвертации изображений написан на полноценном языке программирования, а не на языках конфигурации, таких как Yaml или JSON, мы можем реализовать более сложные пользовательские стратегии конвертации, не ограничиваясь возможностями, предоставляемыми фреймворком. В качестве примера вышеупомянутой конвертации в формат таблицы цветов: формат PAL плохо работает на изображениях с богатой палитрой. В этом случае можно конвертировать изображение в формат, который лучше работает в таких сценариях. Конкретная идея заключается в следующем:
1. Команда `pngquant` поддерживает аварийное завершение работы в случае, если после конвертации в формат PAL качество оказывается ниже заданного значения. Соответственно, настройте параметры команды для этой цели.
2. Измените операцию `color-reduction`, выполняемую функцией `execute` в функции `run-convert`, на выполнение с помощью `execute-try`, и в функции обработки исключений последней используйте операцию конвертации в альтернативный формат.
3. Обработка таких целей, как `preview`, аналогична, но следует отметить, что при конвертации выходного формата обратно в PNG также необходимо распознавать аварийное завершение команды и переключаться на попытку выполнения последующих команд.

В общем и целом, подход аналогичен идеологии shell-скриптов — использование кодов возврата ошибок команд для управления ходом выполнения.

# Симулятор и отладка

Чтобы запустить симулятор, вам нужно перейти в корневой каталог проекта в командной строке и запустить подкоманду `gx emu`. Симулятор Glyphix обладает окружением, которое максимально приближено к условиям работы на реальном устройстве. Это позволяет разрабатывать и отлаживать большую часть интерфейсов и функций с помощью симулятора, избавляя от необходимости часто устанавливать приложение на реальное устройство.

::: tip
Из-за текущих ограничений npm-пакета [`glyphix`](https://www.npmjs.com/package/glyphix) обязательно настройте [`glyphix.config.js`](/tutorials/nodejs.md#glyphix-config-js-配置), иначе при выполнении `gx emu` вы не сможете видеть номера строк исходного кода в сообщениях об ошибках.
:::


## Подкоманда `gx emu`

Запускает симулятор с использованием конфигурации целевого устройства из последней сборки. Эту команду необходимо выполнять в корневом каталоге проекта Glyphix. Она автоматически собирает проект и создает файлы ресурсов, необходимые для симулятора, поэтому предварительное выполнение `gx build` не требуется.

#### Опции команды

- `-d --device=NAME`：указывает имя эмулируемого устройства, по умолчанию `default` (разрешение $410 \times 502\rm px$).
- `-e --emulator-exe=CMD`：указывает исполняемый файл симулятора, по умолчанию `glyphix-emu`. Обычно изменять не требуется.
- `-l --language=NAME`：указывает локаль симулятора, по умолчанию `zh-CN` (упрощенный китайский). Список поддерживаемых языков можно посмотреть с помощью команды `gx list language`.
- `--target=URI`：устанавливает имя пакета или deeplink при запуске симулятора, например `app://com.example.app/SomePage?query=value` или `com.example.app`.
- `-i --inspector`：включает инспектор при запуске симулятора. Инспектор представляет собой веб-страницу, которая позволяет отлаживать элементы интерфейса в симуляторе прямо из браузера.
- `-m --mobile-network`：（еще не реализовано) включает проксирование сети SDK телефона в симуляторе вместо прямого доступа к сети.
- `-w --watch`：отслеживает каталог проекта при запуске симулятора и автоматически пересобирает проект и обновляет интерфейс симулятора при изменении исходных файлов.
- `-r --real-scale`：отображает окно симулятора в реальном размере, а не масштабирует его в соответствии с разрешением устройства. Эту опцию рекомендуется использовать на экранах с высоким разрешением (HiDPI).
- `-t --top`：удерживает окно симулятора поверх остальных окон.
- `-p --profiling`：включает режим профилирования производительности. Из-за значительной разницы в производительности между симулятором и реальным устройством эта опция обычно малополезна.

## Режимы запуска

По умолчанию `gx emu` запускает симулятор, используя конфигурацию устройства, применявшуюся при последней сборке. Поведение запуска симулятора также можно настраивать с помощью опций командной строки.

### Указание модели устройства

Используйте опцию `-d` или `--device`, чтобы указать модель устройства, которую необходимо эмулировать, например:
```bash
gx emu -d generic-watch-466x466
```
Это запустит симулятор для устройства `generic-watch-466x466`. Список установленных устройств можно посмотреть с помощью команды `gx list device`.

Если эта опция не указана, будет использоваться устройство, заданное в прошлый раз. При первом запуске или после `gx clean` симулятор запустится с устройством `default`.

### Запуск через Deeplink

По умолчанию симулятор запускает приложение текущего проекта либо интерфейс меню приложений. Однако при отладке функции жизненного цикла [`onRoute()`](/framework/component/life-cycle.md#onroute) вам может потребоваться запустить приложение через deeplink, чтобы убедиться, что `onRoute()` получает определенные параметры. Для указания deeplink можно использовать опцию `--target`, например:
```bash
gx emu --target app://com.example.app/SomePage?query=value
```
Это запустит приложение с именем пакета `com.example.app`, при этом путь (path) URI Deeplink (включая корневой каталог `/`, то есть `/SomePage`) и поля query будут переданы в функцию `onRoute()` этого приложения.

### Имитация размеров устройства

По умолчанию симулятор использует фактическое разрешение устройства в пикселях. Из-за этого размер отображения на компьютере получается больше реального экрана устройства, и разработчику становится сложно оценить оптимальный размер элементов пользовательского интерфейса (включая макет дизайна) на самом устройстве. Опция `-r` или `--real-scale` позволяет имитировать размеры реального устройства:
```bash
gx emu -r
```
Используя эту опцию, вы можете проверять реальный размер элементов UI без необходимости установки приложения на устройство. Однако, учитывая, что DPI большинства умных часов превышает 300, на мониторах с разрешением 1080p режим real-scale может сделать интерфейс слишком размытым. Эту опцию рекомендуется использовать на экранах с высоким разрешением (HiDPI), таких как мониторы 4K или дисплеи Retina на macOS.

::: tip
В режиме real-scale вам следует указывать целевое эмулируемое устройство с помощью опции `--device`. Стоит отметить: из-за различий в DPI два устройства с одинаковым разрешением могут иметь разные физические размеры экранов, поэтому размеры отображения в режиме real-scale также будут отличаться.
:::

### Автоматическое обновление

Опция `-w` или `--watch` позволяет отслеживать изменения в каталоге проекта во время работы симулятора и автоматически выполнять пересборку и перезапуск приложения при изменении исходных файлов. Обычно ее рекомендуется использовать в сочетании с опцией `-t`, например:
```bash
gx emu -wt
```
Это позволит удерживать окно симулятора поверх остальных окон и автоматически перезапускать приложение после изменения исходных файлов. Это чрезвычайно удобно для разработки и отладки: вы можете переключаться прямо из редактора кода в симулятор без необходимости вручную перезапускать симулятор или постоянно переключать окна.

::: tip
В настоящее время горячее обновление страниц (hot reload) не поддерживается — вместо этого при изменении исходных файлов происходит перезапуск всего приложения. Если вам нужна более высокая скорость отладки, вы можете настроить [`manifest.router.entry`](/framework/application/manifest.md#entry) на разрабатываемую в данный момент страницу, чтобы при каждом перезапуске приложение сразу открывало ее.
:::

## Подключение к телефону

Вы можете подключиться к симулятору с помощью мобильного Android-приложения [Glyphix Debug](https://www.pgyer.com/KLeBQFv6), что удобно для отладки функций, связанных с взаимодействием реального устройства и смартфона.

### Подготовка

Установите приложение Glyphix Debug на свой телефон и убедитесь, что телефон и компьютер находятся в одной локальной сети (например, подключены к одному Wi-Fi). Запустив симулятор и открыв приложение Glyphix Debug, нажмите кнопку «Socket-соединение» (Socket 连接). В приложении появится экран подключения, где вы сможете выбрать найденный IP-адрес симулятора или вручную ввести IP-адрес компьютера и порт симулятора для подключения.

По умолчанию симулятор прослушивает сетевой порт `7768`. Если этот порт занят (обычно при запуске нескольких симуляторов), автоматически выбирается следующий доступный порт, а его реальный номер выводится в консоль при запуске. Например:
```bash
$ gx emu
[simulator.socket] MAS TCP server bind port 7768 successful 
```

::: tip
Если порт симулятора был занят и выбран другой порт (не 7768), приложение Glyphix Debug не сможет автоматически обнаружить этот симулятор. В таком случае для подключения потребуется вручную ввести правильный IP-адрес и номер порта.
:::

Настоятельно рекомендуется включить в симуляторе режим прокси сети телефона (описанный в следующем разделе), чтобы избежать одновременного использования сети компьютера и сети телефона. В противном случае это может помешать корректной работе API взаимосвязи устройств, таких как [`@system.interconnect`](/api/system-interconnect.md).

### Прокси сети телефона

Использование опции `-m` или `--mobile-network` включает только функцию сетевого прокси для SDK телефона, имитируя сетевое окружение реального устройства. При использовании этой опции симулятор не запускает целевое приложение автоматически, а отображает экран со списком приложений.

Прежде чем запускать приложение вручную, необходимо подключиться к симулятору через мобильное приложение Glyphix Debug с помощью «Socket-сети» и только после этого нажать на целевое приложение. В противном случае у приложения не будет доступа к сети.

::: tip
В режиме прокси сети телефона (`-m`) вы можете имитировать обрыв сети, закрыв отладочное приложение на телефоне и повторно подключившись к симулятору. В противном случае симулятор автоматически переключится на сеть компьютера.
:::

### Частые проблемы с подключением

Если вам не удается подключиться к симулятору через приложение Glyphix Debug, убедитесь, что компьютер и телефон подключены к одной локальной сети, а программа симулятора и его порт не заблокированы правилами брандмауэра. Если вы подключены к общедоступной сети (публичному Wi-Fi), соединение может быть недоступно из-за межсетевого экрана или сетевой изоляции.

Если вы используете VPN или прокси-программы, убедитесь, что трафик внутри локальной сети не проксируется, иначе подключение также не удастся установить.

## Другие операции

### Очистка данных приложения

Вы можете использовать [`gx clean`](README.md#gx-clean) для удаления данных работающего приложения в симуляторе. После этого при следующем запуске симулятор начнет работу с состояния первой установки.

### Комбинирование опций команд

Вы можете комбинировать несколько опций вместе, например:
```bash
gx emu -rwt -d default-watch-466x466
```
Это эквивалентно раздельному использованию:
```bash
gx emu -r -w -t -d default-watch-466x466
gx emu --real-scale --watch --top --device default-watch-466x466
```
Рекомендуется установить скрипт автодополнения, как описано в разделе [`gx completion`](#gx-completion), чтобы иметь возможность выбирать имена устройств и опции команд в терминале.

# Утилита сборки Glyphix.js

glyphix.js — это утилита сборки для приложений Glyphix. Она включает в себя инструмент командной строки под названием `gx`, который используется для создания, сборки и запуска приложений Glyphix. Утилита также содержит графический симулятор для имитации работы приложений Glyphix на компьютере.

В этой документации приведены инструкции по установке и использованию glyphix.js. Руководство [Быстрый старт](/tutorials/getting-started.md) представляет собой более простое введение. Ознакомьтесь также с разделом [Сборка и запуск](#сборка-и-запуск), чтобы узнать, как разрабатывать, собирать и публиковать приложение Glyphix.

## Установка

В этом разделе описывается процесс установки утилиты сборки glyphix.js. Для обычного использования достаточно ознакомиться с методом [Установка через npm](#установка-через-npm). Метод [Ручная установка](#ручная-установка) предназначен для особых сценариев, таких как среды с ограниченным доступом к сети или CI-сборки.

### Установка через npm

Для установки утилиты сборки glyphix.js вы можете использовать менеджер пакетов [npm](https://nodejs.org). Рекомендуется использовать опцию `-g` для глобальной установки:
::: code-tabs
@tab npm
```bash
npm install -g glyphix-cli
```

@tab pnpm
```bash
pnpm install -g glyphix-cli
```

@tab yarn
```bash
yarn global add glyphix-cli
```
:::

::: tip
Перед глобальной установкой с помощью pnpm может потребоваться выполнить команду `pnpm setup` для настройки переменных окружения. Команда `pnpm install -g` подскажет, как это сделать.
:::

После завершения установки вы можете проверить успешность установки, выполнив в терминале команду `gx --version`. Например:
```bash
$ npm install -g glyphix-cli
$ gx --version
gx v0.10.1 - The Glyphix applet development toolchain
commit a9337cf1 - Tue Sep 23 10:03:48 2025 +0800
```

Кроме того, для сборки ресурсов приложений под определенные устройства необходимо установить [pngquant](#pngquant).

### Ручная установка

Вы также можете установить glyphix.js вручную из архива: добавьте каталог `bin` из распакованной директории в переменную окружения `PATH`. Ниже описан процесс установки для основных операционных систем.

::: tip
Утилита glyphix.js — это не просто один исполняемый файл. Не забудьте сохранить остальные файлы ресурсов (включая все файлы в каталогах `bin` и `share`).
:::

#### macOS / Linux

Для macOS или Linux для установки утилиты glyphix.js можно использовать команду `tar`. Перед этим необходимо установить такие инструменты, как `xz`:

::: code-tabs
@tab macOS
```bash
brew install xz
```

@tab Ubuntu / Debian
```bash
sudo apt update
sudo apt install xz-utils
```

@tab Arch Linux
```bash
sudo pacman -S xz
```
:::

После скачивания архива glyphix.js используйте следующие команды для его распаковки и установки:
::: code-tabs
@tab macOS
```bash
tar -xvJf glyphix-v0.7.2-darwin-arm64.tar.xz -C ~/.local
```

@tab Linux
```bash
tar -xvJf glyphix-v0.7.2-linux-x86_64.tar.xz -C ~/.local
```
:::
Не забудьте заменить имя файла `.tar.xz` на актуальное скачанное имя файла, соответствующее вашей операционной системе и архитектуре процессора. После распаковки такие команды, как `gx`, будут находиться в директории `~/.local/bin`. Добавьте эту директорию в переменную окружения `PATH`, обновив, например, файл `.bashrc` следующим образом:
```bash
# Если ~/.local/bin нет в PATH, добавляем его
echo "$PATH" | grep -q "$HOME/.local/bin" || echo 'export PATH="$HOME/.local/bin:$PATH"' >> ~/.bashrc
source ~/.bashrc # Перезагружаем конфигурацию bash
```

::: tip
При использовании `Zsh` файл конфигурации `.zshrc` может импортировать `.bashrc`, поэтому достаточно обновить только `.bashrc`. В противном случае обновите `.zshrc` описанным выше способом.

Рекомендуется устанавливать утилиту сборки glyphix.js в пользовательскую директорию `~/.local`, чтобы избежать использования прав root.
:::

#### Windows

Чтобы установить glyphix.js в Windows, скачайте архив соответствующей версии для Windows, а затем распакуйте его с помощью программы, поддерживающей формат `7z` (например, [7-Zip](https://www.7-zip.org/)), в какую-либо директорию, например `C:\glyphix`. Затем добавьте `C:\glyphix\bin` в [переменную окружения `PATH`](https://learn.microsoft.com/zh-cn/previous-versions/office/developer/sharepoint-2010/ee537574(v=office.14)) системы.

Вы также можете использовать инструмент командной строки `7z` для распаковки, например:
```shell
7z x -y glyphix-v0.7.2-windows-x64.7z -oC:/glyphix
```
Это аналогично процессу установки в macOS и других системах.

### Установка системных зависимостей

#### pngquant

Пользователям Linux и macOS необходимо дополнительно установить `pngquant`. Вы можете установить его с помощью `npm`:
```bash
npm install -g pngquant-bin # pngquant-bin поддерживает установку только через npm
```
Пакет `glyphix-cli` для Windows уже включает в себя `pngquant.exe`, поэтому дополнительная установка не требуется.

::: tip
Вы также можете скачать предварительно скомпилированные бинарные файлы с сайта [pngquant.org](https://pngquant.org/) или установить их через пакетный менеджер вашей системы.
:::

#### Системные зависимости Linux

Установочный пакет glyphix.js для Linux не зависит от конкретного дистрибутива, на данный момент доступны сборки только для архитектуры `linux-x86_64`. Мы протестировали его работу на Ubuntu 20.04 (или новее) и Arch Linux.

Если вы используете команду `gx` исключительно для сборки (что часто применяется в CI), дистрибутивы Linux без графического окружения должны работать «из коробки». Запуск графического симулятора зависит от оконной системы X11, поэтому может потребоваться установка пакетов, связанных с xorg. В частности, в окружении Wayland вам также потребуется установить пакет `xwayland` (симулятор пока не поддерживает нативный Wayland).

Для удаления glyphix.js, установленного глобально через менеджер пакетов вроде npm, используйте соответствующую команду удаления:
::: code-tabs

```

@tab pnpm

```

@tab yarn

Команда `tar -tf` выведет список файлов в архиве; замените `glyphix-xxx.tar.xz` на ваше фактическое имя установочного файла. Ручное удаление в Windows выполняется аналогичным образом.

## Сборка и запуск

После установки glyphix.js перейдите в корневой каталог исходного кода приложения и используйте команду [`gx build`](#gx-build) для сборки пакета приложения или команду [`gx emu`](#gx-emu) для запуска симулятора.

После сборки приложения обратитесь к разделу [Отправка пакета приложения](#отправка-пакета-приложения), чтобы узнать, как установить приложение на устройство или отправить его на платформу публикации приложений.

## Параметры командной строки

### Общие опции

#### `gx --help`

Просмотр справки. Справку также можно использовать для конкретных подкоманд, например, `gx build --help` выведет справку исключительно для подкоманды `build`.

#### `gx --version`

Опция `-V --version` используется для просмотра версии команды `gx`.

#### `gx --verbose`

Опция `-v --verbose` включает вывод подробных логов, что обычно не требуется разработчикам приложений.

#### `gx --numeric-version`

Выводит чистый номер версии команды `gx`, например `0.10.1`.

#### `gx --quiet`

Опция `-q --quiet` включающие тихий режим, подавляющий большинство не предупреждающих и не ошибочных логов. Сюда входят логи прогресса сборки при использовании `gx build`. Этот режим обычно используется в CI-средах, где требуется собирать большое количество пакетов приложений.

Просмотр номера версии.

### `gx new`

Создание нового проекта, например `gx new myapp` создаст новый проект с именем `myapp`.

### `gx build`

Сборка проекта (действие по умолчанию). С помощью опции `--device` или `-d` можно указать целевое устройство, например:
``` bash
gx build -d default # Сборка для устройства default
```
Опция `--dump` позволяет вывести подробную информацию о компиляции файлов UX.

Glyphix.js поддерживает инкрементальную сборку: при изменении исходного кода пересобирается только измененная часть.

Параметр `-r --image-rules` позволяет указать файл правил упаковки изображений (по умолчанию `config/image-rules.json`). Значение этого параметра кэшируется, и последующие вызовы `gx build` или `gx emu` будут выполняться в соответствии с предыдущей конфигурацией.

#### Опции команды

- `-d --device=NAME`: указывает имя целевого устройства, которое должно совпадать с именем установленной конфигурации устройства. Список установленных устройств можно посмотреть с помощью команды `gx list device`. Если эта опция не указана, по умолчанию используется устройство `default`.
- `-f --full`: принудительная полная пересборка проекта вместо инкрементальной.
- `-e --emulator`: сборка проекта для симулятора, а не для реального устройства. Эта опция автоматически применяется при выполнении команды `gx emu`.
- `-r --image-rules=PATH`: указывает файл правил упаковки изображений по умолчанию (`config/image-rules.json`).

#### Отправка пакета приложения

После сборки с помощью `gx build` в каталоге проекта будет создана директория `.glyphix-work/dist/<device-name>/<package-name>`, содержащая собранные файлы пакета приложения (файлы `.pkg`). Полученный файл можно установить на устройство через приложение отладки на телефоне или отправить на платформу публикации приложений.

Рекомендуется использовать опцию `-d` для сборки пакетов приложений под все поддерживаемые устройства. Пример структуры каталогов:
```bash
.glyphix-work/dist
├─ generic-watch-368x448
│  └─ com.example.app
│     ├─ bundle.pkg
│     ├─ icon.png
│     └─ manifest.json
└─ generic-watch-466x466
   └─ com.example.app
      ├─ bundle.pkg
      ├─ icon.png
      └─ manifest.json
```
При отправке пакета приложения упакуйте и загрузите **всю** директорию `.glyphix-work/dist`, а не только файл `.pkg` или какую-либо отдельную поддиректорию. Платформа распознает приложение по информации из файла `manifest.json`, а файл `icon.png` может потребоваться в качестве иконки предпросмотра.

::: tip
Пользователи Linux или macOS могут использовать следующую команду для сборки приложений под определенный класс устройств:
```bash
gx list device | grep "^generic-" | xargs -n 1 gx build -d
```
Это соберет пакеты приложений для всех устройств, чьи имена начинаются с `generic-`.

В Windows для пакетной сборки можно использовать аналогичную команду PowerShell:
```shell
gx list device | ? { $_ -match "^generic-" } | % { gx build -d $_ }
```
:::

### `gx emu`

См. документацию [Симулятор и отладка](/tutorials/glyphix.js/emulator.md).

### `gx clean`

Очистка результатов сборки. Эта команда удаляет каталог `.glyphix-work` в папке проекта.

### `gx config`

Эта команда запускает веб-интерфейс для редактирования файла правил упаковки изображений. Следуя подсказкам в командной строке, вы можете открыть страницу в браузере для выполнения операций. Команда имеет два варианта использования:
``` bash
gx config # Находясь в проекте Glyphix, указывать исходную директорию не нужно (в настоящее время может использоваться только в корне проекта)
gx config path/to/dir # Настройка для указанной директории, может применяться для настройки не-проектных ресурсов изображений
```

Параметр `-r --image-rules` задает файл правил упаковки изображений (по умолчанию `config/image-rules.json`).

### `gx image-forge`

Преобразование отдельных файлов изображений. Команда позволяет указать произвольный исходный путь и путь вывода, ее не обязательно выполнять внутри проекта Glyphix:
``` bash
gx image-forge src -o dist
```

Описание опций:
- `src` — исходный путь для конвертации. Команда `image-forge` рекурсивно преобразует все изображения и сохраняет их в целевой каталог, указанный в параметре `-o, --output` (по умолчанию `dist`), сохраняя относительную структуру директорий.
- `-r --image-rules` задает файл правил упаковки изображений (по умолчанию `config/image-rules.json`).
- `-d --device` указывает целевое устройство для конвертации изображений.

### `gx list`

Вывод определенной информации. В настоящее время поддерживается три операции:

# Асинхронные операции

Введение асинхронных операций в сценарии JavaScript преследует главную цель — перенести ресурсоемкие задачи в фоновый режим, чтобы избежать блокировки потока JavaScript. В фоновом режиме в основном выполняются задачи, связанные с интенсивным вводом-выводом (IO-bound). Glyphix предоставляет разработчикам базовый асинхронный фреймворк для JavaScript, который реализует только необходимую абстракцию для асинхронных рабочих процессов, не создавая при этом дополнительных накладных расходов.

## Области применения

Модель асинхронного рабочего процесса применима в следующих сценариях:

- Запрос инициируется кодом JavaScript, обрабатывается нативным потоком асинхронной обработки, после чего возвращается результат;
- Запрос инициируется кодом JavaScript, нативный поток асинхронной обработки выполняет обработку и периодически отправляет отчеты о сообщениях;
  - Код JavaScript может主动 (активно) запросить отмену или аннулирование запроса.

## Режим запроса данных

В режиме запроса данных код JavaScript вызывает C++ API для создания запроса, выполняет операцию в асинхронном потоке и возвращает результат коду JavaScript. В этом процессе данные передаются через асинхронную очередь. Шаблонный класс `async::ResultSession` предоставляет общий операционный фреймворк для этого режима.

### Описание сценариев

Следующие сценарии являются типичными примерами режима запроса данных:

- **Чтение и запись файлов**: при вызове из JavaScript необходимо указать путь к файлу, смещение для чтения и записи, длину данных или записываемые данные; когда запрос отправляется в асинхронный поток для выполнения, происходят реальные операции с файлом, и по их завершении результат возвращается в код JavaScript или отправляется уведомление.
- **Сетевые запросы**: аналогично чтению и записи файлов, при вызове из JavaScript необходимо указать параметры запроса, которые затем обрабатываются в фоновом потоке с возвратом результата.

Сценарии режима запроса данных имеют следующие особенности:
- Результат запроса возвращается однократно, поэтому этот режим не подходит для датчиков или таймеров, которые могут срабатывать многократно;
- Запрос всегда имеет результат: в случае успеха возвращается результат, в противном случае — сообщение об ошибке. Возврат результата также происходит асинхронно;
- Запрос невозможно отменить после его инициации.

### Пример: Получение уровня заряда батареи

#### JavaScript API

Предположим, требуется реализовать асинхронную функцию JavaScript для получения уровня заряда батареи:
``` ts
getLevel(): Promise<number> // API в стиле Promise
getLevel(options: { // API в стиле callback
    success: (level: number) => void,
    fail: (code: number, msg: string) => void // Чтение уровня заряда батареи фактически не вызывает fail
}): void
```
Функция `getLevel()` используется для асинхронного получения уровня заряда батареи и поддерживает два стиля API: в стиле `Promise` и в стиле callback. Код для обоих стилей выглядит следующим образом:
``` js
async function printBatteryLevel() {
    const level = await getLevel() // Асинхронное получение уровня заряда
    console.log(`battery level: ${level}%`)
}
printBatteryLevel() // Печать уровня заряда, пример вывода в консоль:
// battery level: 59%

// Ниже приведен код в стиле callback, его использование не рекомендуется:
getLevel({
    success(level) { console.log(`battery level: ${level}%`) }
})
```

#### Экспорт нативных интерфейсов C++

Функция `getLevel()` в JavaScript фактически реализуется на C++. Когда код JavaScript вызывает эту функцию, он инициирует асинхронный запрос на получение уровня заряда батареи и после получения результата возвращает его в JavaScript через функцию обратного вызова или `Promise`. Функция C++, реализующая `getLevel()`, выглядит следующим образом:
``` cpp
static JsValue getLevel(const JsCallContext &ctx) {
    typedef async::ResultSession<BatteryGetLevel> Session;
    Session *session = new Session; // Создание объекта Session
    session->request(ctx.argc() ? ctx.arg(0) : JsValue());
    return session->promise();
}
```

Шаблонный класс `async::ResultSession` (далее пространство имен `async` опускается) реализует фреймворк, необходимый для асинхронных запросов данных. Каждый асинхронный запрос данных состоит из следующих шагов:
1. Создание объекта `ResultSession`.
2. Вызов метода `ResultSession::request()` для отправки запроса.
3. Использование `ResultSession::promise()` для возврата объекта `Promise` в JavaScript.

Эта строка кода:
``` cpp
session->request(ctx.argc() ? ctx.arg(0) : JsValue());
```
помимо отправки запроса, также передает методу `ResultSession::request()` аргумент под индексом $0$, переданный вызывающим кодом JavaScript. `ResultSession` автоматически определяет стиль (Promise или callback) в зависимости от наличия в этом аргументе функций обратного вызова `success` / `fail` и т. д. Если используется стиль `Promise`, то:
``` cpp
return session->promise();
```
возвращает объект `Promise` для получения результата асинхронного запроса; в противном случае возвращается `undefined`, а результат обрабатывается функцией обратного вызова.

#### Шаблонный класс `ResultSession`

Объявление шаблонного класса `ResultSession` выглядит следующим образом:
``` cpp
template<class T, class H = ResultHandler> class ResultSession;
```
Шаблонный параметр `T` представляет собой класс, реализующий конкретную асинхронную операцию. В данном примере реализуется класс `BatteryGetLevel` для асинхронного получения уровня заряда батареи. Шаблонный параметр `H` определяет способ обработки результата асинхронного запроса; стандартный `ResultHandler` автоматически выбирает стиль callback или Promise, и разработчикам обычно не требуется его изменять.

#### Класс `BatteryGetLevel`

Определение класса `BatteryGetLevel`:
``` cpp
struct BatteryGetLevel {
    async::Result<int> resolve() const {
        return battery_read_level(); // Получение уровня заряда батареи
    }
    // errorMessage() используется для перевода кода ошибки в текст. Чтение заряда не вызывает ошибок, реализация может быть произвольной.
    static const char *errorMessage(Status) {
        return "get battery level failed";
    }
};
```
Как видно, у `BatteryGetLevel` есть две функции-члена. Функция `resolve()` используется для выполнения конкретной операции в асинхронном потоке. Возвращаемое значение функции `resolve()` должно иметь тип `async::Result<T>`, в данном случае — `async::Result<int>`.

Тип шаблонного параметра `T` возвращаемого значения функции `resolve()` (`async::Result<T>`) совпадает с типом данных параметра callback-функции JavaScript API или данных `Promise`. Например, в данном случае `int` соответствует следующему JavaScript API:
``` ts
// Тип возвращаемого значения функции C++ BatteryGetLevel::resolve()
// async::Result<int> соответствует Promise<number> в JavaScript
getLevel(): Promise<number>
```

Иными словами, если `resolve()` возвращает значение `async::Result<String>`, то в JavaScript будет возвращен `Promise<string>`, а для функции обратного вызова — `{ success(value: string): void }`. Подробную информацию о преобразовании типов данных между C++ и JavaScript см. в разделе [Преобразование типов данных](#преобразование-типов-данных).

### Пример: Чтение файлов

#### JavaScript API

Предположим, требуется реализовать асинхронную функцию JavaScript для чтения файлов:
``` ts
readfile(url:string): Promise<string> // API в стиле Promise
readFile(option: {   // API в стиле callback
  uri: string,
  success?: (data: string) => void,
  fail?: (code: number, msg: string) => void,
}): void
```
Эта функция асинхронно читает содержимое файла и возвращает его через объект `Promise`, возвращаемым значением является содержимое файла. Фактический код JavaScript выглядит следующим образом:
``` js
async function printReadFile() {
    const data = await readFile("file.txt") // Асинхронное получение содержимого файла
    console.log('文件读取成功：', data)
}

printReadFile() // Печать содержимого файла в виде строки, пример вывода в консоль:
// 文件读取成功：hello

// Ниже приведен код в стиле callback
readFile({
    url: "file.txt", 
    success: (data: string) => {  
        console.log('文件读取成功：', data);  
    }
})
```

#### Экспорт нативных интерфейсов C++

Функция `readFile()` в JavaScript фактически реализуется на C++. Когда код JavaScript вызывает эту функцию, он инициирует асинхронный запрос на чтение файла и после получения результата возвращает его в JavaScript через функцию обратного вызова или `Promise`. Функция C++, реализующая `readFile()`, выглядит следующим образом:
``` cpp
JsValue readFile(const JsCallContext &ctx) {
    typedef async::ResultSession<ReadFileRequest> Session;
    if (ctx.argc() > 0 && ctx.arg(0).isObject()) { 
        Session *session = new Session;
        // Преобразование поля url аргумента функции JavaScript в String C++ 
        session->client().url = ctx.arg(0)["url"].toString(); 
        session->request(ctx.argc() ? ctx.arg(0) : JsValue());
        return JsValue();
    }
}
```
Описание используемого шаблонного класса см. в разделе [Шаблонный класс resultsession](#шаблонный-класс-resultsession), а пояснение к коду — в разделе [Экспорт нативных интерфейсов C++](#экспорт-нативных-интерфейсов-c) для получения уровня заряда батареи.

#### Класс `readFile`

Определение класса `ReadFileRequest`:
``` cpp
struct ReadFileRequest {
    String url; // URL читаемого файла.
    Result<String> resolve() {
        ByteArray array = File::read(url); // Чтение содержимого файла по URL
        return String(array.charData(), array.size());
    }
    // errorMessage() используется для перевода кода ошибки в текст
    const char *errorMessage(Status) { return "read file error"; }
};
```
Как видно, у `ReadFileRequest` есть две функции-члена. Функция `resolve()` используется для выполнения конкретной операции в асинхронном потоке. Возвращаемое значение функции `resolve()` должно иметь тип `async::Result<T>`, в данном случае — `async::Result<String>`. Стоит отметить, что в функции `resolve()` нельзя обрабатывать типы данных JavaScript: `url` преобразуется в тип `String` C++ внутри функции `readFile()` перед инициацией асинхронного запроса, и подобные преобразования данных нельзя выполнять внутри `resolve()`.

## Режим прослушивания (Listener Mode)

В режиме прослушивания код JavaScript вызывает C++ API для создания запроса на мониторинг многократных асинхронных событий, таких как получение данных с датчиков. При изменении данных выполняется асинхронное событие, которое возвращает результат в JavaScript. Шаблонные классы `async::ListenSession` и `async::Signal` предоставляют общий операционный фреймворк для этого режима.

### Описание сценариев

Следующие сценарии являются типичными примерами режима прослушивания:

- **Мониторинг различных датчиков**: инициируется из JavaScript путем вызова C++ API для мониторинга соответствующего датчика с указанием функции обратного вызова. Когда данные датчика изменяются, новые данные возвращаются в код JavaScript через асинхронный поток в качестве параметра функции обратного вызова.
- **Периодические задачи по таймеру**: при вызове из JavaScript необходимо задать время таймера, функцию обратного вызова по истечении времени, а также признак периодичности. После отправки запроса по истечении каждого интервала таймера асинхронный поток возвращает результат в JavaScript, запуская установленную callback-функцию.

Сценарии режима прослушивания имеют следующие особенности:
- После запуска мониторинга поддерживаются множественные асинхронные запросы, поэтому этот режим может не подходить для однократных асинхронных событий, таких как чтение/запись файлов или сетевые запросы;
- После запуска мониторинга его необходимо обязательно отменить, когда он больше не нужен, иначе возникнет утечка памяти.

### Пример: Мониторинг уровня заряда батареи

#### JavaScript API

Предположим, требуется реализовать асинхронную функцию JavaScript для мониторинга уровня заряда батареи:
``` ts
subscribe(callback: (Level: number) => void): number // Мониторинг уровня заряда батареи
unsubscribe(subscribeID: number): void // Отмена мониторинга
```

Функция `subscribe()` используется для асинхронного мониторинга уровня заряда батареи, а `unsubscribe()` — для отмены мониторинга. Пример использования:
``` js
// Запуск мониторинга, возвращается ID для отмены подписки
let id = subscribe(level => {
  // При изменении уровня заряда батареи вызывается callback-функция мониторинга, пример вывода в консоль:
  // now battery level: 59
  console.log(`now battery level: ${level}%`)
})

unsubscribe(id); // Отмена мониторинга
``` 

#### Экспорт интерфейса прослушивания C++

Функция `subscribe()` в JavaScript фактически реализуется на C++. Когда код JavaScript вызывает эту функцию, запускается мониторинг уровня заряда батареи. При каждом изменении уровня заряда инициируется асинхронный запрос, и результат возвращается в код JavaScript через функцию обратного вызова. Функция C++, реализующая `subscribe()`, выглядит следующим образом:
``` cpp
async::Signal<int> Level; // Создание глобального объекта Level

level(45); // Значение Level изменилось, отправлен асинхронный запрос

static JsValue subscribe(const JsCallContext &ctx) {
    Applet *applet = Applet::current(&ctx.vm());
    if (applet && ctx.argc())  // Проверка передачи параметров
        return applet->bindObject(Level.connect(ctx.arg(0)));
    return JsValue();
}
```
Обязательно требуется создать глобальный объект `Level`. Используемый шаблонный класс `async::Signal` (далее пространство имен `async` опускается) реализует фреймворк запроса мониторинга. Запрос мониторинга включает следующие шаги:
1. Перед началом мониторинга необходимо создать объект глобального класса `Signal`;
2. Использовать метод `Signal::connect()` для связывания первого аргумента, переданного из JavaScript, с объектом `Level`;
3. Вызвать `Applet::bindObject` для привязки объекта `Level`; при изменении состояния `Level` вызывается функция обратного вызова, возвращающая результат в код JavaScript.

Эта строка кода:
```cpp
level(45);
```
изменяет значение `Level` на $45$, запуская механизм мониторинга, который инициирует асинхронный запрос. Измененное значение передается в качестве параметра функции обратного вызова, и в конечном итоге результат возвращается в код JavaScript.

#### Экспорт интерфейса отмены прослушивания C++

Функция `unsubscribe()` в JavaScript также реализуется на C++. Код JavaScript вызывает эту функцию для отмены мониторинга во избежание утечек памяти, когда мониторинг больше не используется. Функция C++, реализующая `unsubscribe()`, выглядит следующим образом:
``` cpp
static JsValue unsubscribe(const JsCallContext &ctx) {
    Applet *applet = Applet::current(&ctx.vm());
    if (applet && ctx.argc() >= 1 && ctx.arg(0).isNumber()) // Проверка правильности переданных параметров
        delete applet->unbindObject<async::Slot>(ctx.arg(0).toInt());   
    return JsValue();
}
```
Для отмены запроса мониторинга необходимо вызвать `Applet::unbindObject` для снятия привязки. Для определения отвязываемого объекта требуется передать ID, возвращенный функцией `subscribe()`.

#### Шаблонный класс `Signal`

``` cpp
template<class T, class H = ListenHandler> class Signal;
```
Шаблонный параметр `T` представляет собой класс, реализующий конкретную асинхронную операцию. В данном примере демонстрируется использование типа `int` для реализации мониторинга заряда батареи. Шаблонный параметр `H` определяет способ обработки результата асинхронного запроса; стандартный `ResultHandler` автоматически выбирает стиль callback или Promise, и разработчикам обычно не требуется его изменять.

## Преобразование типов данных

В `ResultSession` или `ListenSession` данные асинхронных операций должны быть преобразованы в объект `JsValue`, чтобы их можно было использовать в коде JavaScript. Например, в [Классе BatteryGetLevel](#класс-batterygetlevel) определена функция:
``` cpp
async::Result<int> BatteryGetLevel::resolve() const;
```
Это объявление функции означает, что типом возвращаемых данных запроса заряда батареи является `int`. Этот тип данных может быть преобразуем в `JsValue`. На самом деле следующие типы могут быть преобразованы в `JsValue`:
- `bool`: преобразуется в тип `boolean`;
- `int`: преобразуется в тип `number`;
- `float`, `double`: преобразуются в тип `number`;
- `String`: преобразуется в тип `string`.

::: warning
Строки в стиле C не поддерживаются. Они будут преобразованы в тип `boolean`.
:::

Преобразование происходит автоматически, вмешательство разработчика не требуется.

# Настройка Clangd

При разработке прошивки с использованием кросс-компилятора (например, toolchain `arm-none-eabi-gcc`) и систем сборки вроде CMake, вы можете настроить языковой сервер Clangd для улучшения опыта разработки. В частности, вы получите следующие преимущества:
- Точный переход к объявлению или определению на основе реальной структуры проекта;
- Просмотр документации API (документация, написанная в формате Doxygen с использованием `/**`, `//!` и т. д.);
- Поддержка правил форматирования кода, определенных в `.clang-format`;
- Статическая проверка или проверка ошибок в реальном времени без необходимости компиляции;
- Подсказки и автодополнение кода при вводе;
- Поиск мест использования, рефакторинг кода и т. д.

## Подготовка

Прежде всего, вам понадобится редактор с поддержкой LSP (Language Server Protocol), например, Visual Studio Code, а также установленный Clangd и соответствующие плагины. Если вам нужно установить Clangd вручную, вы можете скачать подходящую версию [LLVM](https://github.com/llvm/llvm-project/releases) или воспользоваться пакетным менеджером вашей операционной системы.

После установки необходимых плагинов Clangd может работать без какой-либо дополнительной настройки в простых хост-проектах, однако в сложных средах кросс-компиляции требуется дополнительная конфигурация.

## Настройка среды кросс-компиляции

### Параметры CMake

Если в качестве системы сборки вы используете CMake, необходимо включить опцию `CMAKE_EXPORT_COMPILE_COMMANDS`. Это можно сделать с помощью аргумента командной строки:
``` bash
cmake .. -DCMAKE_EXPORT_COMPILE_COMMANDS=ON # Аргумент командной строки на этапе конфигурации CMake
```
Если использовать аргументы командной строки неудобно, вы также можете определить эту переменную в любом файле `CMakeLists.txt`:
``` cmake
set(CMAKE_EXPORT_COMPILE_COMMANDS ON)
```
Затем при настройке или сборке проекта с помощью CMake в выходной каталоге будет создан файл `compile_commands.json`, который будет использоваться Clangd.

### Настройка Clangd

После настройки CMake и генерации `compile_commands.json` Clangd может работать частично, но вы, скорее всего, столкнетесь со следующими проблемами:
- Файл `compile_commands.json` находится глубоко в иерархии каталогов, и Clangd не может его найти;
- Clangd не может найти стандартные заголовочные файлы для среды кросс-компиляции, такие как `stdint.h` и т. д.

Чтобы решить эти проблемы, сначала создайте файл `.clangd` в корневом каталоге проекта (то есть в каталоге, открытом в редакторе, обычно там же, где находится папка `.git`). Это файл YAML, заполните его следующим содержимым:
``` yaml
CompileFlags:
  CompilationDatabase: "包含 compile_commands.json 的目录的相对路径"
  Add: 
    - -resource-dir=C:/gcc-arm-none-eabi-9-2020-q2/arm-none-eabi/include
    - -IC:/gcc-arm-none-eabi-9-2020-q2/arm-none-eabi/include
    - -IC:/gcc-arm-none-eabi-9-2020-q2/arm-none-eabi/include/c++/9.3.1
    - -IC:/gcc-arm-none-eabi-9-2020-q2/arm-none-eabi/include/c++/9.3.1/arm-none-eabi
    - -IC:/gcc-arm-none-eabi-9-2020-q2/lib/gcc/arm-none-eabi/9.3.1/include
  Remove:
    - -fno-reorder-functions
```
Пожалуйста, измените пути к файлам в соответствии с вашей реальной ситуацией. Затем добавьте следующий параметр командной строки в аргументы запуска Clangd:
``` bash
--query-driver=C:/gcc-arm-none-eabi-9-2020-q2/bin/arm-none-eabi-g++.exe # Путь указывается в зависимости от вашей реальной ситуации
```
После перезапуска языкового сервера Clangd должен заработать нормально.

В VS Code вы можете добавить параметры через `clangd.arguments` в файле `.vscode/settings.json` вашего проекта:
``` json
{
  "clangd.arguments": [
    "--query-driver=C:/gcc-arm-none-eabi-9-2020-q2/bin/arm-none-eabi-g++.exe"
  ]
}
```

<glyphix id="cookbook-blur-overlay" width="410" height="502" title="Размытый слой наложения" inline>

</glyphix>

Главная цель этого руководства — показать, как реализовать интерфейс с размытием с помощью Glyphix.

## Метод реализации

### Тень текста

Тень текста «Hokkaido sika deer» в примере может быть реализована путем наложения слоя размытого текста:
``` html
<stack class="wallpaper-title">
  <p class="shadow">Hokkaido sika deer</p>
  <p>Hokkaido sika deer</p>
</stack>
```
Поместите два одинаковых текста внутрь компонента [`stack`](/components/stack.md), используя нижний текст в качестве тени. Это достигается с помощью CSS-класса `shadow` для нижнего текста:
``` css
.shadow {
  color: #0008;
  /* Добавляем размытие к фоновому тексту для создания эффекта тени */
  filter: blur(8px);
  /* Необходимо использовать transparent, чтобы пометить элемент как прозрачный */
  transparent: true;
}
```
Установите цвет фонового текста полупрозрачным серым и примените компонент текста `<p>` в качестве тени с помощью свойства фильтра размытия ([`filter: blur(8px)`](/framework/generic/styles.md#filter)). Обратите внимание, что цвет текста на переднем плане не должен быть прозрачным, иначе он может смешаться со слоем `.shadow`.

### Пользовательский шрифт

Текст «Hokkaido sika deer» отображается с использованием пользовательского шрифта. В Glyphix вы можете подключать пользовательские шрифты тем же способом, что и в веб-разработке:
``` css
@font-face {
  font-family: 'Playwrite Australia SA';
  src: url('/assets/PlaywriteAUSA-Regular.ttf');
}

.wallpaper-title {
  font-family: 'Playwrite Australia SA', 'sans-serif';
  color: #ffffff;
  margin-top: 25%;
}
```
Как видите, вы можете объявить шрифт в CSS с помощью блока [`@font-face`](/framework/generic/styles.md#font-face-规则) и ссылаться на него в свойстве [`font-family`](/framework/generic/styles.md#font-family) элемента.

### Размытие фонового слоя

Поскольку страницы, вызываемые в настоящее время через [`router` API](/api/system-router.md), не поддерживают полупрозрачный фон, вы не можете использовать страницы для реализации всплывающего меню. Тем не менее, вы можете использовать этот прием для симуляции всплывающей «страницы»:
``` html
<stack class="window" :disabled="popups">
  <image class="wallpaper" src="/assets/images/sika-deer.jpg" />
  ...
</stack>
<div class="overlay" if="popups">
  ...
</div>
```
Вам нужно добавить в страницу два слоя элементов (в данном примере `stack.window` и `div.overlay`) и управлять ими с помощью условия (например, `popups`). В частности:
- `popups` управляет свойством `disabled` фонового элемента, поэтому, когда `popups` имеет значение true, фоновый элемент не реагирует на ввод жестов и т.д.;
- `popups` также управляет рендерингом верхнего элемента: когда оно истинно, верхний элемент отображается.

При появлении слоя наложения свойство [`disabled`](/framework/generic/properties.md#disabled) также предоставляет возможность размыть фоновый элемент:
``` css
.window:disabled {
  filter: blur(40px);
}
```
Когда для элемента установлено свойство `disabled`, также активируется псевдокласс `:disabled` фонового элемента, поэтому эффект размытия в CSS, описанный выше, будет работать.

::: tip
Поскольку Glyphix не поддерживает браузерное свойство [`backrop-filter`](https://developer.mozilla.org/docs/Web/CSS/backdrop-filter), вы не можете напрямую добиться размытия фона с помощью CSS-правил для `div.overlay`, а должны использовать технику из этого примера.
:::

## Риски для производительности

Поскольку эффект размытия требует больших вычислительных затрат, разработчикам следует уделять особое внимание нагрузке на производительность. Мы рекомендуем использовать эффекты размытия только в статичных интерфейсах и желательно добавлять свойство [`quiescent`](/framework/generic/properties.md#quiescent) к элементам, требующим размытия.

Если возможно, вам следует протестировать интерфейсы с размытием на физических устройствах, чтобы убедиться, что они соответствуют ожиданиям по производительности.
