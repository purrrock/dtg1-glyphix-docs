# 开发速览：从 Web 到 Glyphix

本文档专为熟悉 Web 前端（特别是 Vue.js）的开发者设计。我们将跳过基础语法教学，直接切入 Glyphix 框架的核心机制，帮助你快速建立正确的心智模型。

## 核心概念与运行环境

Glyphix 是一个运行在 MCU（微控制器）设备上的应用框架。虽然它使用 HTML/CSS/JS 进行开发，但它**不是**一个浏览器。本框架用于开发完整应用，而不是可刷新的页面，每个应用运行在独立的沙箱容器中。

你需要理解以下几个核心差异：
- **无 DOM**：底层由 C++ 原生引擎直接渲染，不存在 DOM 树。
- **无 Web API**：不支持 `window`、`document`、`localStorage` 等浏览器 API。系统能力（网络、存储、传感器）通过 `@system.*` 模块提供。
- **JS 引擎**：使用轻量级 JS 引擎（支持 ES6 标准），但内存极其受限。

### 资源限制

资源限制是与 Web 开发最大的不同点。MCU 设备的 RAM 通常仅有几 MB。这意味着不要使用网络请求加载超大 JSON 数据，或者直接 [`fetch`](../api/system-fetch.md) 一张图片。请牢记以下几点：
- 可以使用 [`@system.request`](../api/system-request.md) 模块将资源下载为文件，`fetch` 则会将响应加载到内存中。
- 图片资源通常存放在应用包内，尺寸尽可能与屏幕分辨率匹配。
- **后台冻结**：应用进入后台（`onHide`）后，通常会在几十秒内被系统挂起或销毁。请注意保存状态。

### 设备形态

Glyphix 应用通常运行在智能手表等小屏设备上。手表的屏幕尺寸通常为 1.5 到 2 英寸左右，典型分辨率为 466×466 像素，但存在圆形、矩形屏幕。低端设备的像素密度可能更低，但尺寸基本相似。这类设备常用触摸屏进行交互，可能支持物理按键或者旋钮，系统透明地处理了大部分交互细节。

通常使用模拟器进行开发和调试，因为真机部署和调试流程还比较碎片化，耗时较长。

### 典型项目结构

这是我们推荐的项目文件结构，这也是快应用标准的结构：
```bash
src/
├─ manifest.json  # 应用清单：配置权限、注册页面路由
├─ app.js         # 应用入口：全局生命周期 (onCreate, onDestroy)
├─ pages/         # 页面目录
│  └─ Main/
│     └─ index.ux # 页面组件
└─ assets/        # 公共资源
  └─ icon.png
```
你可以根据需要引入 [Node.js](nodejs.md) 工具链来管理依赖。也可以按照需要调整目录结构，但 [`src/manifest.json`](/framework/application/manifest.md) 和 `src/app.js` 必须固定在此位置。

## UI 开发

Glyphix 采用 [`.ux`](../framework/component/README.md) 单文件组件（类似 Vue SFC），风格接近 Vue Options API，但也有显著差异。

### Flexbox 布局优先

Web 默认是流式布局（Flow Layout），而 Glyphix 的页面默认为堆叠布局：如果你在页面中放两个 `div`，它们会**重叠**在一起，而不是上下排列。这是因为本框架支持在 `<template>` 中使用多个根节点，例如：
```html
<template>
  <image class="background" src="/assets/bg.png" />
  <div class="content"> ... </div>
</template>
```
默认的堆叠布局对于这种场景通常非常合适。

尽管 `div` 等容器默认使用流式布局，但推荐使用 Flexbox 来进行布局控制。绝大多数容器都应该显式声明 `display: flex`，再结合 `flex-direction` 控制子元素排列方式。

考虑到设备屏幕尺寸差异较大，请特别注意长度单位的使用：
- 在较小的尺寸中使用 `px` 单位，它是逻辑像素，会根据屏幕密度自动缩放。
- 字体应总是使用 `rem` 单位，它由设备厂商定义基准，更符合系统 UX 规范的一致性要求。
- 可以使用百分比（`%`）单位来实现响应式布局，但是目前限制和缺陷较多，请注意调试。

由于屏幕太小，你可能特别需要 [`scroll`](../components/scroll.md) 组件来实现滚动区域。和 Web 不同，`div` 容器本身不支持滚动，也无法使用 `overflow` 属性来控制。

### 模板语法差异

虽然长得像 Vue 模板，但请注意以下区别：
- 指令无 `v-` 前缀：如 `<div if="show">` 或 `<div for="item in items">`
- 事件绑定用 `on`、`@` 均可，如：`<p on:click="handler">`
- 必须使用 `<p>` 等文本组件：`<text>Hello</text>` 可以正常显示，但是 `<div>Hello</div>` 不会渲染任何内容。
- 支持用 `model:prop="state"` 或 `::prop="state"` [双向绑定](../framework/commands/model.md)任意组件属性，只要有和属性同名的事件触发即可。

### 样式限制

CSS 支持是子集：
- 支持类 (`.class`)、ID (`#id`)、标签 (`div`) 和后代 (`.a .b`)。**不支持** `~`、`+`、`>` 等复杂关系选择器。
- **效果限制**：不支持渐变、阴影等效果。暂不支持 `transition` 动画。
- **性能限制**：避免使用 `transform` 来移动或对齐元素。`object-fit` 默认为 `none` 并推荐保持默认。
- 目前不支持动态 `class` 绑定，也不支持 CSS 变量。

## 组件与逻辑

### 脚本模型

组件脚本非常接近 Vue Options API，以下示范指出了主要差异：
```js
export default {
  // 数据模型 (Data)，不需要声明属性，data 属性自动导出为属性
  data: {
    count: 0, // 修改 this.count 会自动触发视图更新
  },
  timer: null, // 非响应式字段直接定义在组件实例上，也可以不声明
  // 生命周期
  onInit() {}, // 数据已初始化，可发起网络请求
  onReady() {}, // 界面已渲染完成
  onDestroy() {}, // 务必在此清理定时器、订阅事件

  // 方法 (Methods)，直接定义在组件对象中
  handleTap() {
    this.count++
    // 触发自定义事件给父组件
    this.$emit('change', { value: this.count })
  }
}
```
其中 `data` 对象中的字段为响应式属性，它目前只支持 JSON 兼容的类型（不支持 `Date`、`Map`、`Set` 等）。如果不需要响应式更新，推荐将字段定义在组件实例（`this`）上。

::: tip
不要使用 `methods` 对象包裹方法，直接定义在组件对象中即可。也不需要使用 `props` 定义属性，`data` 对象中的字段会自动导出为属性。

也不能用 `document.getElementById` 等 DOM API 查找元素。可以使用 [`this.$element()`](../framework/component/component-apis.md#element) 方法获取指定 ID 的元素实例。
:::

### 页面与路由

Glyphix 应用由多个页面组成，页面间通过路由导航。所有页面均需在 `manifest.json` 中的 [`router.pages`](../framework/application/manifest.md#pages) 字段中静态注册。页面组件与普通组件类似，但支持 `onShow` 和 `onHide` 生命周期钩子。

使用 `system.router` 系统模块进行跳转：
```js
import router from '@system.router'

// 跳转并传递参数
router.push({ uri: 'pages/Detail', params: { id: 123 } })
```
::: tip
不要使用其他的路由库，也不要假装在开发单页面应用（SPA）。否则将无法利用转场动效、页面栈管理等现有功能。
:::

### TypeScript 支持

如果使用 Node.js 脚手架创建项目，使用 npm、pnpm 等安装 `glyphix` 和 `typescript` 等依赖后，可以在项目中使用 TypeScript 进行开发。

对于 `.ux` 单文件组件，可以在 `<script>` 标签上添加 `lang="ts"` 属性启用 TypeScript 支持。例如：
```html
<script lang="ts">
import { defineComponent } from 'glyphix'

export default defineComponent({
  data() {
    count: 0: number
  },
  increment() { this.count++ },
})
</script>
```

## 系统能力集成

不要尝试使用浏览器 API，请使用 Glyphix [标准库](../api/README.md)。

### 常用模块速查

| 功能 | Glyphix 模块 | 说明 |
| :--- | :--- | :--- |
| **网络** | [`@system.fetch`](../api/system-fetch.md) | 必须处理异步回调或 Promise |
| **弹窗** | [`@system.prompt`](../api/system-prompt.md) | 提供 Toast 和 Dialog |
| **存储** | [`@system.storage`](../api/system-storage.md) | 同步本地存储，直接读写对象而非字符串 |
| **路由** | [`@system.router`](../api/system-router.md) | 管理页面栈 |
| **日志** | `console.log` | 输出到调试终端，和浏览器一样 |

### 异步编程模式

系统 API 通常支持异步回调和 Promise 两种风格。推荐使用 `async/await` 以保持代码整洁。

```js
import fetch from '@system.fetch'
import prompt from '@system.prompt'

export default {
  onReady() { this.loadData() },
  async loadData() {
    try {
      const response = await fetch.fetch({
        url: 'https://api.example.com/data',
        method: 'GET', // 默认为 GET
        responseType: 'json', // 这样不需要 JSON.parse 手动解析
      })

      if (response.data.code === 200)
        this.data = response.data.data
    } catch (err) {
      prompt.showToast({ message: 'Network Error' })
    }
  }
}
```

# Быстрый старт

В этой главе мы расскажем, как использовать Glyphix.js для создания простого приложения. Мы начнем с установки инструментов сборки, затем создадим проект и запустим симулятор, чтобы посмотреть результат. В завершение мы кратко рассмотрим структуру проекта и основные файлы. В данном руководстве не рассматривается запуск и публикация приложения на реальном устройстве.

## Подготовка к работе

Прежде чем начать, обратитесь к [этой документации](/tutorials/glyphix.js/README.md#npm-安装) для установки инструмента сборки Glyphix. Если говорить кратко, вы можете использовать [npm](https://nodejs.org) для установки пакета `glyphix-cli`:
```bash
npm install -g glyphix-cli
```

Поскольку инструменты разработки Glyphix преимущественно работают через командную строку, рекомендуется установить современную оболочку, такую как Zsh или PowerShell 7+, а также полезные плагины для повышения эффективности работы.

### Инструменты терминала

Пользователям Linux или macOS рекомендуется установить [Oh My Zsh](https://ohmyz.sh/). Пользователям Windows рекомендуется установить [Windows Terminal](https://aka.ms/terminal) и использовать [Oh My Posh](https://ohmyposh.dev/). Также обратитесь к документации [`gx completion`](/tutorials/glyphix.js/README.md#gx-completion) для установки скрипта автодополнения команды `gx`.

Для разработки приложений на Glyphix вы можете использовать любой редактор, например [VS Code](https://code.visualstudio.com/) или [IDE быстрых приложений (QuickApp IDE)](https://www.quickapp.cn/devtool).

::: tip
В IDE быстрых приложений не встроен инструмент сборки glyphix.js, поэтому вам все равно потребуется установить `glyphix-cli` и использовать команду `gx` в терминале для сборки и запуска проекта. При использовании таких редакторов, как VS Code, рекомендуется связать файлы с расширением `*.ux` с форматом `html`, чтобы получить базовую подсветку синтаксиса.
:::

### Использование Node.js

Если вы решили использовать npm-пакеты в своем проекте или любые ресурсы веб-экосистемы разработки, обратитесь к документации по настройке [Node.js](/tutorials/nodejs.md). Использование Node.js не является обязательным, но оно обеспечивает поддержку современных инструментов разработки, таких как TypeScript.

### Использование инструментов сборки

Когда все будет готово, введите в терминале команду `gx list device`. Если вы получите вывод, похожий на следующий, это означает, что установка прошла успешно:
``` bash
$ gx list device
  default
  ...
```

Затем создайте проект приложения и запустите его в симуляторе! Просто используйте следующие команды:
``` bash
gx new myapp # Создает проект с именем myapp, при этом будет создана директория с именем myapp
cd myapp     # Переходит в директорию myapp
gx emu       # Запускает симулятор
```
Если все прошло успешно, вы увидите окно с надписью «Hello World!». В последующих руководствах будет более подробно рассказано об использовании команд инструмента glyphix.js.

::: tip
Обратитесь к документации [`gx build`](/tutorials/glyphix.js/README.md#gx-build) и [`gx emu`](glyphix.js/emulator.html) для получения дополнительной информации о сборке и запуске симулятора.
:::

## Структура проекта

Вы можете использовать файловый менеджер для просмотра структуры директории `myapp`. В текущей версии она выглядит следующим образом:
``` bash
<app-name>
├─ README.md         # Файл с описанием проекта (README)
└─ src               # Директория с исходным кодом проекта
    ├─ app.js        # Корневой скрипт приложения
    ├─ manifest.json # Конфигурация базовой информации о приложении
    ├─ assets        # Хранилище общих ресурсов (шрифты, изображения и т.д.)
    │  ├─ fonts      # Хранилище шрифтов
    │  └─ images     # Хранилище изображений
    └─ main          # Директория главной страницы
        └─ index.ux  # Файл описания интерфейса главной страницы
```

В шаблоне проекта по умолчанию исходный код находится в директории `<app-name>/src`. Документация и другие ресурсы проекта, не требующие упаковки, могут размещаться в других директориях.

Мы рекомендуем выделять отдельную директорию для каждой страницы (использовать имя страницы в качестве названия директории) и размещать ее в корне директории исходного кода. Исходные файлы компонентов, используемых только на определенной странице (файлы `*.ux`), должны находиться в директории этой страницы, в то время как общие файлы могут размещаться по следующим правилам:
- Общие UX-файлы и скрипты могут размещаться в директории `common`.
- Файлы скриптов, ссылающиеся только на конкретную страницу, хранятся непосредственно в директории этой страницы.
- Файлы шрифтов хранятся в директории `assets/fonts`.
- Файлы изображений хранятся в директории `assets/images`.
- Другие ресурсы могут размещаться в соответствующих поддиректориях директории `assets`.

### Файлы проекта

Теперь вы видите, что в `myapp` есть несколько файлов. Обратите внимание на файлы с расширением `*.ux` и файл `manifest.json` — это файлы, с которыми чаще всего приходится работать во время разработки. В следующем руководстве приводится их краткий обзор.

## Файл `manifest.json`

Файл `manifest.json` является конфигурационным файлом приложения и используется при его сборке. Он содержит основную информацию о приложении, такую как название и версия, а также описание всех страниц приложения и информацию о маршрутизации (роутинге). Иными словами, чтобы добавить описание страницы в коде, его необходимо предварительно прописать в `manifest.json`, иначе переход на эту страницу будет невозможен.

Вот содержимое файла `manifest.json` для шаблонного приложения, сгенерированного командой `gx`:
``` json
{
  "package": "com.example.app",
  "name": "Example App",
  "versionName": "1.0.0",
  "versionCode": 1,
  "features": [],
  "router": { // Информация о маршрутизации страниц
    "entry": "main", // Начальная страница приложения
    "pages": { // Описание страниц
      "main": {
        "component": "index"
      }
    }
  }
}
```

::: warning
В учебных целях в данном фрагменте кода `manifest.json` присутствуют комментарии, однако формат JSON не поддерживает комментарии. Пожалуйста, не добавляйте комментарии в файл `manifest.json` вашего проекта.
:::

### Заполнение информации о приложении

Вы можете указать информацию о своем приложении в файле `manifest.json`.

### Добавление описания страниц

В корневых полях файла `manifest.json` поля `router` и `pages` связаны с описанием страниц. Поле `router` представляет собой таблицу маршрутизации страниц приложения и должно содержать как минимум поле `entry`, определяющее начальную страницу приложения (обычно в качестве начальной используется страница `main`).

Если вы хотите добавить новую страницу, вам нужно внести изменения в поле `pages`. Например, если мы хотим создать новую страницу с именем `NewPage`, а ее корневым компонентом является `NewPage/index.ux`, то поле `pages` будет выглядеть следующим образом:
``` json
"pages": {
  "main": {
    "component": "index"
  },
  "NewPage": { // Это новодобавленная страница
    "component": "index"
  }
}
```
Поле `pages` представляет собой объект JSON, где каждый ключ является именем страницы (по умолчанию оно также совпадает с путем к директории страницы). Значением ключа также является объект, содержащий поле `component` — имя корневого компонента страницы, который должен находиться в директории данной страницы. Поле `component` задает имя файла корневого компонента страницы (без расширения). Все имена чувствительны к регистру.

При добавлении или удалении страниц не забывайте обновлять соответствующие поля в файле `manifest.json`.

Подробное описание структуры файла `manifest.json` см. в соответствующей документации.

## Знакомство с UX-файлами

UX (UI XML) — это файл описания интерфейса в Glyphix. На примере исходного шаблонного проекта содержимое файла `main/index.ux` выглядит следующим образом:
``` html
<template>
  <p>{{text}}</p>
</template>

<style>
  * {
    text-align: center;
  }
</style>

<script>
  export default {
    data: {
      text: "Hello, World!"
    }
  }
</script>
```

UX-файл по сути является XML-файлом и содержит три корневых узла: `<template>`, `<style>` и `<script>`. Узел `<template>` описывает структуру интерфейса, в узле `<style>` определены таблицы стилей, а узел `<script>` содержит JavaScript-скрипты, реализующие логику взаимодействия компонента.

::: tip
VS Code не подсвечивает синтаксис UX-файлов по умолчанию. Вы можете переключить язык в правом нижнем углу на «HTML», чтобы получить хорошую подсветку.
:::

### Введение в компоненты

Объект, соответствующий UX-файлу во время выполнения, называется **компонентом**. Компоненты являются важнейшей концепцией в фреймворке приложений Glyphix JavaScript. Каждый компонент представляет собой элемент интерфейса и обладает следующими характеристиками:
- Компонент имеет собственное визуальное представление.
- Некоторые компоненты могут реагировать на ввод пользователя.
- Некоторые компоненты могут отображать результаты в зависимости от данных и состояния.
- Компоненты могут встраиваться в другие компоненты.

Распространенные элементы интерфейса в фреймворке Glyphix JavaScript являются компонентами, например:
- Текст: используется для отображения текстовой информации.
- Кнопка: кнопка также может отображать текст, но самое главное — она может реагировать на события нажатия (и, конечно же, визуально отображать момент нажатия).
- Список: список вмещает в себя другие компоненты и располагает их вертикально; кроме того, элементы списка можно перемещать с помощью жестов прокрутки.

Компоненты, способные содержать в себе другие компоненты (как, например, списки), также называются **компонентами-контейнерами**.

Как нетрудно догадаться, компонент состоит из двух основных элементов: внешнего вида и логики поведения. Тег `<template>` в UX-файле определяет внешний вид компонента. На примере `main/index.ux`:
``` html
<template>
  <p>{{text}}</p>
</template>
```
Компонент `main/index.ux` отображает контент с помощью компонента `<p>`, который используется для вывода текста. Значение выражения `{{text}}` определяет текст, который будет выведен на экран.

JavaScript-скрипт внутри тега `<script>` реализует логику поведения компонента. Этот тег всегда экспортирует **объект компонента** с помощью ключевых слов `export default`. В первую очередь следует обратить внимание на свойство `data` объекта компонента, которое обычно представляет собой объект:
``` js
export default {
  data: {
    text: 'Hello, World!'
  }
}
```
Здесь у объекта `data` есть свойство `text`, значение которого будет использоваться в качестве отображаемого содержимого упомянутого выше компонента `<text>` (в оригинале `<p>`).

### Модель компонентов и обновление состояния

Допустим, нам нужно спроектировать следующий компонент: при нажатии на компонент он должен менять отображаемый текст. В этом случае нам нужно прослушивать событие ввода на компоненте и обновлять отображаемый контент. Следующий код прослушивает событие нажатия на компоненте `<p>`:
``` html
<template>
  <p on:click="text += '!'">{{text}}</p>
</template>
```
Выражение в атрибуте `on:click` выполняется при нажатии на текст. В результате при каждом нажатии к тексту `text`, отображаемому в компоненте `<p>`, будет добавляться символ `'!'`:

<glyphix id="getting-started-click-p" height="120" width="360" title="Событие нажатия">

``` html
<p on:click="text += '!'">{{text}}</p>
```

``` js

  data: {
    text: "Hello, World!"
  }
}
```

``` css
p {
  font-size: 32px;
  text-align: center;
}
```

</glyphix>

## Использование TypeScript

Фреймворк Glyphix обеспечивает экспериментальную поддержку TypeScript, позволяя вам использовать преимущества типобезопасности и современного синтаксиса JavaScript при разработке приложений.

### Пример базового компонента

Ниже приведен пример компонента, написанного на TypeScript:

```html
<template>
  <p on:click="onClick">{{count}}</p>
</template>

<script lang="ts">
import { defineComponent } from "glyphix"

export default defineComponent({
  data: {
    count: 0
  },
  onClick() {
    this.count++
  }
})
</script>
```

По сравнению со скриптом компонента JavaScript по умолчанию, использование TypeScript требует следующих изменений:
1. В теге `<script>` используется `lang="ts"` для указания языка TypeScript.
2. Функция `defineComponent` импортируется из модуля `glyphix`.
3. Экспортируемый объект компонента должен передаваться в качестве параметра в `defineComponent`, при этом экспортируется результат выполнения этой функции.

После внедрения TypeScript функция `defineComponent` сделает подсказки кода и проверку типов в IDE более точными.

### `app.ts`

Просто переименуйте `app.js` в `app.ts`, чтобы переключиться на использование TypeScript в качестве входного файла приложения, и инструмент сборки обработает его автоматически.

## Что такое Glyphix

Glyphix — это эффективный и легковесный фреймворк для разработки приложений, ориентированный на MCU (микроконтроллеры) устройства. Он предоставляет разработчикам парадигму декларативной разработки пользовательского интерфейса, похожую на веб-экосистему: с помощью HTML-шаблонов, CSS и JavaScript разработчики могут легко создавать страницы и компоненты, а также публиковать приложения на различных умных устройствах (например, умных часах).  

Для получения дополнительной информации обратитесь к разделу [Фреймворк](/framework/README.md).

### Веб-подобный фреймворк

В отличие от традиционной разработки прошивок для MCU, Glyphix ближе к фреймворкам на основе веб-стека технологий. Разработчикам приложений необходимо быть знакомыми с JavaScript, CSS и основами HTML. Вам не нужно осваивать полный стек веб-разработки, такой как DOM браузера, стандартные HTML-теги и сложные цепочки инструментов сборки. Однако, если вы знакомы с веб-фреймворками пользовательского интерфейса, такими как [Vue.js](https://vuejs.org/) ([Options API](https://vuejs.org/guide/introduction#options-api)), вам будет очень легко освоить Glyphix.

::: tip
Стоит отметить, что Glyphix не является платформой «low-code» («малокодовой»). В процессе разработки вы всё равно столкнетесь с такими задачами, как логическая абстракция, организация интерфейса, пользовательский опыт и компромиссы в производительности. Поэтому прочная база JavaScript и правильное фронтенд-мышление помогут вам в полной мере раскрыть потенциал Glyphix.
:::

### Декларативный UI-фреймворк

Традиционная разработка интерфейсов обычно носит императивный характер: необходимо пошагово вызывать функции для создания элементов управления, обновления состояния и перерисовки интерфейса. Такой подход очень гибкий, но бизнес-логика и логика интерфейса в нем сильно связаны, и по мере роста масштаба приложения код быстро становится сложным и трудно поддерживаемым. Появление таких паттернов, как MVC и MVVM, было направлено именно на решение этой сложности.  

Glyphix же использует парадигму декларативного пользовательского интерфейса. Разработчику достаточно описать, «как должен выглядеть интерфейс», а фреймворк автоматически выполнит рендеринг и обновление на основе изменений данных и состояния. Такой подход значительно снижает сложность логики интерфейса и управления состоянием, а также позволяет разработчикам сосредоточиться на функционале и проектировании взаимодействия, вместо поддержания иерархии UI и процесса обновления.

### Контейнер приложений

Glyphix — это не просто UI-фреймворк, он также предоставляет такие функции, как управление жизненным циклом приложения, изоляция прав и системные API. Приложения работают в независимых изолированных контейнерах, что обеспечивает стабильность и безопасность системы.

Пожалуйста, прочитайте руководство [Быстрый старт](getting-started.md), чтобы сразу приступить к разработке приложений на Glyphix.

## Другие вопросы

### Нужно ли быть знакомым с MCU и встраиваемой разработкой?

Разработчикам приложений обычно не нужно понимать специфические знания о MCU и встраиваемой разработке. Тем не менее, следует иметь некоторое представление об ограничениях ресурсов устройства. Например, объем памяти MCU обычно составляет всего несколько мегабайт, и память для выполнения кода JavaScript также ограничена. Это означает, что могут возникнуть ситуации, когда невозможно запросить очень большой JSON из сети или закодировать целое изображение в Base64 и получить его через GET-запрос.

Эти ограничения, совершенно отличные от веб-разработки, действительно обусловлены ограниченными ресурсами устройств MCU, но они также не входят в типичную систему знаний по MCU.

Интуитивно понятный способ убедиться в достаточно хорошем качестве работы приложения — запустить его на реальном устройстве. Вы можете использовать реальное устройство на разных этапах разработки несколько раз, чтобы убедиться в качестве работы.

### Нужно ли использовать C/C++ для разработки приложений?

Разработка приложений на Glyphix полностью использует HTML, CSS и JavaScript, поэтому использование языка C/C++ не требуется.

### Как разработчикам встраиваемых систем приступить к разработке приложений на Glyphix?

Разработчики встраиваемых систем могут следовать разделу [Быстрый старт](getting-started.md) данного учебника, чтобы постепенно понять основные концепции Glyphix. Фреймворк использует механизмы компонентизации и привязки данных, похожие на Vue Options API, что может несколько отличаться для читателей, привыкших к императивным GUI вроде [LVGL](https://lvgl.io/) или Qt widgets, однако декларативный дизайн Glyphix также обеспечивает более интуитивное управление интерфейсом.

Разработчикам не обязательно полностью осваивать HTML, CSS и JavaScript, однако знакомство с базовым синтаксисом JavaScript (таким как переменные, условные операторы, вызовы функций) поможет понять логику рендеринга и обработку событий в Glyphix. Вы можете ознакомиться с этими материалами и ускорить процесс разработки с помощью примеров кода и практических задач в учебниках и документации.

### Стоит ли уделять внимание оптимизации производительности приложения?

Наш фреймворк был глубоко оптимизирован с учетом ограничений ресурсов встраиваемых систем, что позволяет ему хорошо адаптироваться к различным аппаратным средам. Большинство приложений могут достичь достаточно плавной и стабильной работы при настройках по умолчанию, поэтому обычно не требуется тратить дополнительное время на оптимизацию производительности.

Если в будущем возникнет необходимость глубоко изучить конкретные сценарии оптимизации, мы предоставим специализированную документацию по производительности, которая поможет разработчикам еще больше повысить эффективность работы приложений.

### Есть ли разница между средой Glyphix и браузером?

Да, среда Glyphix имеет существенные отличия от браузера. В Glyphix нет структуры DOM, как в браузере, и она не предоставляет такие объекты, как `window` или `document`. Вместо этого она напрямую и исключительно предоставляет набор декларативных интерфейсов, с помощью которых разработчики могут осуществлять разработку компонентов и взаимодействие с интерфейсом. Такой дизайн упрощает процесс разработки и лучше подходит для встраиваемых сред.

# Спецификация именования компонентов

В этом документе описываются обязательные правила именования и рекомендуемые стили для структуры компонентов. Обязательные правила должны строго соблюдаться, так как их нарушение может привести к непредвиденному поведению. Использование рекомендуемых правил именования обеспечивает максимальную совместимость.

## Правила именования шаблонов

Имена тегов в шаблонах должны быть записаны в стиле kebab-case (через дефис) или PascalCase (пар-камерный регистр):
``` html
<Button></Button>
<button></button>
<scroll-area></scroll-area>
<ScrollArea></ScrollArea>
```

Имена атрибутов должны быть в стиле kebab-case или camelCase (верблюжий регистр):
``` html
<component prop-name="expr"></component>
<component propName="expr"></component>
```

Рекомендуется повсеместно использовать стиль kebab-case, соответствующий стандартам Web.

## Правила именования в коде JavaScript


Имена компонентов в коде JavaScript должны быть в стиле PascalCase, а в шаблонах для них используется соответствующий стиль kebab-case.

Имена свойств компонентов в коде JavaScript должны быть в стиле camelCase:
``` js
export default {
  data: {
    propName: 0 // В шаблоне имя свойства будет prop-name
  }
}
```
Эти имена свойств автоматически преобразуются в соответствующие имена kebab-case при использовании в коде шаблона.

## Правила именования файлов

UX-файлы должны называться так же, как и сам компонент, то есть в стиле PascalCase. В теге `<import>` атрибут `src` должен быть чувствительным к регистру URL-адресом файла, а для атрибута `name` следует использовать стиль PascalCase или kebab-case:
``` html
<import src="path/to/UxFile" name="UxFile"/>
<import src="path/to/UxFile" name="ux-file"/>
```
Фактически, требования к именованию атрибута `name` совпадают с требованиями к именам тегов в шаблонах.

# Основы компонентов

В предыдущем документе «[Быстрый старт](getting-started)» было кратко представлено понятие компонентов. Данное руководство познакомит вас с компонентами более подробно. Прежде чем приступить к чтению этого документа, вам необходимо знать, как создавать и собирать проекты, а если вы не умеете редактировать исходные файлы, пожалуйста, прочитайте руководство «[Быстрый старт](getting-started)».

## Введение

В разработке приложений Glyphix все интерфейсы представляют собой компоненты — от маленькой кнопки до целой страницы. Технология компонентов позволяет разрабатывать интерфейсы с использованием простого языка шаблонов:
``` html
<!-- main/index.ux -->
<template>
  <p>{{text}}</p>
</template>

<style>
  * {
    text-align: center;
  }
</style>

<script>
  export default {
    data: {
      text: "Hello, World!"
    }
  }
</script>
```
По сути, это файл `main/index.ux` шаблона проекта по умолчанию. Вы можете использовать команду `gx emu`, чтобы посмотреть результат отображения. Содержимое тега `<template>` является шаблоном компонента, который описывает его внешний вид. Здесь узел `<p>` будет отображать свойство `text` из объекта модели компонента. Обратите внимание, что внутренний фреймворк компонентов связывает содержимое узла `<p>` со свойством `text` модели компонента: при изменении значения свойства `text` интерфейс обновляется синхронно.

Мы можем протестировать это с помощью таймера:
``` js
export default {
  data: { text: "begin!" },
  onInit() {
    let count = 0
    setInterval(() => this.text = "timeout: " + count++, 1000)
  }
}
```
Теперь вы увидите, что отображаемое значение счетчика увеличивается на 1 каждую секунду.

## Программная модель компонентов

Важной функцией GUI-программ является изменение своего внешнего вида в зависимости от данных и пользовательского ввода для обеспечения интерактивности. В традиционном GUI-программировании и нативном HTML разработчикам приходится находить целевой элемент узла в дереве интерфейса, а затем вызывать API для его обновления. Как показывает практика, разработка интерфейсов таким способом весьма сложна, поэтому появились шаблоны проектирования для GUI, такие как MVC, MVP, MVVM, а в сфере веб-разработки возникли новые фреймворки — все эти технологии значительно снизили сложность разработки интерфейсов.

Программная модель компонентов Glyphix очень похожа на фронтенд-фреймворки вроде Vue. Основная идея этих фреймворков заключается в вычислении нового интерфейса на основе состояния модели интерфейса, а не в требовании обновлять элементы интерфейса при изменении состояния. По сравнению с традиционными технологиями, часть представления интерфейса в таком решении является бессостейтной (stateless) и, следовательно, более простой. Давайте продолжим использовать предыдущий пример для пояснения:
``` html
<template>
  <p>{{ text }}</p>
</template>
```
Как мы уже знаем, при обновлении свойства `text` модели компонента интерфейс обновляется автоматически. Однако в традиционных GUI-фреймворках часто требуется вручную обновлять узел `<p>` после обновления `text` в модели (что обычно происходит из-за пользовательского ввода или изменения внутренних данных). Такие фреймворки, как MVC, могут упростить эти операции, но не делают их предельно лаконичными.

Теперь рассмотрим очень простой подход: мы пишем функцию `render()`, которая генерирует дерево интерфейса на основе текущего состояния модели. Если бы мы заменяли исходное дерево интерфейса значением функции `render()` на каждом кадре, то любые изменения модели отражались бы в интерфейсе. Этот подход очень прост, но вы бы отвергли его из-за эффективности. На самом деле, традиционная модель программирования GUI родилась именно для решения проблем эффективности этого подхода: изменяются только те элементы в интерфейсе, которые действительно претерпели изменения. Однако это вводит состояние на уровне представлений (View) и порождает немалую сложность.

Фреймворк компонентов Glyphix основан на этой простой идее: содержимое внутри тега `<template>` выполняет функцию `render()`, в то время как код на JS сосредоточен на поддержке модели, а изменения данных модели автоматически отображаются в соответствующем интерфейсе. Вы можете считать, что фреймворк компонентов Glyphix всегда вычисляет новый интерфейс на основе состояния модели, поэтому нам не нужно вручную обновлять элементы интерфейса.

::: tip
Под капотом Glyphix нет дерева DOM, и, соответственно, нет API для манипулирования элементами DOM. Фактически, именно фреймворк компонентов представляет собой нативный JavaScript API Glyphix.
:::

## Реакция на пользовательский ввод

Некоторые компоненты могут реагировать на события ввода пользователя. В этом случае вы можете использовать директиву `on` для указания прослушивателя событий. Например, прослушивание события клика по текстовому компоненту:
``` html
<template>
  <p on:click="text += ' click'">{{text}}</p>
</template>

<style>
  * {
    text-align: center;
  }
</style>

<script>
  export default {
    data: {
      text: "Text "
    }
  }
</script>
```
Клик по тексту автоматически обновит отображаемое содержимое. Значение свойства `on:click` — `text += ' click'` — является JavaScript-выражением, и Glyphix автоматически привяжет `this` переменных в выражении к объекту компонента.

## Условный рендеринг

Директива `if` используется для условного рендеринга содержимого компонента. Область содержимого, управляемая этой директивой, будет отображаться только тогда, когда значение выражения в директиве `if` истинно (true).
``` html
<p if="display">Hello World</p>
```

Следующий пример реализует эффект взаимоисключающего переключения: при последовательных кликах интерфейс будет поочередно отображать текст "Component A" или "Component B".
``` html
<template>
  <p if="display" on:click="display = false">Component A</p>
  <p if="!display" on:click="display = true">Component B</p>
</template>

<style>
  * {
    font-size: 48;
    text-align: center;
  }
</style>

<script>
  export default {
    data: {
      display: true
    }
  }
</script>
```

## Рендеринг списков

Используйте директиву `for` для многократного рендеринга компонента с целью создания списка. Базовое использование директивы `for`:
``` html
<p for="(index, value) in list">{{index}}: {{value}}</p>
```
Где `list` — это свойство списка в модели компонента (обязательно должно быть типа `Array`), а `index` и `value` — две переменные итерации. Значение `index` представляет собой индекс текущего элемента, а `value` — значение текущего элемента.

Директива `for` может быть записана в нескольких сокращенных формах:
``` html
<p for="list">{{$idx}}: {{$item}}</p>
<p for="value in list">{{$idx}}: {{value}}</p>
<p for="index, value in list">{{$idx}}: {{value}}</p>
```
Первая сокращенная форма представляет собой только выражение для итерации, при этом в качестве имен переменных итерации по умолчанию используются `$idx` и `$item`; во второй форме явно определяется переменная итерации для значения, в то время как для индекса используется имя по умолчанию `$idx`; третья форма является стандартной записью с опущенными круглыми скобками.

::: tip
Из-за особенностей областей видимости (scope), переменные итерации, используемые в директиве `for`, будут эффективны только при их использовании после самой директивы `for`.
:::

``` html
<!-- correct -->
<button for="list" text="{{$item}}"/>
<!-- error -->
<button text="{{$item}}" for="list"/>
```

### Одновременное использование директив `if` и `for`

Вы можете одновременно использовать директивы `if` и `for` на одном элементе, причем директива `if` имеет более высокий приоритет. В этом примере, когда свойство `display` ложно, весь список компонентов `button` не будет отрендерен:
```html
<button for="value in items" if="display">Hello {{value}}</button>
<p if="!display">Paragraph 1</p>
```

Если ваша цель состоит в том, чтобы условно рендерить определенные узлы в списке, созданном директивой `for`, вам нужно поместить директиву `if` на внутренний элемент директивы `for`.
```html
<button for="value in items">
  <p if="display">item: {{value}}</p>
</button>
```

::: tip
Не рекомендуется использовать директивы `if` и `for` на одном и том же элементе, так как это снижает читаемость кода.
:::

## Слоты (Slot)

Подобно распространению контента в других фреймворках, в Glyphix также реализован API распределения контента. Мы можем использовать компонент `slot` в качестве точки выхода для распределяемого контента.

В дочернем компоненте используйте компонент `slot` для размещения содержимого, определенного в родительском компоненте. При рендеринге компонент `slot` заменяется элементами, переданными родительским компонентом.

```html
<div>
  <slot/>
</div>
```

## Комбинирование компонентов

Комбинация нескольких компонентов в более крупные интерфейсы — это способ построения интерфейсов во фреймворке компонентов Glyphix. Если у вас есть компонент с именем `Menu`, вы можете импортировать его, используя тег `<import>` в корневом узле UX-файла, где он необходим:
``` html
<import src="path/to/Menu" name="Menu"/>
```
Свойство `src` — это путь к компоненту, пожалуйста, не добавляйте суффикс `.ux`. Свойство `name` является необязательным именем компонента. Если это свойство не указано, в качестве имени компонента будет использоваться имя его файла.

Используйте тег `<import>` несколько раз для импорта всех зависимых компонентов:
``` html
<import src="path/to/ComA"/>
<import src="path/to/ComB"/>
<import src="path/to/ComC"/>
```

Вы можете использовать пользовательские компоненты так же, как и нативные:
``` html
<div>
  <menu for="menus" on:click="clickMenu($idx, $item)">
    <p>Menu {{$item}}</p>
  </menu>
</div>
```

``` css
div {
  display: flex;
  flex-direction: column;
}

text {
  text-align: center;
}
```

``` js
export default {
  data: {
    menus: ["Dog", "Cat", "Pig", "Fish"],
  },
  clickMenu(id, name) {
    console.log(`clicked id: ${id}, name: ${name}.`)
  }
}
```

Это интерфейс меню, и мы хотим, чтобы при клике пользователя по меню информация о текущем пункте меню выводилась в лог с помощью метода `clickMenu`. Поэтому компонент `Menu` должен уметь отображать содержимое меню и передавать свое событие клика через прослушиватель `on:click`.

Вот содержимое файла `Menu.ux`:
``` html
<template>
  <div on:click="$emit('click')"> <slot /> </div>
</template>

<style>
  div { display: flex; }
</style>

<script>
  export default {}
</script>
```
Мы просто используем нативный компонент `div`, чтобы реагировать на клик пользователя и передавать его наверх (`$emit`). Внутри компонента `div` также будет отображаться дочерний компонент, переданный ранее, что в конечном итоге позволит отобразить список меню.

# Симулятор и отладка

Чтобы запустить симулятор, вам нужно перейти в корневой каталог проекта в командной строке и запустить подкоманду `gx emu`. Симулятор Glyphix обладает окружением, которое максимально приближено к условиям работы на реальном устройстве. Это позволяет разрабатывать и отлаживать большую часть интерфейсов и функций с помощью симулятора, избавляя от необходимости часто устанавливать приложение на реальное устройство.

::: tip
Из-за текущих ограничений npm-пакета [`glyphix`](https://www.npmjs.com/package/glyphix), пожалуйста, обязательно настройте [`glyphix.config.js`](/tutorials/nodejs.md#glyphix-config-js-配置), иначе при выполнении `gx emu` вы не сможете видеть номера строк исходного кода в сообщениях об ошибках.
:::


## Подкоманда `gx emu`

Запускает симулятор с использованием конфигурации целевого устройства из последней сборки. Эту команду необходимо выполнять в корневом каталоге проекта Glyphix. Она автоматически собирает проект и создает файлы ресурсов, необходимые для симулятора, поэтому предварительное выполнение `gx build` не требуется.

#### Опции команды

- `-d --device=NAME`：указывает имя симулируемого устройства, по умолчанию `default` (разрешение $410 \times 502\rm px$).
- `-e --emulator-exe=CMD`：указывает исполняемый файл симулятора, по умолчанию `glyphix-emu`. Обычно не требует изменения.
- `-l --language=NAME`：указывает локаль симулятора, по умолчанию `zh-CN` (упрощенный китайский). Список поддерживаемых языков можно посмотреть с помощью команды `gx list language`.
- `--target=URI`：устанавливает имя пакета или deeplink при запуск симулятора, например `app://com.example.app/SomePage?query=value` или `com.example.app`.
- `-i --inspector`：включает инспектор при запуске симулятора. Инспектор представляет собой веб-страницу, позволяющую отлаживать элементы интерфейса в симуляторе прямо из браузера.
- `-m --mobile-network`：（еще не реализовано) включает проксирование сети SDK телефона только в симуляторе, без прямого доступа к сети.
- `-w --watch`：отслеживает изменения в каталоге проекта во время работы симулятора, автоматически выполняя пересборку и обновление интерфейса симулятора при изменении исходных файлов.
- `-r --real-scale`：отображает окно симулятора в реальном размере вместо масштабирования под разрешение устройства. Эту опцию рекомендуется использовать на экранах с высоким разрешением (HiDPI).
- `-t --top`：удерживает окно симулятора поверх остальных окон.
- `-p --profiling`：включает режим профилирования. Из-за значительной разницы в производительности между симулятором и устройством эта опция обычно малополезна.

## Режимы запуска

По умолчанию `gx emu` запускает симулятор в соответствии с конфигурацией устройства, использовавшейся при последней сборке. Поведение при запуске можно настроить с помощью опций командной строки.

### Указание модели устройства

С помощью опции `-d` или `--device` можно указать модель устройства, которую вы хотите симулировать, например:
```bash
gx emu -d generic-watch-466x466
```
Это запустит симулятор для устройства `generic-watch-466x466`. Список установленных устройств можно посмотреть с помощью команды `gx list device`.

Если эта опция не указана, будет использовано устройство, заданное в прошлый раз. При первом запуске или после выполнения `gx clean` будет использоваться устройство `default`.

### Запуск через Deeplink

По умолчанию симулятор запускает приложение текущего проекта или интерфейс меню приложений. Однако при отладке жизненного цикла [`onRoute()`](/framework/component/life-cycle.md#onroute) может потребоваться запуск приложения через deeplink, чтобы гарантировать получение функцией `onRoute()` определенных параметров. Вы можете использовать опцию `--target` для указания deeplink, например:
```bash
gx emu --target app://com.example.app/SomePage?query=value
```
Это запустит приложение с именем пакета `com.example.app`, а путь (path) URI Deeplink (включая корневой каталог `/`, то есть `/SomePage`) и параметры (query) будут переданы в функцию `onRoute()` этого приложения.

### Симуляция размеров устройства

По умолчанию симулятор использует фактическое разрешение устройства в пикселях. Из-за этого размер отображения на компьютере оказывается больше реального экрана устройства, и разработчику становится сложно оценить оптимальный размер элементов интерфейса (включая макет дизайна) на самом устройстве. Опция `-r` или `--real-scale` позволяет эмулировать реальные размеры устройства:
```bash
gx emu -r
```
Используя эту опцию, вы можете оценить фактический размер элементов UI без необходимости устанавливать приложение на устройство. Однако, учитывая, что DPI большинства часов превышает 300, использование режима real-scale на 1080p мониторе может сделать интерфейс слишком размытым. Рекомендуется использовать эту опцию на мониторах с высоким разрешением HiDPI (например, 4K мониторах или экранах Retina в macOS).

::: tip
В режиме real-scale вам следует указывать целевое устройство для симуляции с помощью опции `--device`. Стоит отметить: из-за различий в DPI два устройства с одинаковым разрешением могут иметь разные физические размеры экранов, поэтому размер отображения в режиме real-scale также будет отличаться.
:::

### Автоматическое обновление

Опция `-w` или `--watch` отслеживает изменения в каталоге проекта во время работы симулятора и автоматически выполняет пересборку и перезапуск приложения при изменении исходных файлов. Обычно её рекомендуется использовать в сочетании с опцией `-t`, например:
```bash
gx emu -wt
```
Это позволит удерживать окно симулятора поверх остальных и автоматически перезапускать приложение после изменения исходных файлов. Это крайне удобно для разработки и отладки: вы можете переключаться прямо из редактора кода в симулятор без необходимости вручную перезапускать симулятор или постоянно переключать окна.

::: tip
Горячее обновление (hot update) страниц в настоящее время не поддерживается, вместо этого при изменении исходных файлов происходит перезапуск всего приложения. Если вам нужна более высокая скорость отладки, вы можете установить [`manifest.router.entry`](/framework/application/manifest.md#entry) на разрабатываемую в данный момент страницу, тогда при каждом перезапуске приложение будет сразу открывать её.
:::

## Подключение телефона

Вы можете подключиться к симулятору с помощью Android-приложения [Glyphix Debug](https://www.pgyer.com/KLeBQFv6), что удобно для отладки функций реального устройства и взаимодействия смартфона с часами.

### Подготовка

Установите приложение Glyphix Debug на телефон и убедитесь, что телефон и компьютер находятся в одной локальной сети (например, подключены к одному Wi-Fi). Запустите симулятор и откройте приложение Glyphix Debug, затем нажмите кнопку «Socket Connection» (Соединение Socket). В приложении появится интерфейс подключения, где вы сможете выбрать IP-адрес найденного симулятора либо вручную ввести IP-адрес компьютера и порт симулятора.

По умолчанию симулятор прослушивает сетевой порт `7768`. Если этот порт занят (обычно при запуске нескольких симуляторов), автоматически выбирается следующий доступный порт, а его реальный номер выводится в консоль при запуске. Например:
```bash
$ gx emu
[simulator.socket] MAS TCP server bind port 7768 successful 
```

::: tip
Если порт симулятора был занят и был выбран отличный от 7768 порт, приложение Glyphix Debug не сможет автоматически обнаружить этот симулятор. В таком случае для подключения потребуется вручную ввести правильный IP-адрес и номер порта.
:::

Настоятельно рекомендуется включить в симуляторе режим проксирования сети телефона (описанный в следующем разделе), чтобы избежать одновременного использования компьютерной и мобильной сетей. В противном случае это может помешать нормальной работе [@system.interconnect](/api/system-interconnect.md) и других API, зависящих от взаимодействия со смартфоном.

### Проксирование мобильной сети

Использование опции `-m` или `--mobile-network` включает только функцию проксирования сети SDK телефона, имитируя сетевое окружение реального устройства. В этом режиме симулятор не запускает целевое приложение автоматически, а отображает интерфейс со списком приложений.

Прежде чем вручную запустить приложение, вам необходимо подключиться к симулятору через мобильное приложение Glyphix Debug с помощью опции "Socket Network", и только после этого нажать на целевое приложение. В противном случае приложение не сможет получить доступ к сети.

::: tip
В режиме проксирования мобильной сети (`-m`) вы можете имитировать обрыв сети, закрыв отладочное приложение на телефоне или переподключившись к симулятору. В противном случае симулятор автоматически переключится на сеть компьютера.
:::

### Частые проблемы с подключением

Если вам не удается подключиться к симулятору через приложение Glyphix Debug, убедитесь, что компьютер и телефон подключены к одной локальной сети, а программа и порт симулятора не заблокированы правилами брандмауэра (файрвола). Если вы подключены к общедоступной сети (публичному Wi-Fi), подключение может быть невозможно из-за брандмауэра или сетевой изоляции.

Если вы используете VPN или прокси-клиенты, убедитесь, что трафик локальной сети не перенаправляется через них, иначе подключение также будет невозможно.

# Управление изображениями

Инструмент сборки glyphix.js управляет всеми ресурсами изображений в формате PNG в проекте (каталог `src`). Связанные модули в основном предоставляют следующие возможности:
- Поддержка файлов конфигурации для ресурсов изображений, а также предоставление соответствующего интерфейса конфигурации.
- Преобразование изображений во время сборки в размеры и форматы, оптимизированные для конкретного устройства.

Разработчикам приложений нужно лишь настроить параметры сборки ресурсов изображений в соответствии со своими потребностями, в то время как поставщики устройств должны определить конкретные стратегии конвертации изображений для своих устройств.

## Настройка разработки приложений

При разработке приложений необходимо настроить параметры сборки изображений для правильной генерации пакета ресурсов.
Настройка свойств `config/image-rules.json`, а также `config.designWidth` и других в файле `src/manifest.json` при разработке приложений влияет на процесс сборки ресурсов изображений. Файл `config/image-rules.json` обычно используется для настройки параметров качества и производительности, в то время как поля в `manifest.json` влияют на глобальный коэффициент масштабирования изображений (используется для адаптации к устройствам с различным разрешением).

::: tip
Файл `config/image-rules.json` можно настроить с помощью команды `gx config` или другими способами, однако не рекомендуется редактировать его напрямую в текстовом редакторе.
:::

При использовании команды `gx config` разработчики будут в основном концентрироваться на двух параметрах: transparent и quality.

### Параметр Transparent

Параметр Transparent указывает, содержит ли изображение прозрачные пиксели. Если установлено значение «нет» (`false`), а исходное изображение содержит прозрачные пиксели, то при генерации эти пиксели будут преобразованы в непрозрачные (обычно путем наложения на черный фон). Поэтому необходимо пометить изображения, которым это требуется, как сохраняющие прозрачные пиксели, иначе эффект наложения будет отображаться некорректно. Поскольку на некоторых платформах производительность непрозрачных изображений выше, а объем их данных меньше, опция transparent по умолчанию отключена.

### Параметр Quality

Параметр Quality представляет качество изображения после сборки и является целым числом в диапазоне $[0, 100]$. Однако обычно используются только 3 примерных уровня качества:
- High: 100, означает наивысшее качество.
- Middle: 50, среднее качество, значение по умолчанию.
- Low: 0, низкое качество.

При конвертации ресурсов изображений оптимизация выполняется на основе параметра качества. Как правило, среднее качество — это стратегия конвертации на целевой платформе, которая соблюдает баланс между качеством отображения, производительностью отрисовки/загрузки и объемом занимаемой памяти, поэтому оно рекомендуется к использованию. Использование высокого качества может обеспечить лучшую детализацию, но способно привести к падению производительности. Низкое качество может применяться для изображений, где допускается потеря качества ради повышения производительности (например, для фотографий). Конкретные целевые платформы также могут игнорировать параметр quality и использовать единую стратегию.

## Адаптация устройств и платформ

Предположим, что разработчики устройств и платформ уже реализовали оптимизированные форматы ресурсов изображений для конкретной целевой платформы, поддерживающие различные параметры качества и пиксельные форматы. Чтобы иметь возможность генерировать эти форматы изображений в glyphix.js, необходимо выполнить следующие действия:
- Реализовать инструмент командной строки для конвертации **одиночных изображений**.
  - Обязательно предоставьте интерфейс командной строки для конвертации изображений из PNG в пользовательский формат с поддержкой вывода по указанному пути (включая перезапись исходного файла).
  - Желательно предоставить интерфейс командной строки для конвертации из пользовательского формата обратно в PNG с поддержкой вывода по указанному пути (включая перезапись исходного файла); без этой функции предварительный просмотр на ПК будет недоступен.
- Написать файл описания устройства и скрипт конвертации изображений.

### Скрипт конвертации изображений

Скрипт конвертации изображений представляет собой файл схемы (scheme). Когда требуется конвертировать изображение, glyphix.js вызывает этот скрипт, который может определить способ конвертации на основе следующих переменных:
- `env.image-path`: Абсолютный путь к конвертируемому изображению, преобразованное изображение перезаписывается по этому пути.
- `env.transparent`: Параметр прозрачности данного изображения.
- `env.quailty`: Параметр качества данного изображения.
- `env.target`: Целевой режим конвертации, описанный ниже.
- `env.verbose`: Включен ли подробный режим (verbose); если да, можно выводить подробные логи, в противном случае логи выводить не следует.
- `env.script-dir`: Абсолютный путь к каталогу, в котором находится текущий файл скрипта. Если команда, необходимая для конвертации, находится относительно этого скрипта, а не в переменной окружения `PATH`, вы можете использовать этот параметр для построения пути.

`env.target` представляет **целевой режим** конвертации изображений, и его значение определяет, какой именно способ конвертации применяется:
- `"device"`: Выполнение полного процесса конвертации для целевого устройства, например, удаление альфа-канала непрозрачных изображений с последующим преобразованием в формат PGF (формат изображений Glyphix) в соответствии с параметром качества.
- `"emulator"`: Выполнение процесса конвертации для эмулятора. Поскольку эмулятор не поддерживает текстурные форматы конкретного оборудования (например, ETC2 и т.д.), для обеспечения нормального отображения изображений в эмуляторе можно только удалить альфа-канал непрозрачных изображений без дальнейшего преобразования в формат целевого устройства (или преобразовать в поддерживаемый программно формат PGF).
- `"preprocess"`: Выполнение только этапа предварительной обработки, то есть удаление альфа-канала непрозрачных изображений с выводом результата в формате PNG.
- `"preview"`: Генерация PNG-изображения для предварительного просмотра. Сначала изображение конвертируется в пользовательский целевой формат по процессу для цели `"device"`, а затем выходное изображение конвертируется обратно в PNG для предварительного просмотра.

::: tip
Если инструмент командной строки для конвертации изображений не поддерживает конвертацию пользовательских форматов в PNG, не реализуйте целевые режимы `"preprocess"` и `"preview"`.
:::

### Инструмент командной строки image-forge

image-forge — это инструмент командной строки для работы с форматом изображений PGF, предоставляемый Glyphix, который обладает следующими возможностями:
- Поддержка конвертации изображений из PNG в формат PGF и обратно из PGF в PNG.
- Поддержка распространенных пиксельных форматов ARGB и PAL с разграничением режима premultiplied alpha (предварительно умноженный альфа-канал).
- Поддержка смешивания прозрачных ARGB-изображений с заданным сплошным цветом фона для преобразования их в непрозрачные изображения (вместо простого отбрасывания альфа-канала).
- Поддержка выравнивания строк по пикселям или байтам.
- Поддержка сжатия LZ4 с возможностью установки минимального порога сжатия (данные изображений ниже этого порога не сжимаются).

Для платформ, использующих другие пользовательские форматы изображений, image-forge также может применяться для удаления канала прозрачности.

## Пример скрипта конвертации изображений

В следующем примере показано, как использовать такие команды, как image-forge, для конвертации PNG в изображения PGF с приоритетным использованием формата палитры (PAL).

Сначала определим правила целевого формата для непрозрачных и прозрачных случаев:
``` scheme
; Определяем правила пиксельного формата для непрозрачных цветов
(define (opaque-formats q)
  (cond ((<= q 50) "pal-rgb")
        (else "rgb24")))

; Определяем правила пиксельного формата для прозрачных цветов
(define (transparent-formats q)
  (cond ((<= q 50) "pal-argb-premul")
        (else "argb32-premul")))

; Вычисляем целевой пиксельный формат под воздействием параметров прозрачности и качества
(define pixel-format
  ((if env.transparent
      transparent-formats opaque-formats)
    env.quailty))

; Конвертировать ли изображение в формат с палитрой
(define palette (<= env.quailty 50))
```

В приведенном выше коде формат палитры используется при качестве меньше или равном 50, а в зависимости от прозрачности применяется `pal-rgb` или `pal-argb`. При качестве выше 50 используется пиксельный формат с 8-битной выборкой RGB или ARGB. В конечном итоге переменная `pixel-format` представляет собой имя фактически используемого пиксельного формата, а `palette` указывает, используется ли формат палитры.

Далее определим команды, необходимые в различных ситуациях:

``` scheme
; Добавлять ли параметр командной строки --verbose
(define if-verbose (if env.verbose "--verbose " ""))

; Вызов команды pngquant для сокращения цветов изображения до 256 или менее; в системе должен быть установлен pngquant
(define color-reduction
  (string-append "pngquant --ext=.png --force " if-verbose env.image-path))

; Конвертация изображения в формат PGF
(define convert (string-append "image-forge "
  "--format=" pixel-format " " ; Указываем выходной пиксельный формат
  "--compress --min-compress-ratio=5 " ; Сжимаем данные изображения для уменьшения размера файла, минимальный коэффициент сжатия равен 5
  "--align=16 --pixel-align " ; Выравнивание изображения по 16 пикселям
  if-verbose
  env.image-path))

; Удаление альфа-канала изображения и добавление фона
(define remove-alpha (string-append "image-forge --bypass "
  ; На часах bes2500ibp для непрозрачных изображений можно удалить альфа-канал и смешать с черным фоном, эта операция может улучшить качество изображения после сокращения цветов PAL
  (if env.transparent "" "--background black ")
  if-verbose
  env.image-path))

; Команда для декодирования изображения PGF обратно в PNG
(define decode
  (string-append "image-forge --decode " if-verbose env.image-path))
```

В следующем коде `execute-try` вызывает указанную функцию `f`, если код выхода команды отличен от 0, а функция `execute` выводит лог ошибки и аварийно завершает скрипт, если код выхода отличен от 0. Функция `run-convert` выполняет полный процесс конвертации изображения целевого устройства (вызывает команды `remove-alpha` и `convert`).

``` scheme
; Выполнение команды и вывод ее содержимого в режиме verbose; если команда завершается с ненулевым кодом ошибки, вызывается функция f
(define (execute-try cmd f)
  (begin
    (if env.verbose ; Если включен режим verbose, выводим содержимое команды
      (display (string-append "Run command: " cmd "\n")))
    (let ((r (system (string-append env.script-dir "/bin/" cmd))))
      (if (= r 0) 0 (f r)))
  ))

; Выполнение команды с выводом содержимого в режиме verbose; если команда завершается с ошибкой, программа завершается
(define (execute cmd)
  (execute-try cmd (lambda (x)
    (begin ; При сбою выводим код ошибки и аварийно выходим
      (display (string-append "subprocess failed (" (number->string x) "): " cmd "\n"))
      (exit-fail)
  ))))

; Конвертация изображения
(define (run-convert)
  (begin
    (execute remove-alpha) ; Сначала удаляем канал прозрачности
    (if palette (execute color-reduction)) ; Если это формат палитры, сокращаем количество пикселей изображения
    (execute convert) ; Выполняем команду конвертации изображения
  ))
```

Макрос `targets` определяет методы обработки для всех целевых режимов, например, режим `"device"` вызовет функцию `run-convert` и т.д.

``` scheme
; Определение стратегии конвертации для конкретной цели
(targets env.target
  ; Режим устройства: процесс конвертации изображений, используемый в конечном итоге для целевого устройства
  ("device" (run-convert))
  ; Режим эмулятора: удаление альфа-канала только для непрозрачных изображений, без конвертации формата
  ("emulator" (execute remove-alpha))
  ; Режим предварительной обработки: удаление альфа-канала непрозрачных изображений и добавление фона
  ("preprocess" (execute remove-alpha))
  ; Режим предварительного просмотра: генерация PNG-изображения предварительного просмотра, идентичного по отображению на реальном устройстве
  ("preview" (begin
    (run-convert) ; Сначала конвертируем изображение в формат PGF
    (decode))) ; Затем конвертируем изображение обратно в PNG
  )
```

### Использование скрипта конвертации изображений

Чтобы использовать скрипт конвертации изображений, необходимо добавить поле в файл описания модели устройства:

``` yaml
description: default watch

screen:
  width: 454 # pixels
  height: 454 # pixels
  dpi: 326 # pixels per inch

#...
image-build: image-convert-pal.scm # Путь к скрипту конвертации изображений относительно этого Yaml-файла
```

### Более сложные стратегии

Поскольку скрипт конвертации изображений написан на полноценном языке программирования, а не на конфигурационном языке вроде Yaml или JSON, мы можем реализовать более сложные пользовательские стратегии конвертации, не ограничиваясь возможностями, предоставляемыми фреймворком. В качестве примера выше с конвертацией в формат палитры: формат PAL плохо работает на изображениях с богатой цветовой гаммой, и в этом случае изображение можно конвертировать в формат, который показывает себя лучше в таких сценариях. Конкретная идея заключается в следующем:
1. Команда `pngquant` поддерживает аварийный выход, если после конвертации в формат PAL качество оказывается ниже заданного значения; соответственно, настройте параметры команды для этой цели.
2. Операция `color-reduction`, выполняемая `execute` в функции `run-convert`, заменяется на выполнение с помощью `execute-try`, а в функции обработки исключений последней используется операция конвертации в альтернативный формат.
3. Обработка таких целей, как `preview`, аналогична, но следует учитывать, что при конвертации выходного формата обратно в PNG также необходимо распознавать аварийное завершение команды и перенаправлять попытку на последующие команды.

В общем и целом, подход аналогичен сценариям оболочки (shell script), использующим коды завершения ошибок команд для управления ходом выполнения.

# Утилита сборки Glyphix.js

glyphix.js — это утилита сборки для приложений Glyphix. Она включает в себя инструмент командной строки под названием `gx`, который используется для создания, сборки и запуска приложений Glyphix. В состав утилит также входит графический симулятор для имитации работы приложений Glyphix на компьютере.

В этой документации представлены инструкции по установке и использованию glyphix.js. Руководство [Быстрый старт](/tutorials/getting-started.md) предлагает более простое введение. Ознакомьтесь также с разделом [Сборка и запуск](#сборка-и-запуск), чтобы узнать, как разрабатывать, собирать и публиковать приложения Glyphix.

## Установка

В этом разделе описывается процесс установки утилиты сборки glyphix.js. Для обычного использования достаточно изучить способ [установки через npm](#установка-через-npm). Способ [ручной установки](#ручная-установка) применяется в особых сценариях, таких как среды с ограниченным доступом к сети или CI-сборки.

### Установка через npm

Для установки утилиты сборки glyphix.js можно использовать менеджером пакетов [npm](https://nodejs.org). Рекомендуется использовать глобальную установку с опцией `-g`:
::: code-tabs
@tab npm
```bash
npm install -g glyphix-cli
```

@tab pnpm
```bash
pnpm install -g glyphix-cli
```

@tab yarn
```bash
yarn global add glyphix-cli
```
:::

::: tip
Перед глобальной установкой с помощью pnpm может потребоваться выполнить `pnpm setup` для настройки переменных окружения. Команда `pnpm install -g` подскажет, как это сделать.
:::

После завершения установки вы можете проверить ее успешность, выполнив в терминале команду `gx --version`. Пример:
```bash
$ npm install -g glyphix-cli
$ gx --version
gx v0.10.1 - The Glyphix applet development toolchain
commit a9337cf1 - Tue Sep 23 10:03:48 2025 +0800
```

Кроме того, для сборки ресурсов приложений под определенные устройства необходимо установить [pngquant](#pngquant).

### Ручная установка

Вы также можете установить glyphix.js вручную из архива: добавьте распакованную директорию `bin` в переменную окружения `PATH`. Ниже описан процесс установки для основных операционных систем.

::: tip
Инструмент glyphix.js — это не просто один исполняемый файл. Не забудьте скопировать остальные файлы ресурсов (включая все файлы в директориях `bin` и `share`).
:::

#### macOS / Linux

Для macOS или Linux для установки утилиты glyphix.js можно использовать команду `tar`. Перед этим также потребуется установить такие инструменты, как `xz`:

::: code-tabs
@tab macOS
```bash
brew install xz
```

@tab Ubuntu / Debian
```bash
sudo apt update
sudo apt install xz-utils
```

@tab Arch Linux
```bash
sudo pacman -S xz
```
:::

После скачивания архива glyphix.js распакуйте и установите его с помощью следующих команд:
::: code-tabs
@tab macOS
```bash
tar -xvJf glyphix-v0.7.2-darwin-arm64.tar.xz -C ~/.local
```

@tab Linux
```bash
tar -xvJf glyphix-v0.7.2-linux-x86_64.tar.xz -C ~/.local
```
:::
Не забудьте заменить имя файла `.tar.xz` на фактически загруженное, соответствующее вашей операционной системе и архитектуре процессора. После распаковки такие команды, как `gx`, окажутся в директории `~/.local/bin`. Добавьте эту директорию в переменную окружения `PATH`, обновив файл `.bashrc`, например, следующим образом:
```bash
# Если ~/.local/bin отсутствует в PATH, добавляем его
echo "$PATH" | grep -q "$HOME/.local/bin" || echo 'export PATH="$HOME/.local/bin:$PATH"' >> ~/.bashrc
source ~/.bashrc # Перезагружаем конфигурацию bash
```

::: tip
При использовании оболочки `Zsh` файл конфигурации `.zshrc` может импортировать `.bashrc`, поэтому достаточно обновить только `.bashrc`. В противном случае обновите `.zshrc` описанным выше способом.

Рекомендуется устанавливать утилиту сборки glyphix.js в пользовательскую директорию `~/.local`, чтобы избежать использования прав root.
:::

#### Windows

Чтобы установить glyphix.js в Windows, скачайте архив для соответствующей версии Windows и распакуйте его с помощью инструмента, поддерживающего формат `7z` (например, [7-Zip](https://www.7-zip.org/)), в какую-либо директорию, например `C:\glyphix`. Затем добавьте `C:\glyphix\bin` в [переменную окружения `PATH`](https://learn.microsoft.com/zh-cn/previous-versions/office/developer/sharepoint-2010/ee537574(v=office.14)) вашей системы.

Это аналогично процессу установки в macOS и других системах.

### Установка системных зависимостей

#### pngquant

Пользователям Linux и macOS необходимо дополнительно установить `pngquant`. Вы можете сделать это с помощью `npm`:
```bash
npm install -g pngquant-bin # pngquant-bin поддерживается только при установке через npm
```
Версия `glyphix-cli` для Windows уже содержит `pngquant.exe`, поэтому дополнительная установка не требуется.

::: tip
Вы также можете скачать предварительно скомпилированные бинарные файлы с сайта [pngquant.org](https://pngquant.org/) или установить их через системный пакетный менеджер.
:::

#### Системные зависимости Linux

Установочный пакет glyphix.js для Linux не зависит от конкретного дистрибутива, на данный момент доступна сборка только для архитектуры `linux-x86_64`. Мы проверили ее работоспособность на Ubuntu 20.04 (и новее) и Arch Linux.

Если вы используете команду `gx` исключительно для сборки (что часто применяется в CI), дистрибутивы Linux без графического окружения должны работать «из коробки». Запуск графического симулятора зависит от оконной системы X, поэтому вам может потребоваться установить пакеты, связанные с `xorg`. В частности, в окружении Wayland также потребуется установить пакет `xwayland` (симулятор пока не поддерживает нативный Wayland).

## Сборка и запуск

После установки glyphix.js используйте команду [`gx build`](#gx-build) в корневом каталоге исходного кода приложения для сборки пакета или команду [`gx emu`](#gx-emu) для запуска симулятора.

После сборки приложения обратитесь к разделу [Отправка пакета приложения](#отправка-пакета-приложения), чтобы узнать, как установить приложение на устройство или отправить его на платформу публикации приложений.

## Аргументы командной строки

### Общие опции

#### `gx --help`

Просмотр справочной информации. Справку также можно использовать для конкретных подкоманд, например: `gx build --help` выведет справку только для подкоманды `build`.

#### `gx --version`

Опция `-V --version` используется для отображения версии команды `gx`.

#### `gx --verbose`

`-v --verbose` включает вывод подробных логов. Разработчикам приложений это обычно не требуется.

#### `gx --numeric-version`

Выводит чистый номер версии команды `gx`, например `0.10.1`.

#### `gx --quiet`

`-q --quiet` включает тихий режим, подавляющий большинство логов, кроме предупреждений и ошибок. Сюда входят логи прогресса сборки при использовании `gx build`. Этот режим обычно используется в CI-средах, где требуется собирать большое количество пакетов приложений.

Просмотр номера версии.

### `gx new`

Создание нового проекта, например: `gx new myapp` создаст новый проект с именем `myapp`.

### `gx build`

Сборка проекта (действие по умолчанию). С помощью опции `--device` или `-d` можно указать целевое устройство, например:
``` bash
gx build -d default # Сборка для устройства по умолчанию (default)
```
Опция `--dump` выводит детальную информацию о компиляции UX-файлов.

Glyphix.js поддерживает инкрементальную сборку: при изменении исходного кода пересобирается только измененная часть.

Параметр `-r --image-rules` позволяет указать файл правил упаковки изображений (по умолчанию `config/image-rules.json`). Значение этого параметра кэшируется, и последующие вызовы `gx build` или `gx emu` будут выполняться в соответствии с предыдущей конфигурацией.

#### Опции команды

- `-d --device=NAME`: указывает имя целевого устройства. Оно должно соответствовать имени установленной конфигурации устройства. Список установленных устройств можно посмотреть с помощью команды `gx list device`. Если эта опция не указана, по умолчанию используется устройство `default`.
- `-f --full`: принудительная полная пересборка проекта вместо инкрементальной.
- `-e --emulator`: сборка проекта для симулятора, а не для реального устройства. Эта опция автоматически применяется при выполнении команды `gx emu`.
- `-r --image-rules=PATH`: указывает файл правил упаковки изображений (по умолчанию `config/image-rules.json`).

#### Отправка пакета приложения

После сборки с помощью `gx build` в директории проекта будет создана папка `.glyphix-work/dist/<device-name>/<package-name>`, содержащая скомпилированные файлы пакета приложения (файлы `.pkg`). Полученный файл можно установить на устройство для отладки через мобильное приложение или загрузить на платформу публикации.

Используйте опцию `-d` для сборки пакетов приложений под все поддерживаемые устройства. Пример структуры директорий:
```bash
.glyphix-work/dist
├─ generic-watch-368x448
│  └─ com.example.app
│     ├─ bundle.pkg
│     ├─ icon.png
│     └─ manifest.json
└─ generic-watch-466x466
   └─ com.example.app
      ├─ bundle.pkg
      ├─ icon.png
      └─ manifest.json
```
При отправке пакета приложения упакуйте и загрузите **всю** директорию `.glyphix-work/dist`, а не только файл `.pkg` или какую-то одну поддиректорию. Платформа распознает приложение по информации из файла `manifest.json` и может использовать `icon.png` в качестве иконки предпросмотра.

::: tip
Пользователи Linux или macOS могут использовать следующую команду для сборки приложений под определенный класс устройств:
```bash
gx list device | grep "^generic-" | xargs -n 1 gx build -d
```
Это соберет пакеты для всех устройств, чьи имена начинаются с `generic-`.

В Windows для пакетной сборки можно использовать аналогичную команду PowerShell:
```shell
gx list device | ? { $_ -match "^generic-" } | % { gx build -d $_ }
```
:::

### `gx emu`

См. документацию [Симулятор и отладка](/tutorials/glyphix.js/emulator.md).

### `gx clean`

Очистка результатов сборки. Эта команда удаляет директорию `.glyphix-work` в папке проекта.

### `gx config`

Эта команда запускает веб-интерфейс для редактирования правил упаковки изображений. Следуя подсказкам в терминале, вы можете открыть страницу в браузере и выполнить необходимые действия. Команда имеет два варианта использования:
``` bash
gx config # При нахождении в проекте Glyphix указывать исходную директорию не нужно (доступно только в корне проекта)
gx config path/to/dir # Настройка для указанной директории (может использоваться для конфигурации ресурсов изображений вне проекта)
```

Параметр `-r --image-rules` задает файл правил упаковки изображений (по умолчанию `config/image-rules.json`).

### `gx image-forge`

Преобразование отдельных графических файлов. Команда позволяет указать произвольные исходный и выходной пути без необходимости выполнения внутри проекта Glyphix:
``` bash
gx image-forge src -o dist
```

Описание опций:
- `src` — исходный путь для конвертации. Команда `image-forge` рекурсивно преобразует все изображения и сохраняет их с учетом относительной структуры директорий в целевой путь, заданный флагом `-o, --output` (по умолчанию `dist`).
- Параметр `-r --image-rules` задает файл правил упаковки изображений (по умолчанию `config/image-rules.json`).
- `-d --device` указывает целевое устройство для конвертации изображений.

### `gx list`

Вывод различной информации. На данный момент поддерживается три операции:
``` bash
gx list device # Вывести список всех установленных конфигураций устройств
gx list template # Вывести список всех установленных шаблонов проектов
```

Эта команда используется для генерации скриптов автодополнения командной строки для `gx`. ## Пути конфигурации по умолчанию

Конфигурации, шаблоны проектов, информация об устройствах и другие данные утилиты glyphix.js могут храниться по следующим путям:
- Системные конфигурации: директория `share/glyphix`, находящаяся на уровень выше директории исполняемого файла `gx`/`gx.exe`. Например, если исполняемый файл `gx` находится по пути `/usr/local/glyphix`, то путем к ресурсам системной конфигурации будет `/usr/local/share/glyphix`.
- Пользовательские конфигурации: в UNIX-подобных системах — `~/.local/share/glyphix`, в Windows — `%APPDATA%\AppData\Roaming\glyphix`.

Файлы конфигурации можно размещать в любом из этих путей, причем пользовательские конфигурации имеют более высокий приоритет. При установке `gx.js` поставляется с файлами конфигурации по умолчанию.

## Шаблоны проектов

Шаблоны проектов хранятся в директории `templates` папки конфигурации. В настоящее время поддерживается только шаблон `simple`, пользовательские шаблоны не поддерживаются.

``` yaml
  width: 454 # Количество пикселей по горизонтали
  height: 454 # Количество пикселей по вертикали
  dpi: 326 # Плотность пикселей экрана в пикселях на дюйм (PPI)

  font-family: sans-serif # Имя семейства шрифтов системы по умолчанию (по умолчанию serif)
  font-size: 3.5 # Размер шрифта системы по умолчанию в пунктах (pt, points), обратите внимание — не в пикселях!
  font-map: true # Использовать ли файл маппинга глобальной конфигурации шрифтов. Если true, системные ресурсы должны содержать

```

В этом руководстве показана техника разработки меню с перекрывающим слоем после размытия фона. В следующем примере продемонстрирован такой интерактивный эффект (нажмите на кнопку «...» в правом нижнем углу, чтобы показать интерфейс перекрытия).

<glyphix id="cookbook-blur-overlay" width="410" height="502" title="Размытый оверлей" inline>

</glyphix>

Основная цель этого руководства — показать, как реализовать интерфейс с размытием с помощью Glyphix.

## Метод реализации

### Тень текста

Тень текста «Hokkaido sika deer» в примере может быть реализована путем наложения слоя размытого текста:
``` html
<stack class="wallpaper-title">
  <p class="shadow">Hokkaido sika deer</p>
  <p>Hokkaido sika deer</p>
</stack>
```
Поместите два одинаковых текста в компонент [`stack`](/components/stack.md) и используйте нижний текст в качестве тени. Это достигается с помощью CSS-класса `shadow` для нижнего текста:
``` css
.shadow {
  color: #0008;
  /* Добавляем размытие фонового текста для создания эффекта тени */
  filter: blur(8px);
  /* Необходимо использовать transparent, чтобы пометить элемент как прозрачный */
  transparent: true;
}
```
Установите цвет фонового текста полупрозрачным серым и примените компонент текста `<p>` в качестве тени с помощью свойства фильтра размытия ([`filter: blur(8px)`](/framework/generic/styles.md#filter)). Обратите внимание, что цвет текста на переднем плане не должен быть прозрачным, иначе он может наложиться на слой `.shadow`.

### Пользовательский шрифт

Текст «Hokkaido sika deer» отображается с использованием пользовательского шрифта. В Glyphix вы можете импортировать пользовательские шрифты тем же способом, что и в веб-разработке:
``` css
@font-face {
  font-family: 'Playwrite Australia SA';
  src: url('/assets/PlaywriteAUSA-Regular.ttf');
}

.wallpaper-title {
  font-family: 'Playwrite Australia SA', 'sans-serif';
  color: #ffffff;
  margin-top: 25%;
}
```
Как видите, вы можете объявить шрифт в CSS с помощью блока [`@font-face`](/framework/generic/styles.md#font-face-规则) и ссылаться на него в свойстве элемента [`font-family`](/framework/generic/styles.md#font-family).

### Размытие фонового слоя

Поскольку страницы, вызываемые в настоящее время через [`router` API](/api/system-router.md), не поддерживают полупрозрачный фон, вы не можете использовать страницы для реализации всплывающего меню. Однако вы можете использовать этот прием для симуляции всплывающей «страницы»:
``` html
<stack class="window" :disabled="popups">
  <image class="wallpaper" src="/assets/images/sika-deer.jpg" />
  ...
</stack>
<div class="overlay" if="popups">
  ...
</div>
```
Вам нужно добавить в страницу два слоя элементов (в этом примере `stack.window` и `div.overlay`) и управлять ими с помощью условия (например, `popups`). В частности:
- `popups` управляет свойством `disabled` фонового элемента, поэтому, когда `popups` имеет значение true, фоновый элемент не будет реагировать на ввод жестов и т. д.;
- `popups` также управляет рендерингом верхнего слоя. Когда он имеет значение true, верхний элемент отображается.

Когда слой перекрытия появляется, свойство [`disabled`](/framework/generic/properties.md#disabled) также предоставляет возможность размыть фоновый элемент:
``` css
.window:disabled {
  filter: blur(40px);
}
```
Когда для элемента установлено свойство `disabled`, также активируется псевдокласс `:disabled` фонового элемента, поэтому эффект размытия в CSS выше начнет работать.

::: tip
Поскольку Glyphix не поддерживает браузерное свойство [`backdrop-filter`](https://developer.mozilla.org/docs/Web/CSS/backdrop-filter), вы не можете напрямую применять правила CSS для `div.overlay` для достижения размытия фона, а должны использовать технику из этого примера.
:::

## Риски для производительности

Поскольку эффект размытия является ресурсоемким процессом, разработчикам следует уделять особое внимание нагрузке на производительность. Мы рекомендуем использовать эффекты размытия только в статических интерфейсах и, желательно, добавлять свойство [`quiescent`](/framework/generic/properties.md#quiescent) к размываемым элементам.

Если возможно, протестируйте интерфейс с размытием на физическом устройстве, чтобы убедиться, что он соответствует ожиданиям по производительности.

# Конфигурация Clangd

При разработке прошивки с использованием кросс-компилятора, такого как arm-none-eabi-gcc, и систем сборки вроде CMake, вы можете настроить языковой сервер Clangd для улучшения опыта разработки. В частности, вы получите следующие преимущества:
- точный переход к объявлениям или определениям на основе реальной структуры проекта;
- просмотр документации API (документация, написанная в формате Doxygen с использованием `/**`, `//!` и т. д.);
- поддержка правил форматирования кода, определенных в `.clang-format`;
- статическая проверка или проверка на ошибки в реальном времени без необходимости компиляции;
- подсказки и автодополнение кода при вводе;
- поиск мест использования, рефакторинг кода и т. д.

## Подготовка

Сначала вам нужно использовать редактор, поддерживающий LSP (Language Server Protocol), например Visual Studio Code, и установить clangd вместе с соответствующим плагином. Если вам нужно установить clangd вручную, вы можете скачать подходящую версию с [LLVM](https://github.com/llvm/llvm-project/releases) или воспользоваться пакетным менеджером вашей операционной системы.

После установки необходимых плагинов clangd может работать без какой-либо конфигурации в простых проектах для хоста, однако в сложных средах кросс-компиляции требуется дополнительная настройка.

## Настройка среды кросс-компиляции

### Параметры CMake

Если в качестве системы сборки вы используете CMake, вам необходимо включить опцию `CMAKE_EXPORT_COMPILE_COMMANDS`. Это можно сделать с помощью аргумента командной строки:
``` bash
cmake .. -DCMAKE_EXPORT_COMPILE_COMMANDS=ON # Аргумент командной строки на этапе конфигурации CMake
```
Если использование аргументов командной строки неудобно, вы также можете определить эту переменную в любом файле `CMakeLists.txt`:
``` cmake
set(CMAKE_EXPORT_COMPILE_COMMANDS ON)
```
Затем при конфигурации или сборке проекта с помощью CMake в выходном каталоге будет создан файл `compile_commands.json`, который будет использоваться clangd.

### Конфигурация Clangd

После настройки CMake и генерации `compile_commands.json` clangd может заработать частично, но вы, скорее всего, столкнетесь со следующими проблемами:
- файл `compile_commands.json` находится в глубокой иерархии каталогов, и clangd не может его найти;
- clangd не может найти стандартные заголовочные файлы для среды кросс-компиляции, такие как `stdint.h` и др.

Чтобы решить эти проблемы, сначала создайте файл `.clangd` в корневом каталоге вашего проекта (то есть в каталоге, открытом в редакторе, обычно там находится папка `.git`). Это файл YAML, заполните его следующим содержимым:
``` yaml
CompileFlags:
  CompilationDatabase: "包含 compile_commands.json 的目录的相对路径"
  Add: 
    - -resource-dir=C:/gcc-arm-none-eabi-9-2020-q2/arm-none-eabi/include
    - -IC:/gcc-arm-none-eabi-9-2020-q2/arm-none-eabi/include
    - -IC:/gcc-arm-none-eabi-9-2020-q2/arm-none-eabi/include/c++/9.3.1
    - -IC:/gcc-arm-none-eabi-9-2020-q2/arm-none-eabi/include/c++/9.3.1/arm-none-eabi
    - -IC:/gcc-arm-none-eabi-9-2020-q2/lib/gcc/arm-none-eabi/9.3.1/include
  Remove:
    - -fno-reorder-functions
```
Пожалуйста, измените пути к файлам в соответствии с вашей реальной ситуацией. Затем добавьте следующий параметр командной строки в аргументы запуска clangd:
``` bash
--query-driver=C:/gcc-arm-none-eabi-9-2020-q2/bin/arm-none-eabi-g++.exe # Путь укажите в соответствии с вашей ситуацией
```
После перезапуска языкового сервера clangd должен начать работать нормально.

В VS Code вы можете добавить параметры через `clangd.arguments` в файле `.vscode/settings.json` проекта:
``` json
{
  "clangd.arguments": [
    "--query-driver=C:/gcc-arm-none-eabi-9-2020-q2/bin/arm-none-eabi-g++.exe"
  ]
}
```

# Асинхронные операции

Основная цель внедрения асинхронных операций в сценарии JavaScript — перенос ресурсоемких задач в фоновый режим во избежание блокировки потока JavaScript. В фоновом режиме в основном обрабатываются задачи, связанные с операциями ввода-вывода (IO-intensive). Glyphix предоставляет разработчикам базовый фреймворк асинхронного программирования для JavaScript, который реализует лишь необходимую абстракцию для асинхронных рабочих процессов и, следовательно, не создает дополнительных накладных расходов.

## Сценарии применения

Сценарии применения модели асинхронного рабочего процесса:

- Запросы инициируются из кода JavaScript и возвращаются после обработки в нативном потоке асинхронной обработки;
- Запросы инициируются из кода JavaScript, а нативный поток асинхронной обработки периодически сообщает о результатах;
  - Код JavaScript может активно запрашивать отмену/аннулирование запроса.

## Режим запроса данных

В режиме запроса данных код JavaScript вызывает API C++ для создания запроса, выполняет операцию в асинхронном потоке и возвращает результат обратно в код JavaScript. В этом процессе данные передаются через асинхронную очередь. Шаблонный класс `async::ResultSession` предоставляет стандартный фреймворк операций для этого режима.

### Описание сценариев

Следующие сценарии являются типичными примерами режима запроса данных:

- **Чтение и запись файлов**: при вызове из JavaScript необходимо указать путь к файлу, смещение для чтения и записи, длину данных или данные для записи; при отправке запроса в асинхронный поток выполняются реальные операции с файлом, по завершении которых результат возвращается или передается в код JavaScript.
- **Сетевые запросы**: аналогично чтению и записи файлов, при вызове из JavaScript задаются параметры запроса, которые затем обрабатываются в фоновом потоке с возвратом результата.

Сценарии режима запроса данных имеют следующие особенности:
- Результат запроса возвращается однократно, поэтому этот режим не подходит для датчиков или таймеров, вызывающих события многократно;
- Запрос всегда имеет результат: в случае успеха возвращается результат, в противном случае — сообщение об ошибке. Возврат результата также является асинхронным;
- Запрос не может быть отменен после его инициации.

### Пример: Получение уровня заряда батареи

#### JavaScript API

Предположим, мы хотим реализовать асинхронную функцию JavaScript для получения уровня заряда батареи:
``` ts
getLevel(): Promise<number> // API в стиле Promise
getLevel(options: { // API в стиле callback
    success: (level: number) => void,
    fail: (code: number, msg: string) => void // Чтение уровня заряда фактически не может завершиться ошибкой (fail)
}): void
```
Функция `getLevel()` используется для асинхронного получения уровня заряда батареи и поддерживает два стиля API: в стиле `Promise` и в стиле callback. Код для обоих стилей выглядит следующим образом:
``` js
async function printBatteryLevel() {
    const level = await getLevel() // Асинхронное получение уровня заряда
    console.log(`battery level: ${level}%`)
}
printBatteryLevel() // Вывод уровня заряда, пример вывода в консоль:
// battery level: 59%

// Ниже приведен код в стиле callback, его использование не рекомендуется:
getLevel({
    success(level) { console.log(`battery level: ${level}%`) }
})
```

#### Экспорт нативного интерфейса C++

Функция `getLevel()` в JavaScript фактически реализована на C++. Когда код JavaScript вызывает эту функцию, он инициирует асинхронный запрос на получение уровня заряда батареи и, после получения результата, возвращает его в код JavaScript через callback-функцию или `Promise`. Функция C++, реализующая `getLevel()`:
``` cpp
static JsValue getLevel(const JsCallContext &ctx) {
    typedef async::ResultSession<BatteryGetLevel> Session;
    Session *session = new Session; // Создание объекта Session
    session->request(ctx.argc() ? ctx.arg(0) : JsValue());
    return session->promise();
}
```

Шаблонный класс `async::ResultSession` (далее пространство имен `async` опускается) реализует фреймворк, необходимый для асинхронных запросов данных. Каждый асинхронный запрос данных включает в себя следующие шаги:
1. Создание объекта `ResultSession`.
2. Вызов метода `ResultSession::request()` для инициации запроса.
3. Возврат объекта `Promise` в JavaScript с помощью `ResultSession::promise()`.

Эта строка кода:
``` cpp
session->request(ctx.argc() ? ctx.arg(0) : JsValue());
```
Помимо инициации запроса, мы также передаем в метод `ResultSession::request()` аргумент с индексом $0$, переданный вызывающим кодом JavaScript. `ResultSession` автоматически определяет стиль (callback или `Promise`) в зависимости от наличия в этом аргументе функций обратного вызова `success` / `fail`. В случае стиля `Promise` код:
``` cpp
return session->promise();
```
возвращает объект `Promise` для получения результата асинхронного запроса, в противном случае возвращается `undefined`, а результат обрабатывается через callback-функцию.

#### Шаблонный класс `ResultSession`

Объявление шаблонного класса `ResultSession`:
``` cpp
template<class T, class H = ResultHandler> class ResultSession;
```
Шаблонный параметр `T` — это класс, реализующий конкретную асинхронную операцию. В данном примере для асинхронного получения заряда батареи будет реализован класс `BatteryGetLevel`. Шаблонный параметр `H` определяет способ обработки результатов асинхронного запроса. Стандартный `ResultHandler` автоматически выбирает стиль callback или Promise, и разработчикам обычно не требуется его изменять.

#### Класс `BatteryGetLevel`

Определение класса `BatteryGetLevel`:
``` cpp
struct BatteryGetLevel {
    async::Result<int> resolve() const {
        return battery_read_level(); // Получение уровня заряда батареи
    }
    // errorMessage() используется для преобразования кода ошибки в текст. Чтение заряда батареи не вызывает ошибок, реализация может быть любой.
    static const char *errorMessage(Status) {
        return "get battery level failed";
    }
};
```
Как видите, у `BatteryGetLevel` есть две функции-члена. Функция `resolve()` используется для выполнения конкретной операции в асинхронном потоке. Возвращаемое значение функции `resolve()` должно иметь тип `async::Result<T>`, в данном случае — `async::Result<int>`.

Тип шаблонного параметра `T` возвращаемого значения `async::Result<T>` функции `resolve()` совпадает с типом аргумента callback-функции JavaScript API или данных `Promise`. Например, в данном случае `int` соответствует следующему JavaScript API:
``` ts
// Тип возвращаемого значения функции C++ BatteryGetLevel::resolve()
// async::Result<int> соответствует Promise<number> в JavaScript
getLevel(): Promise<number>
```

Другими словами, если `resolve()` возвращает значение `async::Result<String>`, то в JavaScript будет возвращен `Promise<string>`, а для callback-функции это будет `{ success(value: string): void }`. Подробную информацию о преобразовании типов данных между C++ и JavaScript см. в разделе [Преобразование типов данных](#преобразование-типов-данных).

### Пример: Чтение файлов

#### JavaScript API

Предположим, мы хотим реализовать асинхронную функцию JavaScript для чтения файлов:
``` ts
readfile(url:string): Promise<string> // API в стиле Promise
readFile(option: {   // API в стиле callback
  uri: string,
  success?: (data: string) => void,
  fail?: (code: number, msg: string) => void,
}): void
```
Эта функция асинхронно читает содержимое файла и возвращает его через объект `Promise`, возвращаемым значением является содержимое файла. Фактический код JavaScript выглядит следующим образом:
``` js
async function printReadFile() {
    const data = await readFile("file.txt") // Асинхронное получение содержимого файла
    console.log('文件读取成功：', data)
}

printReadFile() // Вывод содержимого файла в виде строки, пример вывода в консоль:
// 文件读取成功：hello

// Ниже приведен код в стиле callback:
readFile({
    url: "file.txt", 
    success: (data: string) => {  
        console.log('文件读取成功：', data);  
    }
})
```

#### Экспорт нативного интерфейса C++

Функция `readFile()` в JavaScript фактически реализована на C++. Когда код JavaScript вызывает эту функцию, он инициирует асинхронный запрос на чтение файла и, после получения результата, возвращает его в код JavaScript через callback-функцию или `Promise`. Функция C++, реализующая `readFile()`:
``` cpp
JsValue readFile(const JsCallContext &ctx) {
    typedef async::ResultSession<ReadFileRequest> Session;
    if (ctx.argc() > 0 && ctx.arg(0).isObject()) { 
        Session *session = new Session;
        // Преобразование поля url аргумента функции JavaScript в C++ String 
        session->client().url = ctx.arg(0)["url"].toString(); 
        session->request(ctx.argc() ? ctx.arg(0) : JsValue());
        return JsValue();
    }
}
```
Объяснение используемого шаблонного класса см. в разделе [Шаблонный класс resultsession](#шаблонный-класс-resultsession), а пояснение к коду — в разделе [Экспорт нативного интерфейса C++](#экспорт-нативного-интерфейса-c) для получения уровня заряда батареи.

#### Класс `readFile`

Определение класса `ReadFileRequest`:
``` cpp
struct ReadFileRequest {
    String url; // URL читаемого файла.
    Result<String> resolve() {
        ByteArray array = File::read(url); // Чтение содержимого файла по URL
        return String(array.charData(), array.size());
    }
    // errorMessage() используется для преобразования кода ошибки в текст
    const char *errorMessage(Status) { return "read file error"; }
};
```
Как видите, у `ReadFileRequest` есть две функции-члена. Функция `resolve()` используется для выполнения конкретной операции в асинхронном потоке. Возвращаемое значение функции `resolve()` должно иметь тип `async::Result<T>`, в данном случае — `async::Result<String>`. Обратите внимание, что в функции `resolve()` нельзя обрабатывать типы данных JavaScript: параметр `url` был преобразован в C++ `String` внутри функции `readFile()` перед инициацией асинхронного запроса, и подобные преобразования данных нельзя выполнять внутри функции `resolve()`.

## Режим прослушивания (Listener Mode)

В режиме прослушивания код JavaScript вызывает API C++ для создания запроса на мониторинг множественных асинхронных запросов (например, прослушивание данных датчика). При изменении данных выполняется асинхронное событие, возвращающее результат в JavaScript. Шаблонные классы `async::ListenSession` и `async::Signal` предоставляют стандартный фреймворк операций для этого режима.

### Описание сценариев

Следующие сценарии являются типичными примерами режима прослушивания:

- **Прослушивание различных датчиков**: вызывается из JavaScript путем вызова C++ API прослушивания соответствующего датчика с указанием callback-функции. При изменении считываемых датчиком данных асинхронный поток возвращает новые данные в код JavaScript в качестве параметров callback-функции.
- **Периодические фоновые задачи**: при вызове из JavaScript необходимо задать интервал времени таймера, callback-функцию по истечении таймера, а также флаг периодичности. После отправки запроса при каждом срабатывании таймера асинхронный поток возвращает результат в JavaScript, вызывая установленную callback-функцию.

Сценарии режима прослушивания имеют следующие особенности:
- После запуска прослушивания поддерживается множество асинхронных запросов, поэтому этот режим может не подходить для однократных асинхронных событий чтения/записи файлов или запросов состояния сети;
- После запуска прослушивания его необходимо отменить, когда оно больше не нужно, иначе произойдет утечка памяти.

### Пример: Прослушивание уровня заряда батареи

#### JavaScript API

Предположим, мы хотим реализовать асинхронную функцию JavaScript для прослушивания уровня заряда батареи:
``` ts
subscribe(callback: (Level: number) => void): number // Прослушивание уровня заряда батареи
unsubscribe(subscribeID: number): void // Отмена прослушивания
```

Функция `subscribe()` используется для асинхронного прослушивания уровня заряда батареи, а `unsubscribe()` — для отмены прослушивания. Пример использования:
``` js
// Запуск прослушивания, возвращается ID для отмены прослушивания
let id = subscribe(level => {
  // При изменении уровня заряда батареи срабатывает callback-функция прослушивания, пример вывода в консоль:
  // now battery level: 59
  console.log(`now battery level: ${level}%`)
})

unsubscribe(id); // Отмена прослушивания
``` 

#### Экспорт интерфейса прослушивания C++

Функция `subscribe()` в JavaScript фактически реализована на C++. Когда код JavaScript вызывает эту функцию, он начинает прослушивание уровня заряда батареи. При каждом изменении уровня заряда инициируется асинхронный запрос, возвращающий результат в код JavaScript через callback-функцию. Функция C++, реализующая `subscribe()`:
``` cpp
async::Signal<int> Level; // Создание глобального объекта Level

level(45); // Значение Level изменилось, отправка асинхронного запроса

static JsValue subscribe(const JsCallContext &ctx) {
    Applet *applet = Applet::current(&ctx.vm());
    if (applet && ctx.argc())  // Проверка передачи параметров
        return applet->bindObject(Level.connect(ctx.arg(0)));
    return JsValue();
}
```
Необходимо создать глобальный объект `Level`. Используемый шаблонный класс `async::Signal` (далее пространство имен `async` опускается) реализует фреймворк запроса прослушивания, который включает в себя следующие шаги:
1. Перед началом прослушивания необходимо создать объект глобального класса `Signal`;
2. Использовать метод `Signal::connect()` для связывания первого параметра, переданного из JavaScript, с объектом `Level`;
3. Вызвать `Applet::bindObject` для привязки объекта `Level`; при изменении состояния `Level` вызывается callback-функция для возврата результата в код JavaScript.

Эта строка кода:
```cpp
level(45);
```
При изменении значения `level` на $45$ запускается механизм прослушивания, который инициирует асинхронный запрос, передает измененное значение в качестве параметра callback-функции и возвращает результат в код JavaScript.

#### Экспорт интерфейса отмены прослушивания C++

Функция `unsubscribe()` в JavaScript также реализована на C++. Код JavaScript вызывает эту функцию для отмены прослушивания во избежание утечки памяти, когда прослушивание больше не используется. Функция C++, реализующая `unsubscribe()`:
``` cpp
static JsValue unsubscribe(const JsCallContext &ctx) {
    Applet *applet = Applet::current(&ctx.vm());
    if (applet && ctx.argc() >= 1 && ctx.arg(0).isNumber()) // Проверка корректности переданных параметров
        delete applet->unbindObject<async::Slot>(ctx.arg(0).toInt());   
    return JsValue();
}
```
Для отмены запроса прослушивания необходимо вызвать `Applet::unbindObject` для отвязки, передав ID, возвращенный функцией `subscribe()`, чтобы определить объект для отвязки.

#### Шаблонный класс `Signal`

``` cpp
template<class T, class H = ListenHandler> class Signal;
```
Шаблонный параметр T — это класс, реализующий конкретную асинхронную операцию. В данном примере для прослушивания заряда батареи используется тип `int`. Шаблонный параметр H определяет способ обработки результатов асинхронного запроса. Стандартный ResultHandler автоматически выбирает стиль callback или Promise, и разработчикам обычно не требуется его изменять.

## Преобразование типов данных

В `ResultSession` или `ListenSession` данные асинхронной операции должны быть преобразованы в объект `JsValue`, чтобы их можно было использовать в коде JavaScript. Например, в классе [BatteryGetLevel](#класс-batterygetlevel) определена функция:
``` cpp
async::Result<int> BatteryGetLevel::resolve() const;
```
Объявление этой функции означает, что типом возвращаемых данных запроса заряда батареи является `int`. Этот тип данных может быть преобразован в `JsValue`. На самом деле следующие типы могут быть преобразованы в `JsValue`:
- `bool`: преобразуется в тип `boolean`;
- `int`: преобразуется в тип `number`;
- `float`, `double`: преобразуются в тип `number`;
- `String`: преобразуется в тип `string`.

::: warning
Строки в стиле C не поддерживаются. Они будут преоразованы в тип `boolean`.
:::

Преобразование происходит автоматически, вмешательство разработчика не требуется.
